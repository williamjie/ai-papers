# OpenGame: 用 Agent 从零生成可玩游戏，不只是写代码

**日期**: 2026-04-21

---

论文 : OpenGame: Open Agentic Coding for Games链接 : https://arxiv.org/abs/2604.18394让 AI 写一个能跑的单文件脚本？现在随便一个模型都能搞定。但让 AI 从一句自然语言描述，凭空生成一个结构完整、文件互连、资源加载正确、还能实际玩起来的 2D 游戏？这仍然是目前 AI 编程的”复杂度墙”。
CUHK MMLab 这篇 OpenGame 做的，就是捅破这层墙。而且它没走”拿个通用模型狂 prompt”的路线，而是设计了一整套针对游戏开发特性的方法论——模板演化、调试协议积累、三阶段训练。看完之后我的第一感觉是： 这不是一个”游戏生成工具”，而是一个”面向复杂多文件系统的 Agent 架构设计范本” 。
## 问题在哪：通用 Agent 为什么搞不定游戏？
论文指出了三个反复出现、但很少被系统性解决的失败模式：
- 逻辑不自洽。Agent 在全局状态管理上掉链子，游戏循环要么卡死，要么关键机制根本没实现。
- 引擎知识缺失。模型不知道 Phaser 3 的抽象层怎么调用，干脆自己从零实现物理系统，完全绕过了框架原生能力。
- 跨文件不一致。单个文件看着没问题，但资源 key 对不上、场景连线断了、初始化顺序错了——项目整体就炸了。
这些问题的本质是： 游戏不是函数，是一个实时交互系统 。编译通过 ≠ 能玩。传统 benchmark 用的静态单元测试，根本测不出”游戏能不能玩”。
## 核心方法拆解：三板斧### 1. GameCoder-27B：不是 prompt 出来的，是练出来的模型基于 Qwen3.5-27B 训练，走的是三阶段 pipeline：
持续预训练（Continual Pre-Training, CPT） ：喂开源 Phaser/TS 游戏仓库 + 官方文档 + 社区教程。目的很直接——让模型先”认得”游戏循环、物理系统、资源加载这些模式。
监督微调（Supervised Fine-Tuning, SFT） ：用 GPT-5.1 生成复杂的游戏设计 prompt（比如”实现一个带二段跳和精灵动画的 2D 平台角色控制器”），再用 MiniMax-2.5 生成高质量解答， distilled 成 SFT 数据。这一步教的是”创意意图 → 代码结构”的映射。
执行驱动强化学习（Execution-Grounded RL） ：关键 insight 来了。RL 阶段不生成完整游戏，而是生成单个文件的游戏逻辑模块（碰撞检测、状态机转换），然后跑单元测试， 用执行结果算 reward 。这一步把模型锚定在确定性、可执行的逻辑上，而不是纸上谈兵。
三阶段效果递增（Table 2）：
阶段 Build Health Visual Usability Intent Alignment 基础 Qwen-3.5-27B 62.8 53.8 49.8 + CPT 63.2 54.7 50.6 + SFT 63.5 55.7 52.5 + RL (Full) 63.9 57.0 54.1每个阶段都有增量收益，说明 领域适配不是可有可无的锦上添花，而是实打实的性能提升 。
### 2. Agent 工作流：Hook 驱动，不是从头写这是我最感兴趣的部分。Agent 分为六个阶段：初始化分类 → 脚手架搭建 → 设计文档生成 → 资源合成 → 代码实现 → 验证自修。
关键设计选择：
- Physics-First Classification：不是按”平台跳跃”、“射击”这种模糊的类型分类，而是按物理约束分类。“没有地面支撑的掉落” → 平台架构体；“网格锁定” → 网格逻辑。这直接缩小了后续搜索空间。
- Hook-Driven Implementation（模板方法模式）：Agent 不是从头写代码，而是复制模板文件、重写指定的 hook 方法（比如 setupCustomCollisions）。论文做了 ablation（Table 3），去掉这个约束，Build Health 暴跌 10.1 分，Intent Alignment 暴跌 11.6 分。这是整个工作流里最重要的约束。
- 三层阅读策略：先读 API 摘要 → 再读目标源文件 → 最后读实现指南。用渐进式显著性控制，防止”lost-in-the-middle”。去掉后 Intent Alignment 跌 8.6 分。
简单说： 不是让 Agent 在空白画布上画画，而是给它一块已经搭好框架的乐高底板，让它只拼关键模块 。
### 3. Game Skill：经验积累，让 Agent 越用越聪明这是 OpenGame 的杀手锏。Agent 不是每次从零开始，而是有两个不断生长的能力：
Template Skill ：从一个通用的元模板 M0 开始。每次完成任务后，提取稳定、通用、安全的代码片段，抽象成模板单元，加入模板库 L 。最终演化出 5 种模板族：
- 基于重力的横版- 俯视连续运动- 离散网格逻辑- 路径与波动态- UI 驱动玩法Debug Skill ：维护一个”活协议” P 。每次构建或测试失败，记录（错误签名、根因、验证过的修复），加到协议里。协议还包含轻量级 执行前验证 ——检查资源 key 不匹配、配置字段缺失、场景转换无效这些高频不一致问题。
ablation 结果（Table 4）很说明问题：
模板库 调试策略 Build Health Intent Alignment 单模板 M0 静态规则清单 60.5 51.2 5 种模板族 全量活协议 72.4 65.1从 60.5 到 72.4，差了 11.9 分 。经验积累不是玄学，是实打实的工程收益。
## 实验结果：SOTA，但没到完美在 150 个游戏 prompt 上的评测（Table 1），OpenGame + Claude Sonnet 4.6 的表现：
指标 OpenGame (Claude 4.6) Cursor (Claude 4.6) GPT-5.1 (直接生成) Build Health 72.4 66.8 57.4 Visual Usability 67.2 61.4 52.9 Intent Alignment 65.1 58.9 49.4全面领先。特别是 Intent Alignment 比 Cursor 高 6.2 分，说明结构化规划和模板脚手架确实更好地保住了用户指定的机制。
但别高兴太早—— 即使最强配置，仍有约 34.9% 的机械需求未被完全满足 。游戏生成这活儿，远没到”交差”的时候。
有意思的是，不同模型在不同指标上有 trade-off：Gemini 3.1 Pro 在视觉表现上最强（60.2），但 Intent Alignment 只有 42.1；DeepSeek V3.2 的 Build Health 不错（57.0），但视觉和意图都很弱。这说明 单一”通过率”指标会掩盖不同维度的失败模式 ，OpenGame-Bench 的多维评估设计是有道理的。
## 工程启示- Hook 驱动 > 从零生成。不管做什么复杂系统，给 Agent 一个稳定的骨架，让它只改关键接口，比让它自由发挥靠谱得多。
- 调试协议可以积累。每次错误都是一次知识获取的机会，关键是结构化地记录（错误签名 → 根因 → 修复），下次复用。
- 执行反馈比静态分析强。RL 阶段用单元测试执行结果算 reward，比单纯看代码质量有用得多。游戏尤其如此——能编译不代表能玩。
- 模板不是模板，是经验的结晶。从通用骨架出发，让系统自己演化出领域特定的模板族，这个思路可以迁移到很多代码生成场景。
## 局限与展望论文也坦诚了一些边界：
- 只覆盖了 2D Web 游戏（Phaser 3），3D、主机、移动端不在此列。
- 150 个 prompt 虽然多样，但都是”技术上可实现的”，现实中的创意需求往往更模糊、更复杂。
- 评测依赖 headless 浏览器 + VLM 打分，VLM judge 的主观性仍然是一个隐患。
- 自动调试迭代在 T=3 后就趋于 plateau，说明不是所有问题都能靠多轮修复解决，有些架构级错误可能需要重新规划。
总的来说，OpenGame 最大的价值不在于”它能生成游戏”，而在于 它展示了一种应对复杂多文件系统的 Agent 架构范式 ：模板约束搜索空间、活协议积累经验、执行反馈锚定逻辑。这套思路，放在任何需要 Agent 生成大型结构化代码的场景里，都值得参考。
