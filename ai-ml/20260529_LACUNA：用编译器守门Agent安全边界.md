# ⭐⭐⭐ LACUNA：用编译器守门 Agent 安全边界

**日期**: 2026-05-29

---

论文 : LACUNA: Safe Agents as Recursive Program Holes链接 : https://arxiv.org/abs/2605.28617现在的 AI Agent 开发圈有个尴尬的现状：要么让模型像 ReAct 那样一步步调工具，灵活但慢；要么让模型写代码（Code-as-action），快但危险。一旦把运行时控制权交给模型，它就拥有了“上帝视角”，哪怕只是一个简单的 Prompt Injection，也可能导致不可逆的状态污染或越权操作。
EPFL 团队这篇论文 LACUNA 给出了一个极其硬核的解法： 别只让模型写工具调用，让它写完整的程序逻辑，但必须经过编译器的“毒打”才能运行。 它把 Agent 的动作定义为类型化的代码洞（Typed Holes），利用 Scala 3 强大的静态类型系统和 Capture Checking，在代码执行前就拦截所有错误。
### 痛点：为什么现有的安全防线不够用？
目前的 Agent 架构中，运行时（Runtime）和模型生成的代码是割裂的。运行时掌控循环和上下文，模型只负责提供下一小段指令。这种设计虽然安全，但限制了 Agent 的表达力——它无法自主决定何时启动子代理、如何分支或循环。
如果反过来，让模型生成的代码直接塑造运行时逻辑，Agent 确实更强大，但风险陡增：
- 部分执行污染：传统动态语言（如 Python eval）在遇到错误前可能已经执行了前半段代码，导致环境状态不一致。
- 权限失控：现有的沙箱或策略语言通常只能限制“能做什么”，却无法检查“整个动作是否逻辑自洽”。
### 核心设计：把 Agent 变成“类型化的洞”
LACUNA 的核心 Insight 很简单却极其有力： 将 LLM 的调用嵌入到程序内部，作为需要被填充的类型化代码洞。
具体实现上，它引入了一个原语 agent[T](task) 。当程序执行到这里时，LLM 会生成一段 Scala 代码来填补这个洞。关键在于，这段代码不是直接运行，而是 在当前的词法作用域（Lexical Scope）中进行静态类型检查 。
这种设计带来了三个巨大的工程红利：
-原子性安全（Atomicity）：
这是 LACUNA 最杀手级的特性。如果生成的代码有任何类型错误、未定义变量或权限越界，编译器会直接拒绝整个片段。这意味着，即使代码前半部分试图修改全局状态（如 balance -= 50），只要后半部分返回类型不对，前面的副作用也绝对不会执行。环境始终保持一致。
-能力即作用域（Capability as Scope）：
LACUNA 利用 Scala 3 的 Capture Checking 机制实现权限控制。工具不再是简单的 JSON Schema，而是函数。如果模型想调用某个需要网络权限的工具，它必须持有对应的 Capability 对象。如果生成的代码试图将高权限对象逃逸到外部作用域，编译器会在运行前直接报错。
-递归即控制流：
复杂的 Agent 模式（如 ReAct 循环、子代理分解）不再是特殊的协议，而是普通的代码结构。LLM 可以生成包含嵌套 agent 调用的代码，每个嵌套调用都有自己的类型约束和上下文。这让 Agent 能够像程序员一样思考和控制流程。
### 实验表现：安全与性能的平衡论文在 BrowseComp-Plus 和 τ2\tau^2 -bench 上进行了评估，结果令人印象深刻：
指标 BrowseComp-Plus τ2\tau^2 -bench 准确率 27.1% 76.0% (392个任务) 执行前拦截率 8.6% - 平均重试次数 0.7 次/查询 -在 τ2\tau^2 -bench 上，LACUNA 达到了 76.0% 的准确率，与基线 Agent 持平。这说明引入严格的编译检查并没有显著牺牲 Agent 的智能表现。更重要的是，8.6% 的生成代码在执行前就被拦截了，这直接证明了静态检查能有效过滤掉那些“看似合理但逻辑错误”的代码。
### 工程启示：给开发者的建议- 拥抱静态类型：如果你正在构建高可靠性的 Agent 系统，不要迷信动态语言的灵活性。LACUNA 证明，利用宿主语言的编译器进行运行时检查，是解决 Agent 安全问题的终极方案之一。
- 工具即函数：抛弃复杂的 Tool Registry 和 JSON Schema 转换层。将工具定义为普通的类型化函数，让 LLM 直接调用，能大幅降低幻觉概率。
- 重试机制是核心：由于编译检查会拒绝错误代码，系统必须具备基于编译器诊断信息的自动重试能力（LACUNA 中平均重试 0.7 次）。这意味着你的 Prompt Engineering 需要包含“如何根据编译错误修正代码”的指导。
### 局限与展望LACUNA 目前依赖于 Scala 3 的特定特性（如 Capture Checking），移植到其他语言可能需要重新设计底层编译器支持。此外，虽然它解决了逻辑和权限安全，但对于资源耗尽、死循环等非类型层面的问题，仍需依赖运行时预算限制。
总的来说，LACUNA 为 Agent 开发提供了一条“用工程手段约束 AI 不确定性”的新路径。它告诉我们：最安全的 Agent，可能是那个被编译器管得最严的 Agent。
