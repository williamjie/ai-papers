**日期**: 2026-08-04

---

论文 : SWE-Touch: Benchmarking Coding Agents When Users Touch the Code链接 : https://arxiv.org/abs/2608.02499现在的 Coding Agent 在独立修 Bug 时表现不错，但真实开发中用户随时会改代码。这篇论文直击痛点：当用户在共享工作区修改代码时，Agent 还能不能稳住？
现有基准测试大多假设 Agent 独自工作，或者仅通过消息交互。这忽略了现实中的高频场景：用户直接修改仓库文件。SWE-Touch 填补了这一空白，通过注入“冲突编辑”来压力测试 Agent 的状态感知能力。
### 为什么需要 SWE-Touch？
真实开发是多人协作的共享空间。分析 SWE-chat 数据发现，59.0% 的会话包含用户对仓库的直接修改。
然而，主流基准（如 SWE-bench）通常评估静态初始状态下的修复能力。这种设定掩盖了 Agent 在面对动态变化时的脆弱性。
核心问题是：当用户代码与任务目标冲突时，Agent 能否识别、协调并重新验证？
### 方法拆解：如何制造“可控混乱”？
SWE-Touch 的核心设计是注入 Counter-Edits （对抗性编辑）。这不是随机噪音，而是精心构造的干扰：
- 挖掘关键区域：利用多个模型轨迹交集，定位任务关键代码区。
- 生成冲突补丁：使用独立的 User Patch Generator 创建看似合理但阻碍任务完成的编辑。
- 严格验证：确保该编辑单独存在时不解决问题，且与正确修复组合后仍失败。这迫使 Agent 必须处理冲突，而非忽略或简单合并。
这种设计模拟了最坏情况：用户改了代码，还附带了一句“我本地测过了，请保留”。Agent 必须判断是否覆盖、如何修正，并重新测试。
### 关键结果：独立强不代表协作稳在 SWE-bench Verified 上测试 9 个模型，Counter-Edit 使平均解决率下降 7.7% 。但不同模型表现差异巨大：

### 失败归因：Agent 到底卡在哪？
对失败案例的深入分析揭示了三种主要模式：
- 保留冲突 (63.3%)：Agent 直接接受用户的错误代码，导致任务失败。这在 MiniMax 和 DeepSeek 模型中尤为常见。
- 错误替换 (13.9%)：Agent 试图覆盖用户代码，但修复逻辑本身有误。Claude Opus 4.8 更倾向于这种主动对抗，但也容易出错。
- 不完全协调 (11.6%)：部分修改但未彻底解决冲突。
数据显示，**修订率（Revision Rate）**与性能损失负相关（Spearman ρ = -0.80）。敢于挑战用户代码的模型，通常表现更好。但挑战不等于成功，还需要正确的修复和验证。
### 工程启示- 状态感知是短板：当前 Agent 缺乏对工作区变化的主动检测机制。它们往往假设环境静态，或过度信任用户输入。
- 评估维度需扩展：仅看 SWE-bench 分数不够。部署前必须测试“动态工作区”下的鲁棒性。
- 优化方向：未来 Agent 需要强化“检测变化 - 协调冲突 - 重新验证”的闭环能力，而不仅仅是生成代码。
### 局限与展望SWE-Touch 目前使用受控的对抗编辑，尚未覆盖所有协作场景（如用户正确修改）。此外，它主要测试代码层面，未深入涉及复杂的人类意图理解。
但这篇论文明确指出了从“独立解题者”到“协作开发者”的关键鸿沟。对于正在构建 Agent 系统的工程师来说，这是必须跨越的一关。
