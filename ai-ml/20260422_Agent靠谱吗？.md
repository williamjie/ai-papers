# Agent 靠谱吗？

**日期**: 2026-04-22

---

论文 : On the Reliability of Computer Use Agents链接 : https://arxiv.org/abs/2604.17849做 Agent 的人最怕听到一句话：“它上次明明可以的。”
最近 OSWorld 团队出了一篇论文，专门研究 Computer Use Agents (CUA) 的可靠性。他们发现，哪怕模型、任务、环境完全一样，同一个 Agent 跑十次，可能只有几次能成。这篇论文的核心贡献，就是拆解了 为什么 Agent 会“抽风” ，并给出了一套评估可靠性的量化方法。
对工程实践来说，这太重要了。毕竟，能跑通一次叫 Demo，能跑通一百次叫 Product。
## 痛点：Pass@N 掩盖了真实问题现有的基准测试喜欢用 Pass@k （在 k 次尝试中至少成功 1 次的概率）。这个数字看起来很高，比如 GPT-5 在 OSWorld 上 Pass@10 能达到 78%。但这有个巨大的漏洞：它鼓励了“运气”。
论文提出了一个新视角： 可靠性（Reliability） 是指连续 k 次尝试全部成功的概率，即 Pass^k 。
看一组对比数据：
- Pass@10: ~78% (只要有一次成功就算赢)
- Pass^10: ~36% (10 次必须全赢)
这意味着什么？意味着超过一半的任务，Agent 只是“蒙对”了一次。在航空航天、医疗软件这些容错率为零的领域，这种“一次成功”毫无意义。
## 可靠性失败的三大元凶论文通过控制变量实验，找到了导致 Agent 不稳定的三个核心因素：
### 1. 随机解码（Stochastic Decoding）：关了温度就好？
直觉告诉我们，把 temperature 设为 0 就能消除随机性。实验结果打了脸：
模型 设置 Pass^1 Pass^3 可靠性变化 (b-c) Qwen (S3) Baseline 0.329 0.222 - Qwen (S3) Deterministic (Temp 0) 0.293 0.166 -20 * OpenCUA Baseline 0.226 0.125 - OpenCUA Deterministic (Temp 0) 0.259 0.180 +20 *Insight : 关掉随机性并不总是好事。对 Qwen 来说，确定性解码反而让可靠性显著下降。这是因为在某些场景下，随机性赋予了 Agent 一定的“弹性”，让它能绕过微小的环境噪声。完全确定性反而让 Agent 变得脆弱，一旦遇到微小变化就彻底失败。
此外，即使关掉随机性， Pass^1 到 Pass^3 依然有巨大落差，说明随机性只是部分原因。
### 2. 指令歧义（Instruction Ambiguity）：人话本身就是坑任务指令通常由人类用自然语言编写，这必然带来 歧义 。Agent 和评估脚本对“成功”的定义可能不一致。
实验发现， 澄清指令（Clarification） 能带来巨大提升：
- 对 GPT-5，澄清后可靠性提升显著（b-c = +48*）。
- 对 Kimi，虽然提升较小，但成功率稳步增长。
更有趣的是， 执行中的澄清（Retry with Clarify） 比单纯重试（Retry Binary）更有效：
- GPT-5 在“澄清式重试”下，Pass^3 从 0.454 提升到 0.632。
- 单次澄清指令的效果，甚至优于 5 次盲目重试。
Insight : 歧义是不可避免的。与其靠重试去“猜”用户的真实意图，不如让 Agent 在遇到模糊点时主动澄清，或者在任务开始前明确成功标准。
### 3. 规划变异（Planning Variability）：每次都在重新发明轮子即使指令清晰、环境稳定，Agent 每次执行时选择的 策略 可能不同。有的策略稳健，有的策略脆弱。
论文设计了一个 计划提取与迭代优化（Plan Extraction & Refinement） 的实验：
- Iteration 0: 普通执行- Iteration 1: 从前几次执行中提取成功/失败模式，形成“计划”，指导下一次执行- Iteration 2: 基于新数据进一步优化计划结果：
- GPT-5: 随着迭代，Pass^3 从 0.576 提升至 0.651。
- Kimi: Pass^3 从 0.382 提升至 0.424。
- Claude: 反而下降了。论文推测是因为 Claude 倾向于生成代码解决方案，导致环境状态变化超出了评估器的检测范围，使得反馈失效。
Insight : 从历史经验中学习策略是有效的，但前提是反馈机制要靠谱。如果评估器跟不上 Agent 的行为模式（比如 Claude 的代码执行），反馈就会成为噪声，反而误导 Agent。
## 工程启示- 评估必须看 Pass^k，而不是 Pass@k。如果一个 Agent 的 Pass@10 很高但 Pass^10 很低，它在生产环境中就是个定时炸弹。
- 不要盲目追求确定性。Temperature 0 虽然稳定，但可能降低对环境噪声的鲁棒性。需要权衡。
- 主动澄清优于盲目重试。给 Agent 提供“追问”的能力，或者在任务开始前明确成功标准，比让它试 5 次更有效。
- 利用历史经验，但要小心反馈质量。从历史执行中提取策略能提升可靠性，但反馈机制必须与 Agent 的行为模式匹配，否则会带来负优化。
## 局限与展望论文主要基于 OSWorld 基准，这是一个受控的虚拟环境。真实世界的环境噪声、动态变化更加复杂。此外，不同模型对策略提取的响应差异巨大（如 Claude 的负优化），说明未来需要更通用的、模型无关的可靠性提升机制。
总的来说，这篇论文提醒我们： 能跑通不等于能复用，能复用不等于能规模部署。 可靠性，才是 Agent 走向生产环境的真正门槛。
