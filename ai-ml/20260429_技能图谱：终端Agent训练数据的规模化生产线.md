# 技能图谱：终端Agent训练数据的规模化生产线

**日期**: 2026-04-29

---

论文 : Toward Scalable Terminal Task Synthesis via Skill Graphs链接 : https://arxiv.org/abs/2604.25727终端Agent已经证明能在命令行里搞定复杂任务，但它们的训练被一个根本问题卡住了：高质量的终端操作轨迹太少了。手动收集不现实，于是大家开始用LLM合成任务数据。但问题来了—— 现有方案都在”堆数量”，没人真正控制轨迹的多样性 。
这篇论文戳穿了表面繁荣：图1显示，不同合成任务最终暴露给Agent的执行轨迹，在场景和技能上高度重叠。这意味着模型即使看了再多数据，学到的也是重复套路。SkillSynth的解法很直接： 用图结构显式建模”场景-技能”的流转关系，把任务合成从”随机撒点”升级为”路径规划” 。
## 问题本质：轨迹由什么构成？
论文首先把执行轨迹拆成两个维度：
- 场景（Scenario）：Agent在某个决策点观察到的状态抽象，是历史的充分统计量- 技能（Skill）：在该场景下执行的动作序列，形成从当前场景到下一场景的转移一个轨迹不再是简单的 (obs, action) 堆叠，而是 (场景, 技能) 的交替序列。训练目标也从单纯预测token，变成了 log π(技能|场景, 目标) 。
关键洞察来了： 模型能力受限于训练数据覆盖的”场景×技能”条件对空间 。如果某个 (场景, 技能) 组合从未在数据中出现，模型就永远学不会在那个场景使用那个技能。因此，合成任务的核心目标应该是 最大化这个联合空间的覆盖度 ，而不是单纯增加任务数量。
## SkillSynth怎么做？三步走### 1. 构建场景中介技能图这不是个普通的有向图。节点是 场景 ，边是 技能 ，但技能边的起点不是简单的”当前状态”，而是它的 前置场景 ，终点是 后置场景 。
这带来一个关键优势：技能不再孤立。一个技能的后置场景，自动成为下一个技能的前置场景—— 图的连通性天然编码了技能之间的顺序依赖关系 。
构建过程很扎实：
- 技能过滤：从ClawHub和GitHub筛选可执行、结构化、无恶意、输出可验证的技能- 场景推断：对每个技能，用LLM推断它的前置场景（什么条件下能用）和后置场景（执行后达到什么状态）
- 场景去重：用嵌入聚类合并语义相同的场景描述。论文试了9种聚类算法，最后选了”层次聚合+Louvain粗分桶”
- 跨技能对齐：把A技能的后置场景与B技能的前置场景做语义匹配，双向验证兼容性- 场景合并：通过LLM合并对齐后的场景对，形成统一节点最终成果： 82,073个场景，57,214个技能，185,529个验证过的连接 。规模不小，但更惊人的是连通性： 85.6%的场景属于最大弱连通分量 ，说明图结构高度连贯，能支撑长程路径采样。
### 2. 图引导的路径采样有了图，下一步是从里面采样”工作流路径”。但随机游走不行——它会在高频场景和技能上打转，产生大量冗余路径（论文Fig 1就是证据）。
SkillSynth用了 逆频次加权采样 ：
- 每个场景有个访问计数ν(σ)，采样概率p(σ) ∝ (ν(σ)+1)⁻¹- 每个技能有个使用计数µ(κ)，采样概率p(κ) ∝ (µ(κ)+1)⁻¹- 路径内部禁止重复访问场景和技能，保证单调推进这个机制会让早期高频的节点逐渐变”冷”，迫使采样器探索未覆盖区域，最终逼近 场景-技能空间的均匀覆盖 ——正好呼应训练目标里的条件分布覆盖。
采样长度范围 [1, 7] ，覆盖单技能任务到七步复合任务。算法细节见Algorithm 1，逻辑清晰：从随机场景开始，每一步从未访问的发散技能中逆频次采样，直到达到长度上限或死胡同。
### 3. 多智能体合成器sampled路径只是抽象流程，需要转成可执行的任务实例。直接让LLM一次性生成所有组件（指令、环境、测试、参考答案）会导致：
- 长上下文生成质量不稳定- 模型纠结实现细节，任务复杂度不够所以拆成两阶段：
- 规划器（Planner）：把路径P转成结构化计划，列出子目标和预期产出- 构造器（Constructor）：基于计划生成完整任务实例（instruction.md、environment/、test/、solve.sh）
然后 双重验证 ：
- Oracle执行验证：运行参考答案，看是否能通过测试脚本- Rubric评价验证：LLM-as-a-Judge检查指令与测试的对齐性，以及指令是否泄露答案线索失败的实例会进入 修复循环 （最多3轮，每轮20次工具调用），用反馈逐步修正。Table 1显示这个机制很有效： 95.7%的实例通过Oracle检查，92.0%通过双重检查 ；修复循环挽救了721个首轮失败的实例。
## 关键结果：数字说话先看合成规模和质量：
- 3,721条采样路径 → 3,560个可用任务实例，通过率95.7%- 平均成本$27.3/任务，考虑到任务复杂度，这个成本控制不错- Table 2的难度分布：38%是”硬任务”（3次尝试全败），25%是”已解出”，37%落在”可学习区间”——说明任务集有足够的挑战梯度再看下游效果（Table 3）：在Terminal-Bench 1.0/2.0上，Qwen3-32B + SkillSynth轨迹训练后：
- TB 1.0: 33.8 ± 3.1- TB 2.0: 29.6 ± 1.6相比Qwen3-32B基线，提升明显。更关键的是，这个 小模型（32B）的表现超过了Qwen 3 Coder 480B ——说明 高质量、多样化的数据比单纯堆模型参数更有效 。
消融实验（Table 4）更有意思：
- 单技能基线：25.4 / 21.3- 随机组合多技能：30.8 / 25.8- SkillSynth：33.8 / 29.6SkillSynth比单技能强8.4/8.3分，比随机组合强3.0/3.8分。论文指出，随机组合失败的原因是 技能间缺乏连贯的工作流依赖 ，合成器只能生成”多要求但少步骤”的肤浅任务。而图结构强制了技能的顺序合理性，逼出真正的多步工作流。
多样性指标（§4.5）：SkillSynth轨迹的 唯一场景-技能对覆盖度，比单技能基线高31%，比随机组合高19% 。这直接解释了性能差距——模型接触到了更多样的 (场景, 技能) 组合。
错误分析（Table 5）也值得警惕：
- 部分实现（42.2%）：Agent用自测通过就交了，但漏了指令的某些条款- 自测过度信任（29.5%）：只用happy path的简单断言，忽略边界情况这说明 轨迹质量不仅要看多样性，还要看验证的严格性 。SkillSynth的Rubric检查正是为此设计。
## 工程启示-“先画路径，再实例化”的两阶段思路通用性强。任何需要复杂工作流的Agent训练，都可以先建模”状态-动作”图，采样路径，再生成具体任务。这比直接让LLM编任务更可控。
-逆频次采样是低成本的覆盖率优化器。不需要复杂的强化学习，简单计数+逆概率就能避免热点垄断，适合大规模数据合成。
-合成器本身需要验证-修复闭环。单次LLM调用生成质量不稳定，多层验证（执行+规则）加上循环修复是规模化产出的必备设计。95.7%的通过率不是Prompt工程的结果，而是架构设计的产物。
-失败轨迹也有价值。论文保留了失败轨迹用于SFT，因为里面包含错误诊断和恢复策略。这提醒我们：训练数据不只有”正确示范”，还有”错误案例”。
-数据质量可以弥补模型规模差距。32B模型靠SkillSynth数据超过480B模型，这对资源有限的团队是大利好——与其卷参数，不如卷数据构造。
## 局限与展望论文自己提的限制：
- 当前只采样路径（链式结构），未来需要子图采样来支持并行技能，增加任务复杂度- 规模还能继续扩大，但合成器需要适配更便宜的模型（现在成本虽低，但大规模训练仍可观）
- 技能图依赖贡献者社区（如ClawHub），需要生态持续输入新鲜技能我的观察：SkillSynth目前聚焦 终端命令行 场景，但”场景-技能图”的抽象应该能迁移到其他Agent领域，比如：
- Web Agent：场景=页面状态，技能=操作序列（点击、输入、滚动）
- 代码编辑Agent：场景=代码库状态，技能=重构、测试、调试动作核心都是 把原子能力组织成有向图，通过采样路径生成复合任务 。
## 总结SkillSynth的价值不只是生成了一批终端任务，而是 提供了一个可复现、可扩展的任务合成框架 。它用图结构解决了”多样性”这个老大难问题，用多Agent架构解决了”质量”问题，用逆频次采样解决了”覆盖”问题。
更重要的是，它证明了 任务合成可以不是玄学 ——当你有技能图，你有采样算法，你有验证闭环，规模化生产高质量Agent训练数据就从”看运气”变成了”看工程”。
如果你在训练终端Agent或任何需要工作流合成的Agent，这篇论文提供的不是单个技巧，而是一套可落地的方法论 。数据饥渴的时代，会造数据比会调参更重要。
