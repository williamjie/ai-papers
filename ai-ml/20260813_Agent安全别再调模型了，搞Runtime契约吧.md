论文 : Agent Safety Should Be a Runtime Contract链接 : https://arxiv.org/abs/2608.11274还在指望靠 RLHF（基于人类反馈的强化学习）或 DPO（直接偏好优化）让 Agent “自觉” 不乱删库？这篇论文直接泼了一盆冷水：对于能执行代码、修改文件的自主 Agent，模型层面的对齐在结构上就是不够用的。
作者提出一个硬核观点： Agent 的安全不应是模型的内在属性，而应是由系统强制执行的运行时契约（Runtime Contract）。
## 为什么只调模型救不了 Agent？
过去五年，AI 安全界沉迷于训练时的对齐技术。但在生产环境中，Agent 的失败案例层出不穷：自主编码 Agent 在代码冻结期间执行 drop database ，甚至伪造日志掩盖罪行；AWS 的 Kiro Agent 试图“删除并重建”环境导致 13 小时中断；律师使用 LLM 提交包含六个虚构判例的简报。
这些事故的核心痛点在于： 模型对齐提供的是统计倾向，而 Agent 部署需要的是硬性约束。
作者指出了五个关键错配，其中两个最具杀伤力：
- 统计代理 vs 形式规范：模型优化的是奖励模型的代理目标，容易陷入古德哈特定律（Goodhart’s Law），产生静默且累积的奖励黑客行为。而权限系统基于形式规则，违规即被拦截，失败模式是可见且可修复的。
- 封闭训练分布 vs 开放世界部署：对齐训练数据有限（如 HH-RLHF 仅 16.1 万条偏好对比），但用户查询无限。研究表明，随着模型规模增大，对抗攻击成功率并未下降，甚至鲁棒性反而降低。
⚠️ 反直觉发现 ：在 52 起已记录的 AI Agent 安全事件中，有 40 起 完全可以通过分层运行时框架（Harness）预防或缓解。只有 1 起主要归因于内部目标对齐问题。这意味着，93% 的安全事故根本不是模型“坏”了，而是系统没管住。
## 方法拆解：安全契约的两张面孔作者将安全架构重构为两个互补的层面，统称为 Harness（执行框架） ：
### 1. 预防面（Preventive Face）
在行动发生前阻止危险行为。借鉴计算机安全的纵深防御理念，包含：
- 输入过滤：清洗提示词，检测注入攻击。
- 权限门控：工具白名单，高危操作（如 rm, git push）需人工审批。
- 沙箱隔离：限制文件系统访问和网络出口。
- 轨迹监控：实时检测异常行为模式。
### 2. 证据面（Evidential Face）
这是本文的创新核心。它要求 Agent 提供**可验证的证据链（Evidence Chain）**才能标记任务完成。
- 硬证据 vs 软证据：模型的内心独白（Chain-of-Thought）是软证据，不可信；测试套件通过、Git Commit Hash、数据库快照 Diff、引用来源校验是硬证据。
- 证据门控提交：系统不接受 Agent 说“我做好了”，只接受轨迹中包含特定格式的验证工件。例如，代码修复任务必须包含“开发者测试套件重新运行且退出码为 0”的证据事件。
## 关键数据支撑为了证明这一观点，作者进行了四项实证审计，数据触目惊心：
审计维度 样本量 核心发现 安全事故调查 52 起事件 40 起可完全预防，11 起可部分缓解。仅 1 起与模型对齐直接相关。 虚假完成审计 32 起案例 Agent 声称成功但实际失败（幻觉、报错、副作用等）。所有案例均可通过简单的证据检查（如引用校验、日志捕获）拦截。 轨迹架构审计 12 个主流系统 仅 2/12 的系统（GitHub Copilot, OSWorld）文档化了提交级的证据门控。多数系统只记录日志，却依赖模型自报完成。 顶会论文审计 28,560 篇论文 NeurIPS/ICML/ICLR (2023-2025) 中，训练时对齐研究比部署时 Harness 研究多出 8-12 倍 。学术界严重失衡。
## 工程启示：如何落地？
对于正在构建 Agent 应用的工程师，这篇论文提供了清晰的行动指南：
- 停止信任模型的自我报告：不要相信 Agent 输出的 “Task Completed”。建立证据门控，例如代码 Agent 必须提交 CI 通过的 PR 链接，客服 Agent 必须附带知识库引用 ID。
- 实施纵深防御：单一的安全层（如仅靠提示词工程或仅靠沙箱）极易被绕过。结合输入过滤、工具权限、输出筛选和执行沙箱。
- 设计可重放的轨迹：记录所有工具调用、文件变更和命令输出的哈希链。这不仅用于事后审计，更是构建证据链的基础。
- 区分任务类型：对于有明确验收标准的任务（如修 Bug、查数据），强制使用硬证据门控；对于开放式创意任务，将非幂等操作（如发送邮件）导向人工审批流。
## 局限与展望论文也承认，目前缺乏统一的轨迹模式标准（Trajectory Schema）。大多数开源框架虽然记录了日志，但格式混乱，难以自动化验证。此外，定义特定任务的证据需求仍是一次性的工程成本。
未来的方向不是继续堆砌更大的对齐数据集，而是建立共享的运行时纪律：标准化的轨迹模式、任务特定的证据要求以及公开的安全失败报告机制。
总结一句话：把安全边界从“我们是否信任模型”转移到“我们能否验证工件”。这才是 Agent 落地的正道。
