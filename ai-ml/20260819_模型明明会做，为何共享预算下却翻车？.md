# ⭐⭐⭐½ 模型明明会做，为何共享预算下却翻车？

**日期**: 2026-08-19

---

论文 : R^3-Bench: LLMs Struggle with Resource-Rational Reasoning under Shared Budgets链接 : https://arxiv.org/abs/2608.16033如果你正在构建多任务 Agent 系统，这篇论文必须读。它揭示了一个被长期忽视的工程痛点： 模型在单题上的高分，无法保证在多题共享预算时的表现 。
## 问题与动机：独立预算的幻觉现有的推理基准（如 MATH、LiveCodeBench）和 Agent 基准通常采用“每任务独立预算”。这意味着模型可以无脑把算力砸在当前问题上，无需考虑机会成本。
但在真实生产环境中（如 Codex 或 Claude Code），多个任务往往并发运行，共享有限的 API 配额或推理资源。一旦引入 共享预算（Shared Budget） ，模型不仅要解题，还得决定“何时切换”、“何时止损”。
R³-Bench 正是为了填补这一空白：它模拟了 ICPC 等竞赛场景，要求模型在单一预算下处理 6 道不同难度的题目。
## 方法拆解：如何量化“资源理性”？
论文的核心 Insight 在于构建了一个 离线经验 Oracle（Offline Empirical Oracle） 。
- 难度分层：不用事后准确率，而是用三个参考模型的自然输出长度来定义 Easy/Medium/Hard。这更贴近计算资源的真实消耗。
- 预算校准：针对每个模型单独校准预算压力 ρ\rho。ρ=0.8\rho=0.80.8 为中等压力，ρ=0.2\rho=0.20.2 为强压力。这是为了避免因模型天生输出长短不同而导致的不公平比较。
- Oracle 定义：通过单题测试得到“响应曲线”，利用多重选择背包问题（Multiple-Choice Knapsack）计算出在总预算约束下，理论上能拿到的最高分。
这个 Oracle 不是可执行策略，而是一个 能力上限参考 。如果实际得分远低于 Oracle，说明模型在“分配”上出了问题，而不是在“解题”能力上不足。
## 关键结果：普遍存在的分配缺口论文测试了 DeepSeek-V4-Pro、GPT-5.5、Claude-Opus-4.8 等 6 个旗舰模型。结果令人震惊：
指标 数据表现 Oracle vs Contest 在 72 个主要测试单元中，Oracle 得分在全部 72 个单元中 ≥\ge 实际得分，且在 71 个单元中严格更高 。 平均缺口 Tool-free 设置下，Oracle 比实际得分平均高 1.16 分 （满分 6 分）。 位置偏差 第 6 题的准确率在所有模型和压力等级下均低于第 1 题。前 20% 的题目往往消耗了 50% 以上的预算。
⚠️ 反直觉发现 ：
在强压力下，GPT-5.5 的“平均分配”策略几乎失效。因为单题均分预算太少（Math 仅 38 tokens），导致连简单题都解不出。这说明 固定均匀分配是糟糕的策略 。
关键诊断 ：失败模式随压力变化。
- 强压力 (ρ=0.2\rho=0.20.2)：主要死因是“预算被其他题耗尽”（Spent budget elsewhere）。
- 中压力 (ρ=0.8\rho=0.80.8)：主要死因是“部分进展后放弃”（Stopped after partial progress）。
## 工程启示：调度比解题更重要- 通用能力不预测分配质量：论文对比了 Epoch Capabilities Index (ECI) 与 Gap Ratio。两个 ECI 分数相差不到 3 分的模型，在资源理性上的表现可能相差 20+ 个百分点。高分模型不一定更懂“省着用”。
- 在线调度有效但依赖领域：
Code 领域：引入简单的“覆盖优先”策略（Strategy A）或“验证门控”（Strategy B）能显著提升得分，因为编译反馈能提供明确的信号。
- Math/AR 领域：固定调度策略效果不稳定，甚至可能因浅层检查浪费预算而降低得分。
这意味着，对于工程落地， Code Agent 可以通过简单的运行时规则优化资源分配 ，但 Math Agent 可能需要更复杂的、基于训练的内部调度策略（Inner Scheduling Policy）。
## 局限与展望- Oracle 是离线的：它假设模型能完美预知哪些题在特定预算下能解出，实际在线决策面临不确定性。
- 缺乏动态适应：目前的干预策略（Strategy A/B）是静态指令，无法根据实时反馈动态调整。
- 未来方向：论文建议通过训练一个条件化调度策略，让模型学会根据“剩余预算”、“当前进度”和“领域类型”来决定是继续、切换还是停止。
对于 Agent 开发者来说，这篇论文提醒我们： 不要只盯着 Prompt Engineering 提高解题率，还要关注 Runtime 层面的资源调度逻辑 。在算力昂贵的今天，这比多解一道题更值钱。

挑刺:
- 术语错位：博文称“在强压力下，GPT-5.5 的‘平均分配’策略几乎失效”。原文中的“equal-allocation replay”是作者构建的固定均匀分配基线，并非 GPT-5.5 自身采用的策略。博文表述易让读者误以为模型主动使用了平均分配，而实际模型在 contest 中并未执行该分配。原文明确：“Equal allocation provides a second test. … For GPT-5.5 at ρ = 0.2, the per-problem replay thresholds are only 38, 47, and 6 output tokens”，即这是 replay 的阈值，非模型策略。
- 遗漏关键条件：博文在“关键诊断”部分列举失败模式时未注明这是 Agentic 设置下的分析。原文图 6 及其说明明确是在 agentic 轨迹诊断中得到的结论，而 tool-free 设置下失败原因分布不同。博文直接将其泛化为所有设置下的通用模式，可能误导读者。
- 数字引用偏差：博文说“前 20% 的题目往往消耗了 50% 以上的预算”。原文对应的是“the first position absorbs 20.5–52.9% of attributed output under strong pressure”，即第一题（位置 1，占 1/6 ≈ 16.7%）而非“前 20%”；且 50% 以上仅出现在部分模型（范围上界 52.9%），并非“往往”。博文将“第一位置”替换为“前 20%”并加上“往往”，夸大了结论的普遍性。
总评: ⭐⭐⭐½ 博文整体准确反映了论文的核心发现和工程启示，提炼得当，但存在一处术语错位（将等分基线误称为模型策略）和两处条件/数字的简化偏差，略微损害了精确性。
