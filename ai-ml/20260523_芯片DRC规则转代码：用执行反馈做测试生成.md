论文 : Rule2DRC: Benchmarking LLM Agents for DRC Script Synthesis with Execution-Guided Test Generation链接 : https://arxiv.org/abs/2605.15669芯片制造前的设计规则检查（Design Rule Checking, DRC）是 EDA 流程中的硬骨头。传统上，工程师需要手动将成百上千条自然语言描述的设计规则翻译成可执行的 DRC 脚本，这不仅耗时且极易出错。这篇论文不仅提供了一个大规模基准测试集 Rule2DRC ，更关键的是提出了 SplitTester 这一基于执行反馈的测试生成策略，为 LLM 在垂直领域代码合成中的“自我修正”提供了极具参考价值的工程范式。
### 现有方案的痛点目前 LLM 生成 DRC 脚本面临两个核心瓶颈：
- 评估不准：现有基准集（如 DRC-SG）规模小（通常 <200 条），且多依赖代码相似度评估。然而，同一规则可有多种语法实现（如图 3 所示），表面相似不等于功能正确。
- 缺乏反馈闭环：多数方法忽略 DRC 引擎的执行反馈，或假设拥有带标签的测试布局作为输入。这在现实中不切实际，因为获取 Ground Truth 验证结果本身就需要专家介入。
### SplitTester 的核心 Insight论文提出的 SplitTester 并非简单的“生成测试用例”，其核心直觉在于： 区分度优于覆盖率 。
在 Best-of-N 策略中，LLM 会生成多个候选脚本。传统方法（如 CodeMonkey）往往先剪枝到 Top-3 再生成测试，容易误杀潜在正确答案；而 S∗S^* 方法则关注已区分的候选者。SplitTester 反其道而行之：
- 聚类：将候选脚本按当前测试集上的执行输出进行聚类，找出“表现一致”的组。
- 靶向分裂：优先选择那些规模大且得分高的簇（Cluster）。直觉是，大簇中更可能混杂着正确与错误的答案，高分则意味着这些答案在现有测试下表现良好，值得进一步甄别。
- 生成判别性测试：针对该簇生成新的测试布局，旨在让簇内成员产生不同的执行结果，从而将其“分裂”。
这种设计避免了在已经区分的低分候选者上浪费算力，将有限的测试预算集中在最有可能包含正确答案的“模糊地带”。
### 关键实验结果Rule2DRC 包含 1,000 个任务和 13,921 个评估布局，规模是此前基准的一个数量级。在 GPT-OSS-20B 模型上，使用 Best-of-20 策略时，SplitTester 的表现如下：
方法 成功率 (Success Rate) 错误率 (Error Rate) CodeMonkey 41.1% 14.1% S∗S^* 38.2% 14.9% SplitTester 44.4% 12.6%可以看到，SplitTester 不仅将成功率提升了约 3.3%，还将错误率降低了 1.5%。在更强的 GPT-OSS-120B 上，其成功率从 62.7% 提升至 63.8%，且始终位于帕累托前沿（Pareto Frontier），即在相同运行时下取得最高成功率。
此外，论文强调提供 KLayout API 文档作为上下文至关重要。对于 GPT-OSS-120B，加入 API 文档后，Pass@1 提升了超过 20 个百分点，Pass@20 提升了超过 40 个百分点。这印证了在垂直领域， 领域知识注入（Context Engineering）比模型本身的大小更关键 。
### 工程启示- 执行反馈是金：在代码合成任务中，不要只依赖 LLM 的“直觉”判断代码好坏。构建可执行的验证环境（如 DRC 引擎），利用运行结果作为硬约束信号，能显著提升最终产出质量。
- 测试生成的策略性：随机生成测试用例效率低下。针对“难以区分”的候选群体定向生成测试，是一种高效的资源分配策略，适用于任何需要多轮迭代优化的 Agent 系统。
- 基准集的开放性：Rule2DRC 开源了从 SkyWater130 PDK 提取的真实规则及合成数据，为后续研究提供了宝贵的标准测试床，有助于推动 EDA 领域的自动化进程。
### 局限与展望尽管 SplitTester 效果显著，但其依赖 LLM 生成测试布局并预测预期结果，若 LLM 生成的测试用例本身有误（False Negative/Positive），可能会误导选择过程。此外，目前主要基于 Best-of-N 采样，未来可探索如何将这种执行反馈机制集成到自回归生成过程中，实现更实时的自我修正。
