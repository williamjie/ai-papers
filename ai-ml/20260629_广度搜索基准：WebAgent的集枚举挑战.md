# ⭐⭐⭐½ 广度搜索基准：Web Agent 的集枚举挑战

**日期**: 2026-06-29

---

论文 : Ko-WideSearch: A Korean Breadth-Search Benchmark for Exhaustive Set Enumeration by Web Agents链接 : https://arxiv.org/abs/2606.27595现在的 Web Agent 评测大多在卷“深度”：藏一个答案，让 Agent 翻遍全网找出来。但真实业务里，我们更需要“广度”——比如列出所有韩国廉价航空及其母公司、成立年份和机队规模。这种需要完整枚举封闭集合（Set Enumeration）并填充多维属性的任务，才是工程落地的硬骨头。
这篇论文提出了 Ko-WideSearch ，一个专为韩语环境设计的广度搜索基准。它揭示了当前 Agent 的核心短板：找得到名单，填不全表格。
### 痛点：深度容易，广度难死现有评测如 BrowseComp 或 GAIA，主要考察多跳推理（Multi-hop Reasoning）。它们假设答案是唯一的、离散的。
但“广度”任务完全不同：
- 完整性要求极高：漏掉一个成员就是错，多编一个也是错。
- 属性分散：每个成员的详细属性往往不在同一页面，需要跨源验证（Cross-source Verification）。
- 构建成本高昂：人工标注完整表格极其昂贵，且难以保证“金标准”的完备性。
Ko-WideSearch 通过自动化合成与验证管道解决了构建难题，并引入了两个关键的结构化难度旋钮： 表宽度 （属性数量）和 二维复合键 （如“球队×赛季”的网格结构）。
### 方法拆解：如何制造“难而不偏”的基准？
论文的核心 Insight 在于： 难度不应仅靠信息隐藏，而应通过结构化复杂度来调节。
作者设计了三个难度层级，通过独立控制两个变量来实现：
- Easy：窄表（中位数 3 列），无复合键。主要是列表形式。
- Medium：宽表（5 列）或窄网格。引入部分二维结构。
- Hard：宽网格（7 列），100% 使用二维复合键。例如“所有省份在第 7、8 届地方选举中的当选者”，行数是 17×2=3417 \times 2 = 342=34 行，且每个当选者的年龄需从独立传记页查找。
关键工程细节：归一化感知比较器（Normalization-aware Comparator）
在构建金标准和评分时，作者发现 naive 字符串匹配会误杀大量稳定列（如日期格式、千位分隔符）。因此，他们开发了一个共享的比较器：
- 日期对齐：年份级匹配忽略具体日期差异。
- 数值清洗：去除千位符和单位，应用相对容差。
- 文本归一化：基于子串和 Token 重叠进行保守匹配。
这一设计确保了评分的公平性，避免了因格式微调导致的分数虚低。
### 关键结果：Agent 在“填表”上集体翻车作者在 20 个主流模型（包括 GPT-5.5, Claude-Opus-4.8, DeepSeek-V4-Pro 等）上进行了测试。结果令人深思：
指标 GPT-5.5 Claude-Opus-4.7 DeepSeek-V4-Pro Item-F1 (集合成员召回) 92.8% 94.6% 80.4% Column-F1 (单元格正确率) 74.3% 75.6% 63.9% Row-F1 (整行完全正确) 53.7% 51.6% 45.0% Table Success (全表完美) 19.3% 15.8% 12.3%⚠️ 反直觉发现 ：
最强的 GPT-5.5 能找回 92.8% 的成员，但只有 19.3% 的表格是完全正确的。
瓶颈不在“找”，而在“填” 。Agent 容易遗漏或错误填充那些需要从不同页面获取的自由文本属性（Free-text cells），其准确率仅为 49%，远低于日期（58%）和名称（56%）。
此外，增加搜索次数并不能解决问题。重搜索者（如 Qwen3.6-35B）得分反而最低，说明盲目增加工具调用无法提升结构化数据的完整性。
### 工程启示：如何优化你的 Web Agent？
- 分离检索与填充：不要指望一次 Prompt 搞定所有事。先让 Agent 穷举集合成员（Item-F1），再针对每个成员单独发起属性查询。
- 强化结构化输出约束：论文指出，部分模型（如 Solar-Open-2-preview）甚至无法稳定输出表格格式（Parse Rate 仅 62.7%）。在工程落地中，必须强制使用 JSON/CSV 模式，并配合 Schema 验证。
- 重视归一化逻辑：后端评测和前端展示之间必须有统一的归一化层。不要直接用 LLM 做字符串比对，否则会因为“12,742 km” vs “12742km”这种细枝末节导致大量误判。
### 局限与展望Ko-WideSearch 目前仅覆盖韩语环境，且 Hard 层级中体育赛季类任务占比偏高（30/45）。此外，虽然自动化管道提高了效率，但仍依赖 LLM 进行非记忆性验证，可能存在细微的幻觉风险。
对于工程师而言，这篇论文的价值不在于韩语评测本身，而在于它量化了“广度搜索”的难度梯度。如果你的 Agent 在 Item-F1 上表现良好但 Row-F1 低下，不要急着换模型，先检查你的属性填充策略和结构化输出稳定性。
