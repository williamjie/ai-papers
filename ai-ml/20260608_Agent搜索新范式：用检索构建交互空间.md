# ⭐⭐⭐½ Agent搜索新范式：用检索构建交互空间

**日期**: 2026-06-08

论文 : Towards Retrieving Interaction Spaces for Agentic Search链接 : https://arxiv.org/abs/2606.06880传统的 RAG 把检索当作“填空题”，直接塞给模型；而 DCI（Direct Corpus Interaction）让 Agent 像黑客一样在原始语料库中跑 Shell 命令。前者丢失细节，后者随着数据量膨胀彻底失控。这篇论文提出了一个折中但极具工程价值的方案： 检索不应只返回文档片段，而应构建一个有边界的“交互空间” 。
## 痛点：无边界交互的灾难目前的 Agent 搜索面临两个极端困境。传统 RAG 只是把文档切片塞进 Context Window，Agent 只能被动阅读，无法自主探索文档结构。而 DCI 让 Agent 直接操作整个语料库文件系统，看似强大，实则脆弱。
论文引用了 DCI 的扩展性研究：当语料从 10 万篇增加到 20 万篇时，平均工具调用次数从 38.5 激增到 86.9，准确率暴跌 13.6 个百分点；到了 40 万篇，准确率仅剩 37.5%。核心原因在于，每一次全局 grep 都是全库扫描，Agent 把预算都耗在了筛选 Shell 输出上，而不是回答问题。
## 方法拆解：RISE 的核心直觉作者提出了 RISE (Retrieving Interaction SpacE) ，其核心 Insight 是将检索的角色从“选择阅读内容”转变为“构建探索环境”。这包含两个关键设计约束：
- 必须有边界（Boundary）：检索器需要提供一个显式的、持久的候选文档集。它既不是 DCI 的全库裸奔，也不是 RAG 的上下文窗口限制，而是一个 Agent 可以在外部反复遍历的工作目录。
- 对象需结构化（Navigable Objects）：空间内的文档不能是纯文本，也不能是预切片的 Snippet。作者采用离线预处理，为每篇文档生成带行号的目录（TOC）。这样 Agent 可以通过 Shell 工具直接跳转到特定章节，无需全文扫描。
⚠️ 关键直觉 ：检索的价值不在于把证据塞进 Prompt，而在于划定一个 Agent 可以自由使用 Shell 工具探索的“安全区”。
在实现上，RISE 使用 BM25 构建边界（每次搜索硬链接 Top-K 文档到工作目录），并通过 LLM 生成带行号的 TOC 作为导航元数据。Agent 在这个受限空间内使用 rg 、 grep 和 read 进行精准定位。
## 关键结果：性价比与扩展性的胜利在 BrowseComp-Plus 基准测试上，RISE 展现了惊人的效率优势。以下是核心数据对比（基于 gpt-5.4-mini）：
架构 准确率 单次查询成本 ($) 工具调用次数 RISE 78% 0.28 24.3 RISE-BM25 (无TOC) 77% 0.34 23.0 DCI (全库Shell) 78% 1.10 48.8 Retrieval-Agent 68% 0.46 29.2几个值得注意的发现：
- 成本大幅降低：RISE 以 DCI 四分之一的成本达到了相同的准确率。即使给 DCI 3 倍的模型调用预算和 1.5 倍的时间上限，它依然更贵且不稳定。
- 扩展性碾压：当语料扩展到 100 万篇时，RISE-BM25 的准确率保持稳定（甚至微增至 81%），而 DCI 的准确率跌至 60%，且有 33/100 的查询因超时失败。
- TOC 的价值：在 10 万语料下，加入 TOC 处理的 RISE 比仅做边界限制的 RISE-BM25 准确率高出 1-4 个点，证明了结构化导航对长文档探索的有效性。
## 工程启示对于正在构建搜索 Agent 的团队，这篇论文提供了明确的架构指导：
- 放弃全库 Shell 访问：除非语料极小，否则不要直接暴露原始文件系统给 Agent。
- 中间态工作区：在检索和生成之间，建立一个临时的、可遍历的“工作目录”。让 Agent 在这个受限空间内进行二次探索，而不是在 Prompt 里玩文字游戏。
- 离线结构化优于在线切片：与其在检索时动态切分 Snippet（容易丢失上下文），不如在索引阶段为文档添加结构元数据（如 TOC、锚点）。这能让 Agent 像人类一样“跳读”长文档。
## 局限与展望目前 RISE 的离线 TOC 生成仅验证于 10 万语料规模，扩展到百万级需要额外的预处理成本。此外，实验仅使用了 BM25 作为边界检索器，未来可以尝试结合稠密检索或混合检索来优化边界的精准度。但无论如何，**“交互空间”**这一概念本身，已经为 Agent 搜索指明了比 RAG 和 DCI 更可行的中间道路。
