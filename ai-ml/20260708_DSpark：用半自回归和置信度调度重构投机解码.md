在生产环境中，单纯追求草稿长度毫无意义。如果后续 token 被拒绝率高，反而会因为占用批处理（Batch）资源导致整体吞吐量下降。DSpark 的 Insight 非常清晰：既要利用并行生成的速度优势，又要通过轻量级串行模块修复序列连贯性，最后根据系统负载动态裁剪验证长度。
## 现有方案的死胡同目前的投机解码主要分两派，但都有明显短板：
- 自回归草稿（如 Eagle3）：质量高，但生成速度慢。因为每个 token 都要依赖前一个，延迟随块大小线性增长，被迫使用短块和浅层网络。
- 并行草稿（如 DFlash）：速度快，一次前向传播生成整个块。但由于各位置独立预测，缺乏 Token 间的依赖建模，导致“后缀衰减”严重——越往后生成的 Token，被拒绝的概率越高。
更致命的是系统层面的浪费。在低负载时，验证多余 Token 成本极低；但在高并发下，每一个可能被拒绝的 Token 都在占用宝贵的 GPU 批处理容量。 indiscriminately（不加区分地）验证长序列，在高负载时会严重拖累整体吞吐量。
## DSpark 的核心设计DSpark 通过两个互补机制解决了上述问题：
### 1. 半自回归生成（Semi-Autoregressive Generation）
这是 DSpark 在模型架构上的核心创新。它没有完全抛弃并行，也没有退回纯串行，而是采用“并行骨干 + 轻量串行头”的混合结构。
- 并行阶段：使用类似 DFlash 的并行骨干网络，一次性生成所有位置的隐藏状态和基础 Logits。这保证了 TdraftT_{draft}​（草稿时间）几乎不随块大小增加。
- 串行阶段：引入一个极轻量的模块（Markov Head 或 RNN Head），根据前一个已采样的 Token 注入转移偏差（Transition Bias）。
这种设计的直觉在于：并行网络负责捕捉全局上下文，而轻量串行模块负责修复局部连贯性。例如，当并行网络可能同时预测 “of course” 和 “no problem” 时，Markov Head 会根据前一个词 “of” 抑制 “problem”，从而显著降低多模态碰撞带来的拒绝率。
### 2. 置信度调度验证（Confidence-Scheduled Verification）
这是 DSpark 在系统工程上的杀手锏。它不再固定验证长度，而是动态决定每个请求该验证多少个 Token。
- 置信度头：预测每个位置的前缀存活概率。
- 硬件感知调度器：结合实时引擎吞吐量曲线（SPS），计算全局期望吞吐量最大化。
调度器会将所有请求的候选 Token 按存活概率排序，贪婪地选择高收益 Token 进行验证。一旦加入新 Token 导致整体吞吐量下降（因为批处理变大导致单步延迟增加），就立即停止。这确保了在高负载下，算力只花在“大概率能通过”的 Token 上。

## 工程启示与局限对工程师的指导意义：
- 不要盲目追求长草稿：在资源受限或高并发场景下，短而精的验证比长而乱的草稿更有效。
- 架构混合是趋势：完全并行或完全串行都有缺陷，“重并行+轻串行”的混合架构可能在更多推理加速场景中复用。
- 系统感知至关重要：算法不能脱离硬件孤立存在。DSpark 的成功很大程度上归功于它将调度策略与引擎吞吐量曲线（SPS）绑定，这是纯算法研究容易忽视的点。
局限与展望：
- 校准依赖：置信度头需要后验校准（Sequential Temperature Scaling），这增加了部署前的调优成本。
- 因果性约束：为了保证无损采样，调度器必须采用早期停止机制，这在理论上假设了吞吐量曲线的单��特性，实际工程中可能需要针对非平滑曲线做适配。
