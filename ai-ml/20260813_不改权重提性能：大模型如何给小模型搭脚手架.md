# ⭐⭐⭐⭐ 不改权重提性能：大模型如何给小模型搭脚手架

**日期**: 2026-08-13

---

论文 : AI4AI at Test-Time: Strong-to-Weak Capability Transfer via Harnesses链接 : https://arxiv.org/abs/2608.12307我们习惯认为，想让小模型（Small Language Models, SLMs）具备大模型的推理能力，要么靠昂贵的监督微调（SFT），要么靠复杂的强化学习。但 Salesforce 的这篇新论文提出了一个反直觉的观点： 与其费力修改小模型的权重，不如让强模型在推理时为它搭建一套“脚手架” 。
这种“测试时能力转移”不仅有效，而且效果惊人。对于工程师而言，这意味着我们可以用大模型的“智慧”来编排小模型的执行流程，而无需重新训练任何参数。
### 痛点：微调太贵，Prompt 太脆现有的蒸馏技术（Distillation）核心在于“改模型”。通过教师模型生成数据，让学生模型去拟合。这虽然有效，但有两个工程痛点：
- 成本高：每次任务变化或基准更新，都需要重新训练或微调。
- 认知过载：小模型失败往往不是因为“不懂”，而是因为任务呈现方式让它“晕了”。
本文提出了一种互补思路： 不改变模型本身，而是改变任务的环境 。让一个强大的 Builder 模型构建一套推理时的 Harness（包含路由、模板、验证逻辑等），专门用来辅助固定的弱 Target 模型。
### 核心 Insight：把不确定性外包给确定性代码这篇论文最精彩的地方在于拆解了“脚手架”到底在做什么。
研究者发现，成功的脚手架并不是让弱模型“多想一会儿”，而是 将不稳定的推理过程卸载到确定性的代码中 。
- 传统思路：让弱模型写更长的 Chain-of-Thought (CoT)。
- 本文发现：有效的增益来自格式强制（Format Enforcement）、基准特定路由（Benchmark Routing）以及确定性求解器（Deterministic Solvers）。
简单来说，Builder 模型把任务拆解成小模型能稳定执行的步骤，并用代码锁死输出格式和逻辑分支。这种“认知结构的外部化”比单纯的提示词工程要稳健得多。
### 实验结果：近乎翻倍的性能提升研究在四个心理理论（Theory-of-Mind, ToM）基准上进行了测试，Target 模型固定为 GPT-5.4-mini。数据非常硬核：
指标 数值/对比 Baseline (无脚手架) 宏观平均准确率 0.488 最佳自动脚手架 宏观平均准确率 0.912 性能提升 +0.423 (相对提升 86.7%) 超越更强模型？ 是的，优于无脚手架的 GPT-5.4 (0.619) 和 GPT-OSS-120B 稳定性 标准差仅 0.036，远小于增益幅度⚠️ 反直觉发现 ：Builder 模型的推理努力与脚手架质量呈单调正相关，但 验证集的使用次数并不重要 。
数据显示，验证迭代次数与最终准确率的相关系数仅为 0.17。这意味着， 强 Builder 靠的是“设计质量”而非“暴力搜索” 。几次精准的迭代胜过无数次的盲目尝试。
### 工程启示：Agent 开发的未来范式对于正在构建 Agent 系统的工程师，这篇论文提供了三个关键指导：
- Harness 即产品：不要只关注 Prompt 文本。将路由逻辑、格式校验和工具调用封装成可复用的代码模块（Harness），才是提升小模型表现的关键。
- 强弱搭配的新思路：在成本敏感的场景下，可以用一个大模型作为“架构师”，为多个廉价的小模型生成定制化的推理流程。这比全量微调更灵活，比纯 Prompt 更稳定。
- 确定性优于概率性：在可能的情况下，尽量将逻辑判断交给代码（Deterministic Solvers），而不是让 LLM 去猜。LLM 擅长生成文本，不擅长做严格的逻辑校验。
### 局限与展望当然，自动生成的脚手架仍有边界。在涉及高阶递归信念（如 Hi-ToM 中深度≥2的情况）和贝叶斯目标推断时，自动脚手架的表现仍落后于人工精心设计的 UserHarness。这说明，当任务结构过于复杂、难以编译为规则时，人类专家的系统性设计依然不可替代。
但这不妨碍它成为一种强大的通用策略： 用大模型的认知结构，去填补小模型的能力缺口。
