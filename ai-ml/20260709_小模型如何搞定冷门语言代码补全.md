# ⭐⭐½ 小模型如何搞定冷门语言代码补全

**日期**: 2026-07-09

---

论文 : Teaching LLMs a Low-Resource Language: Enhancing Code Completion in Pharo链接 : https://arxiv.org/abs/2607.04939主流大模型在 Python、Java 上呼风唤雨，但面对 GitHub 仓库不足 2000 个的“濒危”语言 Pharo，它们往往直接摆烂。
这篇论文提供了一个极具工程参考价值的案例：如何通过精细的数据清洗和两阶段微调，让参数量仅 7B 甚至更小的开源模型，在冷门语言的代码补全任务上碾压千亿参数的大模型。
### 痛点：数据荒漠与格式陷阱Pharo 是 Smalltalk 的现代实现，语法独特（控制流也是方法调用），且代码存储格式 Tonel 混合了元数据和逻辑。
这种结构对 LLM 极其不友好：
- 数据极度稀缺：相比 Python 的 2600 万个仓库，Pharo 只有约 2000 个。
- 噪声干扰严重：Tonel 格式中的类定义元数据容易让模型混淆可执行代码与包装信息。
- 现有工具落后：Pharo IDE 目前仅提供单 Token 补全，缺乏上下文感知的多 Token 建议。
### 核心设计：从“读懂”到“像人一样写”
作者没有直接微调，而是设计了严格的端到端流水线，核心 Insight 在于区分“语法学习”与“行为对齐”。
1. 数据清洗是生死线- 许可证过滤：仅保留 MIT 协议仓库，规避法律风险。
- 版本兼容性验证：自动将代码导入 Pharo 10-14 环境，无法加载的仓库直接丢弃。这一步将初始 748 个仓库缩减至 415 个，确保了训练数据的“活性”。
- 防污染切割：以 2024 年 6 月 1 日为界，之前用于训练，之后用于测试，确保评估的公正性。
2. 两阶段训练策略- 持续预训练（Continued Pre-training）：
目标：让模型掌握 Pharo 的语法结构和 API。
- 技巧：混合使用左到右因果语言建模（CLM）和中间填充（FIM）。75% 的数据采用 FIM，模拟编辑器中光标位于代码中间的场景。
- 监督微调（Supervised Fine-Tuning, SFT）：
目标：适应真实的补全场景。
- 创新点：Random-AST 掩码策略。不同于预训练时按 AST 节点完整掩码，SFT 阶段随机选择 Token 作为起点并延伸至语句结束。这模拟了开发者在任意位置请求补全的真实行为。
### 实验结果：小模型逆袭大模型实验对比了基座模型、预训练后模型、微调后模型，以及 Qwen3 Coder (480B) 和 Claude Sonnet 4.5 等巨头。

更惊人的是，这个仅 3B 参数的本地模型，在 Pharo 补全任务上的表现 显著优于 参数量大 60 倍以上的 Qwen3 Coder 480B 和 Claude Sonnet 4.5。
### 工程启示- 领域特异性胜过通用规模：对于冷门语言或垂直领域，专用小模型配合高质量数据，完全可以吊打通用大模型。
- 掩码策略决定上限：预训练用结构化掩码学语法，微调用随机掩码学交互。这种分层设计值得在构建内部代码助手时借鉴。
- 本地部署可行性：7B 模型量化至 4-bit 后仅需 4.3GB 显存，可在普通笔记本上实现实时 IDE 补全，解决了延迟痛点。
### 局限与展望论文主要聚焦于 Pharo 这一特定案例，其他冷门语言（如 Julia、Rust 生态中的小众方言）是否适用此流水线仍需验证。此外，Tonel 格式的特殊性使得数据提取工具难以直接复用，需要为每种语言定制解析器。
但这篇论文证明了：只要数据够干净、训练策略够精细，LLM 也能成为“濒危”编程语言的守护者。
