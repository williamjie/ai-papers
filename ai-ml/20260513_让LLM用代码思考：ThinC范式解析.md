# 让LLM用代码思考：ThinC范式解析

**日期**: 2026-05-13

---

论文 : Teaching Language Models to Think in Code链接 : https://arxiv.org/abs/2605.07237现在的开源大模型在数学推理上卷得厉害，但大多数方案（包括最新的思维链）都存在一个隐蔽的结构性缺陷： “算得慢，错得惨” 。
韩国高丽大学团队提出的 Thinking in Code (ThinC) 框架，直接挑战了当前主流的 Tool-Integrated Reasoning (TIR) 范式。它的核心观点很激进：代码不应该是自然语言（NL）推理的“计算器”或“验证器”，代码本身就应该成为推理的主体。
对于工程落地来说，这意味着我们可以用更小的模型（如 4B 参数），通过改变推理轨迹的结构，超越参数量大几十倍的现有 SOTA 模型。
## 痛点：传统 TIR 的三大结构性死穴在 ThinC 出现之前，TIR 是解决 LLM 算术错误的主流方案。其典型流程是：NL 规划 -> 生成代码 -> 执行 -> NL 解释 -> 再生成代码…… 这种交错式（Interleaved）推理看似完美，但论文指出它有三个致命弱点：
- 后置验证（Post-hoc Verification）：模型往往先用 NL 算出结果，再写代码去“确认”。如果 NL 阶段就错了，代码只是陪跑，没有产生新的计算价值。
- 误差静默传播：NL 中的算术错误（如 500×0.12=50500 \times 0.12 = 500.12=50 而非 60）会被直接硬编码进下一个代码块。解释器无法检测这个逻辑错误，导致最终答案错误且难以调试。
- 角色重叠：NL 描述算法步骤，代码重新实现一遍。两者在做同样的工作，既浪费 Token，又增加了出错概率。
ThinC 的设计直觉非常清晰： 切断 NL 和代码之间的“推导”联系，只保留“规划”联系。
## 方法拆解：ThinC 是怎么设计的？
ThinC 的推理轨迹格式发生了根本性变化：
τThinC=(q,t1,c1,o1,c2,o2,...,cN,oN,a)\tau_{ThinC} = (q, t_1, c_1, o_1, c_2, o_2, ..., c_N, o_N, a) ​ = ( q , t 1 ​ , c 1 ​ , o 1 ​ , c 2 ​ , o 2 ​ , ... , c N ​ , o N ​ , a )
注意看，除了第一步 t1t_1 ​ ，后续只有代码块 cic_i ​ 和执行输出 oio_i ​ 。 中间没有任何 NL 思考过程。
### 1. 角色分离：NL 只负责“想”，代码负责“做”
t1t_1 ​ 被严格限制为高层策略规划（例如：“我将利用对称性计算两个菱形的并集面积”）。一旦策略确定，后续所有步骤完全由代码驱动。代码块 cic_i ​ 直接基于前一步的输出 oi−1o_{i-1} ​ 进行计算，而不是基于 NL 的文本描述。
### 2. 数据蒸馏：SFT 建立“代码-centric”先验训练分为两步。首先是 监督微调（Supervised Fine-Tuning, SFT） 。
作者使用 Qwen3.5-27B 作为教师模型，通过 Few-shot Prompting 蒸馏出 12.2k 条符合 ThinC 格式的轨迹。过滤条件非常严格：
- 轨迹必须正确。
- 代码执行无错误。
- 至少包含 3 个代码块。
- NL 规划部分不超过总 Token 的 50%。
这一步不是为了刷准确率，而是为了 让模型习惯“不写废话，只写代码”的行为模式 。实验显示，仅经过 SFT 的模型准确率反而下降（因为学会了新格式但还没学会怎么解难题），这证明了 SFT 只是建立了结构先验。
### 3. 强化学习：RL 驱动性能跃升在 SFT 基础上，使用 GRPO 算法进行强化学习。由于 ThinC 格式天然可验证（最终答案必须来自代码输出），奖励信号非常清晰。RL 阶段通过三阶段课程学习（逐步增加上下文长度和工具调用次数），让模型学会在代码中处理复杂逻辑和错误恢复。
## 关键结果：小模型打败大模型ThinC 在五个竞赛级数学基准测试（AIME 2024-2026, HMMT 2025, BeyondAIME）上表现惊人。以下是核心数据对比（avg@16）：

- 超越大模型：ThinC-4B 在 HMMT 2025 和 BeyondAIME 等难题上，大幅超过了 235B 的 Qwen3-Thinking。

## 工程启示：为什么 ThinC 更鲁棒？
论文中最令人兴奋的发现之一是 ThinC 的 错误恢复能力 。
在交错式 TIR 中，如果第一步代码报错，模型需要依赖 NL 来理解错误并重新规划。如果 NL 也出错，整个推理链就断了。但在 ThinC 中，由于没有 NL 中介，代码块之间仅通过输出连接。
实验数据显示，在连续 1-3 次代码执行失败的情况下：
- 传统 TIR 基线（如 ASTER, ReTool）的恢复率急剧下降，甚至归零。
- ThinC-4B 保持在 64%-69% 的高恢复率。
这是因为 ThinC 的 RL 训练迫使模型学会在代码内部进行自我修正（例如，重新编写循环逻辑），而不是依赖外部的 NL 解释。此外， 99.2% 的 ThinC 最终答案直接来源于解释器输出，这意味着它彻底消除了“NL 算术错误污染代码输入”的风险。
## 局限与展望尽管 ThinC 表现优异，但它并非银弹：
- 规模限制：目前仅在 1.7B 和 4B 模型上验证，是否适用于 70B+ 模型仍需观察。
- 领域限制：仅针对数学推理。在处理需要多步文本搜索或非结构化数据的任务时，纯代码推理可能不如混合模式灵活。
- 调试难度：纯代码轨迹的可解释性不如 NL，对于非技术用户来说，调试推理过程可能更困难。
## 总结ThinC 的核心 Insight 是： 在数学推理中，代码是比自然语言更精确的符号系统。
它通过强制分离“规划”与“计算”，并利用 RL 强化代码内部的逻辑闭环，实现了小参数下的高性能。对于工程师而言，这提示我们在设计 Agent 或推理框架时， 结构化的数据流（如纯代码管道）可能比灵活的混合文本更可靠、更高效 。如果你的任务涉及大量数值计算或逻辑推导，不妨尝试让模型“闭嘴”，让它直接写代码。
