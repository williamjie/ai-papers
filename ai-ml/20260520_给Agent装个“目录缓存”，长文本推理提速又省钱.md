# ⭐⭐½ 给Agent装个“目录缓存”，长文本推理提速又省钱

**日期**: 2026-05-20

---

论文 : PEEK: Context Map as an Orientation Cache for Long-Context LLM Agents链接 : https://arxiv.org/abs/2605.19932在处理数万行代码或几十万字文档时，Agent 最大的痛点不是“读不懂”，而是“记不住”。每次面对新任务，它都得重新扫描一遍上下文，这种重复的“方向感建立”过程既浪费 Token 又拖慢速度。MIT 和斯坦福提出的 PEEK ，本质上是为 Agent 设计了一个“上下文地图（Context Map）”缓存机制，让 Agent 在多次交互中保留对文档结构、关键实体和常用模式的认知，实现“一次探索，多次复用”。
### 现有方案的死胡同目前的长上下文管理手段主要分为两类，但都有明显短板：
- 被动访问：RAG（检索增强生成）或上下文压缩。它们只保留原始材料的被动访问权，不维护对上下文本身的“认知”。每次查询都是冷启动。
- 状态保持：共享聊天历史（Shared Chat）或提示词学习（Prompt Learning，如 ACE）。共享历史会迅速积累噪声，导致上下文窗口被低密度信息占据；而提示词学习通常优化的是“任务策略”，而非“上下文结构”。
论文指出，对于反复查询同一外部上下文的工作负载，缺失的是 可复用的方向知识（Orientation Knowledge） ：即“这个上下文里有什么、怎么组织的、哪些常量有用”。人类分析师在处理大量反馈数据时，会先建立一张轻量的目录或备忘录，Agent 也需要类似的东西。
### PEEK 的核心设计：像 CPU 缓存一样管理知识PEEK 的创新在于将“上下文地图”视为 Agent 提示词中的一个 固定大小、常驻的缓存区 。其核心架构包含三个模块，模拟了计算机系统中的缓存策略：
- Distiller（蒸馏器）：从 Agent 的执行轨迹（推理步骤、工具调用、观察结果）中提取可转移的知识。它不依赖 Ground Truth，而是通过自我诊断，区分“方向性知识”（如文档结构）和“任务特定事实”，只保留前者。
- Cartographer（制图师）：将蒸馏出的知识转化为结构化的编辑操作（ADD/DELETE/REPLACE）。每个地图条目都有唯一 ID，确保更新是局部且可追溯的，避免噪声累积。
- Evictor（驱逐器）：基于优先级的驱逐策略。地图有严格的 Token 预算（默认 1024 tokens）。当超出预算时，优先驱逐低价值条目（如解析模式），保护高价值条目（如上下文路线图和理解）。
关键 Insight ：分离“提取”与“编辑”至关重要。如果不分离，任务特定的事实会泄漏到缓存中，导致地图变得嘈杂且重复。
### 实验数据：性能与成本的双赢在 OOLONG（长上下文推理）和 CL-bench（上下文学习）基准测试中，PEEK 展现了显著优势。以 GPT-5-mini 为基座模型，对比最强基线 ACE（提示词学习框架）：
指标 OOLONG (Yahoo) CL-bench (Solving Rate) CL-bench (Rubric Accuracy) 基线 RLM 23.0 14.0 54.5 RLM + ACE 42.0 (+19.0) 20.0 (+6.0) 53.5 (-1.0) RLM + PEEK 57.0 (+34.0) 26.0 (+12.0) 63.4 (+8.9)
- 质量提升：PEEK 在 OOLONG 上比 ACE 高出 10.7%，在 CL-bench 上解决率高出 6.0%，细粒度准确率高出 9.9%。
- 效率飞跃：PEEK 比 ACE 少使用 93–145 次迭代。在 OOLONG 上，PEEK 的成本仅为 ACE 的 1/1.7 到 1/5.8。
- 泛化能力：该机制不依赖特定模型。在 GPT-5.5、开源模型 Qwen3-Coder-Next 以及生产级 Agent Codex 上均观察到一致的性能增益。例如，在 Codex 上，PEEK 使 CL-bench 解决率从 24.0% 提升至 34.0%。
### 工程启示与局限对工程实践的指导意义 ：
- 缓存即知识：不要只缓存 KV Cache 或原始文本，要缓存“对上下文的元认知”。对于企业级 Agent（如代码库分析、客服知识库），维护一个小型的结构化地图比维护冗长的对话历史更有效。
- 结构化更新：采用“诊断-编辑-驱逐”的流水线，避免直接让 LLM 重写整个上下文摘要，能显著降低幻觉和噪声。
- 预算控制：固定 Token 预算（如 1024 tokens）是保持效率的关键。实验表明，即使预算从 512 增加到 2048，收益边际递减，小而精的地图往往足够。
局限 ：
PEEK 的价值取决于 Agent 与上下文的交互深度。如果交互无法揭示可复用的知识结构，缓存的价值有限。此外，目前主要适用于“同一上下文、不同任务”的场景，对于上下文频繁变化的场景，维护成本可能高于收益。
PEEK 提供了一个清晰的范式：在 LLM 的 Prompt 工程中，引入类似操作系统缓存的管理机制，是提升长上下文 Agent 效率和准确性的有效路径。
