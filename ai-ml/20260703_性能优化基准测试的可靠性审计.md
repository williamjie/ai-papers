论文 : Are Performance-Optimization Benchmarks Reliably Measuring Coding Agents?
链接 : https://arxiv.org/abs/2607.01211在 Coding Agent 领域，功能修复（如 SWE-Bench）已有成熟标准，但性能优化（Performance Optimization）的评估却充满了“噪音”。这篇论文直接审计了 GSO、SWE-Perf 和 SWEfficiency 三大主流基准测试，揭示了当前排行榜可能存在的误导性。对于正在构建或评估 Agent 的工程师来说，理解这些偏差比盲目追求高分更重要。
### 核心痛点：硬件噪音与评分规则的陷阱性能优化的本质是测量时间，而时间是极易受环境影响的变量。CPU 调度、缓存状态甚至内存带宽竞争都会导致同一补丁在不同机器上表现迥异。
论文的核心洞察在于： 基准测试的“参考补丁”（Reference Patch）并不像我们想象的那样稳定。 如果参考补丁本身的性能增益在跨机器复现时消失，那么基于它计算的 Agent 得分就失去了物理意义。此外，不同的评分规则（Scoring Rules）会极大地扭曲排行榜的真实排名，甚至让少数极端案例主导最终结果。
### 方法拆解：跨机器复现与评分审计作者没有停留在理论推导，而是进行了大规模的实证审计：
- 跨机器复现实验：在四种不同架构的 Google Cloud 机器（Intel Cascade Lake/Milan, AMD Milan/Turin）上，对 740 个官方参考补丁进行三轮复现。
- 评分规则敏感性分析：对比 GSO 的二元制评分与 SWEfficiency 的调和平均数评分，看同一组提交在不同规则下的排名变化。
- 任务级覆盖度分析：不再只看单个 Agent 的表现，而是聚合前 10 个公共提交，观察哪些任务真正具有挑战性。
### 关键结果：数据揭示的真相#### 1. 参考补丁的脆弱性在跨机器复现中，大量参考补丁未能通过原始基准的有效性规则：
基准测试 官方任务数 跨机器有效任务数 有效率 GSO 102 39 38.2% SWE-Perf 140 11 7.9% SWEfficiency 498 411 82.5%⚠️ 反直觉发现 ：SWE-Perf 的参考补丁中位数运行时间变化仅为 -0.03% 。这意味着其性能增益几乎淹没在硬件噪音中，导致统计显著性极易丢失。相比之下，GSO 和 SWEfficiency 的中位数优化幅度分别达到 -54.20% 和 -56.04%，信号更稳健。
#### 2. 评分规则如何操纵排名SWEfficiency 使用调和平均数计算 SpeedUp Ratio (SR)，并设定地板值 f=0.001f=0.001 0.001 。这导致极低分任务具有巨大的惩罚权重：

- 排名翻转：当作者将地板值调整为更合理的 f=0.5f=0.50.5（限制单任务最大惩罚）后，6/8 的提交排名发生变动，8/28 的对决结果翻转。
这意味着，SWEfficiency 的排行榜不仅反映 Agent 的平均能力，更强烈地反映其“避免极端失败”的能力。
#### 3. 任务真的很难吗？
当聚合前 10 个公共提交时，我们发现大部分任务其实已经被解决：
- 450 个复现有效的任务中，449 个有比基准代码更快的公开补丁。
- 384/450 (85.3%) 的任务至少有一个提交达到了参考补丁的速度。
- 剩余的 66 个“未解决”任务中，65/66 已有正确且加速的补丁，只是未达到参考水平。
这表明当前的瓶颈不再是“找到优化方法”，而是“达到专家级优化的深度”。
### 工程启示- 谨慎解读排行榜：不要盲目相信 SWE-Perf 的高分，其参考信号极不稳定。SWEfficiency 的高分可能仅意味着 Agent 没有在某些任务上彻底崩溃，而非全面优秀。
- 优化评估环境：在本地部署 Agent 评估时，务必固定 CPU 亲和性、关闭节能模式，并进行多次采样以消除微架构噪音。
- 关注长尾策略：既然大多数基础优化已被覆盖，未来的 Agent 改进应聚焦于识别热点路径（Hot Path）和采用更复杂的算法级优化策略，而非简单的代码清理。
### 局限与展望论文指出，当前的基准测试可能需要更强的参考目标来区分顶级提交。此外，由于公共提交多为单模型配置，实际生产环境中多智能体工作流（Multi-agent Workflows）的表现可能远超当前排行榜所示。未来的基准设计需考虑更鲁棒的噪音过滤机制和更细致的策略分类评估。
