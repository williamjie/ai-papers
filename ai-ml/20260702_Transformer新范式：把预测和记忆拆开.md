# ⭐⭐⭐½ Transformer 新范式：把预测和记忆拆开

**日期**: 2026-07-02

---

论文 : The State-Prediction Separation Hypothesis链接 : https://arxiv.org/abs/2607.01218Transformer 的每个隐藏层都在干两件互相打架的事：既要预测下一个词，又要为未来存状态。这篇论文提出一个大胆假设：把这两件事拆开，模型训练效率会显著提升。这不是简单的架构微调，而是对 Transformer 核心机制的一次重构。
### 痛点：混合角色的梯度冲突标准 Transformer 中，每个时间步的隐藏状态 hih_i ​ 同时承担“预测当前输出”和“生成 KV Cache 供未来查询”的双重角色。这意味着优化梯度是混合的：既包含为了当下预测准确的梯度，也包含为了让未来预测更准而积累的梯度。这种纠缠导致模型在有限容量下难以兼顾两者，尤其是在长序列中，早期状态既要服务眼前，又要照顾长远，往往顾此失彼。
### 核心设计：双流分离架构论文提出了 State-Prediction Separation (SPS) Transformer。其核心直觉是：既然预测和记忆冲突，那就用两条独立的计算流来承载它们。
具体做法是在每个输入 token xix_i ​ 后插入一个特殊的 <predict> token ρi\rho_i ​ 。序列变成 (x1,ρ1,x2,ρ2,...)(x_1, \rho_1, x_2, \rho_2, ...) ​ , ρ 1 ​ , x 2 ​ , ρ 2 ​ , ... ) 。
- 状态流 (Input Stream)：处理真实的输入 token xix_i​。这些位置的激活值被保留在 KV Cache 中，专门负责积累长期记忆。
- 预测流 (Prediction Stream)：处理虚拟的 ρi\rho_i​ token。这些位置只负责输出下一个词的概率分布，其产生的 KV 条目仅在一个滑动窗口内有效，随后即被丢弃。
⚠️ 关键 Insight ：这种设计从结构上解耦了梯度。输入流的隐藏状态主要接收来自未来损失的梯度（为了记忆），而预测流的隐藏状态主要接收当前损失的梯度（为了预测）。两者不再通过同一个表示向量“抢资源”。
### 实验结果：数据效率翻倍在 FineWeb-Edu 数据集上，从 53M 到 1.678B 参数的五个规模实验中，SPS 均显著优于标准 Transformer。
指标 SPS vs Standard (XL, 1.6B) 验证集 NLL 降低 0.068 零样本准确率 提升 3.1% 数据效率 达到同等质量只需约一半的数据量 推理内存 与 Standard 基本持平 (Ratio 1.01) 推理吞吐 略低，但在 6-10% 范围内最惊人的是数据效率。在 1.6B 参数规模下，SPS 仅用 18B tokens 就达到了标准 Transformer 训练 47B tokens 后的验证损失水平。这意味着在高质量数据日益枯竭的今天，SPS 能让模型“吃得更少，长得更好”。
### 为什么不是简单加步数？
为了排除“只是多算了一步所以变强”的质疑，作者设计了两个基线：
- 2X Memory：保留所有 <predict> 条目。结果发现性能不如 SPS，说明单纯增加内存容量不是关键。
- Delayed State：在预测后才提交状态，但未分离角色。其性能介于 Standard 和 SPS 之间，证明“分离”本身带来了额外的收益。
梯度分析进一步证实了这一点：SPS 的输入流承载了更多来自未来损失的梯度，且这种长期记忆在推理时被更频繁地调用。当强制限制 KV Cache 窗口大小时，SPS 的性能下降幅度远大于其他变体，说明它确实建立了更有价值的长期依赖。
### 工程启示与局限对于工程实践，SPS 的最大吸引力在于 数据效率 。如果你的场景受限于高质量语料的数量（如垂直领域微调），引入这种分离机制可能比盲目增加训练步数更有效。
不过，目前 SPS 的训练计算量因序列长度翻倍而增加，且推理吞吐量略有下降。论文指出，未来可以通过简化预测流的计算深度或共享参数来降低开销。此外，该架构目前仅在预训练阶段验证，其在指令微调（Instruction Tuning）或 Agent 规划任务中的表现仍需进一步探索。
总之，这是一篇从底层逻辑挑战 Transformer 设计的佳作。它提醒我们：或许我们一直强迫模型做太多事，而“分而治之”才是提升智能的关键。
