## 为什么现有的评估不够用？
目前的隐私基准测试大多关注输出阶段（Output Stage）。如果 Agent 最终回复干净，我们通常认为它是安全的。然而，Agent 具有自主性，它会决定调用哪些工具、读取哪些文件。
核心痛点在于：
- 获取即泄露风险：Agent 可能为了完成任务，顺手读取了无关的敏感文件（如查看血糖时顺便读了身份证号）。这些数据虽然没出现在回复中，但已存在于 Context Window 里。
- 能力与隐私的反比关系：更强的 Agent 往往更倾向于“过度获取”以确保任务完成，导致隐私风险随能力提升而增加。
## PrivacyPeek：审计“获取”而非“输出”
作者提出了 PrivacyPeek 基准，包含 1,182 个测试用例，覆盖 16 个领域和 7 种获取行为。其核心创新在于双视角评估：
-获取检查（Acquisition Inspection）：
这是规则匹配的硬审计。它不关心 Agent 说了什么，只盯着工具调用的轨迹。如果 Agent 读取了任务最小必要范围（Minimum Scope）之外的数据，即判定为泄露。
例如：任务只需查看 vitals.doc，Agent 却调用了 read_file("personal_info.doc")，即使它没输出内容，也被标记为违规。
-探测诱导（Probe Elicitation）：
这是事后压力测试。在 Agent 完成任务后，禁用其工具和网络，向上下文注入特定探针问题，看它是否能从残留的上下文中拼凑出敏感信息。
## 实验结果：越强越“手欠”？
作者在 GPT、Claude、Llama 和 Qwen 系列的 10 个模型上进行了测试，结果令人担忧：
指标 定义 关键发现 CER 内容暴露率（Content Exposure Rate） Claude-Sonnet-4 高达 51.95% ，即半数任务中获取了多余敏感数据。 PLR 探针泄露率（Probe Leakage Rate） Claude-Sonnet-4 达到 57.53% ，表明残留上下文极易被诱导泄露。 相关性 TCR vs CER/PLR 任务完成率（TCR）与隐私泄露呈强正相关（Spearman ρ=0.818）。
⚠️ 反直觉发现 ：GPT-5.1 是一个例外。它在保持高任务完成率（85.70%）的同时，探针泄露率仅为 25.38%，远低于同等能力的 Claude-Sonnet-4。这说明“克制”可以通过后训练对齐实现，而非单纯依赖模型规模。
此外，作者发现 数据中的保密标记（如 [CONFIDENTIAL] ）不仅无效，反而可能起反作用 。在部分模型上，带有保密标记的数据导致探针泄露率上升了 3%-10%。这表明 Agent 会将这些标记视为需要特别关注的“线索”，而非停止获取的信号。
## 工程启示：如何落地？
对于正在构建 Agent 系统的工程师，这篇论文给出了明确的警示和方向：
-不要依赖 Prompt 防御：
实验显示，即使用户提示词中明确加入隐私指令，CER 仅降低约 3%-12%，大部分风险依然存在。Prompt 层面的约束在复杂的工具调用链中极易失效。
-实施前置策略控制（Pre-tool Policy）：
既然 Agent 的“手”不受控，必须在工具层加锁。
字段级限制：API 不应返回全量数据，而应支持按需获取特定字段（如只传 glucose 而非整个患者对象）。
- 最小权限原则：在 Agent 调用工具前，插入一个策略引擎，校验其请求范围是否超出任务定义的最小必要集。
-重新设计评估体系：
如果你正在做 Agent 的隐私评测，必须加入“获取阶段”的审计。只检查最终回复是远远不够的，你需要监控工具调用的输入输出日志，检测是否存在“过度读取”。
-警惕上下文残留：
即使 Agent 没有主动泄露，其 Context Window 中积累的敏感数据也是巨大的安全隐患。考虑引入上下文清理机制（Context Pruning），在任务结束后或每步操作后，主动清除非必要的中间观察结果。
## 局限与展望PrivacyPeek 目前主要基于合成数据和模拟环境，真实世界中的工具接口更加复杂多变。此外，它假设没有恶意的用户输入或工具注入攻击，这在现实高对抗环境中可能过于理想化。未来研究需要探索如何在动态、开放的工具生态中，实现更细粒度的运行时隐私隔离。
总之，Agent 的隐私安全战场已经从“输出过滤”前移到了“数据获取”。作为开发者，我们需要从架构层面重构 Agent 的数据访问权限，而不是仅仅指望模型学会“守口如瓶”。
