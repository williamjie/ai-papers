# 网站生成新基准测试：智能体能逃脱盲目执行吗？

**日期**: 2026-05-01

---

论文 : InteractWeb-Bench: Can Multimodal Agent Escape Blind Execution in Interactive Website Generation?
链接 : https://arxiv.org/abs/2604.27419简单说，这篇论文戳中了AI编程领域一个挺痛的现实问题： 当用户自己都说不清要什么时，智能体能怎么办？
现有的网站生成工作——从 Design2Code 到 WebGen-Bench——测试条件都很理想：指令清晰、结构完整、细节充分。但真实世界呢？一个非技术用户提起笔，可能只有”我想做个电商网站”、“要酷炫点”、“背景颜色好看就行”。
这种语义鸿沟，就是论文所指出的 盲执行（Blind Execution） 陷阱：智能体不主动澄清，直接拿模糊需求开干，结果就是生成一堆看似能跑、实则跑偏的废代码。
## 问题与动机论文归因很明确： 非专业用户的 query 存在三类缺陷缺陷类型 Grice 会话准则违背 典型表现 信息不完整 数量准则 只提功能不提细节（P-MIN） 低信噪比 关联准则 废话连篇重点埋没（P-RAM） 语义模糊 方式准则 用主观感受代替技术术语（P-INT） 需求矛盾 质量准则 自相矛盾的技术约束（P-CON）
现有基准都默认用户是”完美提问者”，而作者基于需求工程缺陷分类（Requirement Engineering Defect Taxonomies）搭建了四个人格化用户代理， 系统性注入这些现实噪音 。
值得关注的是： 这是首个多模态交互式网站生成基准 。之前 work 要么纯文本对话（ClarifyCoder），要么被动推理（Persona2Web），没人把 自然语言澄清 + 代码生成 + 可视化反馈 三者闭环做成统一评测环境。
## 方法拆解：为什么是这四个动作？
核心 insight 很朴素： 一个真正能帮用户的智能体，得会”停下来问” 。
论文设计的动作空间 A = {Clarify, Implement, Verify, Submit} 看起来简单，但设计哲学很清晰：
### 1. 统一动作空间 vs 固定流水线传统代码 agent（如 SWE-agent）是”think-act”循环，但动作单一。而这里把 需求澄清 提升为一等公民——不是让模型”顺便问一句”，而是作为可执行动作，与写代码平级。这意味着智能体必须学会 在何时、以何种策略切换到澄清模式 。
### 2. GUI-based 验证的闭环设计a_verify 动作不只是”截图看效果”，而是带记忆的：
“Upon invoking action 𝑎verify, the environment dynamically synthesizes a holistic memory, which fuses the complete user-agent interaction history, the structural context of the latest code artifacts, and prior visual audit trajectory.”
三层记忆融合 避免了重复调试。更妙的是，验证失败时返回的不是简单的”报错信息”，而是：
- 失败点的终端截图- 纯净的浏览器控制台错误- 智能体自己解释的”为什么没通过”
这个反馈结构逼着模型从”我代码有bug”升级到”我是不是理解错了需求”的层面思考 ，而不是无脑打补丁。
### 3. 人格化用户的防作弊设计如果让智能体直接问”完整需求是什么”，用户代理直接背出 golden instruction，就没意义了。论文用了两阶段防泄漏：
- 检索与隔离：根据问题只抽取相关事实片段，不暴露未问部分- 人格过滤：把事实片段塞进对应人格的语言风格里（比如 P-RAM 会把正确答案裹在大量废话中）
这相当于给智能体上了难度： 你得从噪音里挖信息，还得判断信息是否可信 。
## 关键结果：一堆模型，集体陷入盲执行### 整体表现：最高 TCR 不到 39%模型 总体 TCR (%) hallucination 率 (%) Qwen3.6-Plus 38.78 62.4 Kimi-K2.5 38.69 64.1 Qwen3.5-397B-A17B 37.15 56.4 GPT-4.1 35.61 31.7 Gemma-4-31B-it 32.50 61.7即便最强模型也只能完成四成任务 ，而且 hallucination 率普遍超过 60%——说明模型倾向于”先射箭再画靶”，猛加功能来弥补理解不足，结果加的全是多余的。
### 人格化场景对比：怕”没信息”更甚于”有噪音”
四个场景表现排序很一致：P-RAM（啰嗦）> P-INT（模糊）> P-CON（矛盾）> P-MIN（缺信息）
例如 Qwen3.6-Plus：
- P-RAM: 48.86% TCR- P-MIN: 29.74% TCR（差距近 20 个百分点）
关键洞见 ：模型对”信息缺失”比”信息冗余”敏感得多。啰嗦虽然费劲，但总比不知道要干什么强。
### 澄清能力分析：知道要问，但不会问论文用两个指标衡量交互质量：
- 意图对齐分（IAS）：推理与真实需求的匹配度（1-5 分）
- 澄清命中率（CHR）：提出的问题是否切中缺失信息点结果见图 2：所有模型 IAS 都在 3.93-3.99， 几乎满分 ；但 CHR 最高仅 37.5%（Gemma-4-31B-it）， 普遍低于 40% 。
典型行为模式 ：模型能get到需求方向，但提的问题往往是泛泛的”颜色是什么""布局怎么排”，而非针对最小缺失信息集合的精准追问。这说明当前模型的 主动需求 elicitation 能力是弱项 。
### 代码规模 vs 任务完成的反比关系模型 平均代码行数 TCR (%) 每千行 TCR Qwen3.6-Plus 1415.7 38.78 27.4 Kimi-K2.5 1942.3 38.69 19.9 GPT-4.1 440.1 35.61 80.9 Gemma-4-26B-A4B-it 674.6 30.07 44.6代码行数与完成率负相关 。Qwen 系列产出的代码最多，但每千行带来的有效完成度反而最低。说明”靠堆代码弥补理解不足”的策略在此任务上 完全无效 。
### 验证强度与任务改进脱钩论文引入”视觉审慎指数（VCI）” = 验证动作数 / 实现动作数，发现：
- Qwen 系列 VCI 较高（更谨慎），但 TCR 提升有限- Gemini/Gemma VCI 低（更激进），但错误率更高- VCI 与 TCR 无显著正相关致命问题 ：模型看到 GUI 反馈后，只做了 表面修复 （按钮位置不对 -> 动一下 CSS），而没有回溯到” 我是不是误解了功能需求 ”这一层。验证动作被降级为”视觉调参”，而非 需求验证 。
### 视觉质量：结构完整，细节翻车- 视觉缺陷率（VBR）：大多低于 10%，但普遍存在，无模型清零- 美学评分：Kimi-K2.5 最佳，但跨模型差距微弱- 结论：模型能生成大体好看的布局，但卡在细节对齐（如元素错位、覆盖、边距失调）
人类与 GPT-5-mini 评判的 Kendall’s τ = 0.449 ，说明自动化美学评估尚有参考价值，但不可全信。
## 工程启示：怎么让智能体不盲执行？
### 1. 优先学”问问题”而不是”写代码”
如果真实场景中用户指令平均缺失 30% 关键信息（论文没明说，但从 P-MIN 效果反推），那么 澄清能力 ROI 远高于代码生成能力 。
在微调（SFT）或强化学习（RL）时，应该：
- 构造”信息缺失 -> 主动澄清 -> 获得补充 -> 正确实现”的完整轨迹- 奖励澄清的精准度（是否命中真缺失），而非单纯奖励”代码通过测试”
- 惩罚”未澄清直接实现”的高幻觉行为### 2. 验证环节要能”回溯需求”
当前的 Verify 设计是个好开始，但实验表明模型把它用歪了。 需要把视觉反馈与需求槽（Oracle Slots）显式关联 ：
- 当 UI 元素错位时，自动生成反查：“约束中是否有明确布局要求？”
- 当功能缺失时，触发：“哪些 Oracle Slot 尚未实现？”
- 把验证从”看 UI”升级为”查需求覆盖”
### 3. 指令工程：把人格化测试变成训练数据P-MIN/P-RAM/P-INT/P-CON 四个人格可以反向用作 数据增强 ：
- 从黄金指令 I* 出发，用四人格方法生成带噪音的变体- 训练模型在这些变体上识别缺陷类型并生成针对性澄清问题- 这相当于让模型提前”预演”真实用户的混乱表达### 4. 成本控制：探索-利用的权衡明显实验显示 GPT-4.1-mini 探索多（问得多、步数长）但提交率低；Qwen 系列探索少但提交率高。 实际部署时需根据场景选择策略 ：
- B2B 企业工具：允许长对话，高 CHR 优先- 在线网站生成器（用户耐心有限）：需平衡探索次数，设置最大澄清轮次## 局限与后续方向（论文没细说，但值得提）
- 用户人格有限：只覆盖四种经典缺陷。现实用户行为更复杂（比如情绪化、中途改主意、技术背景混合）。
- 任务范围窄：101 个种子网站（扩展至 404 个带人格变体），主要是静态/轻交互页面。复杂 SPA、状态管理等未覆盖。
- 评估依赖 GPT-5-mini：TCR 和 VBR 的最终打分由另一个 MLLM 完成，存在评估链传递误差。
- 未开放代码与环境：目前是论文 + 数据集描述，未有公开可运行的交互环境（论文说”Playwright-based”，但未放仓库）。
后续自然方向 ：
- 把 Clarify 动作细分为：Missing Info Query / Contradiction Resolution / Ambiguity Disambiguation- 加入多轮用户”改主意”场景，测试动态需求追踪- 把视觉验证与单元测试生成结合，实现可复现的验收标准## 总结这篇工作最大的价值不是提出了什么新模型，而是 定义了一个新问题 ：在非专业用户的模糊、矛盾、残缺指令下，智能体是盲目执行还是主动澄清？
实验数据很诚实： 当前所有前沿 MLLM 都卡在盲执行陷阱 。它们产出的代码不少，但 hallucination 高、澄清命中率低、验证流于表面。
工程启示很直接 ：想让 AI 编程 agent 真正可用，不能只训练”写代码”，必须训练” 问对问题 ”的能力。把 Clarify 动作真正纳入优化目标，可能是下一代 coding agent 的关键跃迁。
如果你在做 AI 编程产品，这份基准就是一块试金石——测测你的模型，在用户说”我觉得这个按钮应该大一点、颜色好看点”时，到底会默默改 CSS，还是会反问一句：“您希望按钮在哪个区域？大多少像素？您说的’好看’偏向哪种风格？”
这才是真实世界的工程挑战 。
