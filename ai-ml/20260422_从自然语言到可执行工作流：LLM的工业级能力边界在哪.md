# 从自然语言到可执行工作流：LLM 的工业级能力边界在哪

**日期**: 2026-04-22

---

论文 : Chat2Workflow: A Benchmark for Generating Executable Visual Workflows with Natural Language链接 : https://arxiv.org/abs/2604.19667现在做 Agent 系统，越来越多人放弃 ReAct 那一套自由发挥的链路，转投 Dify、Coze 这种基于可视化工作流（Workflow）的编排方案。原因很简单：ReAct 灵活但不可控，工作流虽然笨重，但可靠、可回溯、可审计。
问题来了——工作流现在全靠人肉设计。开发要把自然语言需求翻译成节点连接关系，写 prompt，反复调试。这玩意儿又贵又慢还容易出错。
浙江大学和腾讯的团队搞了个 Chat2Workflow 基准测试，直接问：LLM 能不能从自然语言自动生成 可执行 的可视化工作流？
答案可能让你失望。
## 问题与动机：为什么这个方向值得做？
先看个现实数据。据 Pan et al. 2025 的访谈调查，超过 70% 的生产环境 Agent 部署用的是现成语言模型，不做权重微调，全靠显式工作流做编排。
工作流本质是一个有向无环图（Directed Acyclic Graph, DAG）：节点是工具或处理单元，边是数据流向。Dify 这类平台把 DAG 在前端画成可视化界面，后端存成 YAML 格式，节点逐个执行，自动处理工具调用和数据流。
但工作流的创建几乎完全依赖手工工程。这就引出了一个核心问题：能不能让人说一段话，LLM 就给你吐出一个能直接在 Dify/Coze 上跑起来的工作流？
## 方法拆解：Benchmark 怎么建？
Chat2Workflow 的构建思路很实在：
数据来源 ：从 Dify 和 Coze 官方文档及 GitHub 收集生产级工作流配置，然后 逆向工程 出对应的创建指令集。
多轮对话设计 ：每个任务包含 2-4 轮指令，每轮基于上一轮的结果做增删改。模拟真实场景中需求不断演化的情况。
数据集规模 ：27 个任务，79 条多轮指令，共 237 个实例。覆盖 6 大领域：AIGC（22.2%）、Research（18.5%）、Document（18.5%）、Developer（14.8%）、Enterprise（14.8%）、Education（14.8%）。
节点简化 ：只选 20 个高频节点，简化输入输出接口——LLM 只需要提供关键变量的键值对，次要变量用默认值。还给每个节点类型做了知识库，塞进 system prompt 里。
输出格式 ：模型需要先输出 CoT（Chain-of-Thought）推理过程，包括节点选择 <node_selection> 、设计原则 <design_principle> ，最后才是 JSON 格式的工作流定义 <workflow> 。JSON 再转换成 YAML 导入平台执行。
## 评估体系：两层过滤这个 benchmark 的评估设计很有意思，分两阶段：
第一阶段：Pass Rate（通过率）
检查工作流表示层是否合法：
- 格式检查：JSON 是否可解析- 转换检查：JSON 能否转成合法 YAML- 变量一致性：输入输出变量是否与预期匹配- 逻辑有效性：CoT 推理与工作流是否一致第二阶段：Resolve Rate（解决率）
检查工作流在实际平台上能否正确执行并满足需求：
- 执行检查：上传到 Dify 后是否报错- 输出验证：执行结果是否符合指令要求简单说， Pass Rate 看”格式对不对”，Resolve Rate 看”能不能用” 。
## 关键结果：差距比你想的大测试了 15 个模型（4 个闭源 + 11 个开源），结果如下：
模型 平均 Pass Rate 平均 Resolve Rate 差距 Gemini-3-Pro-Preview 77.78% 71.59% 6.19% GPT-5.2 68.89% 60.74% 8.15% GPT-5.1 48.89% 45.19% 3.70% Claude-Sonnet-4.5 68.89% 62.97% 5.92% GLM-4.7 80.00% 55.98% 24.02% GLM-4.6 62.22% 60.00% 2.22% Qwen3-235B-A22B 35.55% 32.59% 2.96% Qwen3-Coder-480B 53.33% 39.26% 14.07%几个关键发现：
1. Pass Rate 和 Resolve Rate 之间存在显著鸿沟GLM-4.6 的 Pass Rate 是 62.22%，但 Resolve Rate 只有 60.00%。而 GLM-4.7 更夸张：Pass Rate 高达 80%，Resolve Rate 却只有 55.98%，差距达 24.02 个百分点。在 Education 场景下，GLM-4.6 的差距甚至达到 43.44%。
结论很直白： 格式合法 ≠ 能跑通 。很多模型能写出合法的 JSON，但导入平台后要么拓扑错误，要么节点连接不对，要么变量映射出错。
2. 模型越大越强，但开源模型仍远落后Qwen-3 系列从 8B 到 32B 到 235B，Resolve Rate 从 27.43% 稳步提升到 40.93%。但即便是最强的 Gemini-3-Pro-Preview（71.59%），距离真正可用的工作流规划师还差得远。
3. Thinking 模式 > Instruct 模式Kimi-K2-Thinking 在所有任务上均优于 Kimi-K2-Instruct。Qwen3-Coder-480B-Instruct（39.26%）反而不如参数量更小的 Qwen3-235B-A22B（32.59%），说明思考机制对结构化推理确实有帮助。
4. 多轮对话中性能持续衰减随着对话轮数增加，大多数模型的 Pass Rate 和 Resolve Rate 都呈稳定下降趋势。有意思的是，衰减速率在第二轮后变缓——“边际递减效应”：能撑到第二轮的工作流已经经过了一轮筛选，对需求变化的理解能力有一定基础。
5. 微调只解决格式，不解决逻辑GLM-4.6 在 Enterprise 场景的 Pass Rate（45.83%）高于 GLM-4.7（41.67%），但 Resolve Rate 却远低于后者（6.94% vs 29.17%）。说明仅靠格式合规的微调无法提升实际解决问题能力。
## 工程启示别迷信 Pass Rate。 如果你的评估只看 JSON 能不能解析，你会得到一个严重高估的模型能力画像。Resolve Rate 才是硬指标。
Thinking 模式值得优先尝试。 对于需要结构化推理的任务，带思考过程的模型明显优于纯指令微调模型。
多轮场景要格外小心。 需求变更时，模型保持工作流正确性的能力会快速衰减。如果你的业务场景需要频繁迭代工作流，现在这个水平还不够看。
Agentic 框架能救一点。 论文提出的 error-driven agentic baseline（带 5 次重试 + 自动修复），把 GPT-5.1 的 Resolve Rate 从 39.38% 提升到 44.31%（+4.93%），GPT-5.2 从 54.71% 提升到 60.05%（+5.34%）。有提升，但不多——说明问题本质上是模型能力不足，不是框架不够好。
## 局限与展望论文自己也承认了几个局限：
- 只有 27 个任务、20 个节点类型，远不够覆盖工业级复杂流程- 节点接口做了简化，真实部署需要更精细的参数配置- 数据集虽然经过人工验证，但规模有限总的来说，Chat2Workflow 揭示了一个残酷事实：LLM 能理解你的意图，但离自动生成 可执行、可部署 的工作流还差很远。格式生成是”必要条件”，不是”充分条件”。
这个 benchmark 的价值在于提供了一个真实的测试床——不再是用模糊的自然语言评分，而是让工作流真正跑起来，用执行结果说话。这对推动结构化推理和自适应工作流合成研究，是个实实在在的推进。
