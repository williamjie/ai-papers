# 用对比归因拆解 LLM 为什么犯错

**日期**: 2026-04-22

---

论文 : Contrastive Attribution in the Wild: An Interpretability Analysis of LLM Failures on Realistic Benchmarks链接 : https://arxiv.org/abs/2604.17761我们调试 LLM 出错的例子时，最常干的事就是改 prompt、换模型、看输出。这属于行为层面的分析——知道它哪里错了，但不知道 为什么错了 。行为分析最大的问题是模糊：两个模型表现相似，可能是原因 A（忽略了关键上下文），也可能是原因 B（过度关注无关 token），光看输入输出根本分不出来。
微软和南方科技大学的这篇论文做了件很务实的事：用可解释性工具直接看 LLM 内部的决策过程，而且是在真实 benchmark 上，不是 toy setting。
## 行为分析不够，归因分析来凑现有 LLM 失败分析基本停留在行为层面——测 benchmark、分类错误类型、看扰动敏感度。能告诉你”模型在长上下文任务中容易丢信息”，但说不清是”没关注到关键 token”还是”被无关 token 带偏”。
可解释性领域倒是有不少方法，但大多局限在短 prompt 和结构化模板上。一个 subject-relation-object 三词模板，归因出来当然干净漂亮。但真实场景的 prompt 动辄几千 token，GAIA2 这种 agent benchmark 的平均输入长度是 12374 token，现有的归因工具根本扛不住。
这篇论文的核心思路很简单但有效： 把失败分析建模为对比归因（Contrastive Attribution） 。
## 核心方法：对比归因 + 高效图构建对比归因 的关键在于，不直接问”模型为什么选了这个 token”，而是问”模型为什么选了这个 错误 token 而不是一个 正确 的替代 token”。
具体做法是计算错误 token 和正确候选 token 之间的 logit 差值，然后用 LRP（Layer-wise Relevance Propagation）把这个差值反向传播到输入 token 和内部隐藏状态上。用论文的话说：
“This contrastive formulation closely reflects practical debugging scenarios (asking why the model prefers a specific incorrect token over a plausible alternative) and removes shared, failure-irrelevant computation.”
翻译成人话：对比排除了两者共用的计算部分，留下的就是真正导致模型做出错误选择的信号。
他们用的是 AttnLRP——LRP 的一个变体。为什么不选其他归因方法？论文引用了之前的对比研究，AttnLRP 在 transformer 的输入 token 归因忠实度（faithfulness）上是最高的。
但真正的工程亮点在第二部分：高效 attribution graph 构建。
LRP 本身可以通过一次反向传播算出各层的 relevance 分数，但要构建跨层的归因图——看清楚 relevance 是怎么从一层传到下一层的——就得对每个 hidden state 的 relevance 分别做反向传播。hidden state 维度大得吓人，这计算量直接爆炸。
他们的解决方案是一个 batching trick：把多个归因目标打包到一个 batch 里，用 GPU 向量化的方式一次算完。配合阈值裁剪（丢弃绝对 relevance < 0.01 的节点）和逐层累积质量裁剪（阈值 0.85），最终能在可接受的时间内跑出长上下文输入的归因图。
他们还用了粗到细（coarse-to-fine）的策略：先聚合 hidden state 维度做粗粒度分析，找到重要子图后再细化到 neuron 级别。这对长上下文场景很关键——一次性做 neuron 级别根本不现实。
## 实验结果：归因到底有没有用？
论文在 4 个 benchmark 上收集了数百个失败案例，用 Qwen3 系列（0.6B/1.7B/4B）做了系统分析。
先说一个关键数字：不是所有失败都能归因。四个 benchmark 中能成功找到对比 token pair 的比例分别是：
Benchmark 失败案例数 找到对比 pair 的比例 平均 token 数 IFEval 265 20.8% 54 GAIA2 300 17.0% 12374 MATH 91 40.7% 116 EvalPlus 270 19.6% 169能找到对比 pair 的比例不高，主要是因为有些错误没有明显可替代的正确答案，或者 logit 差值不够大。论文设了 Δℓ > 1 的阈值，确保对比信号足够强（e¹ ≈ 2.7 的 odds ratio）。
对于能归因的案例，论文把结果分了三个等级：
类别 含义 表现 M-IA 输入归因热力图就能看出问题 IFEval、GAIA2、EvalPlus 中占多数 NC-IA + M-AG 热力图看不出来，归因图能揭示 部分案例需要跨层分析 NC-IA+AG 两种方法都看不出来 MATH 中比例显著偏高MATH 的数值推理错误为什么最难归因？因为这类错误往往需要 neuron 级别的精细追踪。论文举了个例子：模型在 “(1.0175)²⁰ ≈ 1.4” 之后错误地倾向输出 “0” 而不是 “1”。要解释这个，得追踪幂运算的 neuron 级细节，粗粒度的 hidden state 归因不够。
发现的两种主要失败模式：
-URT（Underweight Relevant Tokens）：模型低估了关键 token 的重要性。比如 IFEval 中要求输出用逗号分隔，0.6B 模型没有给 “comma” 这个关键词足够的负 relevance，而 4B 模型做到了。
-OIT（Overweight Irrelevant Tokens）：模型过度关注无关 token。EvalPlus 中 0.6B 给 “(a” 分配了高 relevance，而 8B 模型没有。
跨所有 benchmark， URT 是最主要的失败模式 。OIT 也贡献了不少，尤其在 EvalPlus 和 GAIA2 中，而且经常和 URT 同时出现（MATH 除外）。
## 模型缩放真的修好了失败吗？
论文比较了 Qwen3-0.6B、1.7B 和 4B 在 IFEval 失败案例上的表现。大部分数据点落在 y=x 线下方——大模型确实修正了小模型的错误偏好。
但更有趣的是归因层面的证据。看 prompt 三个片段的 normalized relevance 分布：
- 0.6B 的 Instruction 片段 relevance 是非负的（说明指令没有正确抑制错误 token）
- 1.7B 和 4B 的 Instruction 片段变成了明显的负值- 被修正的案例中，三个片段全部呈现负 relevance；没被修正的案例，各模型尺寸的分布几乎一样这说明大模型的改进不是”碰巧蒙对了”，而是 确实改变了内部的 token 权重分配方式 。
## 训练过程中失败模式怎么演变？
用 Olmo-3-7B-Think 系列在不同 SFT checkpoint 上的归因分析，论文发现：
- 最大的相关性变化发生在早期 SFT 阶段（SFT_1000 到 SFT_2000），主要来自 Query 和 Answer 片段的 relevance 下降——模型开始关注任务语义，而不是简单地延续前文 token- 中期 SFT（SFT_8000 到 SFT_10000）有第二个变化拐点- DPO 进一步把所有片段的 relevance 推向更负的方向- RLVR 的贡献相对较小——因为 IFEval 测的是指令遵循能力，SFT 已经修了大部分，RLVR 主要面向多步推理这些归因信号的变化和 logit 差值的下降趋势高度对齐，说明归因分析可以作为训练过程中的监控工具。
## 工程启示1. 针对性 prompt 调优。 论文做了扰动实验：只 mask 掉平均约 2 个 top-attributed 输入 token，就足以让模型从错误 token 切换回来。这意味着用归因热力图定位关键驱动 token，然后针对性修改 prompt，比盲调效率高得多。
2. 训练过程的可解释性监控。 归因模式的变化能追踪失败如何随训练演进，判断改进是”真正学到了正确推理”还是”只是记住了 token 模式”。
3. 对齐训练的 token 级信号。 归因分数可以作为 token 重要性信号，用于 DPO 等对齐训练中的偏好优化——不是平等对待所有 token，而是重点优化驱动失败或偏好差距的关键 token。
## 局限这篇论文最诚实的地方是明确说了归因分析 不是万能的 。三个维度都有天花板：
- 能找到对比 pair 的案例只占 17%-41%，很多失败无法构建有意义的对比- MATH 等数值推理错误需要 neuron 级别的归因，粗粒度方法不够- 归因图构建虽然优化了，但对长上下文仍然计算昂贵归因分析不是替代行为分析，而是 在行为分析够用的时候锦上添花，在行为分析模糊的时候提供额外维度 。它不是 silver bullet，但确实让”模型为什么错了”这个问题有了可测量的答案。
