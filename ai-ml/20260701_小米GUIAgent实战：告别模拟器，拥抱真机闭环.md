论文 : Xiaomi-GUI-0 Technical Report链接 : https://arxiv.org/abs/2606.31410大多数 GUI Agent 在 benchmark 上分数漂亮，一上真机就崩。小米这篇报告直接摊牌：模拟器是骗人的，真机闭环才是正道。
痛点在哪？
现有方案严重依赖离线成功轨迹和模拟环境。但在真实手机里，账号状态、权限弹窗、风控拦截、甚至网络抖动，都在不断重塑交互分布。
⚠️ 核心洞察 ：Benchmark 高分 ≠\neq = 真实可用。模拟器无法复现主流商业 App 的反检测机制（如验证码、支付鉴权），导致模型在“异常态”下的鲁棒性几乎为零。
方法拆解：真机主导的混合基础设施小米没有完全抛弃沙箱，而是搞了一套“真机为主，沙箱为辅”的混合架构。
- 资源层：数百台物理手机和平板作为核心执行环境，覆盖主流品牌和真实账号状态；沙箱仅用于低风险、高并发的标准化测试。
- 调度层：采用 Device-Pull 机制。设备根据自身就绪状态（如登录是否过期、风控等级）主动拉取任务，避免向不可用设备下发指令。
- 执行层：统一动作空间，支持低延迟浏览器控制通道，让维护人员能直接介入恢复异常状态（如手动过验证码）。
数据飞轮：从“错误”中挖掘黄金信号这是本文最工程化的部分。传统飞轮只关注数据量，小米的飞轮关注 错误分布 。
- 高频任务数据：覆盖登录、支付等头部场景，特别标注了约 5,000 个样本的 14 类异常状态（如会话过期、网络错误）。
- 高泛化数据：通过五层功能树和行为桶（Behavior Buckets）合成查询。不仅模拟单 App 操作，还覆盖跨 App 任务（如在微博找视频去 B 站搜索）。
- 错误驱动修复：当模型在真机 rollout 中失败，标注员回放轨迹定位关键错误步，提供修正动作和反思理由。教师模型接管后生成恢复轨迹，形成“错误-反思-恢复”的监督信号。
训练策略：三步走渐进式强化学习- SFT：建立基础操作能力，学习常见 UI 操作和标准路径。
- Step RL：在单步层面应用组相对强化学习，优化动作选择和局部纠错。
- Agentic RL：在真实环境中进行长程规划训练，重点提升状态记忆和异常恢复能力。
关键结果小米自建的 RealMobile 基准测试更贴近实战，涵盖真实设备和异常页面。
基准测试 任务类型 Xiaomi-GUI-0 成功率 备注 RealMobile 真机端到端任务 72.0% 覆盖真实账号、异常页、跨应用场景 AndroidWorld 模拟环境任务 78.9% 传统静态基准，侧重基础感知与执行💡 解读 ：在更严苛的 RealMobile 上达到 72% 的成功率，说明模型不仅学会了“点哪里”，还学会了“遇到弹窗怎么办”、“账号过期怎么切”。
工程启示- 真机数据是护城河：模拟器的数据分布与真实世界存在巨大偏差。构建包含异常态（Exception Handling）的真实轨迹数据，比单纯增加 SFT 数据量更有效。
- 错误即资源：不要丢弃失败轨迹。通过教师模型接管和人工标注，将失败转化为“反思”和“恢复”的监督信号，能显著提升 Agent 的鲁棒性。
- 基础设施决定上限：Device-Pull 调度机制和混合执行环境，解决了真机规模化和状态一致性的工程难题。
局限与展望报告未详细披露模型参数量及推理延迟的具体数值。此外，RealMobile 基准目前主要覆盖小米生态及主流商业 App，跨品牌、跨操作系统的泛化能力仍需更多公开基准验证。但无论如何，这篇报告为 GUI Agent 从“实验室玩具”走向“生产级工具”提供了一条可落地的技术路径。
