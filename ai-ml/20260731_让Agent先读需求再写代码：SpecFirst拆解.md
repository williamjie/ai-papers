# ⭐⭐⭐⭐ 让 Agent 先读需求再写代码：SpecFirst 拆解

**日期**: 2026-07-31

---

论文 : SpecFirst: Behavioral Specification Elicitation as a First-Class Step in Agent-Based Program Synthesis from Scratch链接 : https://arxiv.org/abs/2607.27167现在的 LLM Agent 在修 Bug 或补全代码时表现不错，因为总有现成的代码库作为“锚点”。但如果是从零开始重构一个程序（From-Scratch），现有框架几乎全军覆没。
这篇来自华为加拿大研究院等机构的论文 SpecFirst 指出了一个被忽视的工程常识： 在写代码前，必须先把需求搞清楚。 它通过引入一个专门的“规格说明 Agent”，将行为探索与代码生成解耦，显著提升了从零构建程序的准确率。
### 为什么现有方案会失败？
现有的 Agent 框架（如 SWE-agent、OpenHands）通常采用“单循环”模式：Agent 在同一轮对话中混合进行文档阅读、二进制探针探测和代码编写。
这种混合模式导致三个致命问题：
- 探索不充分：Agent 往往还没完全搞懂目标程序的行为，就急着开始写代码。边缘情况（Edge Cases）和错误路径经常被忽略。
- 上下文漂移：随着对话轮数增加，早期的行为观察会被压缩或遗忘。论文指出，即使 Agent 在第 4 轮发现了所有命名空间，在后续 25 轮的编码中也可能完全忘记这些细节。
- 错误传播：一旦早期对文档的解读出现偏差，后续所有代码都会基于这个错误假设构建，且没有稳定的参考标准来纠正。
### 核心 Insight：把“需求工程”变成一等公民SpecFirst 的核心设计直觉非常简单： 模仿传统软件工程中的需求工程阶段。
它引入了一个两阶段流水线：
-规格说明阶段（Spec Agent）：
这是一个专门的 Agent，唯一任务是通过黑盒探测（Black-box Probing）来理解目标二进制文件的行为。
- 它不写代码，只通过命令行交互、边界测试、错误路径触发等手段，生成一份结构化的 SPEC.md。
- 关键设计：禁止 Agent 使用反编译器或搜索源码，强制其通过用户界面交互来获取知识，确保提取的是“行为规格”而非“源码复刻”。
-代码合成阶段（Code Synthesis Agent）：
接收原始文档、二进制文件以及生成的 SPEC.md。
- 基于这份稳定的行为契约进行实现。如果仍有歧义，可以再次探测二进制文件，但主要依据是 SPEC.md。
这种解耦解决了“注意力分散”问题。Spec Agent 可以自由探索而不必担心编码预算；Code Agent 则拥有一个持久化的、结构化的行为参考，避免了上下文漂移。
### 实验结果：提升显著且稳定论文在 ProgramBench （200 个从零构建实例）上进行了评估，对比了基线方法（Direct-Synthesis）。
模型 Direct-Synthesis (基线) SpecFirst 相对提升 Qwen3.5-397B 33.66% 40.84% +21.3% Qwen3.6-35B 27.51% 31.40% +14.1% GPT-5.5-high 59.02% 65.14% +10.4% GPT-5.4-mini 39.09% 41.78% +6.9%反直觉发现 ：在 hardest 的实例中，GPT-5.5-high 的提升幅度最大，达到 +29.9% 。这说明对于复杂逻辑，明确的规格说明比单纯增加模型算力更有效。
此外，SpecFirst 还将二进制探测覆盖率提升了 9.4%–18.5% 。更重要的是，它改变了 Code Agent 的行为模式：有了 SPEC.md ，Agent 会更早地开始写代码，并持续构建更完整的实现，而不是在“探测”和“编码”之间反复横跳。
### 工程启示- 分而治之是王道：不要指望一个通用的 ReAct Agent 能同时完美处理探索、规划和执行。对于复杂任务，显式的阶段划分（Phase Separation）能显著降低认知负荷。
- 中间产物要有结构：SpecFirst 生成的 SPEC.md 采用了轻量级模板（Overview, Flags, Edge Cases 等）。这比自由格式的对话记录更易于下游 Agent 解析和利用。
- 防止“捷径”：在评估 Agent 能力时，必须严格限制其使用外部工具（如搜索源码、反编译），否则测出的只是“检索能力”而非“推理与重构能力”。
### 局限与展望SpecFirst 目前主要适用于命令行程序（CLI）。对于图形界面或网络服务，如何定义和探测“行为规格”仍是一个挑战。此外，Spec Agent 的终止条件依赖于自我判断，可能导致过度探索或探索不足。
尽管如此，这篇论文提供了一个清晰的范式： 在让 LLM 动手之前，先让它动笔写出需求文档。 这不仅是学术上的创新，更是工程实践中的最佳回归。
