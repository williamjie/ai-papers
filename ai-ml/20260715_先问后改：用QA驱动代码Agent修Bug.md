**日期**: 2026-07-15

---

论文 : Know Before Fix: QA-Driven Repository Knowledge Acquisition for Software Issue Resolution链接 : https://arxiv.org/abs/2607.11111现在的 Coding Agent 修 Bug，最大的痛点不是“写不出代码”，而是“瞎改”。
它们往往缺乏对仓库内部逻辑的深度理解，导致定位错误、违反 API 契约，甚至产生幻觉。这篇来自上海交大的论文提出了 ACQUIRE 框架，核心思路很朴素：像资深开发者一样，在动手修之前，先通过问答搞清楚代码到底是怎么跑的。
### 为什么现有的“预探索”方案不够好？
目前的 Agent（如 Mini-SWE-Agent）通常直接开始搜索或尝试修复。
一些改进方案（如 LingmaAgent）试图预先构建代码库摘要或调用图，但这本质上是 基于关键词的浅层定位 。
核心洞察 ：这些方法没有识别出 Agent 到底“缺什么知识”。它们扔给 Agent 一堆上下文，却指望 Agent 自己从中提炼出修复逻辑。这就像给新手程序员一本字典，却不告诉他查哪个词。
### ACQUIRE 的设计直觉：把“隐性无知”变成“显性知识”
ACQUIRE 将流程拆解为两个完全解耦的阶段： 知识获取 与 知识引导修复 。
第一阶段：问答驱动的知识获取（QA-Driven Acquisition）
这一步引入了两个角色： 提问者（Questioner） 和 回答者（Answerer） 。
- 结构化提问：提问者不再随机搜索，而是基于四类维度生成问题：
机制与行为：逻辑流、状态管理怎么工作？
- 设计与用法：API 契约、设计模式是什么？
- 定位与结构：相关代码在哪？模块关系如何？
- 生态与标准：外部库或协议约束是什么？
- 证据驱动的回答：回答者在只读模式下自主探索仓库，必须引用具体的文件路径和函数名作为证据。
这种设计的妙处在于： 分解复杂度 。让 Agent 去回答“这个系统怎么认证用户”比直接让它“修复认证Bug”要容易得多，且更容易基于代码事实进行 grounding，减少幻觉。
第二阶段：知识引导的修复（Knowledge-Informed Repair）
修复者（Resolver）拿到这些 QA 对后，才开始写 Patch。
关键细节 ：QA 知识是静态预注入的，而不是动态流式插入。这确保了修复从一开始就建立在完整的上下文之上，避免了早期决策因信息不全而跑偏。
### 实验结果：效率与准确率的双赢在 SWE-bench Verified（500 个真实 GitHub Issue）上，ACQUIRE 的表现令人印象深刻。

### 工程启示：别急着写代码，先搞懂上下文这篇论文对构建生产级 Coding Agent 有几个重要指导意义：
- 解耦认知与执行：不要指望一个 Prompt 既负责理解复杂系统又负责生成补丁。显式的“理解阶段”能显著降低后续“执行阶段”的认知负荷。
- 结构化知识优于原始代码：直接喂给 Agent 几百行代码不如喂给它一段经过验证的“机制解释”。QA 对起到了类似“中间表示（IR）”的作用，过滤了噪音。
- 并行化探索：ACQUIRE 中的多个 Answerer 是并行运行的，这意味着知识获取阶段的延迟取决于最慢的那个问题，而不是所有问题的总和。这在工程上非常高效。
### 局限与反思尽管效果显著，ACQUIRE 仍有边界：
- 误导性回归：有 5% 的原本能修的案例因为 QA 提供了“看似合理但错误”的框架而修失败。这说明 Resolver 对注入知识的批判性评估能力仍需提升。
- 依赖基线 Agent：ACQUIRE 本身不生成代码，它依赖于下游 Resolver（如 Mini-SWE-Agent）的执行能力。如果基线 Agent 本身代码生成能力弱，QA 的帮助也会受限。
总的来说，ACQUIRE 验证了一个直觉： 在软件工程领域，正确的提问比盲目的尝试更有价值。 对于正在优化内部 Code Assistant 的团队来说，引入一个“预诊断问答层”是一个低成本、高回报的改进方向。
