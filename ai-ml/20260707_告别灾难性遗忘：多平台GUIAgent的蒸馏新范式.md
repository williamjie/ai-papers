**日期**: 2026-07-07

论文 : UI-MOPD: Multi-Platform On-Policy Distillation for Continual GUI Agent Learning链接 : https://arxiv.org/abs/2607.04425让 AI 同时精通 Windows 桌面操作和 iOS/Android 移动端交互，听起来很美好，做起来却是个大坑。
直接混合数据训练？模型会精神分裂。合并参数？能力互相抵消。这篇来自清华、小米等机构合作的论文 UI-MOPD，给出了一个非常工程化的解法： 多平台在线策略蒸馏（Multi-Platform On-Policy Distillation） 。它不只是微调，而是通过“动态路由”让模型在强化学习过程中，分别向桌面专家和移动专家“请教”，从而在保持各自交互习惯的同时，实现跨平台能力的统一。
### 痛点：为什么简单的混合训练行不通？
GUI Agent 的核心难点在于 交互范式（Interaction Conventions）的差异 。
在电脑上，“返回”可能意味着关闭窗口或按 Alt+Tab；在手机上，则是点击左上角的 Back 按钮或手势滑动。如果直接把桌面和移动端的轨迹数据混在一起做监督微调（SFT），或者简单地将两个专家模型的权重相加（Model Merge），模型学到的往往是一个 被平均化的策略 。
这种“平均”是致命的。它会导致行为模式混淆，甚至引发灾难性遗忘——为了学新平台的操作，旧平台的技能彻底丢了。现有的开源数据集如 OpenCUA 和 OpenMobile 虽然提供了数据，但缺乏高质量、跨平台的统一交互轨迹，且现有方法难以解决这种异构信号冲突的问题。
### 核心 Insight：动态路由的在线蒸馏UI-MOPD 的核心直觉非常清晰： 不要试图用一个静态分布去拟合所有平台，而是在推理过程中，根据当前环境动态选择“老师”。
整个训练分为两阶段：
- 专家构建（Stage 1）：利用构建的高质量跨平台数据集 Uni-GUI（包含近 10K 条高质轨迹），分别对基础模型进行监督微调，得到两个独立的专家教师模型：桌面教师 πrefd\pi_{ref}^dd​ 和移动教师 πrefm\pi_{ref}^mm​。
- 在线蒸馏（Stage 2）：这是重头戏。学生模型 πθ\pi_\theta​ 在混合平台的环境中进行强化学习（RL）。关键在于平台条件路由（Platform-Conditioned Routing）：
当学生在桌面环境 rollout 时，KL 散度惩罚项指向桌面教师。
- 当学生在移动环境 rollout 时，KL 散度惩罚项指向移动教师。
关键设计细节 ：这里使用的是**在线策略（On-Policy）**蒸馏。这意味着教师只对学生当前实际访问的状态分布提供指导，而不是让学生去模仿教师所有的离线轨迹。这极大地提高了蒸馏信号的针对性，避免了“为了模仿而模仿”导致的探索受限。
此外，论文还引入了 自适应 KL 掩码（Adaptive KL Masking） 。如果某个 rollout 已经获得了足够的任务奖励，就减弱教师的约束，允许模型自由探索；只有在奖励不足时，才强力拉回教师的行为分布。这是一种非常聪明的平衡术：既保证了交互规范的正确性，又保留了优化空间。
### 实验结果：小模型打败大基线？
在 OSWorld（桌面）和 MobileWorld（移动）基准测试上，UI-MOPD 的表现令人印象深刻。
方法 OSWorld (桌面) MobileWorld (移动) Qwen3-VL-8B-Thinking (基线) 33.9% 7.7% Mixed-SFT (混合微调) 35.0% 6.4% Model Merge (权重平均) 36.5% 6.8% UI-MOPD (本文) 38.2% 12.0%几个值得注意的数据点：
- 显著的提升：相比基线，桌面成功率提升 +4.3%，移动端更是从 7.7% 飙升至 12.0%（相对提升约 55.8%）。
- 击败大模型：值得注意的是，UI-MOPD 使用的是 8B 参数的学生模型，而它在 MobileWorld 上的表现甚至超过了 32B 的基础模型 Qwen3-VL-32B-Instruct (9.0%)。这证明了方法的有效性不完全依赖模型规模。
- 通用能力保留：在静态 GUI 理解基准 ScreenSpot-Pro 上，UI-MOPD 保持了 43.14% 的准确率，接近基线的 43.71%，而 Model Merge 则暴跌至 37.13%。这说明蒸馏过程没有破坏模型的视觉 grounding 能力。
### 工程启示：如何落地多模态 Agent？
这篇论文对工程师有几个直接的指导意义：
- 拒绝粗暴混合：如果你的业务涉及多种异构环境（如 Web + App + Desktop），不要直接把数据扔进一个桶里训练。异构的交互逻辑会导致策略坍塌。
- 在线蒸馏优于离线模仿：在 RLHF 或 DPO 阶段，引入教师模型的 KL 约束时，考虑使用 On-Policy 的方式。只约束模型当前犯错的状态，比全局约束更高效，也更容易收敛。
- 动态路由的价值：即使最终部署的是一个统一模型，训练时的“多教师”架构也能提供稳定的行为锚点。这在持续学习（Continual Learning）场景中尤为重要，能有效缓解灾难性遗忘。
### 局限与展望尽管效果显著，UI-MOPD 目前主要聚焦于桌面和移动端两大平台。对于更细粒度的平台差异（如不同版本的 Android UI、Web 浏览器的差异），路由机制可能需要更精细的设计。此外，构建高质量的跨平台轨迹数据集 Uni-GUI 本身成本高昂，如何降低数据收集门槛，仍是行业共同面临的挑战。

亮点: 博文准确提炼了论文的两个关键工程价值点：一是“动态路由”（平台条件路由），根据当前环境选择对应教师，避免异构信号混合；二是“在线蒸馏优于离线模仿”，只约束学生当前访问的状态分布，提高信号针对性。博文还抓住了“自适应KL掩码”这一平衡探索与约束的设计细节，并用“小模型打败大基线”的对比直观展示了方法效果。
挑刺: 1. 博文称“在推理过程中，根据当前环境动态选择‘老师’”，而原文明确指出路由发生在训练阶段的rollout时（“UI-MOPD dynamically selects a platform-specific teacher for each rollout environment”），推理时学生是单一模型，不再需要教师。这一表述将训练行为误说成推理行为，可能误导读者。
2. 博文将“platform-conditioned routing”简化为“动态路由”，但原文的路由是根据数据源标签（desktop/mobile）静态划分，而非根据输入状态动态变化。“动态”一词夸大了路由的灵活性，原文并未实现状态层面的动态选择。
3. 博文在“工程启示”中建议“在RLHF或DPO阶段”引入on-policy KL约束，但原文使用的是GRPO-based DAPO强化学习目标（见Section 3.5），并非DPO，RLHF也仅作为类比。这种术语泛化可能让读者混淆具体算法。
总评: ⭐⭐⭐½ 博文整体准确地传达了论文的核心方法和关键结果，但在“训练/推理”术语和“动态路由”表述上存在不精确之处，瑕不掩瑜，属于合格的论文解读。
