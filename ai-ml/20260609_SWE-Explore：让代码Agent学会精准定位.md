**日期**: 2026-06-09

论文 : SWE-Explore: Benchmarking How Coding Agents Explore Repositories链接 : https://arxiv.org/abs/2606.07297现在的代码 Agent 越来越强，SWE-bench 的解决率也在不断攀升。但大多数评估只看最终补丁是否生效，这掩盖了一个致命问题：Agent 到底是怎么找到 Bug 的？如果它只是运气好猜对了文件，那在更复杂的仓库里大概率会翻车。
这篇论文提出了 SWE-Explore ，一个专门评估 Agent“代码库探索能力”的新基准。它不关心你最后修没修好，只关心你能不能在有限的行数预算内，精准定位到那些真正关键的代码片段。这对优化 Agent 的检索策略和上下文管理有极高的实战价值。
### 为什么现有的评估不够用？
目前的 SWE-bench 类基准把修复过程看作一个黑盒：输入 Issue 和仓库，输出 Patch，最后跑测试用例看 Pass/Fail。这种二元指标存在严重偏差：
- 混淆了能力维度：Agent 可能找到了正确的文件（探索能力强），但写不出补丁（生成能力弱）；或者根本没找到代码，靠记忆瞎编却蒙对了。
- 缺乏细粒度反馈：我们不知道 Agent 是读到了关键行，还是仅仅打开了相关文件。对于包含数千个文件的真实仓库，定位到具体行数才是核心难点。
SWE-Explore 的核心洞察是： 探索（Exploration）和修复（Repair）应该解耦 。通过隔离评估“找代码”的能力，我们可以更清晰地诊断 Agent 的短板。
### 方法拆解：从轨迹中提炼 Ground TruthSWE-Explore 最巧妙的设计在于其标签构建方式。人工标注哪些代码行是“必要上下文”成本极高且主观性强。作者采用了一种**基于轨迹的监督（Trajectory-Grounded Supervision）**策略：
- 收集成功轨迹：筛选出至少有两个不同强模型（如 GPT-5.4, Gemini-3-Pro 等）独立成功解决同一 Issue 的案例。
- 提取读取动作：从这些成功轨迹中提取所有明确的文件读取操作（如 cat, grep, 编辑器视图），映射为具体的 (文件路径, 起始行, 结束行)。
- 共识聚合：计算不同轨迹读取区域的交集，得到保守的核心上下文（Core Context）。再结合 LLM 辅助筛选必要的可选上下文，最后由人工审计。
最终，SWE-Explore 包含 848 个实例 ，覆盖 10 种编程语言和 203 个开源仓库。每个实例平均需要定位到 4.3 个文件、4.7 个代码区域和约 1578 行代码。
### 关键结果：Agent 找到了文件，但错过了细节论文对比了传统检索器（BM25, TF-IDF）、轻量级 RAG 以及多种主流 Agent（Claude Code, OpenHands, Mini-SWE-Agent 等）。结果揭示了一些反直觉的现象：

- Agent 远优于传统检索：BM25 和 TF-IDF 的表现接近随机猜测，而所有 Agent 探索器都形成了明显更高的能力层级。这证明多步交互对于代码库理解是必须的。
- 行级召回率是瓶颈：尽管 OpenHands 等通用 Agent 的文件命中率高达 64%+，且排名指标（nDCG）很高，但它们的行级召回率（Recℓ）仅约为 0.15-0.18。这意味着它们经常找到了正确的文件，却漏掉了真正包含 Bug 证据的具体代码行。
- 专用局部化器表现分化：CoSIL 凭借迭代式代码图搜索，实现了高达 0.788 的行级召回率，远超通用 Agent。而其他如 AutoCodeRover 虽然精确度高，但过于保守，导致覆盖率不足。
⚠️ 关键发现 ：下游修复成功率与“上下文效率（Context Efficiency）”的皮尔逊相关系数高达 0.950 。这表明，提供少量高信噪比的代码片段，远比提供大量冗余上下文更有效。
### 工程启示对于正在构建或优化代码 Agent 的工程师，这篇论文提供了明确的改进方向：
- 不要只关注文件定位：如果你的 Agent 能打开正确的文件，但修复率依然低，问题很可能出在行级上下文的提取上。需要增强 Agent 对代码内部结构的细粒度理解能力。
- 重视上下文压缩与筛选：实验显示，缺失核心证据比存在冗余噪音更致命。但在核心证据充足的前提下，现代 Patch 生成模型对冗余代码有一定的容忍度。因此，优化检索器的“信噪比”比单纯增加上下文长度更重要。
- 采用混合评估指标：单一的解决率无法反映探索质量。建议在内部评估中引入类似 SWE-Explore 的指标，如 HitFile、Recℓ 和 CtxEff，以诊断 Agent 是“找不到”还是“写不好”。
### 局限与展望SWE-Explore 目前依赖于强模型的成功轨迹来构建 Ground Truth，这可能引入一定偏差。此外，它主要评估静态探索能力，未涵盖动态调试过程中的交互式探索。未来，随着多模态和长上下文模型的发展，如何评估跨文件、跨语言的复杂依赖关系探索，将是下一个挑战。
