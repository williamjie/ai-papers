# 告别爬虫：用合成数据训练终端Agent

**日期**: 2026-05-29

---

论文 : LiteCoder-Terminal: Scaling Long-Horizon Terminal Environments for Learning Language Agents链接 : https://arxiv.org/abs/2605.29559想让大模型成为真正的“命令行专家”，最大的瓶颈往往不是模型本身，而是缺乏高质量、可执行的训练环境。
这篇来自中科院软件所的论文提供了一个极具工程价值的思路： 完全摒弃对 GitHub 或 Stack Overflow 等外部仓库的依赖，通过零依赖的合成流水线，从零构建可验证的终端训练环境。
## 痛点：为什么我们需要合成数据？
现有的终端 Agent 训练主要依赖从开源社区抓取 Issue 和 PR。这种方式有两个致命缺陷：
- 领域多样性受限：你只能拿到有人提交过的任务，无法覆盖长尾或特定技能短板。
- 环境不可控：抓取的代码往往缺乏统一的执行标准和验证脚本，难以用于自动化评估和强化学习。
LiteCoder-Terminal-Gen 的核心 Insight 在于： 与其费力清洗人类产生的“脏数据”，不如让强大的 Teacher Model 直接生成“干净且可执行”的任务、环境和验证器。
## 方法拆解：五步构建可执行环境这套合成流水线（Pipeline）的设计非常严谨，它不只是生成文本，而是生成一个完整的 Docker 容器化任务。核心流程分为五个阶段：
- 指令精炼 (Instruction Refinement)：将模糊的任务描述转化为具体的文件路径和操作规范。例如，强制要求输入输出绑定到 /app 下的绝对路径，消除歧义。
- 环境初始化 (Environment Initialization)：生成 Dockerfile 和必要的依赖包。关键在于它基于模板扩展，确保环境一致且不会过度简化任务。
- 解决方案合成 (Solution Synthesis)：生成一个参考脚本 solve.sh。这不仅是为了提供答案，更是为了验证任务本身是可解的。如果连 Teacher Model 都写不出正确脚本，说明任务设计有问题。
- 验证器构建 (Verifier Construction)：这是最精妙的部分。为了防止验证器过拟合参考解，作者引入了对抗性迭代：
攻击阶段：模拟“偷懒学生”提交空文件或硬编码假数据，如果验证器通过，说明测试太弱。
- 精炼阶段：模拟“专家 Agent”使用不同策略解题，如果验证器拒绝，说明测试过于僵化。
- 只有经过这两轮攻防的验证器才会被保留。
- 资源配置 (Resource Configuration)：自动估算并生成 CPU、内存和时间限制配置。
这种“因果一致性”设计确保了生成的每个任务都是自洽且可执行的，直接解决了合成数据中常见的“幻觉环境”问题。
## 关键结果：少样本也能打作者在 Qwen 系列模型上进行了监督微调（SFT）和直接多轮偏好优化（DMPO）。结果令人印象深刻：
- 数据效率极高：仅使用 11,255 条合成轨迹，就超越了依赖数十万条抓取数据的基线模型。
- 性能提升显著：
在 Terminal Bench 1.0 上，32B 模型 pass@1 达到 29.06%。
- 在更难的 Terminal Bench Pro 上，32B 模型达到 34.00%。
- 相比之下，仅使用 4B 模型的 SFT 版本，在 TB-2.0 上的表现提升了超过四倍（从 1.12% 到 4.78%）。

## 工程启示- 验证器即资产：在构建 Agent 训练数据时，验证脚本的质量比任务描述更重要。引入“对抗性测试”来加固验证器，是提升合成数据质量的关键手段。
- 垂直领域可定制：由于不依赖外部爬虫，你可以针对特定业务场景（如内部运维、特定数据库操作）快速生成专属训练集，解决通用模型在私有环境下的水土不服。
- SFT + RLHF 闭环：先通过 SFT 学习基本操作范式，再通过基于执行结果的 RL 优化长程规划能力，是目前提升 Agent 鲁棒性的有效路径。
## 局限与展望目前该框架主要基于 Ubuntu Docker 环境，命令集集中在 GNU/Linux 工具链。未来扩展到 Windows 或 macOS 环境，以及更复杂的分布式系统交互，将是下一个挑战。
