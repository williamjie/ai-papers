# Agent 编码的推理时扩展：表示即一切

**日期**: 2026-04-23

---

论文 : Scaling Test-Time Compute for Agentic Coding链接 : https://arxiv.org/abs/2604.16529推理时计算扩展（Test-Time Compute Scaling）在数学推理和单轮代码生成上已经验证有效，但放到 Agent 编码场景就翻车了。Meta 这篇论文直接点破了核心问题：长轨迹没法直接比、没法直接复用，你得先把它变成紧凑的结构化表示。
## 现有方案的痛点SWE-Bench、Terminal-Bench 这类 Agent 编码任务，每个尝试（rollout）产生的是几十步的交互轨迹：读文件、改代码、看日志、执行命令、报错、重试。这些轨迹包含有用信号，但也充斥着噪声。直接拿完整轨迹做比较或作为上下文，模型根本抓不住重点。
论文的核心 insight 很简单： 推理时扩展的本质是表示、选择和复用三个问题 。你把轨迹表示好了，后面的一切都顺了。
## 方法拆解框架分两条线：并行选择和顺序精炼。
并行选择：递归锦标赛投票（Recursive Tournament Voting, RTV）
执行 N 个并行 rollout，每个转成结构化摘要，然后两两比较（G=2），投票聚合（V=8），递归淘汰直到剩一个。
为什么两两比较比一次比 16 个效果好？论文实验说得很清楚：随着锦标赛推进，早期”容易”的对比被筛掉，后期剩下的是需要关注细微差别的难决策。结构化摘要在这种场景下优势明显，因为它保留了关键假设、进展和失败模式，去掉了低信号的轨迹细节。
顺序精炼：Agent 版 PDR（Parallel-Distill-Refine）
从上一轮选 K 个摘要作为精炼上下文，在新环境里跑新一轮 rollout。关键发现：用 4 个摘要做上下文（random-K）明显好于只用 1 个；如果用 RTV 精选的 4 个（select-K）更好。
精炼上下文质量直接决定下一轮效果。Table 2 的数据很直观：当 K=4 个上下文 rollout 全部通过时，Claude-4.5-Sonnet 的下一轮通过率从 random-K 的 98.1% 提升到 select-K 的 97.3%，但 select-K 产生 4/4 通过上下文的任务数从 52.8 个增加到 62 个——精选的价值在于它制造了更多高质量上下文。
## 关键结果默认配置：N=16, T=2, K=4, G=2, V=8。

还有一个容易被忽略的点：精炼后 Agent 的步骤数直接砍半。Claude-4.5-Opus 在 SWE-Bench 上从 41.23 步降到 14.31 步，Terminal-Bench 从 24.43 步降到 12.14 步。高质量上下文让 Agent 少踩坑、少探索，直接上路。
## 工程启示- 结构化摘要是通用接口。不管你是做并行投票还是顺序精炼，先把 rollout 变成紧凑摘要，这个抽象层值得在任何 Agent 系统里复用。
- 小群体递归比较胜过一次性全局排名。这个结论不局限于代码领域，任何需要模型做复杂排序的场景都值得试试。
- 精炼上下文的质量比数量更重要。与其塞 16 个摘要进上下文，不如精选 4 个高质量的。RTV 在这里既是选择器，也是过滤器。
- 推理时扩展让 Agent 解决以前解不了的问题。论文提到 Claude-4.5-Opus 在 Terminal-Bench 上解出了 gpt2-codegolf，Gemini-3.1-Pro 解出了 large-scale-text-editing，这两个任务在 16 个初始 rollout 里都没人过。
## 局限论文没有讨论计算成本的具体数字——16 个并行 rollout 加精炼再跑一轮，token 消耗是 32 倍起步。对于小模型或预算敏感的场景，这个方法的性价比需要仔细评估。另外，摘要质量完全依赖模型自身能力，弱模型可能摘要本身就不可靠，形成恶性循环。
