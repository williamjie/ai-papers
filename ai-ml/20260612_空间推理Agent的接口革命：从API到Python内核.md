## 痛点：为什么现有的 Agent 搞不定空间推理？
目前的工具增强型 Agent 主要依赖两种交互模式，但在处理复杂空间任务时都显得捉襟见肘：
- 单次代码执行（Single-pass Code）：模型必须一次性写出完整程序。这要求它在看到任何中间结果前就确定所有策略。一旦分割掩码错了，或者深度图有偏差，整个推理链条直接崩塌，没有修正机会。
- 结构化工具调用（Structured Tool-Call）：通过 JSON/XML 调用预定义 API。这种方式虽然规范，但灵活性极差。空间推理往往需要即兴组合（比如用 scipy.spatial.KDTree 找最近点），这些临时性的数值计算很难被预定义的 API 覆盖。
核心矛盾在于： 空间推理是动态的、迭代的过程，而现有接口往往是静态的、线性的。
## 方法拆解：把代码当作“可观察的状态”
SpatialClaw 的核心 Insight 非常直观但有力： 代码不应只是一次性的指令，而应是一个可观察、可修改的计算环境。
它构建了一个持久化的 Python 内核（Persistent Kernel），预加载了输入帧和感知工具。Agent 不再一次性输出答案，而是进入一个“规划-执行-反馈”的循环：
- 状态持久化：每一步生成的掩码、深度图、点云都作为普通 Python 变量保留在内存中。后续步骤可以直接复用或修正这些数据，无需重新计算。
- 视觉反馈闭环：内核提供 show() 函数，将中间结果（如分割后的图像）渲染并嵌入到下一个 Prompt 的上下文中。Agent 可以“看到”自己的错误（例如：“这个掩码把门框也切进去了”），从而在下一步修正代码。
- 自由组合能力：除了预置的感知工具（SAM3, Depth Anything V2），内核还开放了 numpy、scipy 等科学计算库。Agent 可以根据问题需求，现场编写几何计算逻辑，而不是受限于有限的 API。
这种设计让 Agent 具备了“调试”能力——它可以在执行过程中发现假设错误，并动态调整策略，这正是人类处理空间问题时的典型思维模式。

## 工程启示：Agent 设计的范式转移这篇论文对工程实践有三个重要指导意义：
- 接口即能力：不要只关注给 Agent 加了什么工具，更要关注如何调用这些工具。从“函数调用”转向“代码执行环境”，能释放 LLM 的逻辑组合潜力。
- 可视化反馈至关重要：在空间任务中，让模型“看到”中间结果（如分割掩码）比仅返回文本描述有效得多。show() 机制是提升推理准确性的关键杠杆。
- 零样本通用性：SpatialClaw 无需针对特定基准进行微调或提示工程调整，在 Qwen 和 Gemma 系列不同规模的模型上均表现一致。这表明良好的接口设计可以跨越模型架构的差异，提供稳定的性能增益。
## 局限与展望尽管效果显著，该方法仍受限于代码生成的稳定性。如果 LLM 编写的 Python 代码存在语法错误或逻辑死循环，虽然系统有静态检查器，但仍可能浪费 Token 和计算资源。此外，持久化内核增加了内存占用，对于超长视频或高分辨率图像序列，状态管理仍需优化。
总体而言，SpatialClaw 证明了在空间推理领域， “慢思考”（迭代修正）优于“快执行”（单次生成） 。对于构建需要复杂几何理解的 Agent，这种基于代码内核的交互模式值得深入借鉴。
