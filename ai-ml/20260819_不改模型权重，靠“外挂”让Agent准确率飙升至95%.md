论文 : StateM: Reaching 95.3% Raw Accuracy, or a $15 Frontier Run, on Terminal-Bench 2.1 via Harness Scaling链接 : https://arxiv.org/abs/2608.15089做 Agent 开发的朋友应该都有过这种崩溃时刻：模型明明每一步都答对了，但整体任务还是挂了。它忘了之前的变量状态、跳过了关键检查、或者在没做完时就提前停止。这篇论文的核心观点很激进： 很多“模型能力不足”其实是“执行框架（Harness）”的锅。 作者通过引入一个名为 StateM 的运行时系统，在不修改任何模型权重的前提下，把 GPT-5.6 Sol 在 Terminal-Bench 2.1 上的准确率从基线的 83.1% 拉到了惊人的 95.3%。
### 为什么需要“Harness Scaling”？
现有的 Agent 方案通常走两个极端：
- 纯软计划：像 Codex 或 Claude Code，靠自然语言提示词（Soft Plans）维持状态。痛点是随着上下文变长，控制信号被稀释，Agent 容易“迷路”。
- 硬编排：像 LangGraph，用代码写死状态机。痛点是灵活性差，把 Agent 拆碎成一个个节点，丢失了通用推理能力。
StateM 的 Insight 在于找到了中间地带： Agent-Native Control Layer 。它不替换模型，而是给模型套上一个“带强制检查点的外壳”。这个外壳是一个 YAML 文件（Runbook），既定义了状态流转，又允许 Agent 和人类共同编辑。
### 核心机制拆解：State 即契约StateM 的设计精髓在于将 State 定义为“上下文与契约的边界”（Context-and-Contract Boundary）。
- 进入状态（In-Hook）：当 Agent 进入某个阶段（如“编码”），系统自动刷新该阶段的局部指令和持久化进度。这解决了“长文本遗忘”问题，不需要 Agent 自己去翻历史日志找上下文。
- 离开状态（Before-Transfer Checks）：这是最硬核的部分。Agent 想从“编码”跳到“测试”，必须先通过预定义的检查点（如运行单元测试、验证文件存在）。如果检查失败，状态机直接阻断转移，强制 Agent 留在原地修复。
- 共享控制权：Runbook 是透明的 YAML。人类可以审计和修改规则，Agent 也可以通过 CLI 命令查询当前状态、请求转移或查看失败原因。
这种设计把隐性的“计划”变成了显性的、可执行的“状态机”，且没有牺牲 Agent 在单个阶段内的自主推理能力。

### 工程启示与局限对工程师的意义：
- 不要只盯着 Prompt Engineering：如果你的 Agent 长任务失败率高，先检查是不是缺少了显式的状态管理和强制检查点。
- Runbook 可复用：论文证明，为 GPT-5.5 开发的 Runbook 可以直接迁移到 GPT-5.6，无需重新调优。这说明控制逻辑（Harness）具有跨模型的通用性。
- 低成本适配：对于开源或较小模型（如 DeepSeek），只需少量 API 费用定制具体的检查规则，就能获得显著的性能提升。
局限与边界：
- 并非万能药：StateM 解决的是“程序性记忆缺口”（Procedural-Memory Gap），即 Agent 知道怎么做但没做对或忘了做。如果模型本身缺乏相关知识（Epistemic Gap），外挂框架也无能为力。
- 维护成本：虽然 Runbook 可共享，但针对特定任务族（如 BusinessBench 中的预算审批）仍需开发具体的检查逻辑。通用性存在边界，当任务结构差异巨大时，增益会缩小（BusinessBench 平均仅提升 0.55%）。
总之，StateM 提供了一个强有力的工程范式： 在模型能力暂时无法突破时，通过强化执行环境的确定性，可以“压榨”出模型现有的全部潜力。
