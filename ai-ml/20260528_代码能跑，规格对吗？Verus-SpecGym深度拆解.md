论文 : Verus-SpecGym: An Agentic Environment for Evaluating Specification Autoformalization链接 : https://arxiv.org/abs/2605.26457AI 写代码越来越溜，但“写得对”和“证明得对”之间隔着巨大的鸿沟。这篇论文戳破了一个残酷真相：即使模型能生成通过测试的正确代码，它往往连正确的形式化规格（Formal Specification）都写不出来。如果规格错了，验证器给出的“数学保证”就是空中楼阁。
### 痛点：谁在定义“正确”？
目前的形式化验证工作流假设规格是现成的。但现实中，用户给的是自然语言描述，验证器要的是逻辑谓词。这个翻译过程叫 规格自动形式化（Specification Autoformalization） 。
现有的评估方法有两个死穴：
- 专家写参考规格太贵：每个问题都要人工写 Gold Standard，无法规模化。
- LLM 当裁判不可靠：用另一个 LLM 判断规格是否忠实于原意，会漏掉细微的逻辑错误。论文数据显示，LLM-as-a-judge 漏掉了 26% 的真实失败案例。
### 核心 Insight：让规格“跑”起来Verus-SpecGym 的核心创新在于 可执行规格评估（Executable Specification Evaluation） 。
Verus 的规格通常是给 SMT 求解器看的逻辑符号，不能直接运行在测试用例上。作者扩展了 Verus 的 exec_spec 机制，将生成的规格编译成可执行的 Rust 代码。这意味着我们可以像跑单元测试一样，用具体的输入输出对去“测”规格。
更绝的是测试数据的来源。除了官方测试集，他们引入了 Codeforces 的 Hacks（对抗性用例） 。这些是其他选手为了卡掉错误解法而专门构造的边界案例。
- Pre-completeness/Soundness：测输入约束是否过松或过紧。
- Post-completeness/Soundness：测输出逻辑是否遗漏或误判。
这种设计不仅解决了评估难题，还利用了人类选手的对抗智慧，弥补了 LLM 构造反例能力的不足。
### 实验结果：前沿模型也翻车在包含 581 个 Codeforces 问题的 VERUS-SPEC-BENCH 上，模型表现分层明显：
模型类型 代表模型 解决率 最强前沿 gemini-3.1pro 77.8% 其他前沿 (未具名) 51.1% - 57.8% 开源模型 (未具名) 21.5% - 25.5%即使是最强的 Gemini，也有近 23% 的任务失败。失败模式主要集中在三类：
- 遗漏输入假设：比如没检查数组是否有序。
- 接受错误输出：规格太松，允许了不符合题意的解。
- 拒绝有效输出：规格太严，把正确答案拒之门外。
### 工程启示- 验证的瓶颈在规格，不在代码：如果你的 Agent 能写出正确代码但写不出正确规格，那么形式化验证对你目前的项目可能弊大于利。
- 对抗测试不可或缺：常规测试集容易过拟合，引入类似 Codeforces Hacks 的对抗用例是发现规格漏洞的关键。
- 执行优于推理：对于逻辑约束的检查，编译成可执行代码进行运行时检查，比让 LLM “想一想”更可靠、更可扩展。
### 局限与展望目前基准仅针对 Rust/Verus，且依赖 Codeforces 这种有明确输入输出结构的算法题。对于涉及复杂状态机或副作用的系统级软件，如何构建类似的自动化评估环境仍是挑战。此外，开源模型与前沿模型的巨大差距（~25% vs ~78%）表明，规格形式化能力目前仍是闭源大模型的“护城河”。
