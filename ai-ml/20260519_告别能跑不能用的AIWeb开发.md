# 告别能跑不能用的AI Web开发

**日期**: 2026-05-19

---

论文 : From Runnable to Shippable: Multi-Agent Test-Driven Development for Generating Full-Stack Web Applications from Requirements链接 : https://arxiv.org/abs/2605.17242现在的 Coding Agent 确实能根据自然语言生成 Web 应用，但有个尴尬的现实：生成的代码虽然能跑（Runnable），但往往没法直接上线（Shippable）。一项基准测试显示，超过 70% 的生成应用无法满足功能需求。核心痛点在于，Web 应用的正确性无法像传统后端代码那样通过编译器或终端输出来验证，它必须部署、在浏览器中模拟交互，并将失败转化为修复信号。这篇论文提出了 TDDev 框架，通过自动化闭环的测试驱动开发（Test-Driven Development, TDD），将这一过程工程化，不仅提升了生成质量，还揭示了模型风格与 TDD 策略之间的关键匹配关系。
### 为什么传统 Agent 搞不定 Web 开发？
传统编程任务中，Agent 可以通过读取终端报错或单元测试结果来迭代代码。但 Web 开发打破了这个反馈回路，面临三大挑战：
- 需求具体化（Requirement Concretization）：用户给出的通常是“做一个购物网站”这样的高层需求，Agent 需要将其转化为具体的浏览器交互脚本（点击、输入、导航）及预期结果。
- 交互式验证（Interactive Validation）：代码生成具有非确定性，UI 结构每次可能不同。静态脚本无法覆盖所有情况，必须通过模拟真实用户交互来验证。
- 失败翻译（Failure Translation）：Web 错误往往是体验层面的（如按钮缺失、状态未更新），而非明确的堆栈跟踪。需要将这些视觉/交互失败转化为 Agent 可理解的修复指令。
### TDDev 的核心设计：自动化 TDD 闭环TDDev 将上述挑战拆解为三个自动化阶段，形成了完整的 TDD 闭环：
- 阶段一：验收测试生成。受“肥皂剧测试”（Soap Opera Testing）启发，TDDev 不直接让 LLM 写测试，而是先让 LLM 扮演具体用户角色（如“协调员”、“接收者”），从用户目标出发推导出多样化的测试用例。每个用例包含功能描述、有序交互步骤和可观察的预期结果。
- 阶段二：交互式验证。TDDev 部署应用后，使用一个轻量级的 LLM 测试代理（Testing Agent）在浏览器中执行测试。该代理观察页面的无障碍树（Accessibility Tree），动态生成 Playwright 代码进行交互，并根据轨迹判断通过或失败。这种设计避免了硬编码选择器，能适应不同生成的 UI 结构。
- 阶段三：失败翻译。当测试失败时，系统不会只返回“Fail”，而是生成结构化报告，记录“尝试了什么”、“在哪里失败”、“观察到了什么”。例如：“登录功能失败：提交表单时未找到提交按钮。观察：表单渲染了邮箱和密码字段，但无提交控件。”
### 关键结果：TDD 策略需匹配模型风格论文对比了四种开发协议：无 TDD 基线、代理自主 TDD（Agentic）、整体项目 TDD（Whole-Project）和增量 TDD（Incremental）。实验数据揭示了两个重要发现：
- TDD 基础设施显著提升质量：在所有 WebGen-Bench 组合中，TDD 相比无 TDD 基线提升了 34–48 个百分点。例如，ClaudeSDK + Qwen-3.5 在增量 TDD 下准确率达 71.4%，而基线仅为 23.3%（+48.0 pp）。
- 最佳协议取决于模型生成风格：
能力强、整体式生成的模型（如 Claude Sonnet 4.6）：最适合代理自主 TDD（Agentic-TDD），准确率达 65.8%。严格的增量约束反而限制了其发挥，导致性能与基线持平（31.5% vs 31.3%）。
- 保守、增量式生成的模型（如 Qwen-3.5）：最适合增量 TDD（Incremental），准确率达 71.4%。若使用代理自主模式，性能大幅下降至 41.0%。
- 错配代价高昂：将协议与模型风格错配，不仅消除 TDD 收益，还可能导致 Token 成本高达 25 倍。

- 测试代理的“保守”是好事：TDDev 的测试代理在正确应用上存在 5% 的假阴性（误报失败），但在错误应用上实现了 100% 的检测率，且无假阳性。这种“宁错杀不放过”的特性在 TDD 闭环中是安全的，因为假阴性只会触发额外的修复轮次，而不会让缺陷溜走。
- 从 Prompt 工程转向流程工程：用户研究表明，TDDev 将人工干预降至零，将工作重心从持续的 Prompt 调整转移到自主的、反馈驱动的优化流程中。
### 局限与展望目前 TDDev 在 ArtifactsBench（偏向简单游戏和动画）上的提升较小（+7.6 pp），说明 TDD 的收益随任务复杂度增加而放大。此外，测试生成模块对高层需求中隐含的结构化导航元素（如全局导航链接）覆盖不足（覆盖率 91.9%），未来需增强对隐式需求的推导能力。
