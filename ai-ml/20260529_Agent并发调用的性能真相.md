# ⭐⭐ Agent 并发调用的性能真相

**日期**: 2026-05-29

---

论文 : AsyncTool: Evaluating the Asynchronous Function Calling Capability under Multi-Task Scenarios链接 : https://arxiv.org/abs/2605.27995现在的 LLM Agent 大多在“同步世界”里跑测试：调用一个 API，等结果回来，再调下一个。但这不符合现实。真实业务中，API 响应往往有延迟，且任务经常并发。这篇论文提出的 AsyncTool 基准测试，直击当前 Agent 评估体系的盲区： 模型能否利用等待时间并行处理其他任务？
### 现有方案的痛点：假装没有延迟现有的工具调用基准（如 ToolBench, BFCL）大多假设工具是“即时响应”的。这种设定掩盖了真实环境中的核心挑战： 时间维度上的协调 。
在实际工程中，如果 Agent 在等待一个耗时查询返回时“发呆”，整体效率会极低。更糟糕的是，当多个任务并发时，模型需要维护多个任务的中间状态，并在依赖关系允许的情况下切换上下文。AsyncTool 指出，现有评估缺乏对这种**异步多任务场景（Asynchronous Multi-Task Scenarios）**的考察，导致我们高估了 Agent 在真实生产环境中的可用性。
### 核心设计：模拟真实的“等待焦虑”
AsyncTool 的核心 Insight 很简单但致命： 延迟是常态，而非异常 。
它构建了一个交互式环境，其中工具调用会产生模拟的响应延迟。Agent 必须在以下约束下工作：
- 并发任务：同时接收多个独立但内部有依赖的任务。
- 延迟反馈：发出调用后，结果不会立即返回。
- 状态保持：Agent 必须记住每个任务执行到了哪一步，并在结果返回后正确恢复。
⚠️ 关键直觉 ：优秀的 Agent 不是“切换得越快越好”，而是“在正确的时间切换”。盲目频繁切换会导致上下文丢失和依赖错误；而完全串行则浪费了等待时间。AsyncTool 通过引入 Same-task Streak （同任务连续步数）指标，量化了这种调度效率。
### 实验结果：延迟让所有模型“降智”
论文评估了 19 个主流模型，结果令人警醒： 异步执行导致性能显著下降 。
模型类别 代表模型 AsyncTool Overall Score 关键表现 闭源顶尖 GPT-4.1 38.06 平衡了准确率与调度效率，Same-task Streak 较低 开源最强 DeepSeek-V3.1-Terminus 28.93 准确率接近闭源模型，但调度稍显僵化（Streak 较高） 闭源主流 Gemini 2.5 Pro 32.44 在从双任务增至三任务时，性能下降最剧烈 (-10.12) 开源小参 Qwen3-8B 10.67 难以处理多任务并发，常出现任务遗忘或依赖错误几个反直觉的发现：
- 准确率与效率不线性相关：图 4 显示，有些模型（如部分开源小模型）切换频率高（Streak 低），但整体得分依然很低。这说明频繁切换本身不是能力，能正确维护多任务状态才是。
- 任务数量是指数级难点：当任务数从 2 增加到 3 时，所有模型性能均大幅下滑。Gemini 2.5 Pro 从 42.56 跌至 32.44，Qwen3-8B 更是从 27.91 暴跌至 10.67。
- 幻觉源于“不等”：低性能模型常在结果未返回时就强行继续下一步，甚至编造参数。这证实了**时间推理（Temporal Reasoning）**是当前 LLM 的短板。
### 工程启示：如何构建更鲁棒的 Agent？
- 显式状态管理：不要依赖模型的隐式记忆来跟踪多任务进度。在 Prompt 或系统设计中，引入显式的“任务队列”和“等待中任务列表”，让模型像操作系统调度器一样工作。
- 容错与重试机制：AsyncTool 显示，依赖错误（Dependency Violation）是主要失败模式。工程上应增加前置条件检查，确保在调用后续 API 前，前置结果已就绪。
- 评估体系升级：如果你正在开发 Agent，仅用同步基准测试是不够的。引入带延迟的并发测试，能更早暴露状态管理缺陷。
### 局限与展望AsyncTool 的数据集基于 BFCLv3 和 NESTFUL 重构，场景覆盖有限。此外，依赖 Gemini 2.5 Pro 进行数据重建引入了额外成本。未来，随着 Agent 在真实业务中承担更复杂的并发工作流，**时间感知（Time-Aware）**将成为评估 Agent 智能程度的新维度。
