# 告别截图幻觉：OpenComputer 如何重构 Agent 评估

**日期**: 2026-05-20

---

论文 : OpenComputer: Verifiable Software Worlds for Computer-Use Agents链接 : https://arxiv.org/abs/2605.19769做 Computer-Use Agent（CUA）的朋友都知道，现在的评估体系有个巨大的坑： LLM-as-Judge 的“看图说话”太不可靠了 。截图看着像做完了，其实数据没存对、格式错了，或者只是界面刷新没到位。这篇 OpenComputer 论文直接掀了桌子，提出了一套“可验证软件世界”框架，核心就一句话： 别猜，直接读应用状态。
### 为什么现在的评估方案不够用？
传统的桌面 Agent 评估（如 OSWorld）主要依赖人工标注或 LLM 对截图进行判断。这带来了两个致命工程问题：
- 环境构建成本高：每个任务都要手动准备文件、配置文件夹，难以规模化。
- 评估存在“视觉欺骗”：LLM 只能看到像素。如果 Agent 把数据填错了单元格，或者在不可见的后台进程里失败了，LLM 往往会给高分。这种“看起来像成功”的奖励信号，会严重误导后续的强化学习（Reinforcement Learning, RL）或监督微调（Supervised Fine-Tuning, SFT）。
### 核心 Insight：验证即构造OpenComputer 的设计哲学非常硬核： 验证器（Verifier）不是事后诸葛亮，而是任务生成的起点。
它没有把验证当成一个独立的评估模块，而是将其作为环境构造的约束条件。整个框架由四个紧密耦合的组件构成：
-应用特定的状态验证器（App-Specific State Verifiers）：
这是最精彩的部分。针对不同软件，它不依赖截图，而是通过底层接口读取真实状态。
浏览器/VS Code：通过 CDP（Chrome DevTools Protocol）或 Electron API 读取 DOM 和内部状态。
- Office/SQLite 应用：直接解析数据库或文档文件。
- 多媒体软件：使用 ffprobe 或 PIL 检查文件元数据。
- 设计工具：解析 SVG、JSON 结构等。
这意味着，Agent 是否“真正”完成了任务，是由代码逻辑决定的，而不是由像素相似度决定的。
-自进化验证层（Self-Evolving Verification Layer）：
验证器代码也是由 Agent 生成的，难免有 Bug。OpenComputer 引入了一个“校准-诊断-修复”闭环：
用强 Agent 执行校准任务。
- 对比“程序化验证结果”与“LLM 参考判决”。
- 如果两者不一致，分析是 Agent 错了还是验证器错了。如果是验证器逻辑缺陷，自动修复代码或文档。
实验显示，经过这一层，验证器与人工标注的一致性从 85.2% 提升到了 94.1%。
-任务生成流水线：
基于可用的验证接口，反向生成任务。如果某个状态无法被程序化检查，该任务就会被过滤掉。这保证了最终发布的 1,000 个任务，每一个都有“机器可审计”的成功标准。
-评估沙箱：
在隔离环境中运行 Agent，记录完整轨迹，最后执行验证脚本计算奖励（Reward）。支持部分得分（Partial Credit），即 N_pass / N_total，这为 RL 提供了更细粒度的信号。
### 关键结果：前沿模型依然很弱OpenComputer 覆盖了 33 个桌面应用 （涵盖浏览器、Office、创意软件、开发环境等），发布了 1,000 个最终任务 。实验结果给所有 CUA 项目泼了一盆冷水：
模型 OSWorld 得分 (参考) OpenComputer 成功率 平均奖励 (Avg. Reward) GPT-5.4 75.0% 68.3% 88.4% Claude-Sonnet-4.6 72.5% 64.4% 76.6% Kimi-K2.6 73.1% 58.8% 70.7% Qwen-3.5-27B 56.2% 32.3% 59.4% GUI-OWL-1.5-8B 52.3% 5.7% 27.8%几个关键发现：
- 开源模型断崖式下跌：GUI-OWL 在 OSWorld 上有 52.3% 的表现，但在 OpenComputer 上只有 5.7%。这说明现有开源模型严重过拟合于特定基准，泛化能力极差。
- LLM Judge 不如硬编码：在 120 个任务的对比中，硬编码验证器与人工判断的一致性为 97.3%，而 LLM Judge 仅为 92.2%。在涉及细微状态（如单元格数据、隐藏元数据）时，截图判断完全失效。
- GUI vs CLI 的效率权衡：在兼容 CLI 的子集任务中，Claude Code (CLI) 的平均耗时仅为 141 秒，而 GPT-5.4 (GUI) 需要 288 秒。CLI 通过直接操作文件和脚本，绕过了缓慢的截图-动作循环，效率优势明显。
### 工程启示- 重新思考 Reward 设计：如果你在做 Agent 的 RL 训练，不要用 LLM 打分。构建基于应用状态的硬性检查器（Hard-coded Checkers），哪怕只覆盖核心字段，其信号质量也远高于视觉评估。
- 混合交互是趋势：对于开发类、文件管理类任务，CLI 接口的效率远高于 GUI。未来的通用 Agent 应该具备“模式切换”能力：简单操作走 CLI，复杂交互走 GUI。
- 验证即测试：OpenComputer 的验证器生成过程，本质上是一套自动化的端到端测试框架。工程团队可以借鉴其“自进化验证”思路，用 Agent 自动生成和修复测试用例。
### 局限与展望目前 OpenComputer 主要依赖“可程序化检查”的状态。对于 Draw.io 中的图形连接关系、复杂的视觉布局等，硬编码验证器难以覆盖。论文中提到了 17 个因无法完全程序化验证而被排除的任务。未来方向显然是 混合验证 ：将底层状态检查与高层视觉判断结合，但这又会回到如何保证视觉判断一致性的老问题上。
总之，OpenComputer 提供了一套高标准的基准和基础设施。它告诉我们：要想让 Agent 真正有用，先别急着调大模型，先把“怎么算成功”定义清楚。
