**日期**: 2026-07-01

---

论文 : SWE-Together: Evaluating Coding Agents in Interactive User Sessions链接 : https://arxiv.org/abs/2606.29957现在的编程 Agent 评测大多太“静态”了。给个需求，跑个测试，看 Pass Rate。但这跟真实开发场景差太远了：用户会改口、会纠正、会补充细节。Meta 这篇 SWE-Together 试图解决这个错位，把真实的交互过程还原成可复现的 Benchmark。
### 为什么现有评测不够用？
主流基准（如 SWE-Bench）是单轮指令式的。Agent 拿到完整描述，直接干活。但现实是：
- 需求是动态的：用户往往先给个模糊想法，中间不断澄清或推翻重来。
- 评估维度单一：只看最终代码对不对，忽略了“为了对，用户花了多少精力纠正 Agent”。
两个 Agent 可能都修好了 Bug，但一个需要用户反复骂它、改逻辑，另一个一次过。现有评测给它们打一样的分，这显然不合理。
### 核心设计：把真实对话变成“可回放”的任务SWE-Together 的核心 Insight 是： 必须保留原始用户的意图，但要让交互过程可控。
他们从 11,260 条真实用户- Agent 会话中，严选出 109 个高质量任务（转化率仅 0.97%）。筛选标准很硬：必须有可恢复的仓库状态、清晰的用户目标、以及可观测的代码变更。
关键技术点：状态条件化的用户模拟器这不是简单的 LLM 角色扮演。他们构建了一个“锚定”模拟器，它不随机说话，而是基于原始会话的分析结果（意图、约束、触发条件）来决定何时介入。
- 如果 Agent 走偏了：模拟器发出纠正信号。
- 如果 Agent 做得好：模拟器保持沉默（no-op），让 Agent 继续。
这种设计避免了“固定脚本回放”导致的时序错乱，也防止了“通用模拟”带来的意图漂移。
### 实验结果：强模型真的更“省心”吗？
他们在 109 个任务上测试了 7 个前沿模型。最关键的发现是： 能力越强，需要的纠正越少。
排名 模型 pass@1 Mean Judge User Correction (↓) 1 Claude Opus 4.8 63% 0.801 1.38 2 GPT-5.5 58% 0.763 1.59 3 Claude Opus 4.6 58% 0.755 1.59 … … … … … 7 MiniMax-2.7 40% 0.630 2.17⚠️ 反直觉发现 ：User Correction（用户纠正次数）与模型能力呈强负相关（Pearson -0.92）。
这意味着，评价一个 Agent 好不好，不能只看它能不能写出正确代码，还要看它能不能“少让用户操心”。Claude Opus 4.8 虽然 Token 消耗最高（74k），但需要的纠正最少，体验最好。
此外，GPT-5.5 在效率上表现惊人：仅用 10.7 分钟和 29.9k Token 就达到了第二名的水平。
### 工程启示- 引入“交互成本”指标：在实际部署 Agent 时，建议监控“用户干预次数”。如果一个模型 Pass Rate 高但需要大量人工修正，它的实际生产力可能很低。
- 评测要贴近真实工作流：静态 Benchmark 正在饱和，区分度下降。多轮交互、动态需求变更的评测更能反映模型的工程落地价值。
- 模拟器的一致性验证：论文提到，人类标注者无法可靠区分模拟用户和真实用户（Turing pass rate 46%），这证明了其模拟器的保真度较高，结果可信。
### 局限与展望目前的方法主要依赖文本轨迹，无法处理视觉界面信息或中断 Agent 的执行过程。且任务多为有明确代码产出的场景，对于开放性、模糊性的需求覆盖有限。
总的来说，SWE-Together 提醒我们：Agent 的价值不仅在于“能干活”，更在于“好合作”。
