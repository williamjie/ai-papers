## 为什么 Nanbeige4.2-3B 开箱即坏？
Nanbeige4.2-3B 是一个基于 Looped Transformer (LT) 的 3B 参数模型。LT 的核心 trick 是让同一组层在 forward pass 中跑两遍，从而在不增加参数量（Parameter Count）的情况下获得双倍的有效深度。
但作者发现，直接用 Hugging Face transformers 加载该 checkpoint 会失败或静默出错。论文定位了五个独立 Bug：
- RoPE 缓冲区归零：inv_freq 在加载后全为 0，导致模型完全丢失位置信息。生成内容看似流畅实则逻辑混乱，极难排查。
- 配置分发 KeyError：自定义建模代码在处理特定 RoPE 类型时抛出 KeyError: 'type'，直接阻断加载。
- API 哨兵不匹配：调用已废弃的 DynamicCache.from_legacy_cache，导致 AttributeError。
- Position-IDs 重裁剪崩溃：仅在 MPS 后端触发 Metal 断言失败（SIGABRT），CPU 上复现不了。
- 权重键名格式错误：导致 save_pretrained() 失败，模型无法重新序列化。
⚠️ 反直觉发现 ：Bug #1（RoPE 归零）是最隐蔽的。它不会报错，只会让模型变成“失忆症”患者。在本地调试时，如果看到生成内容胡言乱语但格式正确，务必检查嵌入层缓冲区是否被意外清零。
## 核心痛点：LT 架构的显存陷阱修复上述 Bug 后，模型能跑了，但 Agentic 任务（如多轮工具调用）依然跑不通。原因在 LT 架构本身。
标准 Transformer 的 Prefill 阶段，注意力矩阵大小为 O(L2)O(L^2) ) 。LT 因为要跑两遍层，显存峰值直接翻倍。在 Apple Silicon 这种统一内存（Unified Memory）架构下，没有 CUDA 那样的高效分页机制，这 32GB 共享内存瞬间见底。
解决方案：Chunked Prefill (分块预填充)
作者没有重写内核，而是用一个简单的循环策略替代一次性 Prefill：
- 将长 Prompt 切分为固定大小的 Chunk（默认 256 tokens）。
- 逐个 Chunk 调用模型 forward，增量更新 KV Cache。
- 最后再交给 generate() 进行解码。
设计直觉 ：虽然总计算量没变，但峰值显存从 O(L2)O(L^2) ) 降到了 O(chunk_size×L)O(\text{chunk\_size} \times L) × L ) 。用时间换空间，在内存受限的端侧设备上极其有效。

Nanbeige 的训练数据中，工具调用的 System Prompt 是硬编码在模板里的。如果用户传入任何自定义 System Message，模板会 丢弃 内置的那条，而不是合并。
- 后果：模型失去了“我是工具调用专家”的身份设定，多轮工具调用格式直接崩坏。
- 修复：必须移除用户传入的 System Message，让模板走默认的自动插入路径，再手动拼接用户内容。
⚠️ 工程警示 ：很多开源模型的 SFT 数据是绑定特定 Chat Template 字节序列的。随意修改 System Prompt 的空白符或结构，可能导致模型能力断崖式下跌。
## 工程启示与局限- 本地部署需“打补丁”：不要指望 from_pretrained 就能跑通最新 SOTA 小模型。检查 RoPE、Cache API 和 Template 是必修课。
- MPS 内存管理缺陷：论文发现 MPS 后端一旦 OOM，进程可用内存预算会永久降级，重启进程才能恢复。在构建 Agent Harness 时，建议每个任务独立子进程隔离。
- LT 架构的取舍：LT 适合参数量受限但算力充足的场景（如 H100）。但在 Apple Silicon 等内存敏感设备上，必须配合 Chunked Prefill 使用，否则长上下文基本无解。
