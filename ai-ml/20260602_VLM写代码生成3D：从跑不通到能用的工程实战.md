# ⭐⭐½ VLM 写代码生成 3D：从跑不通到能用的工程实战

**日期**: 2026-06-02

论文 : 3DCodeBench: Benchmarking Agentic Procedural 3D Modeling Via Code链接 : https://arxiv.org/abs/2606.01057用代码生成 3D 资产（Procedural 3D Modeling）是游戏和仿真领域的刚需，因为它是确定性的、可编辑的，且体积小巧。
但让 VLM 直接写 Blender Python 脚本一直是个地狱级难题：API 极其复杂，几何逻辑难懂，且缺乏高质量的评测标准。
这篇来自 Google DeepMind 的论文抛出了 3DCodeBench ，不仅提供了包含 26K 样本的高质量数据集，更通过大规模实验揭示了当前 VLM 在 3D 编程上的真实能力边界。
### 为什么现有方案不够用？
现有的 3D 生成评测存在三个致命短板：
- 数据断层：ShapeNet 等数据集只有静态 Mesh，没有对应的生成代码，无法评估“生成代理（Agentic）”能力。
- 复杂度过低：之前的基准测试（如 VoxelCodeBench）局限于简单的体素堆叠或预建场景编辑，远低于工业级建模的几何复杂度。
- 缺乏迭代机制：真实开发中，代码报错后需要调试、重构。现有评测多为单次生成（Single-shot），忽略了 Agent 自我修正的核心价值。
### 方法拆解：如何构建高难度基准？
3DCodeBench 的核心 insight 是： 要评测 Agent，必须提供“可执行的环境”和“多轮反馈机制”。
他们从 Infinigen 模拟器中提取了 212 个类别的复杂工厂代码（平均脚本长度 531 行，中位数 387 行），并通过一套 Agentic Data Curation Pipeline 将其转化为独立的 Blender Python 脚本。
这个流水线非常硬核：
- Skills Library：包含代码简化器、沙盒模拟器（Blender 5.0）、视觉批评家（VLM 对比渲染图）和网格分析器（检查非流形几何体）。
- Experience Library：积累 API 迁移规则、去重策略和代码组织规范，避免重复造轮子。
- Human-in-the-Loop：最终由人工审核语义准确性和视觉一致性，确保基准数据的“金标准”地位。
### 关键结果：VLM 到底行不行？
论文评测了 12 个前沿 VLM（包括 Gemini, Claude, GPT 系列），结论相当扎心但也充满希望。
1. 执行率是最大瓶颈，但极易修复在单次生成（Single-turn）中，顶级模型如 Claude Opus 4.7 的执行率仅为 91% ，GPT-5.5 为 90.6% 。
失败的主要原因不是逻辑错误，而是 Blender API 不匹配 。
⚠️ 反直觉发现 ：引入多轮错误反馈（Multi-turn error-feedback）后，所有模型的执行率均飙升至 97%-100% 。
例如，Gemini 3 Flash 的执行率从 54.7% 跃升至 93.6% ，提升幅度高达 +20.8% 。
2. 思考预算（Thinking Budget）对轻量模型更有效增加推理步数对轻量级模型帮助巨大。
- Gemini 3.1 Flash Lite：从 minimal 到 high thinking budget，执行率提升了约 19 个百分点。
- Pro 级模型（如 GPT-5.5）：提升不到 5 个百分点，因为它们在预训练阶段已经记住了正确的 API 用法。
3. Agent 框架能跑通代码，但难改几何结构使用原生 Coding-Agent Harness（如 Claude Code, Codex CLI）后，执行率确实达到了天花板。
但在条件形状质量（Conditional Shape Quality）上，Agent 模式与单次生成几乎无差异。
- SigLIP-2 视图相似度平均变化仅为 -0.010。
- Chamfer Distance 变化仅为 +0.001。
这说明： 目前的 Agent 擅长修语法错误，但不擅长通过视觉反馈去优化复杂的几何拓扑结构。
4. 自动化指标与人类偏好高度相关论文验证了 SigLIP-2 视图相似度是预测人类偏好的最强指标（Pearson r=0.964r = 0.964 0.964 ）。这意味着我们可以用廉价的自动化指标替代昂贵的人工投票，极大地降低了评测成本。
### 工程启示对于正在构建 3D Agent 的工程师，这篇论文给出了明确的落地建议：
- 不要迷信单次生成：必须设计“执行-报错-重试”的闭环。简单的 traceback 反馈就能让执行率提升 20%+，ROI 极高。
- 区分模型能力分配资源：对轻量模型加大 Thinking Budget；对 Pro 级模型，节省 Token 用于其他逻辑推理。
- 几何理解仍是短板：即使代码能跑通，生成的 3D 物体常出现部件断裂、漂浮等问题。未来的微调（SFT）数据应重点包含“视觉自我批评”和“几何修正”的案例。
- 利用自动化指标做快速迭代：SigLIP-2 和 DINOv3 可以作为日常开发的 Proxy Metric，无需频繁启动人工评测平台。
### 局限与展望目前 3DCodeBench 主要关注单体对象生成，尚未覆盖多资产场景组合（Scene Composition）。此外，基准主要基于 Blender API，未来需扩展至 Houdini 或 Unreal Engine 以验证模型的泛化能力。
总之，VLM 写 3D 代码已不再是“能不能做”的问题，而是“如何让它更物理合理”的问题。工程落地的关键，在于构建一个能提供高保真几何反馈的执行环境。
