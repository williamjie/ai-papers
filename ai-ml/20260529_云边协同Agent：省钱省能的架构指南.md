论文 : When Cloud Agents Meet Device Agents: Lessons from Hybrid Multi-Agent Systems链接 : https://arxiv.org/abs/2605.30102Agent 落地最痛的点是什么？不是模型不够聪明，而是 贵 。
长期运行的 Agent 任务（如深度搜索、UI 自动化）会消耗海量 Token。如果全堆在云端 Frontier 模型上，账单会让人肉痛；如果全放在端侧小模型（SLM）上，效果又往往拉胯。这篇来自高通 AI 研究的论文，系统性地拆解了“云+边”混合多智能体系统的架构设计，给出了非常落地的工程建议。
### 痛点：单一部署的困境目前的 Agent 部署两极分化严重：
- 纯云端：性能强，但 API 成本高，且存在隐私顾虑。
- 纯端侧：成本低、隐私好，但受限于 DRAM 和 KV Cache，难以处理长上下文，且小模型在复杂推理上容易“幻觉”。
论文的核心洞察是： 混合架构（Hybrid MAS）不是简单的路由切换，而是角色分工。 关键在于如何将昂贵的云端算力用于“高价值决策”，而将廉价的端侧算力用于“高频执行”。
### 方法拆解：两种核心架构作者设计了两种典型的云边协同架构，分别对应不同的协作逻辑：
-PEVR（Plan-Execute-Verify-Replan）：
角色：云端 Supervisor 负责制定初始计划并定期校验；端侧 Executor 负责执行。
- 机制：如果发现偏离计划，云端介入重新规划（Replan）。
- 直觉：适合强依赖结构化步骤的任务，通过严格的计划约束来保证准确性。
-EVA（Execute-Verify-Advise）：
角色：端侧 Executor 直接接收查询并开始执行；云端 Supervisor 定期观察进度。
- 机制：发现问题时，云端不重做计划，而是提供总结和建议（Advice），并重置端侧上下文。
- 直觉：适合探索性任务，通过轻量级的反馈和上下文重置来节省资源。
⚠️ 关键设计细节 ：两种架构都引入了 上下文重置（Context Reset） 。每当云端介入时，端侧的历史对话会被总结或丢弃。这不仅防止了 KV Cache 无限增长导致的 OOM，还缓解了长上下文中的“迷失中间”问题。
### 实验结果：没有银弹，只有权衡作者在 HotpotQA、FanOutQA 和 AppWorld 三个基准上进行了测试，使用 GPT-4o 作为云端模型，Qwen3 系列（4B/8B/14B/32B）作为端侧模型。
核心发现 1：架构选择高度依赖任务类型- UI 辅助任务（AppWorld）：PEVR 完胜。因为 UI 操作具有状态性，错误的早期动作会导致不可逆后果。PEVR 的严格计划能显著降低错误率。
- 深度搜索任务（FanOutQA/HotpotQA）：EVA 更优。搜索任务需要广泛的探索，PEVR 过于频繁的“重新规划”会打断推理链条，导致性能下降甚至不如纯端侧基线。
核心发现 2：云端算力并非越多越好- 增加云端监督频率（缩短验证间隔）并不总是提升性能。
- 在 FanOutQA 上，过高的干预频率会导致执行器频繁重启，反而降低了准确率。存在一个最优的“监督稀疏度”。
核心发现 3：混合架构显著降低资源消耗- KV Cache 控制：在 AppWorld 中，随着步数增加到 80 步，纯端侧模型的 KV Cache 占用从 5.17GB 激增至 13.12GB（Qwen3-8B）。而 PEVR 架构通过定期重置上下文，将峰值内存控制在 3.82GB 左右。
- 成本效益：混合系统在保持甚至提升准确率的同时，云端 API 成本和端侧能耗均显著低于纯云端方案。

- 不要盲目上“大模型监督”：如果你的任务是开放域搜索或创意生成，采用 EVA 式的“顾问”模式，让端侧模型自主执行，云端只做偶尔的纠偏。
- 状态敏感任务必须“强计划”：涉及数据库操作、UI 点击等不可逆动作时，务必使用 PEVR 模式，由云端生成详细的 Step-by-Step 计划。
- 上下文管理是核心：在端侧部署 Agent 时，KV Cache 是瓶颈。利用云端介入的机会进行“总结+重置”，是解决长任务内存溢出的有效手段。
- 反向架构不可行：论文测试了“云端执行+端侧监督”的对称架构，结果发现这既慢又贵，且效果更差。执行必须在端侧，监督必须在云端。
### 局限与展望目前的研究基于固定的模型组合（GPT-4o + Qwen3）。未来更具潜力的方向是 动态路由 ：根据任务的实时难度和类型，自动选择 PEVR 或 EVA 架构，甚至动态调整监督频率。这将是构建通用型混合 Agent 系统的关键一步。
