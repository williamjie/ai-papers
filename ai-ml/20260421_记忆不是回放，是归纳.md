# 记忆不是回放，是归纳

**日期**: 2026-04-21

---

论文 : Latent Preference Modeling for Cross-Session Personalized Tool Calling链接 : https://arxiv.org/abs/260604.17886做 Agent 的都应该遇到过这种场景：用户说”订个航班”，你没问他舱位，但他上次订酒店选了最便宜的，上次租车选了紧凑型。这时候 Agent 是该傻乎乎地反问，还是该”懂他”？
汉阳大学的这篇论文认为： 个性化不是记忆检索，而是偏好推理。
他们提出了 MPT benchmark 和 PR EFINE 方法，核心观点很直接——用户的偏好不是静态档案，而是需要通过”提出假设 → 验证 → 修正”循环逐步收敛的 潜在约束（Latent Preference） 。
## 问题在哪：现有方案只做了”回放”
现在主流做法就两类：
- 全历史 Prompting：把过去所有对话塞进去让模型自己找规律。问题是 token 爆炸，而且模型经常抓不住重点，把一次性行为当成永久偏好。
- RAG / 摘要式记忆：检索相似历史或存储摘要。问题是——检索只能做”同域复用”，一旦跨域就不行了。
论文里给了个直观例子：用户多次在餐厅选了 cheap、在景点选了 free_entry、在租车选了 Compact。这些看起来是不同领域，但背后有一个统一的偏好约束——“预算敏感”。全历史 Prompting 和 RAG 很难抽象出这种跨域一致性，因为它们本质上是 行为复用 ，不是 偏好推理 。
## 方法拆解：把偏好当”可证伪的假设”
PR EFINE 的核心设计直觉很有意思： 不把记忆当数据库，当 hypotheses。
### Generate-Verify-Refine 循环每到一个新会话，PR EFINE 做三件事：
- 生成（Generate）：基于当前对话和之前接受的记忆，提出候选偏好假设。比如”用户偏好经济型选项”。
- 验证（Verify）：用四个条件过滤——证据支持：有没有多轮一致的行为支撑？
- 抽象质量：是不是过度具体化（比如只针对某个具体 API 的某个 slot）？
- 可操作性：能不能指导未来工具调用？
- 时序一致性：和最近的稳定行为模式矛盾吗？
- 修正（Refine）：被拒绝的假设返回给 Generator 重写，通过后才更新到记忆。
会话 行为 初始假设 验证结果 修正后 s1 选评分6的电影 ”偏好中等评分电影” ❌ 过度具体 — s2 查天气 ”偏好电影内容” ❌ 证据不足 — s3 租车选Standard+餐厅选Cheap ”跨域偏好经济简单选项” ✅ 接受 s4 酒店选1星 ”预算敏感+简洁交互风格” ✅ 接受你看，前两轮的假设都被拒了——要么太具体，要么证据不够。到第三轮跨域信号出现，才收敛成一个稳定的偏好记忆。这个设计的关键 insight 是： 单一会话永远不足以确定偏好，偏好记忆应该是可修正的信念，不是不可变的记录。
### Schema-Agnostic：记忆跟 API 解耦PR EFINE 存的不是 API 签名，而是抽象的偏好约束。比如存的不是 flight_class=Economy ，而是”偏好经济型选项”。具体映射到哪个 slot、哪个值，留到推理时再根据当前 schema 落地。
这意味着： 今天用一套 API 构建的记忆，明天 API 改名、换 schema 了，照样能用。 论文在 §7.5 验证了这点——在完全 unseen 的 API 域上，GPT-5 的 P-EM 从 3.75% 提升到 47.00%。

## 工程启示- 记忆应该做”抽象”，不做”存储”。把用户行为翻译成可复用的约束，比存原始对话有用得多。
- Generate-Verify-Refine 不是 over-engineering。论文证明，不加验证直接存假设，会把 session-specific 的一次性行为当成永久偏好，反而降低准确率。
- Schema-Agnostic 是个实用的设计。API 接口会变，但”用户想要便宜还是贵”这种偏好不会变。把偏好和具体 API 解耦，记忆才有长期价值。
- Token 预算有限时，用 PR EFINE 的思路做记忆压缩，收益远超简单截断历史。
## 局限论文也坦诚了几个边界：
- 有些模型会过度保守。比如 R1-Distill-Llama-8B 在 PR EFINE 下预测的参数更少（3.34 → 2.85），导致 EA-F1 下降。 tighter 的动作空间对齐是以 recall 换 precision 的 trade-off。
- Preference Transfer 仍然依赖推理模型的”应用”能力。PR EFINE 提供了好的记忆，但模型能不能在新场景里正确应用，还是取决于模型本身。Transfer 的提升幅度在不同 backbone 之间差异较大。
- 只评估了测试时方法，没做微调。如果结合 SFT 会不会更好？论文没说，但值得一试。
