# 从文本拼接到结构化查询：SLIDERS 如何解决超长文档问答的聚合瓶颈

**日期**: 2026-04-27

---

论文 : Contexts are Never Long Enough: Structured Reasoning for Scalable Question Answering over Long Document Sets链接 : https://arxiv.org/abs/2604.22294工程上处理长文档问答，大家现在基本都在做两件事：要么把上下文窗口扯到百万 token，要么把文档切片后靠 RAG 拼接。但 Stanford 这篇论文指出了一个扎心事实—— 这些方案其实都没 touches 到真正的痛点 。
为什么？因为当你把 100 个文档切成 500 个 chunk，让 LLM 从每个 chunk 里抽信息，最后还是要面对一个问题： 怎么把这 500 份碎片化的提取结果拼成一个 coherent 的答案？
这就是论文里说的 “Aggregation Bottleneck”（聚合瓶颈） 。你只是把”长上下文问题”换了个马甲，从”一次读不完”变成了”一次合不完”。更麻烦的是，LLM 在自由文本里做数值比较、去重、冲突消解，经常翻车——幻觉、单位混乱、重复计数，全是 audit 地狱。
SLIDERS 的核心 insight 很干脆： 别让 LLM 在文本里推理，让它在数据库里查询 。把文档先抽成结构化表，然后用 SQL 做聚合。听起来简单，但工程细节全是魔鬼。
## 五步 pipeline：从文档到答案整个框架分五个阶段，每一步都在解决一个实际工程问题：
### 1. Contextualized Chunking（上下文感知分块）
文档切片不能乱切。如果把表格 header 从表格 body 分开，提取时肯定出问题。SLIDERS 先给每个文档生成元数据：文档标题、简短描述、结构标签（章节标题、表格、图表说明）。然后基于这些元数据做语义感知的切分，保证每个 chunk 是自包含的。
为什么重要 ？后续 extraction 阶段每个 chunk 要独立处理，如果上下文丢失，提取结果会变成无法解释的碎片。
### 2. Schema Induction（模式推断）
关系数据库需要 rigid schema，但每个问题需要的字段不一样。SLIDERS 有个 schema library，根据问题类型（Ordering / Multiple Choice / Others）和文档类型（Narration / Policy / Dataset）动态生成 schema。
一个字段不只是个名字，而是五个属性的组合：字段名、语义描述、数据类型、单位、量级、归一化规则。比如 accounts_payable 要明确是 float、单位是 USD、量级是 thousands。 这样后续 SQL 才能做数学运算 。
### 3. Structured Extraction with Relevance Gating（带相关性门控的结构化提取）
这里是第一个关键技术细节。SLIDERS 发现，如果直接用 in-context learning 按 schema 抽数据，LLM 会 幻觉 ——哪怕 chunk 里根本没有相关信息，它也会编一个符合类型要求的值出来。
所以加了 两阶段 gate ：先让模型判断这个 chunk 是否包含与 schema 相关的证据，通过了才执行正式提取。实验数据很亮眼：516 个 chunk 里，门控 rejecting 了 282 个， 只产生 1 个 false negative（漏检） 。这说明 gate 基本不伤害 recall，主要作用是 precision 过滤 。
提取结果也不是纯文本，每个字段都打包三元组： <value, provenance, rationale> 。provenance 是支撑该值的最小文本片段，rationale 是模型怎么从 quote 推到 value 的决策过程。 这是后续 reconciliation 的证据基础 。
### 4. Data Reconciliation（数据协调）
这是 SLIDERS 最核心的模块。独立提取的表往往充满：重复行、冲突值、部分信息缺失的行。传统方案可能让 LLM 直接看所有行做 pairwise 比较——复杂度 O(n²)，1000 行就得比 50 万对，根本不可扩展。
SLIDERS 的 insight 是： 关系型结构本身就提供了降维线索 。相同实体或主张的陈述，通常由共同的识别属性锚定。这些就是 主键（Primary Key） 。
Reconciliation 分两阶段：
Phase 1 - Partitioning（划分）
- 让 LLM 根据问题和表样本选出主键（三次投票取多数，robust）
- 用主键做实体对齐（比如 “J. Smith” 和 “John Smith” 归一）
- 按主键 group by，每个 group 成为独立处理单元Phase 2 - Agent-based Reconciliation（基于代理的协调）
对每个 group，一个 SQL-coding agent 干三件事：
- Deduplication（去重）：语义相同但表述不同的行，选最精确的保留- Conflict Resolution（冲突消解）：对同一属性竞争的值，根据 provenance 和 rationale 选支撑最强的- Consolidation（合并）：部分行贡献互补属性，合并成完整记录关键是 所有操作都生成 SQL ，可审计、可复现。agent 会先选操作类型，再生成对应的 SQL 语句，执行后更新表。非主键列的实体解析作为最后一步。
### 5. Question Answering via SQL（基于 SQL 的问答）
到这一步，数据库是干净、一致、可查询的了。问答阶段不再是让 LLM 生成自由文本，而是 让 LLM 写 SQL ，在数据库上做确定性查询。可以迭代：执行、看结果、 refin e查询，直到满意。

## 工程启示：这对我们做本地 Agent 有什么用？
SLIDERS 设计的每个决策都指向一个工程现实问题：
-别迷信长上下文：即使你有 1M token 窗口，让 LLM 在里面做跨文档聚合依然是高幻觉、高成本、不可审计的。结构化存储 + 确定性查询的分离架构更稳健。
-Provenance 是第一等公民：每个 extracted value 都带 quote 和 rationale，不只是为了 audit——在 reconciliation 阶段，这就是消解冲突的客观证据，比让 LLM 猜哪个值更可信靠谱得多。
-主键思维是降维的关键：O(n²) 的 pairwise 比较在数据量增长时迅速爆炸。识别主键、按主键 group，能把问题分解成独立子问题，天然支持并行。这是数据库思维对 LLM 盲目堆算力的降维打击。
-开放模型也能打：SLIDERS 配上 Qwen3.5-122B，在 Oolong 上从 24.89 飙升到 68.00，+43 分。这说明框架收益和 base model 能力正交——正确的架构能释放现有模型的潜力，不一定要追最新 frontier model。
-成本可预测：extraction 和 reconciliation 的一次性成本，换来了后续任意数量问题的零边际成本。在需要多轮问答的场景（比如分析师探索同一份财报的多个指标），这是压倒性优势。
## 局限与下一步论文也诚实列出了短板：
- 主观判断问题处理不好：需要人类常识或价值判断的 query，框架无能为力- 术语歧义：比如 fiscal year vs calendar year，需要领域知识注入- Gold answer 可能有错：他们发现某些标注答案本身值错了、单位错了，或者遗漏跨文档信息——这提醒我们，benchmark 也不是绝对真理后续方向论文提了几个：更灵活的 schema 学习、跨语言文档处理、多模态扩展。但我觉得最有意思的是： 这个范式天然适合做”数据引擎” ——把海量文档转化成结构化事实库，再喂给更小的模型做监督微调（SFT）或检索。毕竟，100 篇 10-Q 抽出来的结构化数据，本身就是一份高质量的金融问答 fine-tuning 数据集。
## 一句话总结SLIDERS 证明： 超长文档问答的 scaling law，不在上下文长度，而在结构化存储与查询 。当别人还在拼谁的上下文更长时，Stanford 已经把数据库搬进了 LLM pipeline——这大概就是工程思维对参数堆砌的温柔秒杀。
