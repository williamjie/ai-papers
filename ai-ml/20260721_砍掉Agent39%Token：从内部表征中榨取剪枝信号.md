# ⭐⭐ 砍掉 Agent 39% Token：从内部表征中榨取剪枝信号

**日期**: 2026-07-21

---

论文 : SWE-Pruner Pro: The Coder LLM Already Knows What to Prune链接 : https://arxiv.org/abs/2607.18213多轮编程 Agent 的上下文膨胀是个老问题，但大多数剪枝方案都显得“笨重”。要么引入额外的评分模型，要么让 Agent 自己写意图提示（Goal Hint）。这篇来自上海交大与抖音团队的论文提出了一个反直觉的观点： Agent 在读取工具输出时，其内部隐藏状态已经编码了哪些代码行重要、哪些可以丢弃。
不需要外挂模型，不需要额外推理步骤。只需加一个极轻量的分类头（Head），直接从 Backbone 的 Prefill 阶段“偷”出剪枝信号。结果不仅省下了高达 39% 的 Token，甚至在某些长上下文任务上提升了准确率。
### 痛点：现有方案为何不够优雅？
在 SWE-Bench Verified 等基准测试中，文件读取命令（如 cat , grep ）产生的原始文本占据了 Agent 消耗 Token 的 70% 以上。这些内容大多冗余，且随着多轮交互不断累积，导致上下文窗口迅速溢出，引发“迷失中间”现象。
现有的两条主流路径都有明显缺陷：
- 通用压缩（如 LLMLingua2）：基于困惑度或句法结构评分，完全无视 Agent 当前的任务意图，容易误删关键逻辑。
- 专用剪枝（如 SWE-Pruner）：虽然考虑了意图，但需要 Agent 每轮显式生成一个 Goal Hint，并调用第二个模型进行评分。这引入了额外的延迟和成本，且破坏了 Agent 的自主性。
### 核心 Insight：信号就在隐藏层里作者的核心假设是：当 Backbone 处理工具输出（Tool Output）时，它必须通过注意力机制理解哪些行对下一步动作至关重要。因此， 保留或剪枝的信号必然存在于最后一层的隐藏状态（Hidden States）中 。
为了验证这一点，他们冻结了 Qwen3-Coder-Next，提取工具输出每行的隐藏状态均值，并训练一个简单的逻辑回归探针。结果显示，保留行和剪枝行在潜在空间中是线性可分的，AUC 达到 0.83 ，远超随机猜测。这证明了“剪枝信号”早已存在于模型内部，无需外部重构。
### 方法拆解：SWE-Pruner Pro 的设计直觉基于上述发现，SWE-Pruner Pro 设计了两个关键组件，直接挂载在 Agent 的推理引擎中：
-长度感知嵌入（Length-aware Embedding）
Why：误删 5 行代码中的 1 行是灾难性的，但在 300 行中误删 1 行几乎无感。传统的静态映射无法处理这种非均匀代价。
- How：引入一个基于行数 NN 的学习嵌入向量 e(N)e(N)，加到每个 Token 的隐藏状态上。这让剪枝头能根据输出长度动态调整阈值。
-样本平衡焦点损失（Per-sample Balanced Focal Loss）
Why：保留行的比例极低（约 30%），常规交叉熵会过度拟合多数类（剪枝行）。且不同样本的保留率差异巨大，全局重加权无效。
- How：在每个样本内部，分别计算保留类和剪枝类的损失并平均。这确保了即使只有 3 行被保留，它们的信号权重也不会被稀释。
工程实现亮点 ：剪枝头在 Agent Prefill 新工具输出时同步运行，复用已计算的隐藏状态，无需额外前向传播。仅在下一轮生成前替换上下文，开销极小。
### 关键结果：省钱又提效作者在两个开源 Backbone（MiMo-V2-Flash, Qwen3-Coder-Next）和四个基准上进行了评估。数据非常硬核：

对比其他方法（如 LLMLingua2, SWE-Pruner），SWE-Pruner Pro 是唯一在 所有 设置下均能减少 Token 消耗且保持质量的方法。LLMLingua2 在 Oolong 上甚至导致 Token 增加 190% ，因为压缩后的语义噪声反而增加了后续推理负担。
⚠️ 反直觉发现 ：在 MiMo-V2-Flash 上，剪枝不仅没降低 SWE-Bench Verified 的解决率，反而提升了 3.8% 。这说明去除冗余上下文实际上帮助模型更聚焦于关键信息，缓解了长上下文退化。
### 工程启示与局限对工程实践的指导意义：
- 拒绝外挂：不要为 Agent 构建复杂的“剪枝微服务”。利用推理引擎内部暴露的隐藏状态，以极低成本实现实时剪枝。
- 长度感知至关重要：在处理代码或长文本时，静态阈值是危险的。必须让模型知道“当前上下文有多长”，才能动态平衡召回率与精确率。
- 损失函数设计：处理极度不平衡的细粒度标签时，样本内平衡（Per-sample balancing）比全局重加权更有效。
局限性与展望：
- 依赖开放权重：目前方法需要访问 Backbone 的隐藏状态，闭源 API（如 GPT-4o）无法直接应用此架构，除非未来 API 支持暴露中间层。
- API 调用次数：在部分 Backbone 上，剪枝后 Agent 可能需要更多轮次交互来确认信息，导致 API 调用次数略微增加（如 Qwen3-Coder-Next 从 131.9 增至 139.8），但总 Token 成本仍大幅下降。
这篇论文展示了一种更“原生”的上下文管理范式： 信任模型自身的表征能力，而非强行附加外部规则。 对于构建低成本、高性能的代码 Agent，这是一个值得深入落地的方向。
