# ⭐⭐⭐½ 代码执行是LLM修Bug的刚需吗？

**日期**: 2026-06-30

---

论文 : To Run or Not to Run: Analyzing the Cost-Effectiveness of Code Execution in LLM-Based Program Repair链接 : https://arxiv.org/abs/2606.26978现在的 LLM 编程 Agent（如 SWE-agent, OpenHands）几乎都标配了“生成-运行-修正”的循环范式。我们默认代码执行是修 Bug 的核心反馈机制，但很少有人停下来算过这笔账：为了这点反馈，我们付出的 Token 成本、等待时间以及环境维护开销，到底值不值？
这篇来自北航和新加坡管理大学的论文直接给出了一个反直觉的答案： 对于当前最强的商业模型，禁止代码执行几乎不影响修 Bug 的成功率，却能省下一半以上的钱和时间。
### 现有方案的痛点：昂贵的“伪反馈”
目前的 Agent 架构中，代码执行被视为不可或缺的环节。Agent 运行测试用例，根据报错信息调整补丁。但这带来了三个巨大的工程负担：
- Token 爆炸：测试日志和堆栈跟踪往往冗长，挤占上下文窗口。
- 高延迟：编译和运行测试套件可能需要数分钟甚至数小时。
- 环境地狱：每个项目都需要维护独立的 Docker 镜像和依赖环境，扩展性极差。
如果执行带来的收益微乎其微，这些成本就是纯粹的浪费。
### 核心洞察：隔离变量，量化边际价值以往的研究（如 Agentless）通过移除整个 Agent 循环来证明“无执行”也能修 Bug，但这混淆了“多轮对话”和“代码执行”两个变量。
本文的核心设计直觉在于 控制变量法 。研究者固定了 Agent 的底层框架（Claude Code, Codex, OpenCode），仅改变对代码执行的访问权限，设计了四种范式：
- Prohibited（禁止）：通过 Prompt 和环境隔离，彻底切断测试运行能力。
- Quota-Limited（配额限制）：允许执行，但设定严格的次数预算（K=1 或 K=3）。
- Budget-Guided（成本引导）：允许执行，但提示 Agent 考虑成本。
- Unrestricted（无限制）：标准模式，随意运行测试。
这种设计能精准测量出“代码执行”这一单一动作的边际贡献。
### 关键结果：禁止执行，性能不减反升？
研究者在 SWE-bench Lite 和 Verified 的前 100 个实例上进行了 3,000 次端到端实验。数据非常震撼：
Agent 数据集 Prohibited (禁止) Unrestricted (无限制) 差异 Claude Code Lite 63.0% 64.0% -1.0pp Claude Code Verified 64.0% 67.0% -3.0pp Codex Lite 74.0% 73.0% +1.0pp Codex Verified 73.0% 75.0% -2.0pp OpenCode Lite 7.0% 6.0% +1.0pp⚠️ 反直觉发现 ：在商业 Agent（Claude Code, Codex）上，禁止执行与无限制的修复率差距平均仅为 1.25 个百分点 ，且统计检验显示无显著差异（p > 0.05）。更有趣的是，Codex 在禁止执行模式下甚至表现更好。
成本对比更悬殊：
- Token 消耗：Prohibited 模式节省了 56–62% 的 Token。
- 耗时：节省了 48–54% 的墙钟时间。
- 环境维护：完全消除了为每个仓库配置测试环境的工程税。
### 为什么执行没用？深度归因如果执行没用，为什么 Agent 还在疯狂跑测试？论文分析了 7,745 条公开 Trace，发现了两个关键原因：
- 定位能力过剩：现代 LLM 的代码理解能力极强。在 Prohibited 模式下，Agent 的定位准确率（Localization Accuracy）依然保持在 95% 以上。这意味着 Agent 不需要通过运行代码来“猜”哪里错了，它读代码就知道。
- 反馈质量低：仅 48.8% 的复现执行能提供可操作的反馈。大量执行要么直接报错（环境配置问题），要么产生无关噪音。
此外， 54–66% 的商业 Agent 案例在单次编辑后就直接完成了，根本没有利用执行反馈进行迭代的空间。对于失败的案例， 81–100% 的失败是因为 Agent 自测通过了但官方评测没通过，这说明执行反馈存在严重的“幻觉”或测试覆盖不足，并未真正帮助修正错误。
### 工程启示：重构你的 Agent 策略这篇论文对实际落地有极强的指导意义：
- 对于商业模型用户：如果你使用 Claude Sonnet 4.5 或 GPT-4o 级别的模型进行代码修复，大胆禁用代码执行。这不仅省钱，还能避免环境依赖的地狱。让模型专注于“阅读-推理-生成”，而不是“试错”。
- 对于开源小模型：情况不同。OpenCode (Qwen2.5-Coder-32B) 在 Quota-1（仅允许 1 次执行）模式下表现最佳，因为小模型需要那一点点真实反馈来校准上下文，防止幻觉失控。
- 执行应作为资源而非默认能力：不要无脑开启 execute 权限。应将其视为一种高成本工具，仅在模型置信度低或定位模糊时触发。
### 局限与展望研究主要聚焦于 Python 生态和 SWE-bench 数据集，其他语言（如 C++、Java）的编译反馈机制可能不同，结论需进一步验证。此外，对于需要复杂运行时状态调试的 Bug（如并发竞态条件），纯静态分析可能依然不足。
但毫无疑问，这篇论文打破了“执行即正义”的迷思。在 LLM 能力飞速提升的今天，我们或许该重新审视那些习以为常的工程范式： 有时候，不做比做更有效。
