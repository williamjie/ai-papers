# 用 YAML 重写 Agent 工作流

**日期**: 2026-04-22

---

论文 : AgentSPEX: An Agent SPecification and EXecution Language链接 : https://arxiv.org/abs/2604.13346最近 Agent 框架卷得厉害，但大家似乎都在重复造轮子：要么靠 ReAct 式的 Prompt 让模型“看着办”，要么用 LangGraph 这种强耦合 Python 代码的框架。这两条路都有硬伤：前者不可控，后者维护成本高且门槛高。
伊利诺伊大学香槟分校（UIUC）刚发的这篇 AgentSPEX，试图走中间路线： 用声明式 YAML 定义 Agent 工作流，用强类型的环境执行 。它的核心直觉很直接：把控制流从 Prompt 里剥离出来，交给解释器。
## 痛点：Prompt 里的“黑盒”与 Python 里的“枷锁”
现在的 Agent 系统主要分两派。
一派是“原生派”（如早期的 ReAct），靠一个大 System Prompt 引导模型自我推理、调用工具。简单是简单，但一旦任务变长，模型很容易迷失，而且结果不可复现。
另一派是“框架派”（如 LangGraph, DSPy, CrewAI）。它们引入了图结构和状态管理，确实更可控。但代价是，工作流逻辑被死死绑定在 Python 代码里。你想改个分支逻辑？得写代码、跑测试、修 Bug。对领域专家来说，门槛太高。
AgentSPEX 的切入点很聪明： 工作流应该是“可执行规范”（Executable Specification），而不是“执行代码” 。
## 核心设计：YAML + 显式状态管理AgentSPEX 的语言结构非常简单，核心就是几个关键词：
- task: 开启一段新的对话（无历史上下文）。
- step: 维持多轮交互（保留历史）。
- call: 调用子模块（Submodule），支持复用。
- if/switch/while/for_each: 标准控制流。
- parallel/gather: 并行执行。
关键 Insight 在于它的 上下文管理（Context Management） 。
在 ReAct 模式下，模型必须自己记住之前发生了什么，随着对话变长，Context Rot（上下文退化）是必然的。而 AgentSPEX 允许用户在每一步明确指定： “这一步只能看到变量 A，不能看到变量 B” 。
这种 显式的状态注入 ，直接减轻了模型的推理负担，也提高了结果的可控性。
## 执行引擎：沙箱与可视化光有 YAML 不够，还得有引擎跑。AgentSPEX 的 Harness 提供了：
- Docker 沙箱: 隔离执行环境，支持文件、浏览器、代码执行。
- Checkpointing: 每一步执行完都存盘，断了可以接着跑。
- Trace Replay: 修改某个 Prompt 后，只重放受影响的步骤，不用从头跑。
- 双向可视化编辑器: 左边是 YAML，右边是流程图，改一处同步刷新。
这个编辑器对于调试 Agent 工作流非常实用，毕竟看代码改图比看图改代码要直观得多。
## 实验结果：结构化真的能赢？
论文在 7 个基准测试上做了对比，主要基线是 CoT（纯思维链）和 ReAct（带工具调用的 React）。
基准测试 领域 CoT ReAct AgentSPEX 提升 SciBench 科学 85.92% 87.79% 90.61% +2.8% StemEZ 科学 82.87% 84.72% 86.57% +1.9% ChemBench 化学 78.90% 77.80% 83.30% +5.5% AIME 2025 数学 94.60% 99.60% 100.0% +0.4% ELAIPBench 论文理解 37.22% 33.80% 43.70% +6.5% WritingBench 写作 79.90% 80.30% 81.00% +0.7% SWE-Bench 软件工程 - 76.2% 77.1% +0.9%几个值得注意的点：
- 在长文本理解任务（ELAIPBench）上，AgentSPEX 大幅领先（+6.5%）。这直接验证了显式上下文管理的价值——模型不需要在几千字的上下文里“大海捞针”。
- ReAct 有时比 CoT 还差。在 ChemBench 和 ELAIPBench 上，ReAct 甚至低于 CoT。论文认为这是因为模型既要处理任务逻辑，又要解析工作流结构，负担过重。而 AgentSPEX 把结构解析交给了引擎，模型只需专注当前步骤。
- SWE-Bench 也有小幅提升，说明在代码生成场景下，结构化工作流依然有效。
## 用户研究：非程序员更喜欢谁？
论文还做了一个对比 LangGraph 的用户研究。23 名参与者中，大部分人认为 AgentSPEX 更易读、更易上手 ，特别适合非编程背景的领域专家。而 LangGraph 则在“复杂工作流定制”上获得更高评价。
这说明 AgentSPEX 的定位很清晰： 它不是要取代 LangGraph 这种给硬核开发者用的框架，而是要填补“低代码/无代码 Agent 编排”的空白 。
## 局限与展望当然，AgentSPEX 也不是银弹。论文承认，在极度复杂的嵌套逻辑中，YAML 的可读性可能不如代码直观。此外，目前的验证主要依赖解释器，未来的方向包括引入形式化验证（如 Lean 或 Isabelle）来保证工作流的正确性。
## 工程启示对于做 Agent 应用的同学，这篇论文最值得借鉴的不是 YAML 语法本身，而是**“控制流与推理分离”**的思想。
如果你的 Agent 经常因为上下文太长而翻车，或者因为逻辑分支太多而变得不可维护，不妨试试把工作流抽离出来，用更结构化的方式管理状态。哪怕不用 AgentSPEX，这种“显式状态管理”的思路也值得参考。
