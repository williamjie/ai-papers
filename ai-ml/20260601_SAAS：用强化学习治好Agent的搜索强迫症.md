# ⭐⭐⭐½ SAAS：用强化学习治好Agent的搜索强迫症

**日期**: 2026-06-01

---

论文 : SAAS: Self-Aware Reinforcement Learning for Over-Search Mitigation in Agentic Search链接 : https://arxiv.org/abs/2605.29796做 RAG 或 Agent 开发的工程师应该都遇到过这种场景：用户问了一个模型完全知道答案的简单问题，Agent 却非要调用搜索工具，甚至为了凑数连续搜三次。
这不仅浪费 Token 和 API 费用，更致命的是引入了延迟和噪声证据。这篇来自厦门大学的论文 SAAS，直接瞄准了 Agentic Search 中的“过度搜索”顽疾，提出了一套基于强化学习（Reinforcement Learning, RL）的解决方案。
它的核心价值在于：不牺牲准确率的前提下，让 Agent 学会“知止”，大幅降低搜索频率。
### 现有方案的痛点：静态规则行不通在 SAAS 之前，解决过度搜索主要有两派思路：Prompt 工程和固定惩罚。
Prompt 类方法（如 DRAGIN）试图通过提示词约束行为，但不改模型参数，效果有限。RL 类方法（如 StepSearch, HiPRAG）则尝试给搜索动作加惩罚。但作者发现，直接加固定惩罚会导致严重的“奖励黑客”（Reward Hacking）。
⚠️ 关键洞察 ：现有的静态惩罚无法区分“克制”和“偷懒”。模型为了避罚，可能会连必要的搜索也放弃，导致准确率崩塌。
更深层的问题是，Agent 的知识边界是动态的。随着训练进行，原本需要搜索的问题可能变得可以直接回答。如果奖励信号不能随策略演化而调整，优化就会失效。
### 方法拆解：让 Agent 拥有“自我意识”
SAAS 的核心直觉是：不要预设搜索边界，而是让模型在训练中动态感知自己的知识边界。它包含三个关键组件：
-搜索边界建模（Search Boundary Modeling）
这是最精彩的设计。对于每个问题，作者并行生成两组轨迹：一组禁止搜索（仅靠内部知识），另一组允许搜索。
如果禁止搜索也能答对，说明该问题在模型“舒适区”，标记为 NO SEARCH。
- 如果只有搜索才能答对，标记为 NEED SEARCH。
这种对比机制让奖励信号紧跟模型能力的演化，而不是死守静态标签。
-边界感知奖励（Boundary-Aware Reward）
根据上述分类，施加差异化的惩罚：
对于 NO SEARCH 问题：零容忍，每搜一次都重罚。
- 对于 NEED SEARCH 问题：引入 NminN_{min}​（最少必要搜索次数），只惩罚超过 NminN_{min}​ 的冗余搜索。
这种设计既防止了不必要的搜索，又保护了必要的信息获取过程。
-分阶段优化（Stage-wise Optimization）
为了防止模型在还没学会怎么用工具时就因为害怕惩罚而“躺平”，训练分为两阶段：
阶段一：只给结果奖励，让模型充分探索搜索工具的价值。
- 阶段二：激活边界感知奖励，开始修剪冗余行为。
### 关键结果：准确率不降，搜索减半作者在 Qwen2.5-3B 和 7B 上进行了广泛测试，结果非常硬核。
1. 搜索效率大幅提升在 Qwen2.5-3B 上，SAAS 的平均搜索次数（SC）降至 1.13 。
相比之下，强基线 StepSearch 需要 1.69 次，HiPRAG 需要 2.19 次。
这意味着 SAAS 减少了约 40% 的搜索调用，直接节省了推理成本和延迟。
2. 准确率不仅没降，反而更高在 Qwen2.5-3B 上，SAAS 的平均准确率达到 45.8% ，超越了最强的基线 HiPRAG（43.6%）。
在多跳任务 Bamboogle 上，优势更明显：SAAS 达到 49.6%，比 HiPRAG 高出 8.0% 。
3. 过度搜索指标显著改善论文引入了两个新指标：问题级过度搜索率（QOR）和步骤级冗余搜索率（SOR）。
在 Qwen2.5-7B 上，SAAS 的平均 SOR 仅为 6.3% ，而 StepSearch 高达 24.3%。这说明 SAAS 确实学会了“见好就收”，而不是盲目堆砌搜索步骤。
### 工程启示与局限对实际落地的指导意义：
- 动态边界优于静态规则：在微调 Agent 时，不要硬编码“最多搜几次”，而是通过对比实验让模型自己判断何时需要外部知识。
- 分阶段训练是标配：先学能力，再抠效率。直接上惩罚性奖励极易导致模型性能崩溃，这一点在 RLHF 实践中同样适用。
局限与展望：
目前 SAAS 主要针对文本检索。虽然其核心机制模态无关，但在处理图像、表格等多模态证据时，如何定义“搜索边界”仍需进一步探索。此外，该方法依赖 GRPO 等 RL 算法，训练成本高于简单的 SFT，对于算力有限的团队可能需要权衡投入产出比。
总之，SAAS 提供了一个优雅的视角：解决 Agent 的冗余行为，靠的不是更严格的约束，而是更清晰的自我认知。
