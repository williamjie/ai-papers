论文 : WebRISE: Requirement-Induced State Evaluation for MLLM-Generated Web Artifacts链接 : https://arxiv.org/abs/2606.03220现在的 MLLM 生成前端代码已经卷到飞起，但大多数评测还在搞“静态截图对比”或“单点脚本点击”。这就像考驾照只检查车漆亮不亮，而不看你能不能平稳换挡。WebRISE 这篇论文直接戳破了这个泡沫： 视觉逼真度（Visual Quality）与交互正确性（Interaction Correctness）完全脱节 。对于工程落地而言，这意味着我们现有的评测指标可能正在误导模型优化方向。
### 现有方案的痛点：为什么“看起来对”没用？
传统评测（如 FrontendBench, WebGen-Bench）主要依赖两种模式：
- 基于脚本/检查点：硬编码选择器或固定路径，一旦 DOM 结构微调就失效，且无法覆盖分支逻辑。
- 基于视觉/探索：让 Agent 瞎逛或对比截图，只能验证局部响应，无法捕捉跨组件的状态一致性（如删除商品后总价未更新）。
核心问题在于： 现有方案缺乏“需求诱导的状态空间”定义 。它们不知道用户到底要什么状态，只知道点击后有没有反应。
### 方法拆解：交互契约图（ICG）的设计直觉WebRISE 的核心创新是提出了 交互契约图（Interaction Contract Graph, ICG） 。这不仅仅是个测试用例集合，而是一个形式化的状态机模型 Gτ=(Sτ,Tτ,Φτ,Mτ)G_\tau = (S_\tau, T_\tau, \Phi_\tau, M_\tau) ​ = ( S τ ​ , T τ ​ , Φ τ ​ , M τ ​ ) 。
其设计背后的关键 Insight 有两点：
-需求驱动的状态建模：
ICG 中的状态 SτS_\tau​ 不是全量 DOM 快照，而是“与需求相关的可观察 UI 配置”。瞬态行为（如 Loading、Toast）不被视为独立状态，而是作为过渡阶段的断言证据。这使得状态空间有限且稳定，避免了因为无关样式变化导致的误判。
-显式与隐式需求的分离：
这是工程价值最大的部分。ICG 将需求分为：
显式需求（Explicit）：用户明确说的功能（如搜索、筛选）。
- 隐式需求（Implicit）：产品级的约束（如状态同步、边界反馈、脏数据清理）。
通过映射 MτM_\tau ​ ，每个转换结果都能回溯到具体是哪类需求没满足。这种设计让评测从“Pass/Fail”变成了“诊断报告”。
### 关键结果：视频最强，隐式约束是瓶颈论文在 442 个任务、5 种输入模态（Text, Markdown, Sketch, Image, Video）和 14 个模型上进行了大规模测试。数据非常硬核：

### 工程启示：如何构建可靠的评测体系？
-引入缺陷注入（Defect Injection）：
WebRISE 通过向 Ground Truth 页面注入状态错误来验证评测器敏感性。结果显示，基于 ICG 的评估检测出 16/25 的状态缺陷，而传统的检查点式评估仅检测到 8/25（宽松标准）或 1/25（严格标准）。这证明：细粒度的状态断言比端到端的结果对比更敏感。
-重视隐式约束的微调数据构建：
既然隐式约束是瓶颈，我们在构建 SFT 数据时，不应只关注“点击 A 出现 B”，而应包含“删除 A 后，列表总数减 1 且选中项重置”这类状态一致性逻辑。
-多模态输入的必要性：
如果业务场景允许，提供交互视频或动态原型作为输入，能显著提升模型对复杂状态流转的理解。纯文本需求太容易丢失时序和边界条件信息。
### 局限与展望WebRISE 目前局限于自包含的 HTML 文件，未涉及后端服务、数据库持久化或多用户并发。这限制了其在真实生产环境中的直接适用性。未来方向显然是将 ICG 扩展为包含沙盒 API 契约和会话级状态转换的更复杂模型。
总之，WebRISE 提醒我们：在 LLM 生成前端代码的竞赛中， “能跑”比“好看”难得多，也重要得多 。工程师们该把评测重点从像素对齐转移到状态一致性上了。
