# 多轮RAG夺冠：Judge仲裁下的异构模型集成

**日期**: 2026-05-08

---

在 Retrieval-Augmented Generation (RAG) 领域，单轮问答已经卷出花来，但**多轮对话（Multi-Turn）**依然是重灾区。SemEval-2026 Task 8 (MTRAGEval) 聚焦这一痛点，而 Novosibirsk State University 的 RaguTeam 凭借一个看似“暴力”却极其有效的方案，在26支队伍中拿下第一。
这篇论文没有发明新的Transformer架构，而是通过 异构模型集成（Heterogeneous Ensemble） 加上 LLM-as-a-Judge 的仲裁机制，解决了多轮对话中“忠实度（Faithfulness）”与“回答完整性”难以兼得的难题。对于工程落地而言，这提供了一种在成本可控前提下，显著降低幻觉、提升多轮上下文理解能力的实用范式。
## 为什么多轮RAG这么难？
多轮RAG的核心难点不在于“检索”，而在于 对话状态的追踪与证据的融合 。系统需要在历史对话、当前查询和检索到的片段之间建立联系，处理指代消解（Coreference Resolution），并在证据不足时果断“拒答”（Abstention）。
现有的单一大模型往往存在固定的失败模式：有的模型过于自信，强行编造答案；有的模型则过于保守，即使有证据也不敢回答。RaguTeam 的核心洞察是： 没有完美的单一模型，但可以通过多样性互补，让一个轻量级Judge选出每个实例的最佳回答。
## 方法拆解：三步走战略RaguTeam 的系统设计非常清晰，分为提示工程、异构生成、Judge仲裁三个阶段。
### 1. 提示工程：抽象指令 vs. 具体示例作者对比了两种提示策略，得出了一个反直觉但极具工程价值的结论： 具体行为示范优于抽象指令 。
- Group 1 (系统提示)：使用经过 Gemini 迭代优化的系统提示，强调严格基于文档、简洁格式和拒答机制。
- Group 2 (少样本提示)：引入基于类别的 Few-Shot 示例。训练数据被聚类为三类：完整上下文、空上下文（必须拒答）、空历史（首问）。通过嵌入空间计算 Medoids，选取最具代表性的4个示例。
关键 Insight ：在“未指定（Underspecified）”这类边缘案例中，Few-Shot 提示比精心打磨的系统提示效果更好。因为模型通过示例能更直观地学习到“何时该追问”或“何时该拒答”的行为模式，而非仅仅理解抽象规则。
### 2. 异构集成：多样性即鲁棒性团队选择了7个模型组成集成，刻意混合了不同厂商、规模和架构，以最大化“故障模式的互补性”：
组别 模型 规模 类型 策略 Group 1 Gemini-3-Pro-Preview Proprietary Proprietary System Prompt Group 1 GLM-4.6 357B Open System Prompt Group 1 Llama-3.3-70B-Instruct 70B Open System Prompt Group 1 Qwen3-235B-A22B 235B Open System Prompt Group 2 Claude 4.5 Haiku Proprietary Proprietary Few-Shot Group 2 Qwen2.5-32B-Instruct 32B Open Few-Shot Group 2 Meno-Lite-0.1 7B Open Few-Shot值得注意的是 Meno-Lite-0.1 ，这是一个7B的领域适配模型。虽然它在最终集成中贡献有限（仅被Judge选中2次），但其独立测试显示，在“拒答”校准上表现优异，证明了小模型在特定技能（如提取、多跳推理）上的潜力。
### 3. Judge仲裁：轻量级选择器生成7个候选回答后，团队使用 GPT-4o-mini 作为 Judge。Judge 的任务不是打分排序，而是评估 忠实度（Faithfulness） ：所有声明是否均由提供的文档支持。
- 选择逻辑：Judge 评分最高者胜出。
- 后处理：对于明确无证据的情况，直接替换为固定回复 “I don’t have an answer”，确保拒答机制的确定性。
## 关键结果：多样性战胜规模在 MTRAGEval Task B 测试集（507个实例）上，RaguTeam 取得了 0.7827 的条件谐波均值（HM3），大幅领先第二名。

- 集成价值：即使去掉 Judge 随机选择，集成性能（0.760）也优于大多数单模型。但加入 Judge 后，在“可回答（Answerable）”实例上进一步提升了 2.5 p.p.，证明 Judge 成功识别出了更忠实的答案。
- Few-Shot 优势：在“未指定”问题上，GLM-4.6 的 Few-Shot 版本比 System Prompt 版本高出 3.7 p.p.。这再次验证了具体示例对边缘案例处理的必要性。
- 规模非万能：357B 的 GLM-4.6 是最佳单模型，但包含更小模型（如7B Meno-Lite）的集成依然胜出了。这说明互补性比参数量更重要。
## 工程启示与局限### 给工程师的建议- 不要迷信单一最强模型：在多轮RAG这种复杂任务中，混合使用不同厂商（如 Google + Anthropic + Open Source）和不同规模的模型，能显著覆盖更多的失败模式。
- Prompt 设计要“具体”：对于拒答或澄清等复杂行为，提供 Few-Shot 示例往往比写长段 System Prompt 更有效。
- Judge 的性价比：使用 GPT-4o-mini 这种轻量模型作为仲裁者，在保持高相关性（Spearman ρ=0.95）的同时，控制了推理成本。
### 局限与反思论文也坦诚指出了系统的弱点：
- 成本与延迟：并行调用7个模型加上 Judge，计算开销大，不适合实时低延迟场景。
- Benchmark 的“捷径”：MTRAGEval 中所有“不可回答”问题的参考片段均为空。这意味着检测到“空片段”并直接拒答就能得满分。这在真实场景中是不存在的，真实场景中不可回答的问题往往伴随着无关的干扰片段，这才是真正的挑战。
总的来说，RaguTeam 的方案证明了在 RAG 2.0 时代， 架构层面的多样性设计 依然比单纯堆砌模型参数更有效。对于资源受限的团队，借鉴其“小模型领域适配 + 轻量 Judge 仲裁”的思路，或许是一条更务实的落地路径。
