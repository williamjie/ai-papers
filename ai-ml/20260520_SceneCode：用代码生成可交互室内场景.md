# SceneCode：用代码生成可交互室内场景

**日期**: 2026-05-20

---

论文 : SceneCode: Executable World Programs for Editable Indoor Scenes with Articulated Objects链接 : https://arxiv.org/abs/2605.19587对于具身智能（Embodied AI）和机器人仿真来说，仅仅“看起来像”的房间是远远不够的。如果生成的衣柜没有铰链，抽屉不能滑动，机器人就无法进行真实的物理交互训练。现有的场景生成方案大多产出静态网格（Static Meshes），或者从固定资产库中检索预制件，这导致生成的场景缺乏真正的可编辑性和物理结构。SceneCode 提出了一种全新的思路：不再生成黑盒式的 3D 模型，而是生成可执行的 Blender Python 代码。
### 痛点：为什么静态网格不够用？
在当前的室内场景合成管线中，存在一个明显的断层。虽然基于检索或扩散模型的方法能生成视觉逼真的房间，但对象通常被视为不透明的几何体。即便包含铰接对象（Articulated Objects），其关节语义和部件结构也是继承自预定义的数据集（如 PartNet）。这意味着：
- 缺乏按需定制能力：如果数据集中没有特定结构的柜子，就无法生成。
- 不可编辑：生成的网格是一堆三角形面片，无法通过修改参数来调整抽屉数量或材质。
- 物理交互缺失：没有显式的关节定义，机器人无法在仿真环境中打开门或拉出抽屉。
### 核心 Insight：代码即世界程序SceneCode 的核心直觉是： 代码是表示可交互场景的自然形式 。代码不仅能描述几何形状，还能显式地定义部件分解、材料分配、物理属性以及运动机制（如旋转或平移关节）。
该方法将室内场景合成公式化为“程序化世界生成”（Programmatic World Generation）。其技术架构分为两个耦合层级：
-房间级代理规划：
系统首先将自然语言提示转化为结构化的房间布局，并通过“规划-设计-批评”（Planner-Designer-Critic）循环，按语义阶段（大型家具、墙面挂饰等）发出对象请求（AssetRequests）。
-代码驱动的对象生成：
这是创新的关键。每个对象请求被路由到五种策略之一（如静态家具、铰接对象等），随后由 VLM 生成基于几何原语的 Blender Python 程序。
部件化构建：程序不是生成整体网格，而是逐个构建部件（如抽屉面板、侧面、底部），并保留语义名称。
- 执行引导的验证：代码在无头 Blender 中执行，如果失败则根据 Traceback 进行修复（最多 3 次），成功后由 Critic 代理检查渲染结果（最多 2 次），确保几何和材质符合预期。
- 物理编译：对于铰接对象，系统推断关节类型（旋转或平移）、轴线和运动范围，并估算质量和惯性张量，最终导出为 SDF 格式供仿真器使用。
### 关键结果：数据说话作者在 30 个自然语言提示上进行了评估，对比了 SceneSmith、HSM 和 LayoutVLM 等基线。
场景级合成表现（Table 1）：
SceneCode 在语义保真度和物理可用性上均表现优异：
- 对象数量（CNT）：79.4%（优于 SceneSmith 的 78.8%）
- 对象属性（ATR）：74.0%（显著高于 HSM 的 58.1% 和 LayoutVLM 的 31.1%）
- 导航性（NAV）：100.0%（完美无碰撞路径）
- 碰撞率（COL）：11.3%（低于所有基线，越低越好）
- 人工评估：在所有对比组中，SceneCode 的提示忠实度（Prompt Faithfulness）均高于基线，相较于 LayoutVLM 提升了 +24.6%。
对象级资产质量（Table 2）：
与基于图像到 3D 的 SAM 3D Objects 相比，代码生成的优势在于结构的清晰度：
- UV 岛数量：SceneCode 平均 22 个，而 SAM 3D Objects 高达 96 个（减少约 4.4 倍），意味着更紧凑、更易于编辑的 UV 布局。
- 面数与顶点数：SceneCode 的面数减半（6013 vs 12036），顶点数减少（4945 vs 7400），显著降低存储和渲染成本。
- 非流形边（NME）：SceneCode 为 0，而基线存在拓扑错误，后者在仿真器中通常需要修复。
此外，MuJoCo 仿真演示表明，生成的铰接对象保留了独立的运动连杆和可执行关节，机器人可以通过接触物理地打开柜门或拉出抽屉。
### 工程启示- 从“生成模型”到“生成代码”：对于需要高精度控制和物理交互的应用，生成可执行代码比生成静态网格更具长远价值。代码提供了语义句柄（Semantic Handles），使得后续的参数化编辑成为可能。
- 执行反馈闭环的重要性：直接让 LLM 生成复杂 3D 代码容易出错。SceneCode 引入的“执行-修复-批评”循环极大地提高了代码的鲁棒性，这种模式可以复用于其他程序化生成任务。
- 资产库的解放：不再依赖有限的预制件库，可以根据需求即时生成具有特定结构（如特定数量的抽屉）和材质的物体，解决了长尾需求的问题。
### 局限与展望尽管 SceneCode 在结构和物理交互上取得了突破，但在视觉真实感上可能仍不及专门的图像到 3D 模型。此外，复杂的有机形状或高度非标准的几何体可能难以用简单的几何原语代码完美表达。未来工作可能集中在提升视觉细节保真度，以及扩大可生成的对象类别范围。
