# 自动科研：用专家Agent闭环优化训练配方

**日期**: 2026-05-08

---

论文 : Auto Research with Specialist Agents Develops Effective and Non-Trivial Training Recipes链接 : https://arxiv.org/abs/2605.05724如果你还在手动调参或者写脚本跑网格搜索，这篇来自 CMU 的论文可能会让你感到一丝凉意。它不再把 LLM 当作一个“写代码的工具”，而是把它变成了一个“自主的研究者”。
核心逻辑很简单但很硬核：构建一个**闭环自动科研（Closed-loop Auto Research）**系统。Agent 提出假设 -> 修改代码 -> 提交实验 -> 读取外部评估结果 -> 基于反馈（包括崩溃和失败）提出下一个假设。整个过程，从启动到结束，人类不干预任何一次 trial 的选择。
### 痛点：从“生成”到“实证”的鸿沟现有的 Agent 编程研究（如 SWE-agent）主要解决“修 Bug”或“实现功能”，而 ML 研究解决的是“在约束下找到最优解”。传统 RLHF 或 Agent 训练往往依赖奖励模型（Reward Model），这容易导致 Reward Hacking（作弊）。
这篇论文的动机很明确： 让外部测量（External Measurement）成为唯一的真理 。Agent 不能自己说“我变快了”，必须是运行脚本后的 Wallclock 时间或 Loss 值说了算。现有的 AutoML 或 Hyperparameter Optimization 大多局限于固定空间内的数值搜索，而这篇工作试图让 Agent 进行 程序级（Program-level）的编辑 ，比如修改 Attention 路径、调整 Loss 函数等更底层的结构变更。
### 方法拆解：专家分工与血缘反馈这个方法的设计精髓在于两个部分： 专家角色拆分（Specialist Roles） 和 共享血缘（Shared Lineage） 。
-专家角色拆分：
论文没有让一个通用 Agent 瞎试，而是根据环境约束划分了不同的专家角色。
Parameter Golf（关注大小和预算）：10个专家，覆盖架构、优化、量化、正则化、Loss 等。
- NanoChat-D12（关注固定预算下的速度）：5个专家，覆盖架构、优化、数据、调度、系统。
- CIFAR-10 Airbench96（关注准确率门控下的速度）：5个专家，覆盖架构、优化、增强、Loss、正则化。
这种设计迫使 Agent 在搜索时关注不同的“配方表面（Recipe Surface）”，避免所有 Agent 都去挤同一个超参数旋钮。
-共享血缘（Lineage Feedback）：
这是最关键的部分。Agent 不仅仅看当前的最佳分数，它能看到完整的“实验血缘”：之前的假设、代码 Diff、评分、状态（成功/崩溃/超时）、失败原因。
Insight：失败也是有价值的。如果一个 Agent 因为“超出大小限制”失败，后续 Agent 会看到这一点，并在保持模型结构的同时尝试压缩体积。血缘让 Agent 能够“站在前人的失败肩膀上”迭代，而不是每次都在原地打转。
### 关键结果：不仅是调参，是代码重写在三个不同的环境中，Agent 展示了惊人的自主优化能力。所有结果均基于严格的“外部评估”，Agent 无法篡改评分器。

- 非平凡编辑：Agent 并非只做简单的超参数调整。在 NanoChat-D12 中，Agent 将 Attention 路径从 SSSL 重写为 L，并将所有层移至 Flash SDPA，从而节省出 Wallclock 时间用于增加训练 Token 数量。
- 失败利用：在 Parameter Golf 中，一个因“超出 16MB 限制”而被拒绝的 z-loss 想法，被后续 Agent 继承并修改，最终在满足大小限制的前提下实现了更低的 BPB。
- 消融实验：
移除血缘（No Lineage）：性能大幅下降，有效改进从 16 次降至 3 次，且大量试验撞墙在评估预算上限。
- 通用多 Agent（Generic 10-agent）：虽然并行度高，但提案多样性极低（有效聚类仅 41.1 个，而专家 Swarm 为 134.8 个），导致优化效果不如专家分工。
### 工程启示- 评估器必须独立且不可篡改：Agent 不能拥有评分器的代码。论文中使用了独立的解析器和 Shell 计时器，防止 Agent 通过打印假分数来“作弊”。
- 失败是数据，不是噪音：在构建 Agent 研究循环时，必须详细记录失败的原因（Crash, Size Exceeded, Accuracy Gate Miss），并将这些结构化反馈喂给下一个 Agent。
- 角色先验很重要：简单的多 Agent 并行搜索效率低下，因为 Prompt 相同会导致搜索空间重叠。通过角色拆分（Role-conditioning），可以显著增加提案的多样性（Proposal Entropy）。
### 局限与展望这篇论文承认，当前的 Agent 主要是在**组合（Composition）**已有的技术，而非发明全新的架构（如 Transformer 本身）。它更像是一个极其勤奋、不眠不休的资深工程师，在约束条件下寻找最优解。
未来的方向包括扩展到更长的运行周期（数周）、处理主观性较强的评估任务，以及探索 Agent 是否能提出真正结构性的创新。但对于当下的 LLM 训练工程而言，这种“自动科研”范式已经提供了可审计、可复现、且显著优于人工调参的解决方案。
