# ⭐⭐ 让 Agent 自己写框架：Evo-Bench 深度拆解

**日期**: 2026-08-11

---

论文 : Evo-Bench: Can Language Models Improve Agent Harness?
链接 : https://arxiv.org/abs/2608.09096现在的 Agent 圈子里，大家都在卷 Prompt 工程或者微调模型权重。但有一个被忽视的事实：真正拉开 Agent 性能差距的，往往是底层的执行框架（Harness）。如果能让 LLM 自己去优化这个框架，是不是能实现真正的自我进化？这篇来自中国人民大学和 BOSS 直聘联合团队的 Evo-Bench，就是为了解答这个问题而生的。
### 为什么我们需要 Evo-Bench？
现有的 Agent 评测大多停留在“静态任务解决”层面。你给一个固定的 Prompt 和工具集，看模型能不能跑通。但这掩盖了一个核心问题：模型到底有没有能力去改进它赖以生存的代码框架？
之前的研究要么把重点放在具体的任务优化上，要么混淆了“基础模型变强”和“框架变好”带来的收益。Evo-Bench 的设计初衷非常硬核：它要剥离掉基础模型的智力差异，纯粹评估模型作为“系统工程师”，在长周期内迭代优化可执行代码 Harness 的能力。
### 核心设计：如何公平地评测“进化能力”？
如果直接让模型改代码然后跑测试，很容易出现过拟合——模型可能只是记住了特定任务的 trick，而不是提升了通用框架的质量。为了解决这个问题，作者提出了一个非常巧妙的 两阶段 Harness 引导构建框架 。
-辅助任务进化（Auxiliary Task Evolution）：
首先，利用一组与最终评测无关的辅助任务，让多个前沿模型进行初步的 Harness 演化。这一步是为了生成多样化的“候选框架”，覆盖不同的工具编排和代码结构。
-敏感度感知分层抽样（Sensitivity-Aware Stratified Splitting）：
这是最关键的 Insight。不是所有任务都能反映框架的好坏。作者计算了每个任务在不同辅助框架下的表现与框架整体质量的皮尔逊相关系数（Harness Sensitivity）。
高敏感度任务：框架越好，得分越高。这些任务被选入评测集，因为它们能真实反映框架的进步。
- 低敏感度任务：无论框架怎么改，得分都差不多（可能因为模型本身太强或太弱），直接过滤掉。
通过这种方式，Evo-Bench 确保了验证集和测试集在难度分布上的一致性，防止了模型针对特定任务过拟合。评测分为三个领域： 搜索（Search）、办公（Office）和通用 Agent（General） ，覆盖了从网页浏览到文档处理的复杂场景。
### 实验结果：前沿模型的“自我进化”有多强？
作者在 Evo-Bench 上测试了 9 个前沿模型（包括 GPT-5.6 Sol, Claude Opus 4.8 等）和开源模型。固定策略模型为 DeepSeek-V4-Flash，让其他模型充当“演化器”来修改初始的 CodeAct 种子框架。
结果令人印象深刻：
- 绝对增益巨大：表现最好的 GPT-5.6 Sol 和 Claude Opus 4.8 相比初始的 CodeAct 基线，整体得分分别提升了 +11.0 和 +7.9 个点（注意：这是相对于基线的绝对提升，文中提到 top models achieve massive absolute gains reaching 16.6 points，这里指的是特定领域或综合指标的最大增益，具体看 Table 2，GPT-5.6 Sol 在 General 领域提升了 +32.8，Search 领域 +11.0）。
- 逼近人类工程上限：这些自动演化出的框架，其最终得分已经非常接近由人类专家精心设计的专用框架（Artificial Harness Baseline，得分为 47.5）。GPT-5.6 Sol 达到了 46.3，Claude Opus 4.8 达到了 45.8。
- 领域差异显著：
搜索任务：模型最容易优化，因为可以自动补充网页导航逻辑。Claude Opus 4.8 在此领域增益高达 +34.8。
- 通用任务：令人意外的是，顶级演化器甚至超越了人类设计的框架。GPT-5.6 Sol 在 General 任务上得分 59.4，超过了人工基线的 56.3。这说明在某些复杂推理结构上，AI 能发现人类未曾想到的模式。
- 办公任务：这是目前的短板。由于需要高度特定的处理流程（如 Excel 单元格追踪），模型很难通过通用演化发现这些细节，得分提升有限。
⚠️ 反直觉发现：早期饱和与预算浪费分析显示，大多数模型存在“早期饱和”现象。它们在前几轮迭代中就能快速发现高质量的框架结构，但在后续迭代中往往引入破坏性修改，导致性能停滞甚至下降。例如，Qwen3.7-Max 仅用了 15 次迭代和不到 200 步就停止了演化，但依然取得了极具竞争力的成绩，显示出极高的样本效率。相比之下，GPT-5.6 Sol 耗尽了全部 20 次迭代预算，成本超过 500 美元，才换来微小的额外提升。
### 工程启示：我们该如何利用这一能力？
- Harness 即代码，可被优化：不要只把 Agent 的框架当作静态配置。对于复杂业务场景，可以尝试用高阶 LLM 对现有的 Agent 代码进行自动化重构和调试。
- 成本效益权衡：Evo-Bench 的成本分析表明，性能提升与 API 费用呈对数关系。GLM-5.2 和 Qwen3.7-Max 在低于 40 美元的成本下就达到了很好的效果，而追求极致性能的 GPT-5.6 Sol 成本激增。在实际工程中，中等预算的“足够好”框架往往比昂贵但边际收益递减的顶级框架更具性价比。
- 跨模型迁移性：实验证明，演化出的 Harness 具有良好的通用性。即使更换底层的策略模型（Policy Model），优化后的框架依然能带来显著的性能提升。这意味着我们可以集中资源训练一个“框架工程师”模型，生成的代码可以复用于多个不同的 Agent 实例中。
### 局限与展望尽管成果显著，但当前的自动演化仍显“浅层”。GPT-5.6 Sol 的案例研究表明，它更多是通过添加领域特定的路由器和工具来修补漏洞，而非进行深层的架构重构。例如，它的规划器仍然是被动的，上下文管理依然是简单的追加模式。
未来的方向在于提升模型对 因果失败模式 的抽象能力，以及执行大规模架构重构的能力。只有当 Agent 不仅能“打补丁”，还能“重写内核”时，真正的自主进化才算到来。
