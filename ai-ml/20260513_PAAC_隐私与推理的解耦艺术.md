# PAAC: 隐私与推理的解耦艺术

**日期**: 2026-05-13

---

论文 : PAAC: Privacy-Aware Agentic Device-Cloud Collaboration链接 : https://arxiv.org/abs/2605.08646在智能体（Agent）落地过程中，我们常面临一个结构性矛盾：云端模型推理强但暴露隐私，端侧模型隐私好但能力弱。现有的设备-云协作方案往往把这个问题简单看作“算力分割”，导致要么隐私泄露，要么能力打折。PAAC 这篇论文提供了一个极具工程启发性的思路： 把隐私保护内化为角色分工本身 ，通过解耦“推理”与“执行”，让云端只处理脱敏后的语义骨架，端侧保留真实数据用于执行。
### 痛点：现有方案的“两难”
目前的设备-云协作主要有几种流派，但都有明显硬伤：
- 路由式（Routing）：要么全上云，要么全在端。这要求端侧模型具备全链路能力，显然不现实。
- 固定流水线（Fixed-Workflow）：如 PAPILLON，让端侧模型重写整个 Query。虽然灵活，但重写过程破坏了工具调用所需的结构保真度（Structural Fidelity），云端 Agent 拿到的是“意译”后的文本，很难生成精确的工具调用指令。
- 模式匹配（PBS）：如 Presidio，基于固定实体分类表替换。它在封闭词汇（如电话号码）上表现不错，但在开放词汇（如订单号、自定义产品名）上覆盖率极低，且容易误杀或漏杀。
- 扰动法（Perturbation）：如 PRISM，给实体加噪声。但噪声往往保留了语义信息，云端模型依然能推断出隐私内容，且无法还原为精确值用于工具执行。
核心问题在于： 如何在云端推理时不看到隐私数据，同时又能保证工具调用的准确性？
### 方法拆解：为什么这么设计？
PAAC 的核心 Insight 是： 推理操作的是语义角色，而非具体实例。
举个论文里的例子：如果问题是“Alice 余额 1234，房租1234，房租 1000，还剩多少？”，云端不需要知道具体的数字，只需要知道它是在做 subtract(BALANCE, RENT) 。只要把敏感值替换为类型化的占位符（Typed Placeholder Tokens），云端就能基于语义进行正确规划，而真实数值留在端侧执行。
为了实现这一点，PAAC 设计了两个关键组件：
#### 1. 解耦的智能体架构（Decoupled Agentic Architecture）
PAAC 将云端和端侧的角色严格对齐到信任边界：
- 云端 Agent（Reasoner）：只接收脱敏后的查询和工具调用计划。它维护自己的推理上下文，但不接触任何原始隐私数据。
- 端侧 Agent（Executor & Judge）：负责隐私脱敏、执行工具、以及评估每一步的结果。
关键设计：单步蒸馏（Single-step Distillation）
在 Agent 交互中，上下文长度会随步骤增加而爆炸，这对端侧设备是灾难。PAAC 让端侧 Agent 只蒸馏 当前步骤 的执行结果为“关键发现（Key Findings）”，而不是压缩整个历史。云端则独立维护其推理轨迹。这种设计避免了单步压缩带来的信息累积损失，同时控制了端侧输入大小。
#### 2. 提议-验证-注册表机制（Proposer-Verifier-Registry）
这是论文最精彩的部分。直接让 LLM 做脱敏容易出错（如替换错误、上下文丢失），而纯规则又不够灵活。PAAC 将脱敏过程拆分为三步：
- 提议（Proposer）：端侧 LLM 仅作为“提议者”，输出候选的敏感片段和对应的脱敏文本对。它不直接执行替换。
- 验证（Verifier）：通过确定性规则验证提议是否合法。如果 LLM 提议替换错误（如语义不匹配），则拒绝提交。
- 注册表（Registry）：所有替换和还原操作由一个追加写（Append-only）的确定性正则表达式注册表完成。
为什么这样设计？
- 结构保真：正则替换是确定性的，保证了工具调用指令的结构不被破坏，云端可以直接执行还原后的动作。
- 隐私锁定：注册表在首轮查询时初始化。后续即使端侧 LLM 被攻击或出错，之前注册过的实体依然会被强制掩码，防止隐私泄露。
- 一致性：相同的实体在不同轮次映射到相同的占位符，保证了跨轮次的指代一致性。

### 工程启示- 角色分离优于流水线：不要试图用一个模型解决所有问题。将“推理规划”与“执行评判”分离，并明确各自的信任边界，能显著提升系统鲁棒性。
- 结构化脱敏是关键：对于 Agent 场景，简单的掩码或重写是不够的。需要保留实体的“语义角色”（如 BALANCE, RENT），让云端模型能基于角色推理，而非具体数值。
- 确定性注册表的重要性：LLM 的生成具有不确定性，不适合直接用于关键的数据替换。将“提议”与“执行”解耦，用确定性规则保证执行层的可靠性，是工程落地的最佳实践。
### 局限与展望PAAC 目前假设云端是“诚实但好奇”的，且主要保护实体隐私。对于更复杂的对抗性攻击或细粒度的数据扰动，仍有探索空间。此外，端侧模型需要具备一定的理解能力来执行“提议”和“蒸馏”，这对端侧模型的质量提出了更高要求。
总体而言，PAAC 为隐私敏感的 Agent 应用提供了一套可落地、高可用的架构范式，值得在金融、医疗等场景深入借鉴。
