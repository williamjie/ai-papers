# LoRA 合并的隐形杀手：输出矩阵 B 里的方向拥挤

**日期**: 2026-04-21

---

论文 : Crowded in B-Space: Calibrating Shared Directions for LoRA Merging链接 : https://arxiv.org/abs/2604.16826LoRA 合并现在几乎是标配操作了——数学、编程、医疗、金融，每个领域都有人微调出专属 adapter，然后指望把它们拼成一个全能选手。但现实很骨感：合并之后性能往往掉得比单独用的时候还惨。
这篇论文干了一件很聪明的事。它没有急着提一个新合并算法，而是先问了一个根本问题： 合并干扰到底从哪儿来？ 答案出乎意料——问题不在你以为的地方。
## 问题：大家默认把 LoRA 当成一个黑盒LoRA 的参数更新写成 ∆W = BA，其中 A 是输入投影（把特征映射到低维空间），B 是输出投影（把低维表示映射回输出空间）。
但现有的合并方法——Task Arithmetic、TIES-merging、DARE、KnOTS——全把 ∆W 当做一个整体来处理。它们做符号对齐、剪枝小权重、或者在共享基上对齐，但 从不区分 A 和 B 。
这就好比修车的时候，你觉得引擎出问题，拆开来发现是排气管堵了。
论文的作者们怀疑：A 和 B 在微调过程中扮演的角色本来就不对称。已有研究表明，单任务微调时，更大的更新变化是由 B 承担的。LoRA-FA 冻结 A 只训练 B，HydraLoRA 共享一个 A 配多个 task-specific B，都在暗示 A 更容易被冻结或共享，而 B 承载了更多任务特定的变化。
那合并干扰是不是也主要集中在 B 上？
## 关键发现：B 矩阵在”挤同一批方向”
作者们在 Llama-3.1-8B 上训练了四个领域的 LoRA adapter（数学、编程、金融、医疗），然后做了几个量化分析。结果非常明确：
B 的跨任务重叠远高于 A，而且随着 rank 增大差距还在拉大。
矩阵 Rank 8 重叠 Rank 16 Rank 32 Rank 64 B (Query) 0.0166 — — 0.0839 A (Query) 0.0035 — — 0.0172 B (Value) 0.0136 — — 0.0801 A (Value) 0.0071 — — 0.0196注意这个趋势：rank 从 8 涨到 64 时，B 的重叠从 0.0166 飙到 0.0839，而 A 只从 0.0035 涨到 0.0172。B 的增长速度是 A 的四倍多。
更惊人的是**有效秩（effective rank）**的数据：
矩阵 Rank 64 时 Query 的有效秩 Rank 64 时 Value 的有效秩 B 2.94 2.59 A 6.55 5.30也就是说，即使你把 rank 设到 64，B 矩阵实际上只用了大约 3 个方向。不同任务的 B 都在重复使用同一小批输出空间方向。而 A 则分散得多，用了 5-6 个方向。
核心 insight 来了 ：合并干扰不是均匀分布在 ∆W 上的，而是集中在 B 的一两个共享方向上。当多个 adapter 合并时，这些共享方向被反复叠加，能量急剧放大，任务特定的方向反而被稀释了。
论文里一个具体例子：在 Query 投影的第 16 层，前 3 个共享方向就占了 53.7% 的共享基能量，前 5 个占了 68.8%。金融、数学、医疗对这些主导方向的贡献比编程更大——这意味着合并后，编程任务的信号更容易被淹没。
## Pico：在合并前给 B 做”方向去拥挤”
既然问题出在 B 的共享方向过度拥挤，解决方案就很直接了： 在合并之前，把 B 里被过度共享的方向降权。
这就是 Pico（Pre-merge interference calibration in output-space）。它不是一个全新的合并算法，而是一个 即插即用的校准步骤 ，可以挂在 Task Arithmetic、TIES、TSV-M 任何下游合并方法前面。
流程就三步：
1. 构建共享基把所有任务的 B 矩阵拼起来做 SVD：B_all = [B1, B2, …, BT] = UΣV^T。U 的列就是共享的输出空间基向量。
2. 给每个方向打分并降权对第 j 个共享方向，计算共享得分 sj（该方向在联合 B 空间能量中的占比），然后算缩放系数：
αj = 1 / (1 + (T-1) * sj / σj² 的归一化形式)
简单说：共享越多的方向，αj 越接近 1/T（被大幅压缩）；共享少的方向，αj 接近 1（保持不变）。
然后构造校准算子 S = I + U diag(α - 1) U^T，只作用在 B 上：B_t’ = S * B_t。A 完全不动。
3. 合并 + 幅度恢复用任意合并方法合并校准后的 ∆W_t’ = B_t’ A_t，得到一个方向更平衡的合并结果。但校准后 Frobenius 范数会变小，所以最后乘一个恢复系数 γ：
γ = (1/∥∆W_calib∥_F) * (1/T) * Σ ∥∆W_t∥_F这一步很关键。消融实验表明，去掉幅度恢复，整体平均从 0.4430 暴跌到 0.3908。方向对了还不够，幅度也得对。
## 结果：简单但有效在八个数据集（四个领域各两个 benchmark）上的测试结果：
Pico 对三种下游合并方法均有提升：
下游合并方法 无校准 + Pico 绝对提升 Task Arithmetic 0.4093 0.4430 +3.4 TIES 0.3859 0.4328 +4.7 TSV-M 0.3473 0.4305 +8.3提升幅度差异很有意思。TSV-M 提升最大（8.3 点），因为 TSV-M 直接在低秩奇异向量空间操作，对 B 的共享方向最敏感。TIES 次之，因为过共享方向在 TIES 的幅度剪枝后更容易存活下来主导符号向量。Task Arithmetic 提升最小，因为它的坐标级平均对谱集中度不那么敏感。
但 Pico 对三者都有效 ，说明它解决的是上游共性问题，不依赖特定合并策略。
更狠的是这个对比：
Adapter 整体平均分 单领域最优 LoRA（平均） ~0.36-0.41 Joint Multi-Task LoRA（全数据联合训练） 0.3688 Pico + Task Arithmetic（合并） 0.4430Pico 合并后的模型，在整体平均上 超过了用全部任务数据联合训练的 LoRA 7.4 个点 。合并比联合训练还强。这在 LoRA 合并领域是非常少见的结果。
消融实验也验证了设计的必要性：
- 只校准 B → 最佳（0.4430）
- 校准 A → 更差（0.3916）
- 校准整个 ∆W = BA → 更差（0.3743）
- 校准 B 但不做幅度恢复 → 0.3908这再次确认了：干扰就在 B 里，动 A 或整个 ∆W 反而破坏了任务特定的结构。
## 工程启示几个值得记住的点：
1. LoRA 合并前先看看 B 的共享程度如果你在用 Task Arithmetic 或者简单平均做合并，效果不好，别急着换算法。先检查 B 矩阵的跨任务重叠。如果重叠很高，Pico 这种校准思路可能比换合并策略更管用。
2. 即插即用的价值Pico 不需要改合并逻辑，不需要额外数据，不需要调超参。它就是一个前置校准步骤。对于已经在用 TIES 或 TSV-M 的团队来说，加几行代码就能白嫖 3-8 个点的提升。
3. 幅度恢复不能省校准方向之后，合并结果的 Frobenius 范数会缩水。必须做幅度恢复，否则方向对了但模型变弱了，性能照样崩。
4. 合并可能比联合训练更香这个结果有点颠覆。通常我们认为联合训练（用全部数据一起微调）应该是最优的。但 Pico 的合并结果反而超越了联合训练的 LoRA。这意味着，如果你有很多现成的领域 adapter，不需要重新收集数据做联合训练，合并可能直接给出更好的结果。
## 局限与展望论文也有一些边界值得注意：
- 实验规模有限。只在 Llama-3.1-8B 和 Qwen3-34B 上验证，rank 覆盖了 8 到 64。更大的模型（70B+）或者不同的架构（MoE）上表现如何，还有待观察。
- 数据-free 是优势也是限制。Pico 不需要校准数据，这很方便，但也意味着它无法利用任务分布的先验信息。如果有少量校准数据，能不能做得更精细？
- 消融显示校准 A 有害。这说明 A 确实保留了更多任务特定的信息。但反过来想，如果某个任务的 A 矩阵本身噪声很大呢？目前 Pico 对 A 完全不做处理。
总的来说，这篇论文最值钱的地方是它改变了我们看 LoRA 合并的视角： 不要只看 ∆W，拆开看 A 和 B。 这种”拆开分析再针对性修复”的思路，在模型合并领域可能是一个范式转变。
