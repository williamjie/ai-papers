# ⭐⭐⭐½ 小模型代码外挂：让准确率飙升的代价

**日期**: 2026-05-20

---

论文 : Code-Guided Reasoning for Small Language Models: Evaluating Executable MCQA Scaffolds链接 : https://arxiv.org/abs/2605.18827在本地部署小语言模型（Small Language Models, SLMs）时，我们常遇到一个尴尬：直接问答案，模型答不对；但一旦给它加上“思考过程”或外部工具，效果往往天翻地覆。但这背后的代价是什么？是单纯的推理能力提升，还是靠堆砌 Token 预算换来的？
这篇来自 IBM 和南卡罗来纳大学人工智能研究所的论文，通过提出**代码引导推理（Code-Guided Reasoning, CGR）**协议，对这一现象进行了极其冷静的拆解。它没有试图训练新模型，而是构建了一个可审计的评估框架，专门研究当 SLM 被嵌入到由大模型生成的 Python 代码脚手架中时，其表现究竟发生了什么变化。
### 为什么直接问答不再够用？
传统的多选问答（MCQA）基准测试通常将模型视为“直接回答者”：输入问题，输出选项 A/B/C/D。但在实际工程中，部署的系统往往包含复杂的控制流：拆解问题、多次调用模型、执行代码计算、最后聚合结果。
CGR 的核心洞察在于： 推理过程本身就是一种系统架构设计 。如果只评估直接回答的准确率，我们就忽略了模型在“可执行动作空间”中的真实能力。论文将评估视角从“模型有多聪明”转向了“模型在脚手架辅助下能跑多稳”。
### 方法拆解：三通道审计机制CGR 的设计非常硬核，它不依赖黑盒提示词，而是引入了一个 生成器-求解器 的双模型结构：
- 生成器（Generator LLM）：为大模型生成一段针对特定问题的 Python 脚手架代码。这段代码定义了如何调用求解器、如何提取答案、如何设置平局打破机制。
- 求解器（Solver SLM）：被评估的目标小模型，它只看到脚手架发出的具体提示，而不知道生成器的全局意图。
- 三通道记录：这是 CGR 最精彩的设计。它分别记录并评分以下三个结果：
直接答案：求解器直接回答问题的结果。
- 辅助答案：求解器在代码脚手架引导下，经过多次调用后得出的最终结论。
- 生成器侧答案：脚手架代码内部由生成器逻辑选出的答案。
这种分离至关重要。因为高分可能来自真正的逻辑分解，也可能来自生成器“偷看”了答案，或者仅仅是因为提取器修复了格式错误。CGR 通过保留完整的代码、调用日志和元数据，让这一切变得可审计。
### 关键结果：准确率飙升，但代价惨重论文在 20,498 条保留结果行上进行了测试，覆盖 MMLU-Pro、MedQA、AIME 等六个数据集和六个求解器模型。数据揭示了一个令人兴奋但也需警惕的现象：
评估分区 直接准确率 辅助准确率 差距 全量样本 23.27% 62.41% +39.14 pp 非零基线分区 38.11% 66.21% +28.10 pp 严格基线 (>30%) - - +14.11 pp注：pp 为百分点 (percentage points)
在非零基线分区（即模型本身具备一定直接回答能力的场景）中，辅助推理带来了 28.10 个百分点 的巨大提升。在 MedQA 和 AIME 等高难度数据集上，某些模型（如 Llama 3.2 11B）的准确率从个位数跃升至 80% 以上。
然而，审计数据揭示了这背后的“通货膨胀”：
- 预算失衡：辅助推理的平均调用次数是 7.18 次，而直接回答仅为 1.01 次。辅助路径消耗的 Token 量是直接路径的 7.36 倍。
- 提取脆弱性：辅助路径中有 15.67% 的样本出现答案提取失败（返回 ‘X’）。
- 负向案例：在 Time-MQA（时间序列问答）数据集中，部分原本直接回答较强的模型（如 Gemma 4 E2B），在引入代码脚手架后准确率反而下降了。这表明过度的分解可能干扰模型对时序信号的直觉捕捉。
### 工程启示对于正在构建本地智能体的工程师来说，这篇论文提供了三条务实的建议：
- 不要迷信“代码即真理”：生成的 Python 脚手架确实能提升准确率，但它引入了新的故障点（如提取失败、硬编码违规）。在工程落地中，必须对生成的代码进行沙箱验证和静态检查。
- 关注“基线信号”：如果模型在直接回答时准确率接近零，辅助推理带来的高分可能只是“格式修复”或“生成器作弊”，而非真正的推理能力。只有在模型具备一定直接信号（如 >30% 准确率）时，辅助增益才更具参考价值。
- 成本意识：28 个百分点的准确率提升，换来的是 7 倍的推理成本。在延迟敏感或成本受限的场景下，需要权衡是否值得引入如此复杂的可执行脚手架。
### 局限与展望CGR 目前仍是一个回顾性的审计框架，而非因果推断实验。它尚未对比“同等预算下的直接自我一致性（Self-Consistency）”或“纯文本思维链（Chain-of-Thought）”。未来的工作应聚焦于将审计发现转化为运行时强制检查，如选项感知的提取器、严格的调用次数限制以及生成代码的自动验证器。
总之，代码引导推理是小模型突破能力瓶颈的有效手段，但它不是免费的午餐。理解其代价，才能在设计系统时做出更聪明的权衡。
