论文 : optimize_anything: A Universal API for Optimizing any Text Parameter链接 : https://arxiv.org/abs/2605.19633如果有一个 API，既能优化你的 Prompt，又能生成高性能 CUDA Kernel，甚至能自动设计 Agent 架构，你会怎么用？Berkeley 团队在 optimize_anything 中给出了答案： 将任何优化问题抽象为“文本工件（Text Artifact）”的迭代进化 。
## 为什么我们需要这种统一框架？
目前的 LLM 优化工具大多是“竖井式”的。FunSearch 和 AlphaEvolve 擅长代码进化，但仅限于单任务；GEPA 和 MIPROv2 专攻 Prompt 优化，能泛化但无法处理代码逻辑；ADAS 等工具搜索 Agent 架构，却缺乏统一的反馈机制。
工程师的痛点在于：每次面对新领域（从 Prompt 到 CUDA，再到调度算法），都要重新适配一套复杂的进化框架。 optimize_anything 的核心洞察是： 无论优化对象是代码、Prompt 还是 SVG 图片，只要序列化为字符串，优化逻辑就是通用的 。
## 核心设计：Side Information 与 Pareto 搜索论文没有停留在“提出了一个新框架”的层面，而是深入解决了两个关键工程问题：
### 1. Side Information (SI) 作为一等公民传统数值优化（如梯度下降）只反馈一个标量分数，LLM 进化框架以往也常忽略诊断信息。 optimize_anything 强制要求评估器返回 Score + Side Info 。
- 设计直觉：LLM 不是黑盒优化器，它是“有经验的工程师”。给它看编译错误、堆栈跟踪、渲染后的图片，比只给一个分数有用得多。
- 效果：在 Prompt 优化实验中，引入 SI 后收敛速度提升 4-6 倍，最终得分显著高于仅使用分数的对照组（86.32 vs 82.5）。
### 2. 基于 Pareto 前沿的搜索策略简单平均分数会掩盖候选方案在特定子任务上的优势。该系统维护一个 Pareto 前沿，保留那些“在某一方面最强”的候选者。
- 多任务迁移：在 CUDA Kernel 生成中，优化 Task A 发现的“内存合并访问”模式，会被保留在前沿中，并自动迁移到 Task B 的优化中。
- 避免早熟收敛：通过保留多样性，系统能在不同算法范式（如贪婪、线性规划、CMA-ES）间跳跃，避免陷入局部最优。

## 工程启示与局限### 对工程师的价值- 降低试错成本：无需为每个新问题手写进化算法。只需定义 evaluate(candidate) -> (score, side_info)，系统自动处理提示词构建、反射和候选选择。
- 诊断即优化：在调试复杂 Agent 或高性能代码时，将错误日志、性能剖析数据作为 SI 喂给 LLM，能极大提升修复效率。
- 无种子模式：对于 3D 建模等难以提供初始代码的领域，系统支持仅通过自然语言目标启动，自动 bootstrap 初始候选。
### 局限与边界- 任务相关性：多任务搜索仅在任务间存在可迁移模式时有效。论文指出，对于完全独立的圆堆积问题（不同 N 值），多任务反而引入噪声，导致性能下降。
- 成本权衡：虽然 GPT-5-nano 能降低 90% 成本，但在最终质量上仍不如大模型。评估器的调用成本往往主导总开销，需优化评估频率。
## 总结optimize_anything 证明了 LLM 驱动的文本优化是一种通用问题解决范式 。它不再局限于“代码”或“Prompt”，而是将任何可序列化的逻辑视为优化对象。对于正在构建复杂 Agent 系统或追求极致性能的后端工程师来说，这套“声明式优化”思路值得深入集成到工作流中。
