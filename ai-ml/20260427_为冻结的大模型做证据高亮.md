# 为冻结的大模型做证据高亮

**日期**: 2026-04-27

---

论文 : Learning Evidence Highlighting for Frozen LLMs链接 : https://arxiv.org/abs/2604.22565今天聊一个很实际的工程痛点：大模型处理长文档时，关键证据经常被噪音淹没——“Lost in the Middle”现象大家都遇到过。这篇论文给出了一个巧妙的解耦思路，不靠压缩、不靠改写，而是教一个小模型学会”划重点”。
## 为什么需要新方法当前处理长上下文的主流思路分两类：
- 硬选择：检索 top-k 段落，直接把其他内容扔掉- 软选择：用摘要/蒸馏压缩上下文，但会丢失细节这两种都有问题。硬选择太粗暴，可能丢掉重要的衔接信息；软选择是损失y的，细微但关键的细节容易被摘要成空气。
更关键的是，现有方案大多把”找证据”和”做推理”捆在一起，让同一个模型同时干两件事。结果就是——模型既要在大海捞针，又要基于找到的针做复杂推理，能力容易溢出。
核心 insight ：这两件事应该分开。让一个轻量模块专门负责 Surfacing Evidence（ surfaced evidence ），让强大的冻结大模型专心做 Reasoning。这就是 HiLight 的基本构思。
## 方法拆解：怎么教模型”划重点”
HiLight 的架构如图 1 所示：一个轻量的 Emphasis Actor 在原始上下文里插入 <start_important>...<end_important> 标记，冻结的 Solver 拿到高亮后的文本做最终推理。
关键设计点：
1. Actor 的输入输出- 输入：Q（问题）+ X（原始上下文）拼接后的表示- 输出：每个 token 的重要性概率 p_i = σ(w_p^T LayerNorm(h_i) / τ)
- 这是一个 Bernoulli 因子化策略，可以采样出 token-level 的二值 mask2. 预算控制Evidences 不能全标，否则成了全 highlight。论文用硬投影：先 Bernoulli 采样，再按 p_i 排序，取 top-k（ k = ⌊γL⌋ ，γ 是预算比例，推荐任务 γ=0.25，其他任务 γ=0.15）。
3. 跨 token 合并token-level mask 太碎，会把一个词拆成两半。所以把相邻 selected token 合并成 spans，中间小间隙（≤δ tokens）也连起来，再在两端插标记。
4. 训练：弱监督强化学习这是难点——我们没有 token-level 的证据标注。论文的做法是：
- Solver 冻结，不碰它的梯度和内部状态- Actor 用 Grouped Policy Gradient 优化- 对每个训练样本，采样 G=4 个不同的 mask- 用 Solver 的任务奖励（如 EM/F1/NDCG）作为 reward- 组内归一化优势：Â_j = (r_j - μ_r) / (σ_r + ε)
- 损失函数：L = L_PG + λ_len * L_len + β_ent * L_entL_len：让平均选中比例接近预算 γ 的长度正则- L_ent：熵正则，防止策略过早坍缩这种设计的精妙之处在于：
- 不依赖证据标签：只用最终任务 reward，在 QA/推荐等任务上通用- 解耦彻底：Actor 只改输入，Solver 完全 frozen，甚至可以是 API 模型- 可解释：高亮标记一目了然，知道模型关注了哪段## 关键结果：数字说话实验覆盖四个典型场景，Evidence 稀疏度差异很大：

- Actor 推理增加 <1.01× 的 token 量（只是几个标记符）
- 延迟增加 0.05s (0.6B) 到 0.34s (4B)，相比 Solver 的 8–18s 可以忽略- 训练成本也低：12K 次 Solver 查询 vs PRL 的 120K、APE 的 60K2. 跨模型迁移能力 ：
论文提到 Actor 可以 zero-shot 迁移到不同 size、不同家族的 Solver，甚至是 API 模型。这意味着——你可以针对一个开源模型（比如 Llama3-8B）训练一个 Actor，然后直接把它用在 GPT-4 或 Claude 上，效果依然有效。这打开了组合使用的想象空间。
3. 适用场景判断 ：
- 特别适合：长历史推荐、长文档 QA、Agent 轨迹分析等证据稀疏、噪音大的场景- 效果有限：当瓶颈主要是复杂推理而非证据定位时（如 PubMedQA，提升仅 +1.08% Acc）
- 不太适合：短上下文任务（ overhead 不划算）
4. 工程落地思路 ：
- 把 Actor 当作预处理模块，和下游 Solver 解耦部署- Actor 可以 batch 处理，缓存 highlight 结果，避免重复计算- 标记格式可以自定义，不影响 Actor 训练好的策略## 局限与展望局限性 （论文有提及）：
- Actor 需要在自己的长上下文上训练，对极端长文本（>32K）的扩展性没有充分验证- 当前用单一固定预算 γ，动态调整预算可能是下一步- 训练还是需要 RL，有一定不稳定性和计算成本后续方向 （我的脑洞）：
- 流式场景：对话中历史不断增长，如何增量更新 highlight？
- 多模态：图片、表格、代码混排的长文档，证据定位更复杂- 与 RAG 结合：检索器返回一堆文档，HiLight 在 retrieved 集合内再做精筛- Prompt 压缩对比：和 Gist、AutoCompressor 等压缩方法系统地对比，明确适用边界## 一句话总结HiLight 证明：与其让大模型自己在大海捞针，不如给它一副专用的”高亮眼镜”——一个轻量 Actor 负责划重点，冻结的 Solver 专心推理。这种方式既保留原始上下文完整性，又提升证据利用率，计算开销低，还能跨模型迁移，是长上下文场景下一个实用且可解释的工程解法。
