# BM25 还能打？深度搜索的性价比反转

**日期**: 2026-05-13

---

在构建深度研究（Deep Research）Agent 时，我们往往陷入一种误区：认为检索器是天花板，必须用昂贵的稠密检索（Dense Retrieval）或重排模型来兜底。但最新论文《Rethinking Agentic Search with Pi-Serini》给了一个反直觉的结论： 如果 LLM 足够强，且检索配置得当，简单的 BM25 完全足以支撑高效的深度搜索，且成本更低。
论文 : Rethinking Agentic Search with Pi-Serini: Is Lexical Retrieval Sufficient?
链接 : https://arxiv.org/abs/2605.10848## 问题与动机：被低估的 BM25过去，业界倾向于认为 BM25 这种基于词法的方法无法处理语义匹配，因此在 RAG（检索增强生成）和深度搜索中逐渐边缘化。然而，随着 GPT-5、Claude Opus 等前沿模型在推理和工具使用能力上的飞跃，Agent 的闭环决策能力大幅提升。
这篇论文的核心动机很直接： 当 LLM 变得更聪明时，我们是否还需要死磕检索器的语义能力？ 作者通过引入 Pi-Serini，试图剥离“检索器能力”与“工程配置”的影响，验证 BM25 在深度搜索场景下的真实潜力。
## 方法拆解：Pi-Serini 的核心 InsightPi-Serini 并不是提出了一个新的检索模型，而是重新设计了 Agent 与检索器的交互方式 。其核心 Insight 在于： BM25 的弱点往往不是算法本身，而是浅层检索和糟糕的配置。
### 1. 工具链分离：搜索、浏览、阅读传统 Agent 通常只暴露一个 search 工具，一次性返回 Top-K 文档全文，这导致上下文窗口迅速膨胀，且 Agent 缺乏筛选机制。Pi-Serini 将交互拆分为三个独立工具：
- search: 执行 BM25 查询，返回 Top-1000 结果的缓存排名（Search ID），仅展示前 5 个片段。
- read_search_results: 基于 Search ID 分页浏览缓存结果，允许 Agent 在不发起新请求的情况下探索更深层的排名。
- read_document: 按需读取具体文档的特定部分。
这种设计让 Agent 能够 先浏览排名，再决定读取哪些文档 ，极大地提高了上下文窗口的利用率。
### 2. BM25 参数调优：为长文档而生BrowseComp-Plus 数据集的平均文档长度约为 5,179 词，中位数约 2k tokens。ANserini 默认的 BM25 参数（ k1=0.9,b=0.4k_1=0.9, b=0.4 ​ = 0.9 , b = 0.4 ）是针对短文本优化的。
作者通过网格搜索发现，针对长文档调优后的参数（ k1=25,b=1k_1=25, b=1 ​ = 25 , b = 1 ）能显著提升召回率。这是因为长文档中术语频率饱和，需要更高的 k1k_1 ​ 来平衡词频贡献，更高的 bb 来归一化文档长度。
### 3. 时间预算引导（Time-Budget Steering）
不同于传统的固定迭代次数限制，Pi-Serini 采用硬时间预算（如 300 秒）。在 70% 时间点后，强制 Agent 停止搜索并基于已有证据生成答案。这防止了 Agent 在无意义的搜索循环中浪费 Token 和金钱。

## 工程启示- 不要忽视 BM25：在构建 Agent 时，BM25 依然是极具性价比的基础设施。它的速度快、成本低、可解释性强。
- 检索深度是关键：浅层检索（Top-5 或 Top-10）往往不足以支撑复杂推理。给予 Agent 更深的检索缓存（如 Top-1000）并允许其分页浏览，能显著提升证据覆盖率。
- 参数需针对场景调优：默认参数往往不是最优解。对于长文档场景，调高 k1k_1​ 和 bb 参数是低成本的优化手段。
- Agent 的工具设计比检索模型更重要：通过分离搜索、浏览和阅读工具，让 Agent 具备“先浏览后细读”的能力，比单纯提升检索模型的语义能力更有效。
## 局限与展望尽管结果亮眼，Pi-Serini 仍存在局限。首先，它依赖强大的 LLM（如 gpt-5.5）来有效利用检索结果。其次，Agent 在浏览缓存排名时仍存在“过早分支承诺”（Premature Branch Commitment）的问题，即一旦误判线索，难以回退。
未来的改进方向可能不在于进一步提升检索器的语义能力，而在于 设计更好的工具接口 ，帮助 Agent 更敏锐地识别和分配上下文给正确的证据。毕竟，当检索器已经找到了所有线索，剩下的挑战是如何让 Agent 聪明地使用它们。
