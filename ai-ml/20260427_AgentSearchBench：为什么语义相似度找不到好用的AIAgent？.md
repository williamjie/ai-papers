# AgentSearchBench：为什么语义相似度找不到好用的 AI Agent？

**日期**: 2026-04-27

---

论文 : AgentSearchBench: A Benchmark for AI Agent Search in the Wild链接 : https://arxiv.org/abs/2604.22436AI agent 生态正在爆发——从 GPT Store 到 Agent.ai，每天都有新的 agent 上线。但一个核心问题被严重低估： 你怎么知道哪个 agent 真的能搞定你的任务？
这篇论文戳破了一个幻觉：靠文档描述匹配来搜索 agent，大概率会翻车。
## 问题出在哪？agent 和传统工具真不一样传统工具检索（比如函数搜索）假设能力是静态的：一个 send_email 函数，签名就是一切。但 agent 的能力是 组合式 且 执行依赖 的——同一个“写代码”agent，有的能重构，有的只能补全 Bug；有的擅长 Python，有的精通 Rust。文档里写的“代码专家”可能只是营销话术。
更麻烦的是，agent 生态是开放的，能力边界模糊，文档质量参差不齐。Table 1 对比了现有基准：
Benchmark 类型 #候选 真实来源 任务类型 ToolBench Tool 16,464 ✓ Exec. ToolRet Tool 43,215 ✓ Exec. TREC 2025 LLM 1,131 ✓ Exec. AgentSquare Agent 16 ✗ Exec. OKC Bench Agent 127 ✗ Exec. AgentSearchBench Agent 9,759 ✓ Exec. / Non-exec.
问题清晰了： 现有研究要么候选池太小，要么假设功能明确，要么只支持可执行查询，没有覆盖“从一段话猜 agent”的真实场景。
## 核心设计思想：用执行结果定义“相关性”
论文最大的 insight 是： agent 的相关性不能靠文本相似度判断，必须通过任务执行来测量。
他们构建了一个两层问题框架：
- 可执行任务查询 (Task Query)：直接可运行的指令，比如“用 Python 实现快速排序”
- 高层任务描述 (Task Description)：抽象目标，比如“为一个教育平台设计一套互动的数学练习系统”
对于第一种，agent 跑一遍就知道行不行；对于第二种，需要背后关联多个具体查询，看 agent 在多个场景下的稳定表现。
然后， 用执行分数打标签 ：跑分 ≥ 4 分（5 分制）就算相关（ rel(a,Tq)=1 ）；对于任务描述，取所有关联查询的平均相关性。
更精细的是，如果 agent 成功完成了 文档没写的任务 ，相关性打折（比如 0.5）——这说明能力可能是侥幸，不可靠。
## 数据规模与多样性：真实世界的混乱Figure 2 展示了数据规模：
- 9,759 个真实 agent（来自 GPT Store、Google Cloud Marketplace、Agent.ai）
- 2,952 个可执行查询（单 agent 2,452 个 + 多 agent 500 个）
- 259 个任务描述，每个关联约 10 个查询- 66,740 次执行，用来打分heterogeneity 很足：agent 覆盖 16 个领域（软件开发、数据分析、医疗、教育…），文档风格、粒度、功能重叠程度千差万别——这正是开放生态的现实。
## 实验结果：语义相似度与实际能力的鸿沟### 1. 检索阶段（Table 2）
先看可执行任务查询： 工具感知的检索器赢了 。ToolRet 的 NDCG@5 达到 37.52%，比 BM25 的 32.41% 高出 5 个百分点。这说明 agent 的工具使用信息对匹配能力很重要。
但换到高层任务描述，形势逆转： BGE-Large 的 NDCG@5 达到 23.08% ，超过 ToolRet 的 21.15%。因为抽象目标需要语义推理，单纯工具信号不够用了。
关键是， 所有方法的 Completeness（召回全部相关agent）都很低 ——可执行查询下，最好的 ToolRet 在 @20 时 Completeness 仅 27.80%，说明前 20 个结果里漏掉了很多能打的 agent。
### 2. 重排序阶段（Table 3）
在 top-20 候选池里精排：
- 可执行查询：各种重排器差距不大，NDCG@5 在 61-64% 之间。说明表层信号对具体任务够用了。
- 高层描述：RankGPT Qwen-3 32B 拿到 66.00% NDCG@5，比 Cross-Encoder 类高 4-8 个点。LLM 的强推理能力在这里发挥作用，能 decode 出潜在需求。
但 Completeness 仍然惨淡——即使是 LLM 重排，在任务描述上也几乎为 0。这意味着 靠文档排序，很难把真正能 cover 复杂目标的 agent 排到前面 。
### 3. 语义-性能错配有多严重？（Figure 4）
这是论文最震撼的图：比较“模型排序”和“黄金排序（按真实跑分）”的累积得分。
所有方法都远低于 oracle。关键是 提升是平缓分布的 ——不是前几名就能搞定，而是排名越往后的 agent，真实得分越高。这说明 文档写得好 ≠ 跑得赢 ，大量靠谱 agent 被埋没了。
### 4. 文档完整度的影响（Figure 5b, 5c）
比较“仅用描述索引” vs “完整文档（含示例）索引”：
- 大多数模型在完整文档下 NDCG@5 提升 0.05-0.15（5-15 个百分点）
- 说明使用示例是宝贵的行为信号，甚至比描述本身更有用### 5. 轻量级探测有效吗？（Figure 6）
这是工程上最实用的发现：让 LLM 生成一些探测查询，去执行 agent，然后用执行结果增强排序。
前提条件 ：探测响应要在 agents 之间有 中等或高方差 ——如果所有 agent 都给出相似答案，这问题没区分度。
效果（Table 6b）：BGE Reranker + 探测，NDCG@5 从 57.93% → 58.16%（+0.40%）；Tool-Rank 8B 从 60.82% → 61.71%（+1.46%）；Qwen Reranker 4B +1.56%。
虽不是颠覆性提升，但在已有 pipeline 上加几行探测代码就能获得收益， 投入产出比极高 。
## 工程启示：给你的实践建议-不要迷信 agent 文档。Semantic similarity ≠ capability。像 BGE 这种 embedding 模型在抽象任务上只能达到 23% 的 NDCG，漏掉 70% 以上靠谱 agent。
-执行信号是王道。最简单的策略：给你的检索 pipeline 加上轻量探测——生成 5-10 个任务相关探测查询，让候选 agent 跑一遍，用结果 rerank。实验显示这能带来稳定提升，尤其当探测问题有区分度时。
-索引时一定要存使用示例。完整文档比纯描述 NDCG@5 高 0.1-0.15，说明开发者写的 usage example 是 gold mine。
-高层任务需要更强的推理模型。从“写个爬虫”到“帮我竞品分析”，抽象度每提升一级，cross-encoder 就不够看了，得用 LLM-based reranker（RankGPT 类）。
-多 agent 任务更难。Figure 4(b) 显示多 agent 查询的累积得分曲线更平缓——说明能力是分布式的，没有单个 agent 能全包，需要组合发现。这指向一个方向：agent 搜索不能只做 point-wise 检索，要做任务分解 + 多阶段检索。
## 局限与未来方向论文自己也承认局限：
- 执行依赖于特定 LLM judge，可能存在 bias- 真实用户查询的多样性远超合成数据- multi-turn 交互未被充分覆盖未来的方向很明确：
- 在线适应性探测：根据中间结果动态调整探测策略，而不是一次性生成- 跨 provider 的一致性：不同平台 agent 的文档风格差异大，需要统一表示- 成本-效益权衡：全量执行太贵，如何用最少探测次数最大化排序收益## 一句话总结AgentSearchBench 用 1 万个真实 agent 和 6.7 万次执行证明：靠文档搜 agent 是玄学，轻量执行探测才是工程落地的正途。
如果你正在做 agent 编排或 agent 市场，这篇论文的数据和 pipeline 值得认真研读——特别是那个“生成探测查询 → 执行 → 增强排序”的闭环，成本低、见效快。别再卷 embedding 了，让 agent 跑起来看结果，才是硬道理。
