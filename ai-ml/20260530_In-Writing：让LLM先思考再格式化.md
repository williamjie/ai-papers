# ⭐⭐⭐½ In-Writing：让 LLM 先思考再格式化

**日期**: 2026-05-30

---

论文 : Thinking Before Constraining: A Unified Decoding Framework for Large Language Models链接 : https://arxiv.org/abs/2601.07525在工程落地中，我们常陷入两难：想要 LLM 的推理能力，就得忍受它不稳定的输出格式；想要严格的 JSON 结构，又往往牺牲了模型的思考深度。这篇来自 Nokia Bell Labs 的论文提供了一个优雅的解法： In-Writing 。它不修改模型权重，也不搞复杂的双阶段流水线，仅通过解码器的状态切换，就实现了“自由推理 + 严格格式化”的完美统一。
### 为什么现有的方案都不够好？
目前处理结构化输出的主流方案主要有三种，但各有硬伤：
- 自然生成（Natural Generation）：让模型随便写，最后用正则或另一个模型去提取答案。痛点是不可靠，一旦模型“话痨”或者格式稍有偏差，解析就会失败。
- 硬约束解码（Constrained Decoding）：从第一个 token 开始就强制符合 JSON/Regex 语法。痛点是扼杀推理，研究表明，过早的格式限制会严重损害模型的逻辑表达能力，导致准确率大幅下降。
- NL-to-Format 流水线：先让模型生成自然语言，再调用一个大模型将其转换为结构化数据。痛点是成本高且延迟大，多了一次推理调用，且无法保证最终格式的绝对合规。
还有一种混合方案 CRANE，试图通过分隔符在自由和约束间切换，但它依赖复杂的 Prompt 工程，且在多字段提取时容易失效。
### In-Writing 的核心 Insight：解耦思考与格式化In-Writing 的核心直觉非常简洁： 推理（Reasoning）和格式化（Formatting）是两个正交的任务，不应该混在一起。
传统约束解码的问题在于，它在模型还在“思考”的时候，就强行限制了它的词汇选择空间。In-Writing 改变了这一顺序：
- 自由推理阶段：模型完全不受限制地生成思维链（Chain-of-Thought），直到遇到一个特定的触发令牌（Trigger Token）。
- 结构化生成阶段：一旦检测到触发令牌，解码器立即切换到约束模式，严格按照预定义的 Schema（如 JSON）生成最终答案。
⚠️ 关键设计细节 ：如何避免“过早触发”？
如果模型在推理中途误触发了格式标记怎么办？论文发现，将 <eos> （结束符）作为唯一的触发令牌是最稳健的策略。因为在大多数思维链任务中， <eos> 通常标志着推理的结束。这种简单的策略几乎彻底消除了“过早触发”导致的截断问题。
从数学上看，传统约束解码是 P(A∣R,q,F)P(A | R, q, F) ，即答案和推理都受格式 FF 影响；而 In-Writing 将其解耦为 P(R∣q)×P(A∣R,q,F)P(R | q) \times P(A | R, q, F) P ( A ∣ R , q , F ) ，保留了推理的自由度，同时保证了输出的规范性。
### 实验结果：性能与效率的双赢论文在 GSM8K、Last Letter Concatenation 等多个基准测试上，对比了 Baseline（自然生成）、Constrained（硬约束）、NL-to-Format 和 In-Writing。数据非常有说服力：

- 超越 NL-to-Format：在 GSM8K 上，In-Writing 比两阶段流水线高出 3.2%。这是因为 In-Writing 的约束解码不仅起到了格式化作用，还充当了“纠错器”，利用语法约束修正了推理中可能存在的细微偏差。
- 彻底解决解析失败：Baseline 方法的解析率波动极大，而 In-Writing 实现了 100% 的格式有效性。对于工业级应用来说，这是决定性的优势。
- 极低的额外开销：相比 NL-to-Format 需要额外的模型调用和输入 Token，In-Writing 仅增加了 5-20 个 Token 的输出长度（即最终的 JSON 结构部分），几乎不增加推理延迟。
### 工程启示与局限对于正在构建 Agent 或需要结构化输出的开发者来说，In-Writing 是一个极具性价比的升级方案：
- 无需微调：直接在现有 LLM 上应用，通过修改解码逻辑即可实现。
- 兼容性强：基于 Outlines 等库扩展实现，支持 Pydantic 定义的复杂 Schema。
- 提升鲁棒性：即使 Prompt 没有明确指导输出格式，模型也能在推理结束后自动补全正确的结构。
局限性 ：论文承认，目前的评估是在“无特殊提示”的基准下进行的。如果针对 In-Writing 专门优化 Prompt（例如明确告知模型何时触发），效果可能会更好。此外，对于需要极长上下文且中间穿插多次结构化输出的复杂任务，单一触发点的策略可能需要进一步扩展。
总之，In-Writing 证明了： 不要试图在思考时戴上手铐，而应该在思考结束后穿上制服。 这种“先思后构”的模式，或许将成为未来 LLM 推理的标准范式。
