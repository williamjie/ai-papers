论文 : Getting Better at Working With You: Compiling User Corrections into Runtime Enforcement for Coding Agents链接 : https://arxiv.org/abs/2606.13174你是否经历过这种绝望：明明在上一轮对话里纠正过 Agent “提交前请清理调试文件”，结果下一轮它依然把 debug.log 推到了主分支？
现有的 AI 编程助手（Coding Agents）普遍存在一个隐蔽的痛点： “记住”不等于“遵守” 。
大多数系统依赖长期记忆（Long-term Memory）或提示词增强（RAG），试图让模型在下次对话中“回想”起你的偏好。但 Notre Dame 和 IBM Research 的最新研究指出，这中间存在巨大的 访问-合规差距（Access-Compliance Gap） 。即使模型成功检索到了相关记忆，它依然可能为了完成眼前的编码任务而忽略这些约束。
这篇论文提出的 Trace 框架，不再把用户的纠正视为“建议”，而是将其编译为 运行时强制检查（Runtime Enforcement） 。
### 核心 Insight：从“软建议”到“硬门禁”
传统方案的逻辑是：用户纠正 -> 存入记忆库 -> 下次检索 -> 放入 Context Window -> 模型自行决定遵循与否。
Trace 的核心直觉非常工程化： 自然语言偏好是不可靠的，必须转化为可执行的代码检查。
当用户说“停止前清理调试文件”时，Trace 不会只存这句话。它会通过轻量级 LLM（如 Gemma 4 31B）将其拆解为：
- 原子规则（Atomic Rule）：清理特定后缀的文件。
- 适用条件（Applicability）：当任务涉及临时文件生成时触发。
- 验证器（Verifier）：在 Agent 提交或终止前，实际检查文件系统中是否存在这些文件。
如果验证失败，Agent 的执行流程会被直接拦截（Hook），强制其修正行为，直到通过检查才能继续。这就把“个人化偏好”从 Prompt 里的软约束，变成了 Runtime 里的硬门禁。
### 实验数据：记忆有多不可靠？
论文在诊断性实验中给出了令人震惊的数据。在包含真实用户摩擦场景的测试中，即使使用了先进的 Mem0 记忆后端，仍有 57.5% 的适用偏好检查被违反。
相比之下，Trace 的效果显著：
方法 合规率 (Compliance Rate) 备注 No Rules 31.6% 基线 Mem0 Memory 42.5% 即使检索到记忆，仍大量违规 All Rules (Context) 55.0% 全量规则放入上下文 Trace (Compiled) 70.1% 运行时强制检查在更严格的分布外（OOD）测试中，Trace 的优势进一步扩大。在 ClawArena 基准上，Trace 将偏好违规率从 100% 降至 2.0% ，而传统记忆基线依然接近 100% 的违规率。
⚠️ 反直觉发现 ：增加上下文中的规则数量（All Rules）并不能保证合规。模型往往会“选择性失明”，优先满足主要编码目标，而牺牲次要的格式或清理要求。只有强制性的运行时检查才能打破这种优化偏差。
### 工程启示：Agent 架构的新范式这篇论文对构建生产级 Coding Agent 有直接的指导意义：
- 记忆与执行解耦：不要指望 RAG 能解决所有个性化问题。对于关键的工作流约束（如代码规范、文件清理、权限控制），必须引入独立的验证层。
- 规则即代码：用户的自然语言反馈应被视为“需求文档”，通过编译器转化为可执行的检查脚本（Scripts/Hooks），而非仅仅存入向量数据库。
- 低成本拦截：Trace 的运行时开销极低（平均每轮仅增加约 40 秒，与无记忆基线持平），因为它只在关键节点（如提交、终止）触发检查，而非全程监控。
### 局限与展望目前 Trace 主要依赖于规则提取的准确性。如果轻量级 LLM 错误地解析了用户的模糊指令，生成的验证器可能会过于严格或失效。此外，对于高度语义化、难以形式化的偏好（如“代码风格要优雅”），目前的确定性检查手段仍显不足。
未来的方向可能是结合 运行时执行引擎 与 大模型语义判断 ，构建更灵活的混合验证层。但无论如何，Trace 证明了一点：想让 Agent 真正“听懂人话”，光靠让它“记住”是不够的，你得给它装上“刹车”。
