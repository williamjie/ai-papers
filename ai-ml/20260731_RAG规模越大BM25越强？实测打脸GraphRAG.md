论文 : BM25 Wins at Scale: A Scaling Study of Retrieval-Augmented Generation Paradigms链接 : https://arxiv.org/abs/2607.26497这篇论文给正在纠结“上 GraphRAG 还是 Agent”的工程团队泼了一盆冷水。它通过严格的控制变量实验证明：随着知识库规模扩大，看似过时的 BM25 检索反而在准确性和成本上全面碾压复杂的图检索和 Agent 搜索。这直接挑战了当前 RAG 领域“越复杂越好”的直觉。
### 痛点：我们真的需要复杂的 RAG 吗？
目前 RAG 方案百花齐放：有基于词法的 BM25，有向量检索（Dense Retrieval），有构建知识图谱的 GraphRAG（如 MS-GraphRAG、LightRAG），还有像 Claude Code 那样通过文件系统工具进行多步探索的 Agent。
但现有评估大多存在两个致命缺陷：
- 规模固定：只在单一数据集大小上比较，无法反映企业知识库随时间增长后的表现。
- 基准不一：不同方法使用不同的评测集和阅读器模型，导致结果不可比。
这就导致了一个盲区：当数据量从几千文档膨胀到几十万时，哪种范式才是性价比之王？
### 核心洞察：全局排序优于局部探索论文的核心 Insight 在于揭示了“规模依赖的交叉点”（Scale-dependent Crossover）。
在小规模语料库中， 文件系统 Agent （File-System Agent）凭借多步推理和工具调用，能精准定位信息，表现最佳。但随着语料库扩大，Agent 需要进行的探索步骤呈指数级增长，Token 消耗剧增且容易迷失方向。
相反， BM25 虽然简单，但它提供的是全局候选排序（Global Candidate Ranking）。这种“一次性全局扫描”的能力在大规模数据中极具优势，因为它不受搜索空间膨胀的影响。
反直觉发现 : 在语料库达到约 1000 万 Token 时，BM25 的准确率曲线反超 Agent。在全规模（6 亿 Token）下，BM25 的得分比 Agent 高出近 20 个百分点。
### 关键结果：数据不会撒谎论文在 EnterpriseRAG-Bench 上构建了 28 个严格嵌套的数据层级，从 1,144 篇文档扩展到 511,959 篇文档（约 6 亿 Token），保持问题和干扰项不变。以下是核心对比：

- GraphRAG 的构建墙：HippoRAG 2 和 LightRAG 在达到全规模前就因构建成本过高而停止。LightRAG 预计需要约 4 个实例年才能完成全量构建，这在工程上不可接受。
- Agent 的效率崩塌：在全规模下，Agent 的查询 Token 消耗是 BM25 的 39 倍以上（从 5.8K 涨到 226K+），且准确率大幅下降。这是因为 Agent 在庞大的文件树中进行局部搜索，难以找到全局最优解。
- BM25 的鲁棒性：BM25 不仅准确率高，而且查询成本几乎不随规模变化，始终保持在 Pareto 前沿的低成本端。
### 工程启示：如何落地？
- 默认首选 BM25：对于企业级知识库（尤其是包含大量精确术语、代码、日志的场景），BM25 是最稳健的默认选择。它能有效过滤掉语义相似但事实错误的“陷阱”文档。
- Agent 的正确用法：不要直接用 Agent 进行全局搜索。论文建议采用 BM25 + Agent 的组合模式：先用 BM25 进行全局候选发现，再让 Agent 对筛选后的少量文档进行深入推理。这种混合模式下，准确率可从 36.9 提升至 69.4，且 Token 消耗仅为纯 Agent 的九分之一。
- 谨慎使用 GraphRAG：除非你的场景极度依赖实体关系推理，且数据量较小（<10 万文档），否则 GraphRAG 的构建成本和噪声引入往往得不偿失。
### 局限与展望该研究主要基于企业内部的非结构化文档（邮件、工单、代码等），这些文本具有强烈的词汇锚点特征。在高度依赖语义理解的开放域问答中，Dense Retrieval 可能仍有其用武之地。此外，论文未探讨多模态 RAG 的扩展性，这也是未来值得关注的方向。
总之，这篇论文提醒我们：在 RAG 工程中， 简单且可扩展的全局排序往往优于复杂但脆弱的局部探索 。不要为了炫技而引入 GraphRAG，BM25 依然是大规模场景下的王者。
