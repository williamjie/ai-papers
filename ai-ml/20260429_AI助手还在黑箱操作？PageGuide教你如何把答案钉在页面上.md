# AI 助手还在黑箱操作？PageGuide 教你如何把答案钉在页面上

**日期**: 2026-04-29

---

论文 : PageGuide: Browser extension to assist users in navigating a webpage and locating information链接 : https://arxiv.org/abs/2604.23772讲个你可能经历过的场景：你问 ChatGPT “亚马逊最远源头发源于哪条溪流？“，它回答 “Quebrada Carhuasanta”。听起来挺对，但 它没在页面上高亮那段文字 ——你得自己Ctrl+F去维基百科翻。再比如你想隐藏社交媒体上的政治帖子，但 AI只能口嗨，改不了页面 。
这就是当前 AI 助手的最大问题：它们要么全自动帮你操作（ opaque 的黑箱），要么只给文字答案（无法落地到页面）。用户始终处于” 盲信 ”状态——要么不知道AI点了哪里，要么找不到答案出处。
Auburn 大学这篇 PageGuide，干了一件很酷的事： 把 LLM 的答案，直接”钉”在 HTML DOM 上 。不是 sidebar 里显示引用，而是页面上真实出现高亮。听起来简单？但这背后是一套完整的”可验证的混合协作”设计哲学。
## 为什么现有方案都不行？
翻翻论文的Table 1（虽然正文没直接画表，但Figure 1对比得很清楚），当前方案可以归成两类：
高自治、低可解释性 ：OpenAI Operator、BrowserUse 这类全自动 agent。它们能帮你填表、下单、导航，但你看不到它们为什么点那个按钮。论文引用了一堆事故案例：误删数据、点错下载链接、 unintended 购买。用户成了旁观者，只能祈祷 AI 别手滑。
低自治、无页面锚定 ：ChatGPT、Claude 这类聊天助手。它们能总结、能回答，但回答是悬浮的——你得自己回到页面找证据。更别说”隐藏内容”这种操作，它们连尝试都不敢。
中间地带呢？几乎没有。这就是 PageGuide 要填补的 gap： 既保留用户控制权，又把 AI 的输出直接映射到页面元素 。
## 核心设计：Find–Guide–Hide 三角框架Paper 的核心 insight 很朴素： 用户需要三种操作，分别对应三种交互模式 。
-Find（找证据）：用户问事实性问题，AI 不仅要回答，还要在页面上高亮支撑文本。比如问”亚马逊源头发源于哪？“，AI 返回的答案里，“Quebrada Carhuasanta” 是可点击的，点击后页面直接滚动到那段话并高亮。设计关键是inline citation：每个事实声明后面都跟一个 [N:"exact phrase"] 的标注，N 是 DOM 索引，phrase 是精确文本。这样用户一眼就能验证——不用来回切换上下文。
-Guide（分步指导）：针对多步骤任务（比如”改 GitHub 密码”），AI 不直接代劳，而是一次只给一步指令，且高亮当前按钮。Figure 2 的交互很精妙：侧边栏显示”Step 1: Click Settings”，同时页面的 Settings 按钮有个脉冲动画。用户点”Next”才进入下一步，过程中随时可以”Stop”。这就是 mixed-initiative 的精髓——AI 带路，但方向盘在你手里。
-Hide（智能隐藏）：针对干扰内容（广告、政治帖子），AI 不是用固定规则（传统 ad blocker 那一套），而是用 LLM 理解你的语义意图，逐个 DOM 元素打分，然后弹出一个确认框，列出”要隐藏的元素 + 隐藏理由 + 内容预览”，你可以逐个勾选确认才执行。论文强调的是透明度：每个隐藏决定都有解释，用户可以 override。
## 技术直觉：SoM + Router + DOM 锚定实现这三板斧，Paper 用了三个核心技术：
Set-of-Marks (SoM) 索引 ：PageGuide 先把当前页面的 HTML DOM 遍历一遍，给每个可见、可交互、含文本的节点分配一个整数索引。数据结构是 (id_j, text_j, tag_j, bbox_j) 。这样 LLM 就不用 parsing 混乱的 HTML，直接通过索引引用元素。这是 页面表征的标准化 。
Router 路由 ：用户输入 query 后，Router（一个轻量 LLM 分类）判断这是 Find/Guide/Hide 哪一种模式，然后分发给对应的 handler。Prompt 里给了 canonical examples，确保分类稳定。这一步很关键—— 不同模式需要不同的推理策略 ，混在一起 prompt 效果会打折扣。
HTML DOM 直接突变 ：所有输出最终都以 DOM mutation 形式落地。Find 是包裹高亮 span；Guide 是叠加 pulse beacon；Hide 是 display:none + 理由浮层。 页面本身成为输出媒介 ，而不是聊天框。这保证了用户视线不需要离开页面。
还有一个细节：Guide 模式是迭代的。每确认一步，系统 重新读取更新后的 DOM ，再生成下一步。这解决了”页面跳转后状态变化”的难题——典型的 web agent 挑战。

## 工程启示：我们该怎么抄？
这篇论文的工程价值，不在于算法多复杂，而在于 交互范式的转变 。对我们实际做 agent、本地模型、前端集成，有几点直接启发：
1. DOM 锚定比文本引用更可靠 。很多 RAG 系统会给答案加 [来源1] ，但用户还得自己回去翻。PageGuide 证明： 把引用转化成页面上的视觉锚点 ，体验提升巨大。我们在做文档问答、代码助手时，应该把”定位”和”回答”打包输出。
2. 分步指导 + 用户确认 = 更高成功率 。纯自动化 agent 在 WebArena 上 task success rate 也就 30-40%，而 PageGuide 的 Guide 模式在 用户配合 下达到 53%。这说明 对于复杂任务，混合智能（human-in-the-loop）不仅安全，而且更有效 。工程上，我们可以设计”建议-确认”的工作流，而不是全权委托。
3. 意图驱动的隐藏需要 LLM 语义理解 。传统 ad blocker 用规则，但遇到”隐藏让人不舒服的帖子”这种主观需求就抓瞎。PageGuide 用 LLM 逐个元素打分，并附上理由。这提示我们： 任何需要语义过滤的场景（评论审核、信息降噪），都可以用”LLM评分 + 人工确认”的模式 。
4. SoM 索引是轻量级但强大的页面表征 。SoM 不是新概念（ScreenAI、WebQuest 都用过），但 PageGuide 把它用在三个模式里，证明了它的通用性。做本地 agent 时，我们可以先跑一个轻量模型提取 SoM，再用小 LLM 做 routing 和 reasoning， 平衡速度和精度 。
5. Error Recovery 很重要 。Guide 模式里，如果用户确认点击后页面没按预期跳转，系统会 重新读取 DOM 并重生成剩余步骤 。这种”观察-调整”的闭环，是 robust web agent 的必备能力——不要假设世界是确定性的。
## 局限与未竟之路论文也坦诚了几个局限：
Hide 模式目前只支持 display:none ，没处理动态加载（infinite scroll）的内容。如果页面滚动后新元素出现，用户得重新触发 Hide。这提示我们需要一个 持续监控的过滤器 。
评估用的是学生样本 ，且任务限时 3 分钟。真实场景下（比如老年人用网页、高压工作环境），表现可能不同。
Router 是单点 LLM 调用 ，没有 fallback 机制。如果分类错了（比如把 Hide 当成 Find），用户体验会打结。生产环境可能需要规则兜底。
扩展性 ：SoM 索引在巨型页面（比如超长社交媒体流）上可能变慢。需要 element filtering 或视窗裁剪。
后续方向论文提了： 个性化 hide 策略学习 （根据用户历史偏好自动调权）、 跨会话记忆 （记住用户常隐藏的元素类型）、 多模态 grounding （结合截图+DOM双重验证）。
## 一句话总结PageGuide 的贡献不是”更聪明的 AI”，而是 更诚实的 AI ——它不替你做完，而是告诉你”我在哪里、要做什么、为什么这么做”。
这种”锚定页面元素”的设计，把 AI 从黑箱执行者变成了 可审计的协作者 。对于做本地 agent、浏览器插件、或任何需要人机协作的场景，这个范式值得借鉴： 让输出落地到用户正在看的界面，而不是飘在侧边栏 。
如果你也在折腾 Web Agent，别只关心 task success rate，问问自己：我的系统，能让用户 相信 它吗？
