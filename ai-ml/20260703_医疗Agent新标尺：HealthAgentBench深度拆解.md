论文 : HealthAgentBench: A Unified Benchmark Suite of Realistic Agentic Healthcare Environments for Challenging Frontier AI Agents链接 : https://arxiv.org/abs/2606.31179如果你还在用 MedQA 这种静态问答集来评估你的医疗 Agent，那你可能低估了现实临床工作的复杂度。微软研究院最新发布的 HealthAgentBench，直接把评测场景从“给个 Prompt 答个问题”升级到了“扔进终端环境自己折腾”。这不仅是基准的更新，更是对当前 AI Agent 落地能力的真实压力测试。
## 为什么现有的评测不够用了？
传统医疗基准（如 MedQA）主要考察模型在给定上下文下的推理能力。但真实的临床工作流往往是多模态、长周期且数据庞大的：医生需要查看 3D CT 体积、分析吉像素级病理切片，还要在纵向电子健康记录（EHR）中追溯病史。
现有的 Agent 评测要么局限于单一模态，要么预设了固定的工作流步骤。HealthAgentBench 的核心洞察在于： 真正的 Agent 能力体现在自主探索和非结构化环境中的规划执行 。它不再提供“喂到嘴边”的数据，而是让 Agent 在 Docker 容器中面对原始数据，自行决定调用什么工具、如何裁剪图像、怎样查询数据库。
## 方法拆解：终端即环境，极简指令HealthAgentBench 包含 54 个任务，覆盖 7 大类别，贯穿患者旅程的诊断、研究、治疗规划等阶段。其设计有几个关键直觉：
- 终端环境（Terminal Environment）：所有任务封装为 Docker 容器，Agent 通过命令行交互。这模拟了开发者或数据科学家的真实操作界面，迫使 Agent 具备安装包、运行脚本、处理文件的能力。
- 极简指令（Minimal Instructions）：只给目标，不给路径。例如“修正这份 X 光报告”，Agent 必须自己决定是先看图、再查历史病历，还是直接调用图像处理库。这测试的是原生规划能力，而非对特定工作流的记忆。
- 防作弊设计：黄金标签和验证代码仅在评估阶段挂载，Agent 容器内不可见。文件名去标识化，禁止联网搜索，确保 Agent 必须通过逻辑推理和数据探索得出答案。
- 低随机成功率：任务设计避免简单的二分类（随机猜对率 50%），而是采用多标签或多步骤验证，使随机猜测的成功率低于 10%，确保分数反映真实能力。
## 关键结果：SOTA 模型也仅及格边缘评测结果显示，即便是最强的前沿 Agent，表现也远未饱和。以下是核心数据对比：

### 细分领域的强弱项- EHR 建模与格式转换（强项）：在 EHR Format Conversion 任务中，9/10 的 Agent 达到了 100% 成功率。这表明当前 Agent 在处理结构化数据清洗和 ETL 管道构建上已接近人类专家水平。
- 医学影像（弱项）：CT 异常分类、病理肿瘤区域选择等任务仍是难点。特别是对于 Claude Code 系列模型，影像处理能力明显落后于 Codex GPT 系列。
- 大海捞针式检索（瓶颈）：在 EHR Data Quality Auditing 中，Agent 需要在 800k+ 行数据中找出注入的错误。最佳成功率仅为 42%（Claude Code Opus-4.6）。实验表明，搜索空间的大小和组合推理的复杂度是当前 Agent 的两座大山。当需要同时检测多种错误类型时，性能显著下降。
## 工程启示- 多智能体架构的价值：Copilot CLI 表现优于原生 Claude Code，部分原因在于其多 Agent 架构允许主模型将子任务委派给专用后端（如检索、验证），这种分工在复杂工作流中更有效。
- 成本效益优先：在医疗场景中，延迟和成本至关重要。Codex GPT-5.5 以更低成本和更短时间实现了最高成功率，提示我们在部署时应优先选择 Pareto 前沿上的模型，而非盲目追求参数最大的模型。
- 影像能力需专项优化：通用 LLM Agent 在处理高维视觉数据（如 3D CT、WSI）时仍显吃力。未来可能需要结合专门的视觉编码器或中间表示层，而非直接让 LLM “看”原始像素。
## 局限与展望HealthAgentBench 目前主要依赖终端交互，这可能限制了某些图形界面重度依赖的工作流评估。此外，虽然它涵盖了多种模态，但在实时临床决策支持（如急诊分诊）的动态交互场景中仍有空白。随着 Agent 在长程推理和工具使用上的进步，这个基准将帮助行业更清晰地追踪从“玩具 Demo”到“临床可用”的差距。
