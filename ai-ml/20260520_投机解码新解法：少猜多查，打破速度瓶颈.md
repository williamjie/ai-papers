# ⭐⭐⭐⭐ 投机解码新解法：少猜多查，打破速度瓶颈

**日期**: 2026-05-20

论文 : Draft Less, Retrieve More: Hybrid Tree Construction for Speculative Decoding链接 : https://arxiv.org/abs/2605.20104大语言模型（LLM）推理加速一直是工程界的硬骨头，而投机解码（Speculative Decoding）是目前最主流的无损加速方案。但现有的树形投机解码（如 EAGLE-3）面临一个尴尬的帕累托前沿：树越密，接受率越高，但显存带宽和计算开销也爆炸；树越稀疏，速度虽快，却因剪枝过度导致接受长度（MAT）暴跌。
这篇来自阿里通义实验室和浙江大学的论文 Graft ，提出了一种反直觉的思路： 与其费力去“猜”那些低置信度的 token，不如把省下来的算力预算，用来“查”现成的上下文。 这种“剪枝+检索”的混合策略，不仅打破了原有的速度-长度权衡，还在 Qwen3-235B 这种超大模型上实现了惊人的加速效果。
### 痛点：剪枝的代价被低估了目前的动态树构建方法（如 DDD, SVIP）通常通过动态深度剪枝来减少计算量。逻辑很简单：如果草稿模型对某个分支没信心，就剪掉它，避免浪费验证算力。
但这有一个致命缺陷： 剪枝是不可逆的信息丢失。 一旦剪掉，原本可能有效的候选路径就彻底没了。论文 Figure 1 清晰地展示了这一点：纯剪枝方法（如 ECHO）虽然向右移动（速度提升），但其接受长度（MAT）始终低于密集树的上限。这意味着，你为了速度牺牲了吞吐量，且无法弥补。
作者敏锐地指出， 剪枝释放的不是“垃圾空间”，而是宝贵的“计算预算” 。既然目标模型的验证预算（Verification Budget）是固定的，剪枝省下的 slot 为什么空着？或者继续让草稿模型去瞎猜？
### 核心 Insight：用检索填补剪枝的空缺Graft 的核心设计在于 “Prune-then-Graft” （先剪后接）：
- 预算释放（Pruning）：基于校准的置信度阈值，在特定深度剪掉低置信度的草稿分支。这一步省下了大量的草稿计算开销。
- 预算补偿（Grafting）：利用省下的验证 slot，通过检索填入候选 token。这里的检索不是传统的 CPU 端向量搜索，而是基于 GPU 驻留的邻接矩阵（GPU-resident Adjacency Matrix）。
为什么这么设计？
- 零同步开销：传统的检索方法（如 PLD）往往依赖 CPU 查找或复杂的同步，这在高并发下是灾难。Graft 将邻接矩阵直接放在 GPU 显存中，检索退化为一次简单的行-列 Gather 操作，延迟几乎为零。
- 并行执行：检索分支以当前 token 为根，与草稿树的生成并行进行。只有当剪枝发生，释放出预算时，检索结果才会被“嫁接”进树中。
- 在线更新：矩阵内容并非静态，而是通过目标模型的验证信号在线更新。即使是被拒绝的节点，其目标分布也能提供有价值的后继概率，用于刷新矩阵。
这种设计巧妙地绕过了“剪枝导致覆盖率下降”的难题：剪枝负责提速，检索负责保量，两者在固定的验证预算下达成了互补。

### 工程启示与局限对工程实践的意义：
- 无需训练：Graft 是完全训练免费（Training-free）且无损的。你不需要重新训练草稿模型，只需集成这个混合树构建模块即可。
- 长文本友好：随着上下文变长，草稿树的注意力计算开销激增，剪枝的收益更大；同时长文本提供了更丰富的局部转移模式，提高了检索命中率。Graft 在长文本场景下的加速比（3.22×）非常可观。
- 易于集成：由于保持了标准的树注意力接口和验证预算，现有的推理引擎（如 vLLM, SGLang）只需修改树构建逻辑，无需改动核心的验证内核。
局限与展望：
- 冷启动问题：虽然通过 Warm-up 和在线更新缓解了邻接矩阵的冷启动，但在生成初期，检索的质量可能不如经过充分训练的草稿模型。
- 超参敏感：剪枝阈值 τd\tau_d​ 和检查点深度 DpruneD_{prune}​ 需要针对特定模型进行校准，这增加了一定的调优成本。
总的来说，Graft 提供了一个非常优雅的解决方案： 不要试图让草稿模型变得全能，而是让它专注于高置信度区域，剩下的交给廉价的上下文检索。 这种“术业有专攻”的资源分配思想，值得在更多推理加速场景中借鉴。
