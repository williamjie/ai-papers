论文 : AISPA: User-Centric System Prompt Auditing for Large Language Model Applications链接 : https://arxiv.org/abs/2607.28617我们常把注意力集中在模型权重的安全对齐上，却忽略了真正控制产品行为的“黑盒”——System Prompt。斯坦福团队提出的 AISPA 框架，首次从用户视角系统性地审计了 88 款商业 AI 产品的系统提示词，揭示了开发者在透明度和安全性上的真实水位线。
## 为什么 System Prompt 需要独立审计？
现有的 AI 安全研究多聚焦于防御外部攻击（如 Prompt Injection），将 System Prompt 视为受保护的“可信资产”。但这忽略了一个核心风险： 开发者可能主动编写有害指令 。
例如，为了提升留存率，某些提示词会指示模型“绝不透露自己是 AI”或“巧妙地将对话引向新方向”。这些指令即便在基础模型对齐良好的情况下，也会直接损害用户利益。目前缺乏标准化的第三方审计机制，导致用户在不知情的情况下与具有潜在操纵性的系统交互。
## AISPA 的核心设计直觉AISPA 的创新不在于提出复杂的算法，而在于构建了一套 基于人权规范的审计分类学 。其核心 Insight 是：System Prompt 的优劣不应由开发者自说自话，而应映射到具体的用户权利上。
框架定义了八个维度，每个维度都对应《世界人权宣言》的具体条款：
- 身份透明度：是否隐瞒 AI 身份？
- 信息真实性：是否允许幻觉或误导？
- 数据隐私：是否过度收集或泄露数据？
- 工具安全：执行代码前是否验证权限？
- 用户代理权：是否存在暗黑模式或情感依赖诱导？
- 不安全请求处理：是否拒绝越狱尝试？
- 危害预防：面对自残等高危话题是否提供专业指引？
- 公平与中立：是否避免歧视或偏见？
⚠️ 关键设计 ：审计单位不是整个 Prompt，而是 Span（片段） 。这种粒度允许在同一提示词中同时标记“保护性指令”和“问题指令”，从而揭示出许多产品中“安全与风险并存”的矛盾现状。
## 审计结果：繁荣下的隐患研究团队采用“LLM 初筛 + 人工复核 + 专家仲裁”的三级流水线，对 3,249 条指令进行了标注。数据揭示了几个反直觉的事实：
### 1. 保护性指令普及，但覆盖面极窄- 98.9% 的产品包含至少一条保护性指令。
- 然而，仅有 23.9% 的产品覆盖了全部八个审计维度。
- 这意味着大多数产品的安全策略是碎片化的，存在明显的监管盲区。
### 2. 问题指令依然普遍- 约 40% 的产品包含至少一条损害用户利益的指令。
- 即使在 2025 年 Q3 降至低点（19%），Q4 又反弹至 29%。
### 3. 厂商间差异巨大不同组织在提示词设计上的投入天差地别：

### 4. 提示词正在变得冗长且复杂从 2024 到 2025 年，平均 System Prompt 长度从 9K 字符激增至 30K+ 字符。保护性指令数量也翻了一番（15.0 -> 38.4）。这说明开发者确实在堆砌安全护栏，但也带来了维护成本和潜在冲突的风险。
## 工程启示对于正在构建 Agent 或垂直应用工程师而言，AISPA 提供了直接的行动指南：
- 建立内部审计清单：不要只依赖模型自带的安全能力。在发布前，对照 AISPA 的八个维度检查你的 System Prompt，特别是“身份透明度”和“用户代理权”这两个易被忽视的领域。
- 警惕“灰色地带”：论文发现了许多处于边界状态的指令（如诱导情感依赖）。在追求用户体验时，需明确界定“个性化”与“操纵”的界限。
- 模块化提示词管理：鉴于 Prompt 长度激增，建议将安全指令模块化，并通过自动化测试验证各模块是否冲突。
## 局限与展望AISPA 目前主要基于泄露或公开的提示词样本，可能存在选择偏差。此外，对于高度动态生成的 System Prompt（如 RAG 场景下的上下文注入），静态审计框架的适用性仍需探索。未来，如何将这种人工审计流程自动化，并集成到 CI/CD 流水线中，将是工程落地的关键一步。
