# ⭐⭐⭐½ 多智能体协作新范式：AgentFugue 集体推理

**日期**: 2026-05-29

---

论文 : AgentFugue: Agent Scaling for Long-Horizon Tasks through Collective Reasoning链接 : https://arxiv.org/abs/2605.24486做长程任务（Long-Horizon Tasks）的 Agent，大家通常有两种思路：要么堆算力让单个模型变强（Scaling Up），要么搞一堆角色分工复杂的系统（Orchestration）。但这两种路径都有瓶颈：单点探索容易陷入局部最优，而复杂的角色编排又引入了巨大的维护成本。
这篇来自中国人民大学和北京智源研究院的论文提出了一个很性感且落地的概念： AgentFugue 。它不玩角色分工，而是让一群“平级”的 Agent 通过一个共享的**推理中枢（Shared Reasoning Hub）**进行“集体推理”。简单说，就是让多个 Agent 像复调音乐（Fugue）一样，各自独立探索，但能实时听到并复用同伴的发现。
### 为什么现有的多 Agent 方案不够好？
目前的多 Agent 系统主要有两类痛点：
- 孤立搜索：像 Best-of-N 采样，多个 Agent 跑完后才汇总结果。这意味着如果 A 发现了关键线索，B 还在原地打转，直到最后才“撞车”，效率极低。
- 过度编排：传统的 Multi-Agent 框架（如 MetaGPT）需要预设复杂的角色和工作流。这不仅工程实现繁琐，而且一旦任务偏离预设流程，系统就容易崩溃。
AgentFugue 的核心 Insight 是： 不需要中央调度器，只需要一个能“写笔记”和“查笔记”的外部通信层。
### 方法拆解：共享推理中枢是怎么工作的？
AgentFugue 的设计非常简洁，核心在于那个 共享推理中枢（Hub） 。它不是另一个 Agent，而是一个经过专门训练的插件层。
-Episode Writing（写笔记）：
每个 Agent 在探索过程中，当上下文窗口达到一定阈值（Write Budget），就会把当前的一段交互历史压缩成一条简短的“笔记”（Note）。这条笔记只记录关键信息：确立了什么、尝试了什么、排除了什么。原始细节存入 Hub 存储，摘要留在 Agent 的工作上下文中。这既节省了 Context Window，又产生了可共享的结构化知识。
-Intent-Driven Reading（按需读取）：
Agent 不会被动接收所有同伴的信息（那样噪音太大）。当 Agent 觉得需要更多信息时，它会向 Hub 发起一个**意图驱动（Intent-driven）**的请求：“我需要关于 X 的证据”。Hub 会根据这个意图，检索其他 Agent 的相关原始片段，并合成一份针对性的指导反馈给该 Agent。
-训练策略：
Hub 模型基于 Qwen3.5-9B，经过两阶段训练：
监督微调（SFT）：学习如何写摘要和回答查询。
- 端到端强化学习（GRPO）：直接在多 Agent 闭环中优化，奖励函数结合任务成功率和搜索路径的简洁性。这意味着 Hub 学会了“只说有用的话”。
### 关键结果：Scaling Out 真的有效吗？
作者在 BrowseComp、WideSearch 和 HLE 三个长程基准上进行了测试。数据非常硬核，证明了“横向扩展（Scaling Out）”确实能带来能力增益。
1. 全面碾压基线在 DeepSeek-v4-Flash 骨干模型下，AgentFugue 的平均准确率达到了 65.0% ，比传统的 Swarm-Multi-Agent 高出 +7.4% ，比 Naive-Multi-Agent 高出 +7.7% 。即使在检索密集的 BrowseComp 上，也比基线提升了 +15.0% （从 56.2% 到 71.2%）。
2. 同质化团队的规模效应即使所有 Agent 都是同一个模型（Qwen3.5-35B-A3B），增加数量依然有效：
- 当团队从 N=1 增加到 N=5 时，单个 Agent 的平均准确率显著提升。
- 效率提升：随着团队扩大，每个 Agent 的搜索/访问调用量下降，而 Hub 的记忆调用量上升。这说明系统从“盲目探索”转向了“高效协作”。
3. 异构团队的互补性当引入不同骨干模型（Qwen + DeepSeek + GLM + Kimi）时，效果更明显：
- 弱者受益最大：能力较弱的 Agent 通过 Hub 吸收了强者的发现，准确率大幅拉升。
- 强者不拖后腿：最强的 Kimi-K2.5 在团队中依然比单独运行高出几个点，说明 Hub 提供的信号是净正向的。
### 工程启示- 通信层即能力：不要试图在 Prompt 里硬编码复杂的协作逻辑。训练一个专门的、轻量级的通信模型（Hub），比调整主 Agent 的 Prompt 更有效。
- 结构化共享优于广播：AgentFugue 的“笔记+按需读取”机制避免了信息过载。在实际工程中，设计 Agent 间的数据交换格式时，务必区分“摘要索引”和“详细内容”，并支持基于意图的检索。
- 异构部署的价值：如果你的业务允许混合使用不同模型（如一个强推理模型 + 几个快速搜索模型），AgentFugue 证明了这种组合能通过共享中枢实现性能互补，且弱模型能“搭便车”提升整体表现。
### 局限与展望论文也指出了当前方法的边界：
- 参数敏感：Hub 的上下文预算（Context Budget）对性能影响呈倒 U 型。太小截断证据，太大稀释注意力。目前最佳点在 32K-64K 之间，这需要针对具体任务调优。
- 误导传播风险：如果某个 Agent 产生了错误的中间假设，Hub 可能会将其传播给其他 Agent。虽然实验显示整体收益为正，但在高可靠性场景下，如何过滤“毒性”笔记仍是挑战。
总的来说，AgentFugue 提供了一条清晰的工程路径：用轻量级的共享记忆层，把孤立的 Agent 搜索变成协同的集体推理。对于正在构建复杂长程任务系统的工程师来说，这是一个值得借鉴的架构模式。
