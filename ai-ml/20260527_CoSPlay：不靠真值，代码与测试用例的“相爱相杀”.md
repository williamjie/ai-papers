# ⭐⭐⭐⭐ CoSPlay：不靠真值，代码与测试用例的“相爱相杀”

**日期**: 2026-05-27

---

论文 : CoSPlay: Cooperative Self-Play at Test-Time with Self-Generated Code and Unit Test链接 : https://arxiv.org/abs/2605.23491如果你正在尝试用大模型写代码，或者在做 Agent 开发，你肯定遇到过这个死循环：没有 Ground-Truth（GT）单元测试来验证生成的代码，而让模型自己生成的测试用例又往往充满噪声，甚至和错误的代码“串通”一起通过。这篇论文提出的 CoSPlay 框架，巧妙地利用推理时的计算资源，让代码和自生成的单元测试在测试阶段进行“合作式自我博弈”，不仅不需要昂贵的 RLVR 训练，还显著提升了代码生成的准确率。
### 痛点：没有 GT，我们拿什么当尺子？
目前的 SOTA 方案通常分为两派：
- RLVR（带可验证奖励的强化学习）：如 CURE、AceCoder，它们依赖海量的人工标注或官方提供的单元测试数据进行训练。这成本太高，且难以规模化。
- TTS（测试时扩展）：在推理时采样更多代码并筛选。但在没有 GT 的情况下，现有的 TTS 方法直接使用自生成的单元测试，结果往往因为测试用例质量低、与错误代码虚假耦合而失效。
核心矛盾在于： 没有可靠的代码，无法验证测试用例；没有可靠的测试用例，无法筛选正确代码。 CoSPlay 的 Insight 是：不要试图单独优化某一方，而是让两者在推理时共同进化（Co-evolve）。
### 方法拆解：三步走的“相爱相杀”
CoSPlay 是一个完全无需训练、无需 GT 数据的三阶段框架：
-探索-攻击引导的初始化与其让模型随机生成测试，不如先让它思考。模型首先探索多种解题思路（Solution Ideas），然后针对每种思路的潜在失败模式，生成具有针对性的“攻击型”单元测试想法（Attack UT Ideas）。这种基于逻辑缺陷生成的测试，比随机生成的更具区分度。
-执行矩阵驱动的迭代自我博弈这是核心。构建一个代码-测试执行矩阵，通过双向的“通过率”信号进行迭代优化：
清理全挂代码：如果一个代码在所有测试上都失败，大概率是错的，直接替换。
- 打破虚假耦合：如果某个测试用例只被少数几个代码通过（低支持率），它可能和特定的错误逻辑“串通”了。CoSPlay 会重新生成这个测试，打破这种可疑的关联。
- 修复代码：利用那些通过率高但并非全过的“非平凡最佳测试”，去指导模型修复失败的代码。
- 替换无效测试：随着代码变好，一些测试变得要么全过（太简单）要么全挂（太偏），这些失去区分度的测试会被新样本替换。
-输出共识聚类选择当多个代码都通过了相同的最高数量测试时，如何抉择？CoSPlay 生成随机有效输入，观察这些候选代码的输出签名。正确的代码在相同输入下必然输出一致，而错误代码往往发散。因此，选择输出最一致的“最大聚类簇”中的代码作为最终结果。
### 关键结果：吊打基线，媲美 RLVR在 LiveCodeBench、LiveBench 等四个高难度基准上，CoSPlay 表现惊艳：
模型 Average BoN (Best-of-N) UT Accuracy (自测准确率) Qwen2.5-7B-Instruct (基线) 22.1% 14.6% Qwen2.5-7B + CoSPlay 33.2% (+11.1%) 78.3% (+63.7%) CURE-7B (RLVR, 需4.5k GT数据) 32.9% 54.9% CURE-7B + CoSPlay 38.6% (+5.7%) -数据来源：Table 1可以看出，CoSPlay 让 Qwen2.5-7B 的自测准确率从惨不忍睹的 14.6% 飙升到 78.3%，最终代码生成准确率甚至略微超越了需要大量 GT 数据训练的 CURE-7B。更有趣的是，当 CoSPlay 叠加在已经经过 RLVR 训练的 CURE-7B 上时，BoN 准确率还能再提升 5.7%。
### 工程启示- 推理预算换质量：CoSPlay 证明了将计算资源从“训练阶段”转移到“测试阶段”是可行的。对于没有能力进行大规模 RLVR 训练的团队，这是一个极具性价比的提升路径。
- 自一致性不仅是投票：传统的 Self-Consistency 只是简单多数投票。CoSPlay 将其升级为基于执行反馈的迭代修复和聚类选择，信息利用率更高。
- 警惕“虚假通过”：在构建代码 Agent 时，不能盲目信任模型自己生成的测试用例。必须引入类似 CoSPlay 中的“打破耦合”机制，防止错误逻辑自我合理化。
### 局限与展望CoSPlay 的效果依赖于基础模型本身具备一定的能力边界。如果基座模型太弱，初始的测试用例质量可能低于阈值，导致执行矩阵信号混乱，无法收敛；如果模型太强，池子容易饱和，迭代收益递减。此外，该方法增加了推理延迟和 Token 消耗，适合对准确率要求极高、且允许较长响应时间的场景（如复杂算法题求解、核心模块生成），而非简单的代码补全。
