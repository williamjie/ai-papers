# ⭐⭐⭐½ 用函数填空训练代码 Agent 的中间微调策略

**日期**: 2026-07-16

---

论文 : Function-Aware Fill-in-the-Middle as Mid-Training for Coding Agent Foundation Models链接 : https://arxiv.org/abs/2607.12463现在的代码大模型（Code LLM）在写单文件脚本时表现不错，但一旦变成需要调用工具、处理外部返回值的软件工程师（Coding Agent），能力往往断崖式下跌。这篇论文提供了一个极具工程落地价值的思路：在预训练和后训练之间，插入一个基于“函数级填空”的中间微调阶段，能显著提升 Agent 解决真实软件工程问题的能力。
### 痛点：Agent 的逻辑与代码结构不匹配现有的代码大模型大多通过左到右的下一个词预测（Next-Token Prediction）进行预训练。这种模式擅长生成线性代码，却难以处理“上下文 →\rightarrow 动作 →\rightarrow 外部返回 →\rightarrow 继续执行”这种非线性的交互逻辑。
论文作者敏锐地发现， 函数调用点（Function Call Site）在结构上与 Agent 的每一步操作是同构的 。
- Caller 绑定参数 对应 Agent 的历史上下文（History）。
- Callee 执行并返回 对应 Agent 的动作及外部环境的观察（Observation）。
- 下游代码消费返回值 对应 Agent 基于观察继续推理。
普通的随机跨度填空（Random-span FIM）往往切断语句，缺乏语义完整性。而函数级的双向依赖关系，正是 Agent 所需要的归纳偏置（Inductive Bias）。
### 方法拆解：函数感知的中间微调作者提出了一种名为 Function-Aware Fill-in-the-Middle (FIM) 的中间微调（Mid-Training）策略。其核心不在于“填什么”，而在于“怎么选”和“怎么练”。
1. 基于程序依赖图的目标选择不是随机掩码，而是解析抽象语法树（AST）构建程序依赖图（PDG）。通过两个指标筛选要掩码的函数：
- 复杂度 (H^\hat{H}^)：结合代码行数、圈复杂度和嵌套深度。太简单没意义，太难学不会。
- 可推断性 (I^\hat{I}^)：评估从周围上下文（调用方参数、文档字符串、类内兄弟方法等）恢复该函数的可能性。
只有同时满足一定复杂度和可推断性的函数才会被选中掩码。这确保了训练样本既有挑战性，又在模型的推理能力范围内。
2. 嵌入思维链（CoT）
在 FIM 的中间部分（Middle Span），模型不仅要生成被掩码的函数体，还要先生成一段逐步推理的思维链（Chain-of-Thought）。
- 格式：<fim_prefix> ... <fim_suffix> ... <fim_middle> [Rationale] [Code Body]- 目的：模拟 Agent “思考-行动”的模式。虽然使用了 Gemini 生成高质量 CoT，但消融实验证明，即使使用模型自生成的 CoT（Self-CoT），也能保留大部分增益，说明核心价值在于结构而非单纯的知识蒸馏。
### 关键结果：不仅更强，而且更稳作者在 Qwen2.5-Coder (7B/14B) 和 Qwen3-8B 上进行了实验，所有模型都经过相同的 Agent 后训练流程（如 R2E-Gym, SWE-Smith）。
1. 核心任务显著提升在软件工程师基准测试 SWE-Bench 上，中间微调带来了稳定的提升：
模型 基线 (Post-train only) + FIM Mid-Train 提升幅度 Qwen2.5-Coder-7B 15.00% 17.80% +2.80 Qwen2.5-Coder-14B 26.20% 29.20% +3.00 Qwen3-8B 31.80% 35.00% +3.20值得注意的是，在 SWE-Bench-Lite 上，Qwen3-8B 甚至获得了 +5.40 的大幅提升。这表明该结构先验并未被更大的预训练模型完全吸收，具有持续的边际收益。
反直觉发现 ：
纯 Agent 后训练会导致模型在其他任务上的能力严重退化（Capability Erosion）。例如，Qwen2.5-14B 在经过 R2E-Gym 后，LiveCodeBench 得分暴跌 13.10 分。而加入 FIM 中间微调后， 恢复了 +11.10 分 ，几乎弥补了所有损失。
2. 跨领域迁移能力尽管训练数据仅包含 Python 代码且无任何工具使用轨迹，但这种“函数调用”的结构先验竟然迁移到了非编码工具使用基准：
- τ\tau-bench: +3.90- BFCL: +2.40这直接证实了“函数调用”与“工具调用”在认知结构上的同构性。
### 工程启示- 中间微调是必经之路：对于构建专业 Agent，直接在通用基座上跑 SFT/RL 效率低且容易灾难性遗忘。插入一个针对特定结构（如函数依赖、工具交互）的自监督中间阶段，性价比极高。
- 数据质量 > 数据数量：本文仅使用了 968 个去重的高质量 GitHub 仓库（约 2.6B tokens），通过 PDG 筛选出的 40 万个样本就取得了显著效果。对于工程团队而言，构建小规模、高结构一致性的微调数据集，比盲目堆积海量噪声代码更有效。
- 关注“恢复率”：分析显示，经过 FIM 训练的 Agent 在遇到错误观察（Negative Observations）时的恢复率从 24.8% 提升至 28.8%。这意味着模型学会了在外部反馈不符合预期时，如何调整后续步骤，这是 Agent 鲁棒性的关键指标。
### 局限与展望目前该方法主要局限于 Python 语言，且依赖较强的教师模型（如 Gemini）来生成初始 CoT。虽然 Self-CoT 方案缓解了这一点，但在开源生态中，如何低成本地获取高质量的结构化推理数据仍是挑战。此外，对于单文件脚本或 Notebook 等非模块化代码，PDG 分析的效果可能会打折扣。
总体而言，这是一篇将理论洞察（结构同构）转化为高效工程实践（中间微调）的典范工作，值得所有从事 Agent 开发的工程师深入研读并尝试复现。
## 📝 AI 点评点评时间：2026-07-16 07:05 ｜ reviewer: DeepSeek V4 Flash核心贡献：原文针对代码基座模型在agent后训练中暴露的归纳偏置不足问题，提出在预训练与后训练之间插入函数感知的填空式中间训练（function-aware FIM mid-training），利用程序依赖图分析和复杂度–可推断性双准则选择掩码目标，并嵌入思维链，以自监督方式将代码中函数调用的结构同构性迁移至agent的“上下文→动作→外部返回→继续”循环。
亮点：
- 博文精准抓住了“函数调用点与agent步骤的结构同构”这一核心洞察，并用通俗语言解释了“caller绑定参数→callee返回→下游消费”与“历史→动作→观察→继续”的对应关系，降低了理解门槛。
- 博文对“能力恢复”结果（LiveCodeBench +11.1，τ-bench +3.9）的强调到位，突出了中间训练不仅提升目标指标，还能缓解agent后训练带来的能力侵蚀，这一工程价值点被清晰传达。

挑刺：
- 遗漏多函数组选择这一核心方法组件：原文2.3.5节详细介绍了多函数组（k=2, k=3）的选样算法，且3.4节消融实验表明80%单函数+15%对+5%三元的混合配置达到最佳效果（16.10 vs 单函数15.60）。博文完全未提及多函数组，仅描述“通过两个指标筛选要掩码的函数”，使读者误以为方法只选择单个函数，忽略了跨函数依赖训练这一关键设计。
- 对评分函数的描述过于简化：博文说“只有同时满足一定复杂度和可推断性的函数才会被选中”，但原文实际使用谐波均值形式 FIM(v) = Ĥ·Î/(Ĥ+Î) · ρ(Δ)，并包含一侧困难惩罚ρ(Δ)。博文未说明组合方式，也未提及阈值τ=0.08等具体数字，可能让读者理解为简单的双阈值过滤，而非精细的连续评分+惩罚机制。
- 后训练流程表述不准确：博文说“所有模型都经过相同的Agent后训练流程（如R2E-Gym, SWE-Smith）”，但原文中Qwen3-8B使用的是SWE-Lego，与Qwen2.5-Coder的R2E-Gym/SWE-Smith不同。原文明确说明“this single comparison varies the post-training pipeline jointly with the base model”。博文的“相同”一词造成误导。
- 表格仅列出SWE-Bench-Verified：原文表1同时给出Verified和Lite两列，博文表格只列了Verified，虽在文字中提到了Lite的+5.4，但表格呈现不完整，削弱了数据对比的全面性。
