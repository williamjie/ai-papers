# 让 AI 做游戏不再靠碰运气

**日期**: 2026-04-23

---

论文 : CreativeGame:Toward Mechanic-Aware Creative Game Generation链接 : https://arxiv.org/abs/2604.19926让 LLM 写个游戏代码，这事大家都不陌生了。但生成的代码跑不起来、改来改去没有进步、“创意”评分全靠 LLM 拍脑袋——这三个问题，基本卡死了 AI 做游戏的工程落地。CreativeGame 这篇论文的核心价值在于：它没有试图用一个更大的模型来解决这些问题，而是把游戏机制（Mechanic）从”事后描述”变成了”事前规划对象”，配合一套以确定性信号为主的代理奖励（Proxy Reward），让迭代进化变得可追踪、可度量。
## 痛点：LLM 做游戏的三个死循环-一次性生成的脆弱性：单次生成出来的 HTML5 游戏代码，看起来像那么回事，运行时一堆 bug。游戏循环函数定义了但不调用、requestAnimationFrame 没有递归自调用、DOM 在 window.onload 之前访问……论文统计，这些是 LLM 生成代码最常见的失败模式。
-经验无法积累：v1 踩的坑，v2 继续踩。没有跨版本的经验传递机制，每一代都从零开始。
-创意评分不可靠：用 LLM 当裁判打分，存在三个问题：分数饱和（GPT 类模型不管输入什么默认给 7/10）、不可验证（7 变 8 跟噪声没区别）、古德哈特定律风险（优化 LLM 判断会导致输出”听起来有创意”但机制上毫无新意）。
## 核心思路：把机制变成一等公民论文最关键的 insight 就一句话： 机制（Mechanic）不应该只是生成完之后贴个标签，而应该在写代码之前就被显式规划、在写代码过程中被约束、在写完代码之后被对照检验。
具体怎么落地？四个耦合设计：
### 1. 机制引导的规划循环（Mechanic-Guided Planning Loop）
传统流程是：Prompt → 代码。CreativeGame 插入了一层：Prompt → 检索机制库 → 生成机制计划 → 代码。
规划器（Planner）从全局机制档案库（774 条条目）中检索相关、未充分探索、过度使用和禁忌模式，然后输出一个标注好的机制计划——哪些机制保留、哪些新增、哪些移除、哪些重组。这个计划在后续生成、评估、反思阶段全程可见，实现了”计划 vs 实际”的对照。
### 2. 代理奖励（CreativeProxyReward）
这是论文最有工程价值的部分。奖励公式由 7 个加权信号组成：
信号项 权重 类型 MechanicRealization（机制实现度） +0.20 确定性 StructuralMechanicChange（结构机制变化） +0.25 确定性 RelativeMechanicNovelty（相对机制新颖度） +0.20 确定性 LLM_Creativity（LLM 创意评分） +0.15 LLM RuntimePlayability（运行时可玩性） +0.10 确定性 CosmeticOnlyPenalty（纯外观惩罚） -0.15 确定性 RegressionPenalty（回退惩罚） -0.10 确定性三个机制相关信号占了最大正权重的 65%，LLM 判断只占 15%。还有两个门控条件：可玩性低于 0.6 时奖励乘以 0.25（软门控），运行时测试不通过时奖励乘以 0.5（硬门控）。
硬门控是关键设计——它确保系统不会奖励”看起来有创意但根本跑不起来”的代码。这个信号无法被 LLM 优化作弊，因为它真正执行了代码。
### 3. 谱系感知记忆（Lineage-Aware Memory）
所有同谱系（lineage）的版本共享一个记忆池，跨谱系隔离。记忆项用 (意图, 表征, 价值估计, 访问计数) 四元组表示，每次迭代后用指数平均更新：q’ = (1-α)q + αr，α=0.3。检索时结合语义相似度和学习到的价值，平衡”复用相关经验”和”利用历史成功模式”。
三层架构：谱系级学习记忆 → 跨谱系资源（机制档案库、创意规则）→ 临时管道上下文。
### 4. 运行时验证器（Runtime Validator）
两级验证：
- Tier 1：深度静态分析器，9 项检查（括号平衡、游戏循环调用、递归自调用、canvas 上下文、输入监听器、渲染调用、状态更新等），<10ms/游戏，无依赖。
- Tier 2：无头浏览器执行检查，加载 HTML、等 canvas 绘制、发基础输入、收集控制台错误。不可用时优雅降级到 Tier 1。
验证失败触发修复阶段（Repair agent，温度 0.3），修复后重新测试。
## 实验结果系统规模：71 个存储谱系、88 个保存节点、774 条全局机制档案、6181 行 Python 代码。
可靠性：三层错误恢复机制（重试、阶段回退、容错格式化）将管道失败率从 ~10% 降到 <2%。
四个真实 4 代谱系的案例分析展示了机制级别的创新如何在迭代中出现：
- Fireboy & Watergirl：从双角色平台跳跃 → “记忆接力”（停车状态、重放幽灵、重力印记）
- Flappy Bird：从单键躲避 → “路线编写”（完美通过改写未来关卡、死亡回声辅助后续运行）
- Happy Glass：从画线引导 → “可编程流体逻辑”（吸收笔画存储水滴、释放事件重写重力）
- Plants vs. Zombies：从静态防线 → “充能拦截”（能量发生器故意阻挡友军射击、存储电荷、通过弯折通道释放）
共同模式：最有意思的变化是机制重新诠释，不是视觉抛光。系统从”表面模仿”走向”显式因果结构”。
## 工程启示-奖励函数设计：当你的优化目标难以直接度量时，用确定性信号做主体、LLM 判断做辅助，是一个务实的选择。CreativeProxyReward 的权重分配值得借鉴。
-机制显式化：把隐式的”创意”拆解为可规划的中间表示（机制计划），再对照检验，这个模式可以迁移到其他生成任务——比如 UI 设计中的交互模式、文案中的修辞手法。
-运行时验证即奖励：把执行结果直接纳入奖励信号和修复触发器，比单纯靠静态检查或 LLM 评审可靠得多。
## 局限论文自己也承认：当前奖励实现是工程代理而非形式化框架的完整实现；创意评分（平均 ~7.0/10）尚未与人类判断对照验证；LLM 评分饱和问题依然存在。谱系数量（71 个）和节点数（88 个）对于统计显著性来说还偏小。
但作为一个让 AI 游戏生成从”碰运气”走向”可追踪进化”的框架，CreativeGame 的设计思路值得每个做 agent 系统的人认真看看。
