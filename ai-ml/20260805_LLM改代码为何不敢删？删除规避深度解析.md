# ⭐⭐½ LLM改代码为何不敢删？删除规避深度解析

**日期**: 2026-08-05

---

论文 : To Add Is Machine, To Delete Is Human: Measuring and Mitigating Deletion Avoidance in LLM Code Editing链接 : https://arxiv.org/abs/2607.28887现在的 AI 编程 Agent 越来越强，但你可能也遇到过这种尴尬：PR 通过了所有测试，代码却变得臃肿不堪。这篇论文直接撕开了这个伪装： LLM 存在严重的“删除规避”（Deletion Avoidance）倾向 。它们宁愿加一堆 if-else 把旧逻辑包起来，也不愿意干脆利落地删掉它。
### 痛点：测试通过了，代码却烂了SWE-bench Verified 榜单上的高分模型，在真实仓库修复中表现如何？论文分析了五个头部模型（如 Opus 4.5, GPT-5 等），发现了一个反直觉的现象： 即使任务被判定为“解决”，模型也遗漏了大量必要的删除操作。
具体数据触目惊心：
- 删除召回率极低：在五个模型都解决的 197 个任务中，模型平均只完成了开发者补丁中 28.3% 到 34.8% 的删除操作。
- 定位没问题，就是手软：模型找到了包含目标代码的文件（>92%），甚至进入了正确的函数作用域（~70%），但真正执行删除行的比例不足 52%。
⚠️ 核心发现 ：模型不是“找不到”要删的代码，而是“不想删”。它们倾向于保留原有逻辑，通过添加条件判断来绕过它。这种模式被称为 Guard-and-Go 。
### 方法拆解：为什么 LLM 不敢删？
论文提出了一个关键假设： 删除行为在预训练和后训练数据中严重欠拟合。
人类工程师也偏爱“加法”而非“减法”，而 LLM 继承了这一偏差。更致命的是，现有的基准测试（如 SWE-bench）主要验证行为正确性（Test Pass），很少检查代码是否被干净地移除。这导致模型发现： 只要加个 if 把旧逻辑包起来，测试照样过，还不需要承担删除可能带来的风险。
为了剥离“定位难”和“实现复杂”的干扰，作者构建了 CanItDelete 基准：
- 纯删除任务：从真实提交中挖掘出 200 个 仅涉及删除、不涉及新增代码的任务。
- 确定性评估：不依赖 LLM 打分，而是通过 AST 和行号精确匹配，判断目标代码是否彻底消失。
- 诊断阶梯：提供从“自然语言指令”到“精确行号”的四种提示模式，定位失败根源是意图理解、搜索能力还是边界控制。
### 关键结果：给行号也没用，除非你微调在 CanItDelete 基准上，最强模型 Claude Opus 4.8 的成功率仅为 79% ，开源模型甚至低至 18% 。
最反直觉的实验结果是 “精确行号”干预 ：
- 即使直接告诉模型“删除第 X 到 Y 行”，GPT-5.6 Sol 仍有近 20% 的任务失败。
- 失败模式从“删不掉”变成了“删过头”或“胡乱添加”。这说明模型缺乏的是对删除边界的控制力（Control），而非单纯的代码生成能力。
微调才是解药：
论文在一个 7B 模型上进行了小规模后训练实验，仅加入 0.7% 的删除样本数据：
- CanItDelete 成功率从 6.5% 提升至 13.7%。
- SWE-bench Verified 整体得分提升 +5.3 个百分点。
- 这证明“删除规避”是可以被纠正的学习缺陷，而非模型能力的天花板。
### 工程启示：如何落地？
- 重构评估指标：如果你的团队使用 AI 生成 PR，不要只看测试通过率。引入 “删除敏感度检查”，验证旧逻辑是否真正消失。论文显示，加上这一条后，原本“通过”的补丁有 33.7% 会被判定为不合格。
- 针对性微调（SFT）：在代码模型的 Post-training 阶段，刻意增加纯删除或少量修改的数据比例。哪怕只占 1% 的数据量，也能显著改善模型在复杂重构中的表现。
- 提示词优化：对于关键的重构任务，显式要求模型“移除冗余逻辑”并给出预期删除的代码片段，比泛泛的“修复 bug”更有效。
### 局限与展望目前的研究仍局限于 Python 和 JavaScript，且微调实验仅在 7B 小模型上验证。未来的方向在于如何在大参数模型中平衡“加法创新”与“减法维护”，以及如何在自动化评估中更精准地识别 Guard-and-Go 这种隐蔽的代码腐化。
