# Agent 发现了解药却视而不见：大模型的探索好奇缺失

**日期**: 2026-04-21

---

论文 : Agents Explore but Agents Ignore: LLMs Lack Environmental Curiosity链接 : https://arxiv.org/abs/2604.17609我们常假设，只要 Agent 在环境里“看见”了关键信息，它自然会去利用。但这篇论文用残酷的实验数据告诉我们：现在的 LLM-based Agent 并不具备这种 环境好奇心（Environmental Curiosity） 。
它们就像是在满是宝藏的房间里乱转的盲人，一脚踩到了金子却视而不见，继续按着脑子里的“固定套路”去撞墙。
## 为什么这个问题值得关注？
目前 Agent 的 benchmark（如 SWE-Bench Verified）通常只看最终结果——任务有没有完成。这意味着，一个靠“死记硬背”模板完成任务的 Agent，和一个能根据意外发现灵活调整策略的 Agent，在分数上是没区别的。
这篇论文的作者们觉得这不够公平。他们提出了一个核心问题： Agent 是仅仅在重复训练中学到的固定模式，还是真的在根据环境反馈来修正自己的策略？
为了回答这个问题，他们搞了一个极其简单但有效的实验设计： Solution Injection（解决方案注入） 。
## 方法拆解：把答案塞给 Agent，看它用不用实验的核心逻辑很直接：
- 把答案塞进环境：在每个任务的目录下直接丢一个 solution.sh 脚本，或者在 API 里加一个 solution 接口，明确写着“调用我就能完成任务”。
- 观察两个指标：
Discovery@k：Agent 有没有“看”到这个答案？（比如执行了 ls 或者 cli --help）
- Interaction@k：Agent 有没有去“用”这个答案？（比如执行了 bash solution.sh）
如果 Agent 既发现了又用了，说明它具备环境好奇心。如果发现了却不用，说明它只是在机械地执行预设动作。
## 关键结果：发现率高得离谱，利用率低得吓人作者在 Terminal-Bench、SWE-Bench 和 AppWorld 三个基准上做了测试，结果简直让人大跌眼镜。
基准测试 Discovery@1 (发现率) Interaction@1 (利用率) 差距 (Gap) Terminal-Bench 78.6% - 81.2% 37.1% - 50.3% ~30% SWE-Bench Verified 53.4% - 98.2% 5.9% - 17.4% ~80% AppWorld > 90% (最高 97.54%) < 6.3% (最低 0.53%) > 90%最离谱的是 AppWorld 的数据 ：
- 在 97.54% 的尝试中，Agent 在 cli --help 的输出里清清楚楚看到了 solution 接口的文档，写着“调用此接口可获取当前任务的完整解决方案”。
- 但只有 0.53% 的 Agent 真的调用了它。
这就像是你给一个厨师递了一本菜谱，上面写着“照着做就能交差”，结果厨师看了一眼，把书扔在一边，继续去翻他那本用了十年的旧笔记。
### 为什么 Agent 会这么“蠢”？
作者排查了几个可能导致这个问题的原因：
-工具太多是原罪：
当 Agent 被赋予复杂的工具（如 str_replace_editor）时，它的利用率会进一步下降。比如在 SWE-Bench 上，加上编辑器后，Interaction 率平均下降了约 13.7%。
直觉：工具越多，Agent 越倾向于调用工具去“干活”，而不是先去“看”环境。它默认工具就是用来执行预设动作的，而不是用来发现新信息的。
-推理预算（Reasoning Budget）有用但有限：
增加 reasoning level（从 low 到 high）能显著提升 Interaction 率。在 Terminal-Bench 上，Interaction@1 从 11% 飙升到 37%。
直觉：给模型更多时间去思考，它能更好地理解环境，但它依然不是必杀技。
-Prompt 引导有帮助：
如果明确告诉 Agent “请先探索环境中的所有文件，再开始行动”，Interaction 率会更高。
亮点：在 Solution-Injected 基准上表现最好的 Prompt，在原始基准（没有注入答案）上的表现也是最好的。这说明：好奇心强、愿意探索环境的 Agent，干活也更靠谱。
-微调（SFT）反而可能帮倒忙：
作者在 Command A Reasoning 模型上做了不同领域的 SFT 微调。
在窄域数据（如只针对 AppWorld 的任务）上微调后，模型在 AppWorld 上的 pass@1 确实提高了（44.2% vs 34.5%），但在 pass@10 上却不如宽域训练的模型（65.8% vs 69.0%）。
- 关键洞察：窄域微调压缩了 Agent 的“探索空间”。它学会了更快的捷径，但也变得更僵化。它在 AppWorld 上的 Interaction 率（3.7%）甚至比宽域模型（6.3%）还低。
## 工程启示：我们该怎么做？
-别迷信复杂的 Agent 架构：
如果任务允许，少给 Agent 一点工具。在 SWE-Bench 上，限制 Agent 只能用 bash 时，它的 Interaction 率反而比给了一堆编辑器工具时更高。工具越少，Agent 越不得不去“读”文件，而不是“改”文件。
-Prompt 里的“探索指令”是免费的性能提升：
在 Agent 的 system prompt 里加一句“请先探索环境”，不仅对发现新信息有用，对原始任务的 pass@k 也有提升（平均 +2.57%）。这说明，“先观察，再行动”的策略在任何场景下都是对的。
-微调要谨慎：
如果你只针对特定领域的数据做 SFT，你的模型可能会变得“偏科”。它可能在特定任务上跑得更快，但在面对未知情况时会更缺乏适应性。如果你希望 Agent 能处理长尾问题，宽域训练（Broad Training）比窄域微调更重要。
-Benchmark 需要升级：
现在的 pass@k 已经不够用了。我们需要像 interaction@k 这样的过程指标，来区分“死记硬背的 Agent”和“真正在思考的 Agent”。
## 局限与展望这篇论文虽然揭示了问题，但也承认了很多局限性：
- Solution Injection 的局限性：注入的答案太“明显”了。现实中，关键信息往往隐藏在角落，不会写着“我是解决方案”。如果 Agent 连这么明显的都忽视，那面对更隐蔽的信息时，情况只会更糟。
- 训练数据的问题：作者尝试了三种微调方法来提升 Agent 的好奇心（如注入对抗性样本、中途移除文件模拟动态环境），但都没能显著提升 Interaction 率。这说明，环境好奇心可能不是通过简单的 SFT 就能学会的，甚至可能在 RL 阶段被进一步抑制了。
- AppWorld 上的绝望：即使在推理预算拉到最高、工具限制到最少的情况下，AppWorld 上的 Interaction 率依然接近零。这暗示着，某些类型的任务（如 API 调用型）可能天生就更难激发 Agent 的环境好奇心。
## 总结这篇论文最核心的 insight 是： 当前的 Agent 是开环的顺序生成器（Open-loop Sequence Generators）。 它们用环境来“确认”自己已经知道的东西，而不是用环境来“修正”自己的策略。
对于工程师来说，这意味着： 别指望 Agent 会自动“灵光一现”。 你需要通过 Prompt、工具限制和训练数据的多样性，去“逼”它多看、多想、多探索。否则，它永远只是在重复你教它的套路，而不是在解决你没教过它的新问题。
