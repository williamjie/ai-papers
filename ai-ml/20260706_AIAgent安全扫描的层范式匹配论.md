论文 : Securing the AI Agent: A Unified Framework for Multi-Layer Agent Red Teaming链接 : https://arxiv.org/abs/2606.31227腾讯朱雀实验室发布的 AI-Infra-Guard 框架，直击当前 AI 安全工具“一刀切”的痛点。它提出一个核心观点：AI 系统的攻击面是分层的，必须为每一层匹配最合适的检测范式，而不是试图用单一工具解决所有问题。
### 为什么现有工具不管用？
传统 Web 扫描器在 AI 时代面临三大鸿沟：
- 目录缺失：主流指纹库没有 Ollama、vLLM 等新兴组件的签名。
- 版本混乱：AI 项目常用 b7824 或 latest 等非语义版本号，导致传统 CVE 匹配逻辑失效。
- 威胁模型错位：高危风险不再是 SQL 注入，而是未授权计算资源访问、API 密钥泄露及提示词注入。
更关键的是，这些风险分布在四个截然不同的层级，证据类型完全不同。
### 核心 Insight：层-范式匹配原则论文提出了“层适应型评估”（Layer-Adaptive Assessment）理论。其直觉非常清晰： 不要用锤子去拧螺丝 。
攻击面层级 特征与证据类型 匹配的检测范式 基础设施层 已知组件、明确签名；需速度与零误报 确定性规则匹配 (Deterministic Rule Matching) 协议/工具层 MCP 服务器、Skill 包；需语义理解代码逻辑 LLM 驱动的代理审计 (LLM-driven Agentic Auditing) Agent 行为层 运行时交互暴露；需多轮对话激发漏洞 黑盒红队测试 (Black-box Red Teaming) 模型层 对齐鲁棒性；统计性质问题 大规模攻击枚举 + LLM 裁判这种设计的精妙之处在于承认了检测能力的边界。例如，在基础设施层使用 LLM 审计不仅昂贵，而且牺牲了确定性规则带来的可复现性和零误报优势。
### 关键技术拆解-基础设施扫描的“去正则化”
框架并未简单依赖正则表达式，而是实现了一个小型布尔表达式解释器。它支持 body、header、icon 等字段的组合匹配（如 body="<title>Dify</title>" || icon="97378986"）。
⚠️ 亮点：针对 AI 软件版本混乱的问题，引擎内置了版本归一化逻辑。将 latest 映射为最大哨兵值，解析 .dev/rc1 后缀，确保 < "0.8.0" 这类比较能正确工作。
-Prompt-as-Rule 范式在协议层（如 MCP 服务器审计），传统静态分析无法理解自然语言描述的恶意意图。框架引入“提示词即规则”（Prompt-as-Rule），将漏洞知识编码为自然语言检测标准，由 LLM 作为领域审计员执行语义分析。
-成本可控的红队测试Agent 行为层扫描采用多轮黑盒对话。为了控制 API 成本，框架设计了“升级阶梯”和“停止规则”，仅在必要时深入探测，并通过金丝雀令牌（Canary-token）验证攻击成功与否。
### 工程落地数据AI-Infra-Guard 已开源并具备相当的规模：
- 覆盖范围：涵盖 75+ AI 组件。
- 规则库：包含 107 条指纹规则和 1,443 条漏洞规则（中文语料库）。
- 攻击算子：集成 26+ 种越狱攻击算子，覆盖 16 个数据集。
### 给工程师的启示- 安全架构分层设计：不要指望一个 WAF 或扫描器解决所有 AI 安全问题。基础设施用传统扫描，Agent 逻辑用 LLM 审计，模型对齐用统计测试。
- 重视供应链安全：MCP 服务器和 Agent Skill 包是新的攻击面。恶意工具描述可导致“工具中毒”（Tool Poisoning），需引入语义级审计。
- 版本管理规范化：在内部部署 AI 组件时，尽量遵循语义化版本控制，否则自动化漏洞扫描将难以生效。
### 局限与展望目前框架主要依赖 LLM 进行语义审计，其准确性受限于底层模型的能力。此外，Agent 行为的动态复杂性可能导致黑盒测试覆盖不全。未来方向包括扩展插件系统以支持更多 AI 生态组件，以及优化 LLM 审计的成本效率。
