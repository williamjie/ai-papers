# 循环缩放：用同一个层循环推理，实现 CTR 预测 SOTA

**日期**: 2026-04-22

---

论文 : LoopCTR: Unlocking the Loop Scaling Power for Click-Through Rate Prediction链接 : https://arxiv.org/abs/2604.19550推荐系统的 CTR（点击率）预测模型正在变得越来越大。从 DNN 到 Transformer，再到现在的 MoE（混合专家）架构，工程师们一直在通过堆叠层数、增加宽度来换取性能提升。但工业界有个死穴： 延迟 。
阿里和人大联合提出的 LoopCTR 给出了一个反直觉的思路： 不要堆层，要“循环” 。它提出了一种 Loop Scaling 范式，在训练时让模型多次循环迭代推理，在推理时直接跳过循环，实现“训练多次、推理零次”的极致效率。
## 为什么需要 Loop Scaling？
现有的 Transformer 基座模型（如 OneTrans, HSTU）在 CTR 预测中表现不错，但它们的 Scaling 路径很单一：
- Depth Scaling：堆叠更多层。参数和计算量线性增长。
- Width Scaling：增大 Embedding 维度。存储压力巨大。
LoopCTR 的作者发现， 计算量（Computation）和参数量（Parameters）是可以解耦的 。
核心 Insight 是： 递归复用同一组参数（Shared Layers） 。
想象一下，你有一个强大的思考引擎，训练时让它对自己“深思熟虑”多轮（Multi-loop），但推理时，因为参数已经内化了这种深度思考的能力，你只需要让它“直觉判断”一次（Zero-loop）就够了。
这就像学生考试：训练时多做十遍模拟题（Loop），考试时凭直觉一次作答（Inference）。
## 方法拆解：三明治 + 超连接 + 过程监督LoopCTR 的架构并不复杂，但每个组件都针对 CTR 场景做了精细化设计。
### 1. 三明治架构（Sandwich Architecture）
模型分为三部分：
- Entry Block：特征编码。将用户行为序列、全局特征投影到统一空间。
- Loop Block：核心迭代层。这是唯一重复执行的部分，包含共享参数的 Transformer Block。
- Exit Block：预测头。将最终表示映射为点击概率。
关键细节 ：序列 Token（用户行为）和全局 Token（用户画像）采用非对称注意力。全局 Token 可以关注序列，但序列 Token 不关注全局。这使得推理时可以缓存序列表示，极大加速候选物品打分。
### 2. 超连接残差（Hyper-Connected Residuals, HCR）
简单复用同一层会导致表达能力瓶颈（Expressiveness Bottleneck）。因为标准残差是固定的 h+f(h)h + f(h) f ( h ) ，递归应用时信息流受限。
LoopCTR 引入了 HCR：
- 将隐藏状态复制为 nn 个流。
- 使用输入依赖的动态系数（Input-dependent Coefficients）控制信息在各流之间的混合。
- 初始化时退化为标准残差，训练过程中动态调整。
Why ：这让模型在每一轮 Loop 中都能自适应地调整信息流动，避免了共享参数带来的表达能力退化。
### 3. 混合专家（MoE）增强在 Attention 和 FFN 中引入 MoE，在不增加推理 FLOPs 的前提下，大幅扩展模型容量。每个 Token 只激活少量专家，保持推理效率。
### 4. 过程监督（Process Supervision）
这是实现 “Infer Zero-Loop” 的关键。
- 传统做法：只在最终输出计算 Loss。
- LoopCTR：在每一层 Loop 的输出上都接一个 Exit Block 计算 Loss。
- 总 Loss 是所有 Loop 深度 Loss 的平均值。
Why ：这迫使模型在每一轮迭代中都学习有用的表示，而不是依赖最后一轮“擦除”之前的错误。最终，即使推理时跳过 Loop，Entry Block 的输出已经足够好，因为共享参数在训练时已经被“深度迭代”的过程所塑造。

- Zero-Loop 即 SOTA：推理时完全不执行 Loop Block，性能已超过所有基线。
- Loop Scaling 效应：训练时 Loop 越多，性能越好（Amazon: 0.8662 -> 0.8728）。
- 共享优于堆叠：在相同 FLOPs 下，共享参数的 LoopCTR 优于堆叠不同参数的 StackCTR，证明共享参数是一种更强的归纳偏置（Inductive Bias），防止过拟合。
- Oracle 潜力：如果为每个样本动态选择最优 Loop 数，还能提升 0.02-0.04 AUC。更有趣的是，训练 Loop 越少，Oracle 上限越高，暗示了动态推理的巨大空间。
## 工程启示- 训练/推理不对称是趋势：不要害怕在训练时使用昂贵的迭代结构。通过 Process Supervision 或蒸馏，可以将这种“深思熟虑”的能力压缩到轻量级的推理模型中。
- 共享参数是防止过拟合的利器：在稀疏的推荐数据上，共享参数比堆叠参数更鲁棒。
- 动态推理是未来：Oracle 分析表明，当前固定 Loop 数的策略远未达到上限。未来可以探索根据样本复杂度动态调整 Loop 数的 Adaptive Inference。
## 局限与展望- 推理延迟并非绝对零：虽然 Zero-Loop 很快，但 Entry Block 的处理仍有开销。
- MoE 的训练稳定性：MoE 引入的路由平衡损失需要仔细调参，否则可能导致专家坍塌。
- 动态推理尚未实现：论文指出了 Oracle 潜力，但动态 Loop 选择仍是一个开放问题。
总之，LoopCTR 是一个典型的“用时间换空间，再用知识压缩时间”的聪明设计。对于工程团队来说，它是一个值得尝试的架构，尤其是在延迟敏感的场景下。
