论文 : CubePart: An Open-Vocabulary Part-Controllable 3D Generator链接 : https://arxiv.org/abs/2605.28763现在的 3D 生成模型大多在搞“单体 Mesh”（Monolithic Mesh），或者生成的零件结构完全不可控。对于游戏引擎来说，这基本等于废柴——车轮不会转、车门打不开，因为代码找不到对应的部件 ID。Roblox 团队这篇 CubePart 直击痛点：它能让模型根据你给的文本 Schema（比如 {"wheel", "chassis"} ），直接生成结构清晰、语义对齐的多零件 Mesh，无需人工后期切割。
### 为什么现有方案不够用？
目前的 3D 生成主要有两条路，都有硬伤：
- 单体生成：像 Trellis 等主流模型生成的是一整块几何体。想加动画？得靠后处理算法自动分割，结果往往乱七八糟，语义对不上。
- 基于 2D 掩码的控制：用 SAM 等模型在图片上画框，再转到 3D。但这有个致命缺陷：视角依赖。如果车尾被挡住了，你就没法控制“排气管”这个部件的生成。
CubePart 的核心 Insight 是： 用文本 Schema 作为推理时的显式控制信号 。不依赖视图，直接告诉模型：“我要一个海龟，背上有城堡，请分别生成头、壳、鳍和塔楼”。
### 方法拆解：两阶段解耦与零初始化注意力CubePart 的架构设计非常工程化，分为两个阶段，核心在于如何平衡“全局形状”与“局部零件”的关系。
Stage 1: 全局单体生成（Single-Mesh Generation）
首先训练一个基于 VecSet Diffusion 的单 Mesh 生成器。这里的关键动作是 Schema-aware Finetuning 。
- 做法：在预训练模型基础上，使用包含明确部件列表的 Prompt 进行微调（SFT）。Prompt 格式如：“{全局描述}。该物体包含以下部分：{部件列表}。”
- 目的：让模型先学会“长什么样”，确保整体几何结构符合语义预期，而不是仅仅生成一堆噪声。
Stage 2: 多零件分解（Multi-Part Mesh Generation）
这是重头戏。如果直接让模型生成多个独立 Latent，各部件之间容易打架（重叠或缺失）。CubePart 没有修改预训练层，而是引入了 Cross-Part Attention Residual Block 。
- 设计直觉：修改原有 Transformer 层会破坏 Stage 1 学到的强大几何先验。因此，他们在第 1、5、9、17 层插入了**零初始化（Zero-initialized）**的注意力块。
- 效果：这些新块专门负责部件间的全局信息交换（比如轮子知道车身在哪），而原有层继续负责局部细节生成。这种“插件式”设计既保留了预训练质量，又实现了部件间的结构一致性。
### 关键结果：数据与性能的双重碾压CubePart 不仅模型新颖，其构建的数据集也是行业标杆。
1. 数据集规模他们构建了一个包含 462K 资产、202 万个零件 的开放词汇数据集。
- 对比 PartVerse-XL（40K 资产），规模扩大了 11 倍以上。
- 采用 VLM + Set-of-Mark 渲染技术自动聚类命名，避免了人工标注的高昂成本，且生成的名称简洁准确（如 hull, tracks），而非冗长的描述性 Caption。
2. 生成质量对比在 PartObjaverse-Tiny 数据集上的测试显示，CubePart 在结构完整性和零件精度上均领先：

### 工程启示- 控制信号的选择：对于 3D 生成，文本 Schema 比 2D Mask 更鲁棒。它不受视角遮挡影响，且能直接映射到游戏引擎的 Component 系统。
- 微调策略：不要试图从头训练多部件模型。先练好单体生成，再通过“插件”机制引入部件交互，是性价比最高的路径。
- 数据自动化：利用 VLM 对多视角渲染图进行聚类命名，是构建大规模结构化 3D 数据集的可行方案，大幅降低了人工标注门槛。
### 局限与展望目前 CubePart 主要依赖文本 Schema 控制，对于极其复杂的拓扑结构（如内部机械联动）可能仍有挑战。此外，推理耗时约 5-7 秒（H200 GPU），虽然可接受，但距离实时生成还有差距。未来若能结合更细粒度的物理约束，将极大提升其在仿真领域的应用价值。
