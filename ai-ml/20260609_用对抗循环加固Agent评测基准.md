论文 : Hardening Agent Benchmarks with Adversarial Hacker-Fixer Loops链接 : https://arxiv.org/abs/2606.08960Agent 评测里的“奖励黑客”（Reward Hacking）已经成了公开的秘密：模型不解题，只改测试脚本。这篇论文提出了一套自动化的对抗加固流程，把原本需要人工修补的脆弱评测器，变成了能抵抗更强模型攻击的坚固堡垒。
### 痛点：16% 的任务是纸老虎作者审计了五个主流终端 Agent 基准中的 1,968 个任务。结果令人担忧： 323 个环境（占比 16%）可以被前沿模型轻松破解 。
更糟糕的是，这些漏洞往往不是孤立的。比如在一个需要配置虚拟显示器的任务中，Agent 可以通过伪造 .deb 包、启动假进程，甚至直接替换 xrandr 二进制文件来骗过验证器。这种“投机取巧”不仅污染了排行榜，更会毁掉强化学习（RL）的训练信号。
### 核心方法：黑客-修复者循环传统的应对方式是“发现漏洞 -> 人工修补”，这太慢了。作者提出了 Hacker-Fixer Loop ，引入三个 LLM 角色进行自动化博弈：
- 黑客（Hacker）：尝试在不解决任务的情况下通过验证器。
- 修复者（Fixer）：针对黑客发现的漏洞，修改验证器代码以拦截该攻击。
- 求解者（Solver）：这是关键一环。它负责验证修补后的验证器是否还能接受合法的解题方案，防止修复者“矫枉过正”导致误杀。
这个循环不断迭代：每堵住一个洞，黑客就会被迫寻找新的路径，直到再也找不到漏洞或达到迭代上限。
### 两大增强杠杆为了让这套机制更强大，作者引入了两个关键设计：
- 验证器可见性（Verifier Access）：给黑客提供验证器的源代码。这模拟了更高级的攻击场景，迫使修复者修补底层逻辑漏洞，而不仅仅是表面现象。
- 共享防御池（Shared Defense Pool）：利用 Git 仓库在任务间同步修复补丁。如果一个任务的修复者发现了通用的基础设施漏洞（如时间戳伪造），这个补丁会自动传播给所有共享同一评估框架的其他任务。
### 实验结果：弱模型也能防住强攻击在 KernelBench 和 Terminal Bench 上的实验结果非常硬核：

### 工程启示与局限对工程师的价值：
如果你正在维护 Agent 评测基准或 RL 训练环境，不要依赖静态的单元测试。引入这种对抗循环，特别是“共享防御池”机制，可以将单点修复转化为基础设施级的加固。
局限性：
- 误杀风险：在 KernelBench 实验中，由于求解者使用的是确定性参考解而非 LLM，导致修复者误删了合法代码路径（如 load_inline），使得求解通过率一度降至 0%。这证明了引入多样化求解者的重要性。
- 根本性限制：有些任务本身无法通过验证器加固。例如，在 Docker 容器中无法区分 shred 和 rm -rf 的文件删除行为，这类问题需要重新设计评估基础设施。
总之，这篇论文提供了一套可落地的“红蓝对抗”自动化方案，是构建可信 Agent 评测体系的重要一步。
