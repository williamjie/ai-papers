### 为什么现有基准测不出真本事？
之前的 Benchmark（如 OSWorld 1.0）任务太短、太孤立。平均只需 30 步，耗时约 2 分钟，且通常只涉及单一应用。这种“短平快”的任务掩盖了 Agent 在复杂工作流中的状态丢失问题。
OSWorld 2.0 的核心动机是还原 真实世界的复杂性 。它引入了 108 个长程任务，中位人类操作时间长达 1.6 小时 （是 v1.0 的 48 倍）。Agent 平均需要执行 318 次工具调用 ，且任务横跨多个应用（如邮件、银行、本地文件、遗留系统），要求 Agent 具备跨源推理和动态环境适应能力。
### 核心设计：从“操作”到“工作流”的范式转移OSWorld 2.0 的创新不在于堆砌难度，而在于精准打击 Agent 的 认知盲区 。其设计包含三个关键直觉：
- 隐式状态推断（Implicit-State Inference）：任务信息不全在 Prompt 里。Agent 必须从历史邮件、银行流水或之前的报告中“拼凑”出缺失的关键字段（如员工 ID）。这测试的是记忆与关联能力，而非简单的 OCR。
- 动态环境（Dynamic Environment）：任务执行中途会注入新邮件或消息，改变任务状态。Agent 不能只按初始计划走，必须实时监测并调整策略。这是区分“脚本执行者”和“智能体”的关键分水岭。
- 细粒度部分奖励（Fine-grained Partial Reward）：摒弃非黑即白的 Pass/Fail，采用平均 27.25 个检查点的评分体系。这能更精准地定位 Agent 是在哪一步“断片”的——是忘了约束条件，还是忽略了中途到达的新信息？
### 实验结果：最强模型也仅完成 20%数据非常残酷。即使在 500 步 的预算下，配置最强的 Claude Opus 4.8 （开启最大思考+批量工具调用）二进制完成率仅为 20.6% ，部分得分为 54.8% 。

### 失败归因：不是手残，是脑雾论文深入分析了 Agent 的失败模式，发现它们并非在基础 GUI 操作上出错，而是死在 高层认知 上：
- 状态漂移：随着步骤增加，Agent 逐渐遗忘初始约束条件。
- 被动交互：面对信息缺失，Agent 倾向于“瞎猜”而不是向用户确认（Proactive Interaction 缺失）。
- 缺乏验证：很少花费预算（<7%）去检查自己的错误，导致小错累积成大崩盘。
### 工程启示与局限对于正在落地 Agent 的工程师，这篇论文给出了明确信号： 不要迷信长上下文窗口能解决所有问题 。在长程任务中，显式的状态管理、中间结果的强制校验以及动态环境的监听机制，比单纯增大模型参数更有效。
OSWorld 2.0 目前主要覆盖桌面端 GUI 操作，对纯代码或 API 调用场景涉及较少。但其揭示的“状态保持”难题，是所有通用 Agent 面临的共性挑战。未来的突破点可能不在于更大的 LLM，而在于更鲁棒的 工作流编排框架 和 自我纠错机制 。
