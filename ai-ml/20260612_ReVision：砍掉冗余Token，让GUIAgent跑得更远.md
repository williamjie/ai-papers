# ⭐⭐⭐⭐ ReVision：砍掉冗余Token，让GUI Agent跑得更远

**日期**: 2026-06-12

---

论文 : ReVision: Scaling Computer-Use Agents via Temporal Visual Redundancy Reduction链接 : https://arxiv.org/abs/2605.11212做 GUI Agent 的工程师都知道一个痛点：上下文窗口（Context Window）太贵，且根本装不下长历史。
大多数现有方案要么只看当前截图，要么硬塞几张历史图进去。结果就是 Token 数量爆炸，模型在重复处理那些根本没变的背景像素上浪费算力，导致它“记不住”前几步的操作逻辑。
这篇来自 UBC 和微软研究院的论文 ReVision 提出了一个很直觉但有效的解法： 既然连续截图之间有大量冗余，为什么不直接在 Patch 级别把没变化的部分删掉？
### 痛点：历史不是越多越好，而是越精越好在传统的 Computer-Use Agents (CUAs) 中，每一步截图都会被编码成数千个视觉 Token。随着交互步数增加，Token 成本线性增长。
作者统计了多个基准测试（如 OSWorld, AgentNetBench），发现了一个惊人的数据： 连续截图中，平均有 45.4% 的 Patch 是完全冗余的 。在某些场景下，这个比例甚至高达 56%。
这意味着，如果你保留 5 张历史截图，其中超过一半的计算量是在处理“没用的信息”。这不仅浪费算力，更挤占了模型用于推理的上下文预算。
### 核心 Insight：训练时就要学会“忽略”
很多 Token 压缩工作只在推理阶段做（Inference-time Pruning），但这往往需要修改模型架构或复杂的后处理。
ReVision 的核心设计在于： 它在训练阶段就引入了冗余感知机制 。
- 轻量级选择器 (RTS)：作者训练了一个只有三层 MLP 的分类器，输入是当前 Patch 和上一帧对应位置的 Patch 特征。它预测当前 Patch 是否冗余。
- 保留空间结构：删除 Token 时，保留原始的位置 ID（Position IDs）。这很关键，因为 MLLM 依赖相对位置信息来理解 UI 布局。如果直接压缩序列，空间关系就乱了。
- 端到端微调：模型是在“被删减过”的数据上训练的。这迫使模型学会从稀疏的视觉历史中恢复上下文，而不是单纯依赖当前帧。
⚠️ 反直觉发现 ：作者对比了“向前删除”（删除后续冗余）和“向后删除”（保留最新帧完整）。结果发现， 向前删除效果最好 。
为什么？因为如果最后一张图是完整的，模型会产生惰性，不再去挖掘历史图中的线索。强制删除当前帧的部分冗余，反而逼迫模型更有效地利用长短期记忆。
### 关键结果：少即是多在 Qwen2.5-VL-7B 基础上，使用 5 张历史截图的窗口，ReVision 的表现令人印象深刻：
指标 提升幅度 Token 消耗 -46% (平均) 成功率 (SR) +3% (相比 No Drop 基线) 推理延迟 ~22 ms (RTS 模块开销极低)
更有趣的是，随着历史长度增加，ReVision 的优势反而扩大。在 WebTailBench 上，它达到了近 50% 的成功率，而强基线模型通常低于 30%。
此外，作者还发现了一个**饱和点（Saturation Point）**现象：
- No Drop 基线：当历史图像超过 7 张时，性能开始下降（因为 Token 太多，注意力分散）。
- ReVision：性能一直提升直到 11 张图像才趋于平稳。
这说明 ReVision 不仅省 Token，还真正延长了模型的有效记忆窗口。
### 工程启示- 别盲目堆历史图：如果你的 Agent 表现不佳，不要简单地增加 history_length。先检查是否充满了冗余视觉噪声。
- 微调优于推理时剪枝：直接对现成模型做 Token 删除通常会灾难性失败（论文中 Random Drop 90% 导致成功率暴跌至 4.6%）。必须通过 SFT 让模型适应这种“残缺”的输入分布。
- 轻量级插件即可：RTS 模块极小，且只需 ~22ms 延迟。这意味着你可以将其作为现有 MLLM Pipeline 的一个中间件插入，无需重新训练整个视觉编码器。
### 局限与展望ReVision 并非万能药。它高度依赖 RTS 分类器的准确性。如果界面中有细微但关键的状态变化（如加载动画、微小图标闪烁），可能会被误判为冗余而删除，导致推理错误。
此外，该方法主要针对 GUI 场景。对于视频理解或机器人视觉等动态变化剧烈的场景，冗余度较低，收益可能有限。
总的来说，ReVision 提供了一个低成本、高回报的思路： 通过显式建模时间冗余，我们可以用更少的 Token，做更长远的规划。 这对于部署在边缘设备或需要低延迟响应的 Agent 应用来说，极具实用价值。

挑刺：
