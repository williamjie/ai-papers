# Agent长程任务评估：从二元通过到密集奖励

**日期**: 2026-07-13

---

论文 : Long-Horizon-Terminal-Bench: Testing the Limits of Agents on Long-Horizon Terminal Tasks with Dense Reward-Based Grading链接 : https://arxiv.org/abs/2607.08964现有的 Agent 评测大多停留在“短平快”阶段，要么几分钟内解决代码 Bug，要么通过简单的单元测试。这种二元（Pass/Fail）的评估方式掩盖了长程任务中的核心痛点：Agent 往往能完成大部分工作，却在最后一步因缺乏自我验证而功亏一篑，或者在预算耗尽前陷入无效循环。
腾讯 HY LLM Frontier 团队提出的 Long-Horizon-Terminal-Bench (LHTB) 试图打破这一僵局。它引入了基于子任务的密集奖励（Dense Reward）机制，不再只看最终结果，而是量化 Agent 在长程工作流中的每一步进展。这对于理解 Agent 在真实复杂环境下的“耐力”和“规划能力”至关重要。
### 为什么现有评测不够用？
传统终端评测（如 Terminal-Bench）主要关注局部修复或短指令执行。但在复现实验、调试编译工具链或多阶段 ML 训练等场景中，任务通常需要数百个步骤、数十分钟甚至数小时。
二元评估的致命缺陷在于信号稀疏：一个完成了 90% 工作的 Agent 和一个刚起步就报错的 Agent，得分都是 0。这导致我们无法区分模型是“完全不懂”还是“差最后一步”。LHTB 的核心 Insight 是： 将长任务拆解为具有语义意义的子任务（Subtasks），通过确定性的环境检查器给予部分信用（Partial Credit）。
### 方法设计：密集奖励如何工作？
LHTB 包含 46 个任务，涵盖实验复现、软件工程、多模态分析等九大领域。其评估机制并非简单的黑盒测试，而是精细化的子任务评分：
- 二元子任务：检查特定布尔条件（如单元测试是否通过、服务端口是否响应）。
- 连续/阈值子任务：针对量化目标（如图表复现误差、指标匹配度），误差越小得分越高。
- 回合聚合子任务：针对游戏或重复审计场景，计算成功回合的比例。
最终奖励 RR 是各子任务加权平均。这种设计迫使 Agent 不能仅靠硬编码通过公开测试，必须处理隐藏的压力测试（如嵌套数据格式、注入噪声、字段重命名等），从而真实反映其鲁棒性。
### 关键结果：长程执行仍是瓶颈在 15 个前沿模型的评测中，LHTB 展现了极高的难度和区分度。以下是核心数据对比：

### 工程启示：从“能跑”到“能完”
LHTB 揭示了当前 Agent 的两个主要失败模式，对工程落地有直接指导意义：
-虚假完成（False Finishes）：
约 19% 的未完成任务是 Agent 主动提前退出。分析显示，许多模型在奖励达到 0.75-0.90 时就认为任务完成并停止，尽管隐藏验证器仍未通过。这表明当前模型的自我验证（Self-Verification）能力严重不足。
建议：在构建 Agent 时，需引入专门的“反思与验证”步骤，强制模型在提交前检查所有约束条件，而非依赖其主观判断。
-长程状态管理缺失：
随着步数增加（平均 231 步），上下文窗口压力剧增。Agent 容易遗忘早期决策或陷入重复调试循环。
建议：优化记忆机制，如使用外部知识库记录关键中间状态，或采用分层规划策略，将长任务分解为可独立验证的短期目标。
### 局限与展望LHTB 虽然通过密集奖励解决了信号稀疏问题，但其构建成本较高（需人工设计子任务和隐藏测试）。此外，评测主要依赖确定性环境检查器，对于开放性更强、无标准答案的创意类任务，该方法的可扩展性仍有待验证。
未来，随着 Agent 在长程规划上的进步，LHTB 中的“近失”（Near-misses）案例将成为微调数据的重要来源，帮助模型学习如何更精准地判断任务完成度。对于工程师而言，关注 Agent 的“部分进度”而非仅看最终通过率，是提升复杂工作流自动化成功率的关键一步。
