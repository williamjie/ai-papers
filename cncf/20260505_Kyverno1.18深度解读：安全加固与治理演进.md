# Kyverno 1.18 深度解读：安全加固与治理演进

**日期**: 2026-05-05

---

原文 : Announcing Kyverno release 1.18!
来源 : https://www.cncf.io/blog/2026/05/05/announcing-kyverno-release-1-18/Kyverno 从 CNCF 孵化器毕业后的首个重大版本 1.18 已经发布。对于习惯用策略即代码（Policy as Code）管理 Kubernetes 集群的团队来说，这次更新不仅仅是功能堆叠，更是一次从“可用”向“可信、可控”迈进的关键转折。特别是在 SSRF 防御、CLI 本地测试体验以及长期支持策略上的调整，直接影响了生产环境的安全基线和运维成本。
## 痛点与背景：策略引擎的“信任危机”与“运维负担”
在云原生治理中，策略引擎（Policy Engine）通常面临两个核心痛点：一是执行过程本身的安全风险，二是大规模部署下的噪音与性能瓶颈。
Kyverno 允许通过 HTTP CEL 库调用外部服务进行策略判断。过去，这种灵活性是一把双刃剑：虽然方便集成外部审计服务，但也容易成为 SSRF（服务器端请求伪造）攻击的入口。此外，随着集群规模扩大，策略引擎产生的事件日志（Events）往往呈指数级增长，导致监控告警疲劳，运维人员难以从海量信息中筛选出真正的异常。
## 方案拆解：从“开放”到“零信任”
Kyverno 1.18 的核心设计思路非常清晰： 收紧默认权限，提升本地开发体验，优化大规模执行性能。
### 1. 安全加固：默认拒绝，最小权限这次更新最硬核的部分在于对 HTTP 执行的安全加固。针对 CVE-2026-4789 和 CVE-2026-41323，Kyverno 引入了类似防火墙的机制：
- 黑白名单强制生效：默认情况下，回环地址（Loopback）和云厂商元数据服务（Metadata Services）被严格禁止。这意味着即使策略逻辑中有 http.get，只要目标地址不在白名单内，请求直接拦截。
- 命名空间策略默认禁用：为了进一步缩小攻击面，命名空间级别的策略（Namespaced Policies）默认禁止发起 HTTP 调用，必须显式开启。
- 作用域令牌（Scoped Token）：之前的 HTTP 调用携带的令牌可能被滥用，现在改为独立的受限令牌，确保外部服务无法利用该令牌冒充 Kyverno 控制器。
这种“零信任”设计思路，将策略引擎从“可信任的内部组件”转变为“需严格约束的边界节点”，大幅降低了横向移动风险。
### 2. CLI 增强：让策略测试脱离集群对于开发者而言，每次修改策略都要 kubectl apply 到测试集群再验证，效率极低。1.18 版本显著扩展了 kyverno apply 和 kyverno test 命令的能力，支持清理策略（Cleanup Policies）、HTTP 授权策略以及 mutateExisting 规则。
这意味着团队可以在 CI/CD 流水线中实现真正的“本地优先”测试。结合新增的 --exceptions-with-policies 标志，测试工作流更加接近生产环境的真实逻辑。
### 3. 性能与可观测性：降噪与扩容在大规模集群中，Kyverno 1.18 引入了细粒度的成功事件过滤（Success Event Filtering）。通过 ConfigMap 配置，用户可以精确控制哪些成功事件被记录。这解决了“策略通过即日志刷屏”的问题，让运维人员能聚焦于失败或异常事件。
同时，内存基于 HPA（Horizontal Pod Autoscaler）的自动伸缩能力，让 Admission Controller 能更灵活地应对流量高峰，配合 TLS 支持 metrics 端点，提升了生产环境的可观测性标准。
## 工程启示：策略治理的“生命周期”管理Kyverno 1.18 最容易被忽视但影响深远的变化，是其 支持策略的调整 。
项目正式宣布采用 “main + 1” 补丁支持模型：仅支持当前版本和上一个版本，且补丁仅限于高危 CVE 和关键修复，支持周期约 3 个月。
这一变化对工程实践有以下指导意义：
- 升级策略前置：不要等到版本停止支持才行动。建议团队建立季度升级节奏，或在 3 个月窗口期内完成平滑迁移。
- 拥抱新策略类型：ClusterPolicy 即将在年内弃用。团队应尽快将现有策略迁移至 ValidatingPolicy、MutatingPolicy 等新型策略。这不仅是语法变更，更是执行引擎对齐 CEL 标准的过程，能带来更好的性能和一致性。
- 商业版考量：如果需要超过 3 个月的长期支持（LTS），可能需要评估商业分发版，或者投入内部资源维护旧版本（不推荐，安全风险高）。
## 局限与思考尽管 Kyverno 1.18 在安全性和 CLI 体验上进步明显，但“main + 1”的支持模型对中小团队是个挑战。它要求团队具备较强的自动化测试能力和快速响应升级的能力。
此外，虽然 CLI 功能增强，但对于复杂的多集群策略分发，Kyverno 仍依赖于 Helm Chart 的定制化能力，相比一些全功能治理平台，在跨集群一致性保障上仍需额外投入。
## 总结Kyverno 1.18 是一个“成熟化”的版本。它不再仅仅关注功能覆盖，而是开始审视自身作为基础设施组件的安全边界和运维可持续性。对于云原生工程师来说，现在正是迁移到新策略类型、利用新 CLI 工具链优化开发流程的最佳时机。
