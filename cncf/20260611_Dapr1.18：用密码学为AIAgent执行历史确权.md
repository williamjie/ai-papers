# ⭐⭐⭐ Dapr 1.18：用密码学为 AI Agent 执行历史确权

**日期**: 2026-06-11

原文 : Introducing Verifiable Execution in Dapr 1.18来源 : https://www.cncf.io/blog/2026/06/11/introducing-verifiable-execution-in-dapr-1.18/Dapr 1.18 的发布标志着云原生工作流从“高可用”迈向了“可验证”。当 AI Agent 开始自主决策时，我们不再只关心系统是否崩溃，更关心它到底做了什么、谁批准的、以及历史记录是否被篡改。
### 为什么可观测性不够用了？
过去几年，我们花了大量精力构建日志（Logs）、指标（Metrics）和链路追踪（Traces）。这些工具能告诉我们“发生了什么”，但它们有一个致命弱点： 它们需要信任 。
在分布式系统中，日志可以被修改，审计记录可能被篡改，执行上下文在服务间传递时可能丢失。对于传统应用，这或许只是运维问题；但对于金融交易、医疗理赔或自主 AI Agent，缺乏密码学保证的执行历史意味着巨大的合规与安全风险。
核心痛点 ：可观测性告诉你事实，但无法证明事实未被篡改。Verifiable Execution（可验证执行）则是用密码学来“证明”它。
### Dapr 的三重防御体系Dapr 1.18 引入了三个关键能力，共同构建了可验证执行的基石：
-工作流历史签名（Workflow History Signing）
随着工作流执行推进，Dapr 会对历史记录生成密码学签名。这创造了“防篡改”的执行历史。即使数据库被入侵，攻击者也无法在不破坏签名的情况下修改状态转换记录。这对受监管行业（如银行、制药）至关重要，提供了比单纯日志更强的完整性保证。
-工作流历史传播（Workflow History Propagation）
分布式系统很少孤立运行。一个工作流可能调用活动，活动再调用服务，服务又触发其他工作流。传统上，重建这种血缘关系需要拼凑多个日志。Dapr 1.18 让执行血缘随请求一起流动。下游服务可以直接看到：
执行起源于哪里- 哪些工作流参与了- 事件的执行序列- 传入工作的来源证明-工作流认证（Workflow Attestation）
历史传播建立了血缘，而认证建立了信任。Dapr 允许工作流和活动接收密码学可验证的执行上下文。应用可以基于“已验证的来源”而非“假设”来做决策。例如，银行汇款系统可以只接受来自经过批准的工作流的请求，防止直接 API 调用绕过欺诈检查。
### 基于 SPIFFE 的身份基石这一切建立在 Dapr 长期采用的 SPIFFE 工作负载身份之上。每个启用 Dapr 的应用都拥有密码学可验证的身份。
- SPIFFE 回答：“你是谁？”（Who are you?）
- Verifiable Execution 回答：“你是怎么来到这里的？”（How did you get here?）
两者结合，不仅验证了发起请求的工作负载身份，还验证了导致该请求的执行血缘链条。这种信任链跨越了工作流编排器、活动、服务、AI Agent 甚至外部系统。
### 对 AI Agent 架构的深远影响AI Agent 与传统应用不同，它们频繁调用外部工具、委派任务、与其他 Agent 协调。随着 Agent 承担关键业务决策，以下问题变得至关重要：
- 哪个 Agent 发起了此操作？
- 哪个工作流批准了它？
- 执行历史是否被修改？
传统 Agent 系统往往依赖编排器、工具和服务之间的信任假设。Dapr 的方案让系统能够推理“谁在发起请求”以及“该请求是如何产生的”。这为构建可信的 AI 系统提供了新的基础设施积木。
### 工程启示与局限谁应该关注？
- 金融/医疗团队：需要严格审计追踪和合规性证明的团队。
- AI Agent 开发者：正在构建多 Agent 协作、需要确保决策来源可信的系统。
- 安全工程师：希望将信任从通信层扩展到执行层的实践者。
局限与思考虽然方案强大，但引入密码学签名和传播会增加一定的计算开销和网络负载。在极高吞吐量的场景下，需要评估性能影响。此外，这主要解决了“执行历史”的可验证性，对于数据内容本身的完整性（如输入数据是否被投毒）仍需结合其他安全手段。
从持久化执行到可验证执行，Dapr 1.18 迈出了关键一步。在云原生架构演进中，验证工作是如何执行的，终将变得与从故障中恢复同样重要。
