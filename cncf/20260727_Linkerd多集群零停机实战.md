原文 : Federating clusters for zero-downtime Kubernetes来源 : https://www.cncf.io/blog/2026/07/27/federating-clusters-for-zero-downtime-kubernetes/在多区域部署中，最尴尬的时刻莫过于一个集群彻底宕机。此时，远在另一个区域的同名服务副本形同虚设，因为流量根本无法自动感知并切换过去。传统的故障转移往往依赖繁琐的 Runbook：恢复数据、重定向 DNS，然后眼睁睁看着业务中断。这篇文章通过 Linkerd 的多集群扩展，展示了如何实现真正的“零停机”联邦架构。
### 痛点：多集群不是简单的复制粘贴很多团队误以为只要在不同区域部署了相同的服务，就实现了高可用。但如果没有统一的入口和自动化的负载均衡，这些服务就是孤岛。Linkerd 的多集群方案提供了三种模式，且它们可以在同一套链路中混合使用：
- 联邦（Federated）：所有同名服务合并为一个端点，自动负载均衡。适合需要“无感故障转移”的核心业务。
- 扁平镜像（Flat Mirror）：通过 Pod IP 直接通信，保留集群名称后缀（如 api-west）。适合需要数据本地性或明确指定后端集群的场景。
- 网关镜像（Gateway Mirror）：通过 Gateway IP 路由，无需底层网络互通。适合跨云或网络隔离的场景。
### 架构拆解：三种模式共存的艺术文章的核心价值在于演示了如何在三个 GKE 集群（West, East, North）中同时运行这三种模式。
- Frontend 服务：采用联邦模式。在三个集群中部署，通过标签 mirror.linkerd.io/federated=member 标记。客户端访问 frontend-federated，Linkerd 会自动将流量分发到所有健康的 Pod（共 9 个）。
- API 服务：采用扁平镜像模式。仅在 West 和 East 部署，North 集群通过 api-west 或 api-east 明确调用。这要求底层网络必须是扁平的（Pod IP 可达）。
- Analytics 服务：采用网关镜像模式。仅部署在 East，West 和 North 通过 Gateway 访问。这是为了证明即使没有扁平网络，也能与其他模式共存。
### 关键细节与工程陷阱实现这一架构并非易事，文章揭示了几个极易踩坑的细节：
- VPC 对等连接的陷阱：仅仅创建 VPC Peering 是不够的。必须启用 --export-custom-routes 和 --import-custom-routes，否则 Pod CIDR 不会被通告，导致连接挂起且无日志报错。
- CIDR 重叠是静默杀手：GKE 默认分配的 CIDR 可能重叠。如果重叠，路由会静默失败，请求可能被发送到错误的集群。必须手动指定不重叠的 Pod 和 Service CIDR。
- 控制器数量匹配：每个消费侧集群需要为每个 Link 运行一个 service-mirror controller。如果漏配，Link CR 创建成功但服务不镜像，且健康检查依然显示绿色，排查极其困难。
- 成本优化：GKE Regional 集群默认在每个可用区部署节点。脚本通过锁定单个可用区（--node-locations），将节点数从 3 减至 1，显著降低演示成本。
### 混沌测试验证：联邦的价值文章通过混沌工程测试验证了方案的有效性：
- 联邦服务：当 East 集群下线时，Frontend 流量自动从 33/33/33 重平衡为 West/North 各 50%，无错误发生。
- 镜像服务：当 East 下线时，访问 api-east 直接返回 503。这是预期行为，因为客户端显式指定了集群，故障转移应由客户端逻辑或 TrafficSplit 处理。
### 工程启示对于多区域部署的团队，Linkerd 的这种混合模式提供了极大的灵活性。 联邦模式应作为默认选择 ，用于那些需要高可用且无需关心具体物理位置的服务。而对于有数据本地性要求或网络隔离的场景，镜像模式则是更好的补充。
⚠️ 注意 ：联邦服务的名称固定为 <svc>-federated ，无法自定义后缀。建议在应用层通过 TrafficSplit 将标准服务名指向联邦端点，以保持接口一致性。
总之，这套方案将多集群的复杂性封装在服务网格中，让开发者只需关注一个标签（Label）即可决定跨集群行为，极大地降低了运维负担。
