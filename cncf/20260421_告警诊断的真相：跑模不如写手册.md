# 告警诊断的真相：跑模不如写手册

**日期**: 2026-04-21

---

原文 : Auto-diagnosing AI investigation pipeline with HolmesGPT and CNCF tools来源 : https://www.cncf.io/blog/2026/04/21/auto-diagnosing-kubernetes-alerts-with-holmesGPT-and-CNCF-tools/SRE 圈里现在有个迷信：只要模型够大，告警就能自动修。STCLab 两个 SRE 试了一圈自托管和托管大模型后，给出了一个反直觉的结论——决定 AI 排查质量的不是模型，是 Runbook。
## 问题不在数据，在”接下来干啥”
STCLab 的观测性栈其实很标准：OpenTelemetry 往里灌，Mimir、Loki、Tempo 接着存。Robusta OSS 负责把 Prometheus 告警 enrich 一下，丢进 Slack。
数据从来不是问题。问题是告警响了之后，SRE 要干啥：查 Pod、查 Prometheus、翻 Loki、拉 Trace，然后试图把它们串起来。每回 15 到 20 分钟，雷打不动。
他们想做的很简单：让这第一轮排查自动跑，结果直接贴回同一个 Slack 线程。
## HolmesGPT 的 ReAct 套路选型上他们用了 HolmesGPT（CNCF Sandbox），核心思路是 ReAct 模式——让 LLM 自己决定下一步查什么。
LLM 读告警 → 选工具 → 读结果 → 决定下一步比如 Pod 重启了，模型可能先看退出码，再拉 Loki 日志，然后查 Prometheus 的 CPU 压力。路径不是写死的，取决于模型实际发现了什么。
这点很重要，因为 STCLab 不同 namespace 的观测性能力差异极大：有些有完整的日志、Trace，有些什么都没有，只有 kubectl 和 Prometheus。
他们把这种差异写进了 Runbook，每个 Runbook 带一个 metadata header：
字段 作用 scope 限定 namespace tools 可用工具列表 caution 注意事项，比如某些容器不采集日志Holmes 一开始就调 fetch_runbook ，metadata 告诉它哪些工具能用、哪些该跳过。
## Runbook 才是真正的神器这才是这篇文章最值回票根的部分。
没有 Runbook 时 ，模型纯靠猜。它可能去查 Istio 指标（namespace 里根本没有 sidecar），或者去翻 Loki（那里根本没数据收集）。最后要么死循环，要么返回”我需要更多信息”。
加了 Runbook 后 ，核心动作是告诉模型”别干啥”。比如写了”这里没有 Loki、Tempo、Istio，只用 kubectl 和 PromQL”，浪费的工具调用从每次 16 次降到 2 次。
他们做了受控对比，同一个 ClickHouse 握手告警，四种情况：
条件 找到根因所需调用 结果 有 Runbook 3-4 次 命中已知错误模式，剩余步数用于验证 无 Runbook 20+ 次 追了三个完全不同的假设（代理扩容、schema 不匹配、端口配置错误）
同一个模型，同一个告警。Runbook 没直接给答案，只是把搜索空间缩小了，12 步的 budget 就够用了。
## 模型试错史他们试过 7 个模型，踩了不少坑：
部署方式 模型 结果 自托管 (Spot GPU) 7B 无法生成有效工具调用 自托管 9B thinking 模式和 ReAct 循环冲突，返回空响应 自托管 14B 看起来可行，但 Spot 驱逐频繁，冷启动要 5-8 分钟 托管 API 多数 搞不定 HolmesGPT 的 prompt caching 标记 托管 API 一个韩国模型家族 全部通过现在用的是混合架构：staging 自托管，production 托管 API。切换只需要改一个 YAML block：
modelList :
primary :
model : "provider/model-name" # 换 provider 和 model ID 就行api_base : "https://endpoint" # 托管 API 或自托管端点temperature : 0每次排查成本约 0.04，一个月大概0.04，一个月大概 12。管道、playbook、Runbook 都不用动——模型是被替换的那个部件。
## 实际效果- 40 条原始告警 → 去重后约 12 个独立调查- 工程师 2 分钟内看完 Slack 线程总结（原来是 15-20 分钟手动排查）
- 约 40% 的调查自动解决：OOMKilled、ImagePullBackOff 这种已知模式，Holmes 匹配 Runbook 就能直接定位根因## 给其他团队的三条建议- Runbook 优于模型。受控测试里，同一个模型在有 Runbook 时得 4.6/5，没有时 3.6/5。排除规则比换模型管用得多。
- 胶水代码是真实工作量。那 200 行 Python 处理了时序、去重、路由、线程匹配。HolmesGPT 只负责推理，两者缺一不可。
- 为模型迁移设计。他们已经换过三次后端，管道没动过一行代码。playbook 是稳定核心，模型是随时可以替换的零件。
下一步他们打算加入 Inspektor Gadget（CNCF）的 eBPF 网络指标——TCP 重传、连接延迟——通过 Prometheus 喂给同一个管道。架构不变，Holmes 只是拿到了更好的数据。
## 我的思考这篇文章戳破了一个当下 AI 圈的泡沫：很多人以为把告警扔给 LLM 就能自动化运维。现实是，LLM 在工具调用场景下最大的敌人不是智商不够，是 搜索空间太大 。
Runbook 在这里扮演的角色，本质上是一个 约束函数 ——它不告诉模型答案，但排除了 90% 的错误路径。这和传统专家系统的思路不谋而合：与其让推理引擎盲目搜索，不如用领域知识剪枝。
对于正在考虑 AI 运维的团队，我的建议是： 先写 Runbook，再选模型 。花一周时间把你的 namespace 观测性能力、排除规则、常见故障模式写成结构化文档，比花一个月调 Prompt 管用得多。
