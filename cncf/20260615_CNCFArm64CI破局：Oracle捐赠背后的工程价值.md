原文 : Improving Arm64 support in CNCF projects with OCI credits来源 : https://www.cncf.io/blog/2026/06/15/improving-arm64-support-in-cncf-credits/云原生架构的“多架构并行”时代已全面到来。Arm64 不再是边缘选项，而是现代云基础设施的标配。对于维护者而言，如何低成本、高效率地实现 x86 与 Arm64 的 CI/CD 对等支持，是当下的核心痛点。
## 为什么 Arm64 支持从“可选”变为“必选”？
数据不会说谎。截至 2025 年底，AWS 上新增实例中超过 50% 运行在 Arm64 CPU 上，Azure 这一比例也达到了 33% 。
这意味着，如果你的项目只关注 x86，你正在主动放弃半数以上的潜在用户和性能红利。然而，尽管大多数 CNCF 项目已经发布了 Arm64 镜像，但 CI（持续集成）和测试覆盖率往往捉襟见肘。
⚠️ 核心痛点 ：历史遗留的 Arm64 构建节点稀缺，导致开发者缺乏稳定的开发、测试环境。这直接导致了 Arm64 版本的稳定性远低于 x86 版本。
## Oracle $3M 捐赠：不仅是钱，更是基础设施解耦2023 年底，Oracle Cloud 宣布向 CNCF 项目捐赠 $300 万 的 Arm64 计算资源（基于 Ampere Computing CPU）。这笔资金不是用来发奖金的，而是专门用于解决“算力瓶颈”。
CNCF Infra 团队利用这些资源，为数十个项目提供了自托管的 GitHub Actions Runner。这解决了两个关键问题：
- 性能瓶颈：GitHub 官方提供的托管 Arm64 Runner 存在容量限制（CPU 核心数和内存较小），难以应对大型构建矩阵或多架构容器构建。
- 灵活性缺失：通过 OCI Credits，项目可以申请任意大小的实例，专门用于长时间运行的 CI 任务或性能验证。
## 落地实践：从申请到集成对于项目维护者来说，接入这套基础设施的流程已经非常标准化：
- 申请流程：提交 CNCF Service Desk 工单，说明用途、涉及的 OCI 服务及预估用量。
- 资源护栏：作为共享社区资源，初始月度支出建议控制在 $5,000 USD 以内，确保长期可持续性。
- 快速集成：Infra 团队提供现成的 Runner 访问权限，维护者只需在 GitHub Actions workflow 中指定 Runner 名称即可。
目前，OpenTelemetry、Longhorn、Crossplane 和 Jaeger 等十几个项目已受益。据 Oracle 2025 年初的数据，新项目接入后，仅两个月信用额度消耗就超过了去年总和。
## 一线反馈：Arm64 CI 带来的信心重塑真正的价值体现在维护者的态度转变上。以下是几位知名项目维护者的真实反馈：
- OpenTelemetry (Antoine Toulmé)：“Arm 上的性能远超传统 x86 服务器……毫无疑问，我彻底被转化了。”
- Falco (Federico Di Pierro)：“Falco 迫切需要 Arm64 Runner 来提升架构支持水平并扩大用户群。”
- containerd (Phil Estes)：“如果现在 Arm CI 挂了，我们绝不会合并代码……我们现在对 Arm64 作为目标平台充满信心。”
这种“信心”是软件质量的基石。当 CI 管道具备同等强度时，Arm64 版本才不再是“二等公民”。
## 工程启示与局限思考对团队的指导意义：
如果你的项目面向云原生环境， 必须 建立原生的 Arm64 CI 流水线。不要依赖交叉编译（Cross-compilation）作为唯一测试手段，因为运行时行为差异往往只能在原生环境中暴露。
潜在局限：
- 资源竞争：虽然 Oracle 捐赠了巨额额度，但这是共享资源。高负载项目需合理规划，避免挤占其他小项目的生存空间。
- 生态依赖：部分底层依赖库可能在 Arm64 上存在兼容性问题，需要社区协同解决，而非单个项目能独立完成。
## 结语Arm64 支持正在成为云原生项目的“入场券”（Table Stakes）。通过 OCI Credits 和 CNCF Infra 的支持，基础设施障碍已大幅降低。维护者应将重心从“如何构建 Arm64 镜像”转移到“如何利用原生 CI 提升代码质量”上。
不要等待，现在就是完善多架构支持的最佳时机。
