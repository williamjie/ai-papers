# ⭐⭐⭐⭐½ 为什么 Agent 必须能读文档

**日期**: 2026-07-21

---

原文 : Why your agent needs access to your documentation来源 : https://www.cncf.io/blog/2026/07/21/why-your-agent-needs-access-to-your-documentation/在云原生领域，我们常把 Kubernetes、Prometheus 等项目的文档视为“用户界面”的延伸。当我们在产品中嵌入 AI Agent（智能体）时，往往误以为精心设计的 API 工具（Native Tools）才是核心。然而，基于 1,192 次真实对话的数据分析揭示了一个反直觉的事实： 让 Agent 具备读取文档的能力，比堆砌原生工具更重要。
### 背景：当 Analytics 遇上 Chat Interface团队在内部产品中部署了一个数据分析 Agent，旨在通过聊天界面解决传统分析工具（如聚类、标签、过滤器）无法覆盖的长尾需求。
架构上，该 Agent 配备了 30 个原生工具（如 search_conversations 、 display_chart ），用于直接操作平台数据。同时，它只有一个 search_knowledge_base 工具，用于检索文档、代码示例、FAQ 和 API 参考。
直觉告诉我们，原生工具应该承担主要工作流。但数据显示， search_knowledge_base 的使用频率最高，几乎等同于所有 30 个原生工具的总和。 这一现象对 CNCF 生态极具参考价值：在文档庞大且快速迭代的云原生项目中，Agent 是应该依赖专用工具，还是应该“阅读”文档？
### 核心发现：文档的三重角色通过对对话模式的拆解，我们发现文档搜索并非简单的“备用方案”，而是承担了三种关键职能：
#### 1. 兜底机制（Fallback）
占比：32.1%这是最直接的用途。当用户提出原生工具无法直接回答的产品性问题时，文档充当了安全网。
- “如何配置 Slack 集成？”
- “为什么 Widget 出现 CORS 错误？”
- “网站爬虫多久抓取一次数据？”
如果没有文档检索能力，Agent 只能拒绝服务或胡乱猜测。用户倾向于将数据分析 Agent 视为全能产品助手，而文档工具正是满足这一预期的关键。
#### 2. 上下文补充（Contextualization）
占比：7%原生工具回答“当前状态是什么”，文档回答“这意味着什么”。
例如，用户询问：“我配置了哪种 MCP 集成？它与其他选项有何不同？”
- list_integrations 原生工具返回当前配置。
- Agent 调用文档搜索，获取不同集成类型的对比说明。
两者缺一不可：原生工具提供事实（State），文档提供语义（Meaning）。这是文档最传统但也最被低估的角色。
#### 3. 行动规划（Planning）—— 反直觉发现占比：剩余主要部分⚠️ 关键洞察 ：文档不仅是答案，更是 Agent 的“行动简报”。
在一个典型案例中，用户要求查找“负面情绪”的对话。产品中并没有直接的“情感过滤器”或字段。
- 若仅依赖原生工具，Agent 会因找不到对应接口而失败。
- 实际上，Agent 先搜索文档，发现“负面信号”在系统中被记录为“点踩（downvotes）”和“反馈评论”。
- 随后，Agent 调用正确的原生工具，并应用对应的过滤条件。
在这里， 文档没有直接回答用户，而是教会了 Agent 如何正确使用现有工具。 它解决了用户自然语言与系统 Schema 之间的映射问题。
### 工程启示：重新定义 Agent 架构对于云原生开发者而言，这篇分析提出了一个重要的设计原则： 文档是 Agent 推理过程的一部分，而不仅仅是静态参考。
角色 传统认知 实际价值 原生工具 核心执行者 提供精确的状态数据，但缺乏语义理解 文档检索 边缘辅助/FAQ 核心协调者 ：处理长尾问题、解释结果、规划行动路径如果你的项目拥有深厚且不断演进的文档体系（如 K8s Operator 生态），在设计 Agent 时请记住：
- 不要低估文档的覆盖率：原生工具永远无法覆盖所有用户意图，文档是必要的缓冲区。
- 文档即 Schema：通过让 Agent 阅读文档，你可以动态扩展其能力，而无需为每个边缘用例编写新的 API 接口。
- 推理链的关键环节：文档检索应被视为 Agent “思考”的一部分，用于将模糊的用户需求转化为精确的工具调用参数。
我们部署了 30 个原生工具和 1 个文档阅读工具。 正是那个读文档的工具，让其他 30 个工具变得真正有用。 在构建下一代云原生智能助手时，请务必给予文档访问权同等的架构优先级。
