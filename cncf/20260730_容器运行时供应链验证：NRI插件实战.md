原文 : Runtime Supply Chain Verification using the Node Resource Interface (NRI)
来源 : https://www.cncf.io/blog/2026/07/30/runtime-supply-chain-verification-using-the-node-resource-interface-nri/我们常以为配置了 Kyverno 或 OPA Gatekeeper 就能高枕无忧，但 Kubernetes 的静态 Pod（Static Pods）和直接 Kubelet API 调用能轻易绕过准入控制器。这篇文章介绍了一种基于节点资源接口（Node Resource Interface, NRI）的插件方案，将供应链验证下沉到容器运行时层，填补了这道关键的安全缺口。
### 为什么准入控制器不够用？
现有的供应链验证工具大多运行在 Kubernetes API 层，作为准入 Webhook 拦截 Pod 创建请求。这种架构有两个致命弱点：
- 可被绕过：静态 Pod 由 Kubelet 直接管理，根本不经过 API Server，因此 Webhook 对其无效。
- 可用性风险：如果 Webhook 服务宕机且配置为“失败即拒绝”（Fail-Closed），会导致整个集群无法创建新 Pod，甚至引发节点恢复死锁。
⚠️ 核心洞察 ：防御纵深（Defense-in-depth）要求我们在容器实际执行前设置最后一道防线，无论它是通过何种调度路径启动的。
### NRI 插件：运行时层的“守门人”
该方案利用 CRI-O 和 containerd 支持的 NRI 接口，在 CreateContainer 阶段同步拦截容器创建。
- 不可绕过：只要容器要在节点上运行，就必须经过运行时调用，NRI 插件在此处同步返回错误即可阻止容器启动。
- 覆盖全面：包括预拉取（Pre-pulled）或缓存中的镜像，在容器实例化时才会进行验证，而非拉取时。
### 验证什么？SLSA、VEX 与 VSA插件主要验证三种声明（Attestations），分别回答不同维度的安全问题：
类型 全称 核心问题 作用 SLSA Supply-chain Levels for Software Artifacts 这个镜像是怎么构建的？ 验证构建者身份、源码仓库及构建环境。 VEX Vulnerability Exploitability eXchange 已知漏洞真的可被利用吗？ 判断 CVE 状态（如 fixed, not_affected），阻止高危容器。 VSA Verification Summary Attestation 是否已有可信方验证过？ 短路优化 ：若存在可信 VSA，直接跳过其他检查，大幅降低节点负载。
### 工程落地细节1. 性能与韧性设计- 并行校验：若无 VSA，SLSA 和 VEX 检查并行执行。
- 缓存预热：插件启动时通过 NRI 的 Synchronize 回调获取所有运行中容器，后台预热缓存，避免重启时的“惊群效应”。
- 熔断机制：针对注册中心设置断路器，防止注册中心宕机导致节点级联失败。
2. 配置分离策略插件将操作配置（TOML）与安全策略（JSON）分离：
- 操作配置：控制超时、缓存 TTL、熔断参数等，由运维团队管理。
- 安全策略：定义信任根（Issuers）、SLSA/VEX 缺失策略等，按命名空间隔离，由安全团队管理。

### 渐进式落地路径不要试图一夜之间开启强制验证。建议分三步走：
- 观察期（Observe）：设置 verification = "warn" 和宽松的缺失策略。通过 Prometheus 指标 nri_supply_chain_verification_total{result="fail"} 评估当前供应链合规基线。
- 收紧期（Tighten）：为生产命名空间配置严格的 missingPolicy: "deny"，开发环境保持宽松。识别并修复缺乏声明的镜像。
- 强制期（Enforce）：切换至 verification = "enforce"。此时未通过验证的容器将被运行时直接拒绝，错误信息会体现在 Pod 事件中。
### 局限性与思考- 节点信任假设：如果攻击者已获得节点 Root 权限，可以杀死插件进程或禁用 NRI。此方案防御的是 API 层绕过和中间人攻击，而非完全受损的节点。
- 网络依赖：当前版本需要节点能访问注册中心以获取声明，暂不支持纯离线环境（Air-gapped）。未来需结合本地缓存或镜像捆绑声明来解决。
对于重视供应链安全且存在静态 Pod 使用场景的团队，NRI 插件提供了比 Webhook 更底层的保障。它不是替代准入控制器，而是构建真正无死角的防御纵深。
