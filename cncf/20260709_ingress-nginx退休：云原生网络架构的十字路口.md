# ⭐⭐⭐ ingress-nginx 退休：云原生网络架构的十字路口

**日期**: 2026-07-09

原文 : Navigating the ingress-NGINX retirement来源 : https://www.cncf.io/blog/2026/07/09/navigating-the-ingress-nginx-retirement/Kubernetes SIG Network 正式宣布 ingress-nginx 控制器于 2026 年 3 月停止维护。这不仅是社区的一个里程碑，更是给所有生产环境用户的一记警钟。
很多团队可能还沉浸在“稳定运行”的错觉中。但现实很残酷：继续使用该控制器意味着你将独自面对未修复的安全漏洞（CVEs），且不再有任何功能更新或社区支持。
这里有一个常见的误解需要澄清： Kubernetes Ingress API 并没有退休 。
Ingress 标准本身依然被广泛支持和活跃使用。真正走到生命尽头的是那个由社区维护的、基于 Nginx 的具体实现—— ingress-nginx 控制器。
这意味着，基础设施团队现在必须做出一个关键的技术决策：是继续修补旧船，还是借此机会重建航海图？
## 核心困境：两条迁移路径面对这一变化，组织通常面临两种截然不同的架构选择。这不仅仅是替换软件包的问题，更是关于技术债务管理和未来扩展性的战略抉择。
### 路径 A：平滑过渡（Lift-and-Shift）
如果你追求最小化干扰，可以选择将流量控制器从 ingress-nginx 切换到另一个成熟的 Ingress 控制器，例如基于 Envoy 的 Contour 。
操作逻辑 ：
你可以保留现有的 Ingress YAML 资源文件，只需更改底层的 ingress class。这种方式对标准路由定义的破坏性最小。
⚠️ 致命陷阱 ：
虽然基础资源不变，但所有专有注解（Annotations）都会失效。
nginx.ingress.kubernetes.io/* 下的配置在 Contour 中完全无效。你必须手动将这些注解翻译为 Contour 的等价注解，或者使用其 CRD 重建逻辑。
### 路径 B：架构演进（Gateway API）
如果你愿意投入精力进行现代化改造， Gateway API 是上游推荐的继任者。
核心价值 ：
它引入了基于角色的设计范式，明确分离了基础设施关注点与应用路由逻辑。这解决了 Ingress-NGINX 难以维护的结构性缺陷，如流量拆分、高级头匹配和跨命名空间安全路由的标准缺失问题。
## 深度对比：为何要选 Gateway API？
为了帮助团队决策，我们将从工程实践角度对比这两条路径。
维度 路径 A: Contour (Ingress API) 路径 B: Gateway API 迁移成本 低到中。需手动翻译注解。 高。需重写路由清单。 运维范式 单所有者模式。Ops 管理单体定义。 基于角色模式。Ops 管 Gateway，Dev 管 HTTPRoute。 未来前景 低。Ingress API 功能已冻结。 高。上游积极开发中。 能力边界 严重依赖专有注解实现高级功能。 高级特性内置于核心规范中。
关键洞察 ：Ingress API 已经“功能冻结”。选择路径 A 只是用时间换空间，而路径 B 则是拥抱云原生网络的未来标准。
## 工程启示与迁移策略对于大多数团队，直接全面重构是不现实的。建议采取以下分步策略：
- 审计技术债务：仔细盘点当前所有的 nginx.ingress.kubernetes.io/* 注解。这是最容易被忽视的隐藏成本。
- 利用自动化工具：使用如 ingress2gateway 等工具自动化翻译过程，减少人工错误。
- 渐进式 rollout：并行运行新旧架构，优先迁移非关键工作负载。
## 局限与思考如果团队时间极度紧张，缺乏重构的工程周期，迁移到 Contour 或其他受支持的 Ingress 控制器是一个务实的短期止损方案。
但这只是一个权宜之计（Stopgap measure）。Ingress API 的功能冻结意味着你最终仍会面临同样的现代化压力。
对于正在规划更广泛平台现代化的组织，Gateway API 提供的灵活性和能力是无可替代的。选择哪条路，取决于你的运营约束、迁移时间表以及对未来架构愿景的承诺。
不要等到 CVE 爆发才行动。现在就是评估技术债务的最佳时机。
