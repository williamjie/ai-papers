# ⭐⭐⭐ K8s多集群数据库架构：如何构建容灾高可用方案

**日期**: 2026-07-22

原文 : Multi-Cluster databases on Kubernetes: Architecture and deployment来源 : https://www.cncf.io/blog/2026/07/22/multi-cluster-databases-on-kubernetes-architecture-and-deployment/单集群的自愈能力很强，Pod 挂了能重启，Node 坏了能驱逐。但面对整个区域断电、控制平面损坏或网络分区时，单集群就是“一损俱损”。这篇文章提供了一个基于 Kubernetes 多集群（Multi-Cluster）构建 MongoDB 高可用架构的深度实践，核心在于利用 Percona Operator for MongoDB 和 MCS API 解决跨集群的服务发现与状态管理问题。
### 痛点：单集群的边界在哪里？
标准 Kubernetes 擅长处理“内部”故障，却对“外部”灾难无能为力。如果你依赖单一集群运行数据库，以下场景是致命的：
- 区域性中断：整个云区域宕机，数据虽然还在存储层，但服务不可用。
- 控制平面损坏：API Server 挂了，Pod 调度停滞，无法恢复。
- 网络分区：集群内部节点失联，导致脑裂或选举失败。
要解决这些问题，必须将数据库节点分散到多个独立的 Kubernetes 集群中。这不仅是为了灾备（DR），还能支持 零停机维护 和 云厂商迁移 。你可以一边升级一个集群，另一边继续承载写入流量，无需计划内停机。
### 架构核心：主从角色与 MCS API跨集群部署的最大难点在于： 如何防止多个 Operator 互相打架？
如果两个集群的 Operator 都试图初始化副本集、生成证书或管理用户，必然导致冲突和数据不一致。Percona Operator 通过定义 Site Roles 解决了这个问题：
- Main Site（主站点）：完全由 Operator 管理。负责持有 Primary 节点，处理应用写入，并生成 TLS 证书和用户凭证。
- Replica Site（副本站点）：Operator 运行在 unmanaged: true 模式。它不生成证书，不初始化副本集，而是从 Main Site 复制 Secrets 后加入现有的副本集。
这种设计确保了数据库层面的状态一致性由单一源（Main Site）控制，避免了“双头管理”的脑裂风险。
### 关键技术：MCS API 打通跨集群网络既然节点分布在不同的集群，它们如何互相发现？这里引入了 Kubernetes Multi-Cluster Services (MCS) API 。
通过在 CR 中设置 multiCluster.enabled: true ，Operator 会自动创建 ServiceExport 和 ServiceImport 资源。这使得不同集群中的 Pod 可以通过共享的 DNS 后缀（如 svc.clusterset.local ）互相通信。
⚠️ 注意 ：MCS API 不是 K8s 默认组件。你需要额外部署实现方案，如 Submariner、Cilium ClusterMesh 或 GKE Fleet。这是架构落地的前置条件。
### 高可用设计：2+2+1 投票模式MongoDB 副本集选举 Primary 需要严格多数（Strict Majority）。如果只有两个集群各放 2 个节点（共 4 票），一旦网络中断，两边都只有 2 票，无法形成多数，数据库将停止接受写入。
解决方案是引入第三个位置的仲裁节点，形成 2+2+1 模式：
- Main Site: 2 个数据节点- Replica Site: 2 个数据节点- Third Location: 1 个投票节点（可以是轻量级实例）
总票数 5 票，多数为 3 票。即使 Main Site 完全宕机，Replica Site 的 2 票加上第三地的 1 票，正好凑齐 3 票，自动选举新的 Primary。
### 部署与故障转移细节部署流程强调顺序和配置隔离：
- 连通性：先确保跨集群网络互通（Submariner/Cilium）。
- 主站点部署：应用 CR，确保 Pod 暴露为 ClusterIP（MCS API 要求）。
- 同步凭证：从 Main Site 复制 TLS Secrets 到 Replica Site。
- 副本站点部署：设置 unmanaged: true，加入现有副本集。
- 配置外部节点：在 Main Site 的 CR 中通过 externalNodes 添加其他集群节点的地址和投票权重。
故障转移时，MongoDB 内置协议会自动检测失败并选举。默认情况下，新 Primary 选举时间通常不超过 12 秒 。应用层需配合重试写入逻辑以应对这短暂的窗口期。
### 工程启示- 适用团队：对 RTO（恢复时间目标）要求极高、运行在多云或混合云环境、需要执行滚动升级不停机的数据库运维团队。
- 架构权衡：虽然实现了跨集群高可用，但故障后系统处于“降级状态”，冗余度降低。如果第三地节点也失效，系统将变为只读。因此，2+2+1 中的“1”必须足够稳定。
- 技术趋势：随着 MCS API 成为 K8s 标准的一部分，跨集群服务网格和数据平面互联将变得更加标准化，不再依赖厂商私有方案。
这篇博文不仅展示了如何部署，更揭示了在分布式系统中，通过角色分离和标准 API 解决复杂状态同步的工程智慧。对于正在探索多集群数据库架构的工程师来说，这是一个可落地的参考模板。
