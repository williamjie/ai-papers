原文 : OpenCost 1.121.0: First-of-a-kind Kubernetes inference cost tracking来源 : https://www.cncf.io/blog/2026/08/05/opencost-1-121-0-first-of-a-kind-kubernetes-inference-cost-tracking/对于正在大规模部署大模型推理的企业平台团队来说，OpenCost 1.121.0 的发布是一个里程碑。它首次将 Kubernetes 基础设施成本与 LLM 推理的 Token 流直接挂钩，解决了“每个 Token 到底多少钱”这个长期悬而未决的黑盒问题。
### 痛点：GPU 账单里的“雾区”
现在的 AI 平台团队普遍面临一个尴尬局面：能看到巨大的 GPU 基础设施支出，也能监控到 Token 吞吐量，但两者之间缺乏连接。
你无法回答执行层的硬核问题：
- 自建推理服务真的比调用 SaaS API 便宜吗？
- 哪个模型在当前的流量水平下最具成本效益？
- 是哪个团队的 Agent 工作负载烧掉了你的 AI 预算？
没有基于实际资源消耗的 Per-Model 和 Per-Token 成本数据，所有的优化决策都像是在赌博。更糟糕的是，GPU 的闲置成本极高——即使没有请求，加载了模型权重的 VRAM 依然在燃烧预算。这种“暖但闲置”的状态可能占据低流量模型 95% 的时间，却产出零有效 Token。
### 核心洞察：两种成本，两个问题OpenCost 1.121 与 CNCF 沙箱项目 llm-d 的集成，核心在于区分了两种截然不同的成本视角。这不是简单的功能叠加，而是对 FinOps 逻辑的重构。
1. 基于分配的成本（Allocation-based Cost）
这是“让模型可用”的全部代价。包括 GPU 内存预留、活跃推理计算以及网关、KV Cache 存储等共享基础设施的分摊。
- 回答的问题：“维持这个模型在线，我们花了多少钱？”
- 适用场景：对账、Build-vs-Buy 决策。
2. 基于使用的成本（Usage-based Cost）
仅包含活跃推理期间消耗的 GPU 和基础设施成本，并计入 KV Cache 命中的节省效应。
- 回答的问题：“这个模型实际处理的工作花了多少钱？”
- 适用场景：模型性能基准测试、与外部 API 价格对比。
⚠️ 关键公式 ：利用率 = 基于使用的每百万 Token 成本 / 基于分配的每百万 Token 成本例如，如果 Usage 成本是 1.00/MT，而Allocation成本是1.00/MT，而 Allocation 成本是 4.00/MT，说明你的 GPU 利用率仅为 25%。剩下的 75% 是在为“随时待命”买单。
### 避开“自建更便宜”的陷阱很多团队在计算自建推理成本时犯了一个致命错误：只对比 Usage-based Cost。
如果自建模型的活跃计算成本是 1.00/MT，而SaaSAPI收费1.00/MT，而 SaaS API 收费 2.00/MT，乍看之下自建划算。但如果利用率只有 25%，实际的 Allocation 成本高达 $4.00/MT。此时，SaaS 反而更便宜。
正确的决策逻辑是：
- 低利用率（<50%）：外部 API 通常更具经济性。
- 高利用率（>50%）：自建开始具备竞争力。
- 优化目标：通过智能路由、模型共享或流量整合提高利用率，从而降低 Allocation-based Cost per Token。
### 技术实现细节该集成利用了 vLLM 现有的指标（如 vllm:prompt_tokens_total ），结合 OpenCost 的分配引擎，通过 Prometheus 暴露新的指标。
关键指标：
- llm_total_hourly_cost：每小时模型成本。
- llm_cost_per_million_tokens：每百万 Token 混合成本，细分为输入和输出 Token 成本。
特别值得注意的是，它区分了 Prefill（输入）和 Decode（输出）阶段的成本。在解耦服务部署中，这两者可能运行在不同硬件上，精确归因至关重要。此外，KV Cache 命中的影响也被纳入计算，因为缓存命中直接降低了输入 Token 的处理成本。
除了 GPU，llm-d 的基础设施组件（如 EPP 调度器、网关代理、KV Cache 存储）的成本也通过 SharedLabels 机制被准确分摊到各个模型上，确保了成本视图的完整性。
### 工程启示：从数据到行动这套指标体系不仅用于看报表，更能驱动自动化决策：
- FinOps 团队：识别未充分利用的模型，量化缩容或下线带来的节省。
- 智能路由：llm-d 正在开发的智能路由器可以利用 REST API，将 Per-Token 成本与延迟、吞吐量结合，动态选择最优推理节点。
- 内部结算：通过 Namespace 和 Team 标签生成 Showback 报告，让业务团队为 AI 资源消耗负责。
### 局限与展望目前该功能已在包含 109 个 GPU 和 30 个 AI 模型的集群中验证。未来 OpenCost 将继续改进空闲 GPU 检测、UI 集成以及优化节省估算。对于正在构建大规模 AI 基础设施的团队，理解“分配成本”与“使用成本”的差异，是避免算力浪费的第一步。
