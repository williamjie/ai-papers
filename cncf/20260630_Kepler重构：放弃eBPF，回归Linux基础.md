# ⭐⭐⭐ Kepler重构：放弃eBPF，回归Linux基础

原文 : Kepler, re-architected: Improved power accuracy and a community call to action!
来源 : https://www.cncf.io/blog/2026/06/30/kepler-re-architected-improved-power-accuracy-and-a-community-call-to-action/在 Kubernetes 集群中精确归因工作负载的能耗，一直是绿色云原生领域的“圣杯”。随着 AI 算力需求激增，数据中心电力消耗预计将在 2030 年翻倍，Kepler 作为 CNCF 旗下的能效观测项目，其架构的每一次演进都直接影响着生产环境的落地可行性。
这篇文章最核心的信号是： Kepler 团队决定重写核心代码，彻底摒弃 eBPF，回归传统的 /proc 和 /sys 接口。
这听起来像是“技术倒退”，实则是为了生存和准确性的必要妥协。让我们拆解背后的工程逻辑。
### 为什么放弃 eBPF？
eBPF（Extended Berkeley Packet Filter）因其高性能和无侵入性，曾是 Kepler 获取细粒度进程利用率的理想选择。但在实际大规模部署中，它带来了三个致命痛点：
- 权限壁垒：运行 eBPF 需要 CAP_BPF 和 CAP_SYS_ADMIN 等高权限。在安全合规严格的生产环境中，这往往是无法逾越的红线。
- 数据失真：eBPF 在追踪极短生命周期的内核进程时容易出错，导致大量短期进程漏报。这不仅让能耗数据偏低，更严重污染了用于训练 VM 能耗模型的底层数据。
- 维护噩梦：复杂的抽象层使得代码库难以扩展和维护，社区贡献者的学习曲线陡峭。
⚠️ 反直觉发现 ：追求极致的“细粒度”技术（eBPF），反而导致了宏观层面的“不准确”和“难部署”。在工程实践中，有时“简单”比“先进”更重要。
### 重构方案：回归基础，动态适配新版 Kepler 的设计哲学是“少即是多”。
- 信号采集：不再依赖 eBPF，而是直接读取标准的 /proc 和 /sys 文件系统。这些接口在所有 Linux 系统上通用，无需特殊权限，通过 Helm Chart 即可开箱即用。
- 硬件适配：旧版 Kepler 假设硬件功率结构是固定的（如 RAPL 包含 Core、DRAM 等）。但现实中的硬件拓扑千差万别。新版 Kepler 在运行时动态发现主机的功率计量器结构，避免了将数据映射到不存在的“地面真值”上。
### 准确性验证：数据不会撒谎团队通过两组实验验证了重构的效果，结论令人振奋。
实验一：对比新旧版本与 IPMI 基准在裸金属节点上同时部署旧版（kepler-old）和新版（kepler-new），并以硬件 BMC 的 IPMI 读数作为参考。
- 现象：旧版数据经常出现超过 IPMI 物理极限的多千瓦尖峰，这是明显的估算错误。
- 结果：新版 kepler_node_cpu_watts 指标紧密跟随 IPMI 负载变化曲线，消除了异常尖峰，且在压力测试下能正确反映 CPU 能耗趋势。
实验二：归因间隙（Attribution Gap）趋近于零通过对比节点总功率与进程归因功率之和，新版 Kepler 的归因间隙几乎为 0 Watts 。
- 细节：差异仅在几毫瓦级别波动。这证明了新的架构在进程级功率追踪上的极高精度。
- 保障：项目测试覆盖率提升至 90%，为长期可维护性打下基础。
### 工程启示与行动指南对于云原生工程师而言，这次重构意味着 Kepler 从“极客玩具”变成了“生产就绪”的工具。
- 降低部署门槛：无需再为权限问题与安全团队扯皮，普通节点即可部署。
- 关注 AI 负载：目前 GPU 功率监控仍处于实验阶段。如果你运行 AI/ML 工作负载，现在是测试和反馈的最佳时机。
- 参与模型训练：虚拟化环境缺乏硬件计数器，依赖机器学习模型估算。社区急需有 ML 经验的贡献者来优化 VM 功率模型。
### 局限与思考尽管进步显著，新版 Kepler 目前仅归因 活跃 CPU 使用量 。这意味着空闲功耗（Idle Power）尚未被精确分配到具体 Pod。虽然这是为了避免状态混淆的临时策略，但未来需要改进以提供更完整的能耗视图。
此外，对于完全依赖硬件计数器的方案，在纯虚拟化环境中仍需依靠模型估算，这部分的不确定性依然存在。
总结 ：Kepler 的重构是一次务实的胜利。它证明了在云原生基础设施中，稳定性、可部署性和准确性往往比炫技式的底层技术堆叠更有价值。如果你的团队关注碳足迹或能耗成本优化，现在就是重新评估 Kepler 的最佳时机。
